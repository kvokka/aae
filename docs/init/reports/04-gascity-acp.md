# 04 — ACP-провайдер внутри Gas City: почему он «не работает нормально» (H2)

Снимок: gascity `f1f75f53c` (main, 2026-11-10); спека ACP — клон `agent-client-protocol` @ `ab82539` (schema v1.30.0 от 2026-11-09, v2 — alpha.14); адаптеры, на которых ставились опыты: `@agentclientprotocol/claude-agent-acp` 0.73.0 и `@agentclientprotocol/codex-acp` 1.13.1 (установлены на машине как зависимости `npm-paperclipai`). Метки: **[П]** = ПРОВЕРЕНО, **[В]** = ВЫВОД, **[Н]** = НЕ ПРОВЕРЕНО. Пути без префикса — от корня gascity.

## 1. Выводы за 60 секунд

- **H2 подтверждена: ~80% проблем ACP-пути — недоработка Gas City, ~12% — дыры протокола ACP v1, ~5% — адаптеры, ~3% — харнессы.** Это доли по каталогу из 32 дефектов (раздел 2.5), а не измерение.
- **Для claude, codex и pi ACP в gc — витрина.** У `claude` стоит `SupportsACP: true`, но нет `acp_command`: `session = "acp"` запустит обычный `claude`, который ACP не говорит. У `codex` и `pi` флага нет вообще — конфиг отклоняется. Слов `claude-agent-acp` / `codex-acp` нет нигде в репозитории.
- **Реально живой ACP-путь — семейство opencode** (ACP по умолчанию у opencode, cerebras, groq, kimi), и большинство пользовательских баг-репортов — от пользователей opencode (ещё hermes и Devin).
- **gc использует 4 из 13 агентских методов ACP v1**: `initialize`, `session/new`, `session/prompt`, `session/cancel`. Не использует `session/load`, `session/resume`, `session/set_mode`, `session/set_config_option`, `authenticate`, `fs/*`, `terminal/*`.
- **Resume через ACP в gc не существует**: всегда `session/new`, ветка resume явно выключена для ACP. Оба адаптера при этом объявляют `loadSession: true` и `resume` — проверено опытом.
- **Корневое несоответствие — владение соединением.** gc рассчитан на «любой процесс gc может дёрнуть сессию» (tmux-сервер — общий демон). ACP по stdio живёт в памяти одного процесса; отсюда `ACP provider does not own session`, недоставленные nudge, потеря сессий при рестарте контроллера.
- **Структурированный поток ACP сплющивается в текст**: `session/update` превращается в кольцевой буфер на 1000 строк ради `Peek`; 9 из 14 типов событий отбрасываются, включая `usage_update` с данными о квоте.
- **Квота/429 через ACP в gc не детектируется**: детектор — поиск строк на экране pane. Код и `data` ошибки JSON-RPC теряются.
- **Диалект gc совместим с реальными адаптерами** (опыт): handshake и ход «reply OK» прошли на обоих, лишнее не-спековое `initialized` молча игнорируется. То есть wire-уровень рабочий, сломана обвязка.
- **Неожиданное: codex-acp на ошибке провайдера вернул `stopReason: "end_turn"`**, а текст ошибки отдал как обычное сообщение агента. Стандартными полями ACP v1 упавший ход от успешного не отличить.
- **Неожиданное: опции gc (модель, effort, режим прав) под адаптером молча не применяются** — gc передаёт их флагами CLI, адаптер их игнорирует; нужен `session/set_config_option`, которого в gc нет.
- **Путь живой, но молодой и узкий**: 6 119 строк не-тестового кода, 88 коммитов, 73% — один автор; permission-запросы, `session/cancel` и учёт ходов появились только в октябре 2026.
- **При системе «вокруг ACP» большинство дефектов исчезает само**; остаются четыре вещи, требующие обхода: stdio-only транспорт, модель хода v1, отсутствие стандартных сигналов квоты, дрейф адаптеров.

## 2. Факты

### 2.1. Архитектура провайдера

- **Один процесс на сессию.** `Start` делает `exec.Command("sh", "-c", command)` с `Setpgid` (`internal/runtime/acp/acp.go:281-282`) и ровно один `session/new` на процесс (`acp.go:592-623`). Возможность ACP держать много сессий на одном соединении не используется. **[П]**
- **Handshake**: `initialize` → `initialized` → `session/new` (`acp.go:566-626`), `protocolVersion: 1` (`protocol.go:230`). Уведомления `initialized` в ACP нет (в `schema/v1/meta.json` его нет); gc читает поле `serverInfo` (`protocol.go:91`), а спека отдаёт `agentInfo`. `agentCapabilities`, `authMethods` и версия из ответа не читаются вовсе. **[П]**
- **Клиентские возможности**: `fs` и `terminal` объявлены `false` (`protocol.go:233-236`); любой запрос агента, кроме `session/request_permission`, получает `-32601` (`agent_requests.go:75-96`). **[П]**
- **Вокруг JSON-RPC надстроено**: control-сокет на сессию с командами `stop`, `interrupt`, `ping`, `pid`, `turn`, `interrupt-turn` (`acp.go:1240-1274`) — без `prompt` и без `peek`; sidecar-файлы метаданных; flock-замок жизненного цикла; собственный JSONL-захват трафика (`capture.go`). **[П]**

| Метод ACP v1 (stable) | В gc |
|---|---|
| `initialize`, `session/new`, `session/prompt`, `session/cancel` | используются |
| `session/update` | читаются 5 из 14 вариантов, только как текст (`conn.go:273-296`) |
| `session/request_permission`, `$/cancel_request` | обслуживаются с 2026-10-11 (PR #6598) |
| `session/load`, `session/resume`, `session/list`, `session/close`, `session/delete` | не используются |
| `session/set_mode`, `session/set_config_option`, `authenticate`, `logout` | не используются |
| `fs/*`, `terminal/*`, `elicitation/*` | отклоняются `-32601` |
| `systemPrompt`, `additionalDirectories` в `session/new`; блоки image/audio/resource | не используются; файлы инлайнятся текстом ≤1 MiB (`protocol.go:320-358`) |

Обработка исходов: `stopReason` записывается дословно, `usage` декодируется (`turns.go:214-227`). При ошибке JSON-RPC сохраняется только `message`; `code` и `data` теряются (`protocol.go:40-43`, `turns.go:215-216`), а вызывающему уходит строка в stderr (`acp.go:915-919`). **[П]**

### 2.2. ACP на интерфейсе `runtime.Provider`

Базовый `Provider` — 19 методов (`internal/runtime/runtime.go:476`); в пакете `runtime` 66 интерфейсов. tmux-провайдер подтверждает 33 из них, ACP — 15. **[П]** (подсчёт `grep` по compile-time assert'ам)

| Метод Provider | Что делает ACP-провайдер | Где |
|---|---|---|
| `Start` | spawn + handshake + первый prompt. Из 30 полей `runtime.Config` напрямую читает 7: `WorkDir`, `Command`, `Env`, `MCPServers`, `Nudge`, `PromptSuffix`, `PromptFlag`; ещё overlay- и copy-поля — через `StageSessionWorkDir`. `PreStart`, `SessionSetup`, `SessionLive`, `ProcessNames`, `ReadyPromptPrefix` игнорируются | `acp.go:157-498` |
| `Nudge` | `session/prompt` после ожидания простоя до 60 с, иначе `busy`; только в процессе-владельце | `acp.go:781-789`, `829-834` |
| `Peek` | последние N строк текстового буфера; не владельцу — пустая строка | `acp.go:937-945`, `conn.go:324-342` |
| `SendKeys`, `RunLive` | no-op | `acp.go:926`, `931` |
| `Attach` / `IsAttached` | ошибка / `false` | `acp.go:760-766` |
| `Interrupt` | `session/cancel`, затем до 2 SIGINT; сессию не убивает | `acp.go:723`, `interrupt.go:41-58` |
| `ProcessAlive` | имена процессов игнорирует | `acp.go:770-775` |
| `Place.Exec` | `ErrExecUnsupported` | `seams.go:102` |
| Сон | только по таймеру | `acp.go:1404-1406` |

Где импеданс виден в коде:

- **Владение.** `Nudge` от не-владельца возвращает `ACP provider does not own session` (`acp.go:786`). CLI-процесс gc строит собственный провайдер и соединения не имеет; sidecar-поллер nudge для ACP намеренно не запускается (`cmd/gc/cmd_nudge.go:2998-3006`). **[П]**
- **Долговечность.** Дизайн-док прямо говорит: tmux-сессии переживают рестарт контроллера, ACP-потоки — нет, «forces a restart»; tmux — default, acp — «premium transport» (`engdocs/design/worker-runtime-transport-v0.md:366-373`). **[П]**
- **Ход против клавиш.** `AGENTS.md` провайдера: «ACP still reports `keystroke` mode», поэтому слой сессий не пользуется turn-fence (`internal/runtime/acp/AGENTS.md:102`). Follow-up и steer для ACP выключены (`internal/session/submit.go:90`, `steer.go:40`). **[П]**
- **Особые случаи расползлись.** 206 строк с `"acp"` / `IsACP` в не-тестовом коде вне провайдера, больше всего в `cmd/gc/providers.go` (27). **[П]**
- **Обратная сторона, в пользу ACP.** В `internal/session/submit.go` 12 предикатов TUI-костылей (soft-Esc для codex/kimi, hard-restart для pi, сброс хода для gemini, очистка поля ввода для claude) для ACP возвращают `false` (`submit.go:605-868`). Слой скрейпинга диалогов `internal/runtime/dialog.go` (2 225 строк) ACP не нужен. **[П]**

По файлам провайдера: примерно 47% кода — сам протокол (`protocol`, `conn`, `permission`, `interrupt`, `turns`, события; 2 861 строка), 53% — процессы, сокеты, sidecar'ы, межпроцессные ограждения и адаптация к seam-интерфейсам (3 258 строк). **[В]** (сумма `wc -l` по моей разбивке файлов)

### 2.3. Какие харнессы заявлены и что тестируется

| Харнесс | `SupportsACP` | ACP-команда | Статус |
|---|---|---|---|
| opencode, cerebras, groq, kimi | да | есть (`acp_args`) | ACP по умолчанию (`internal/config/provider.go:351-387`) |
| kiro, mimocode | да | есть | только явный `session = "acp"` (`provider.go:367-382`) |
| **claude** | да (`internal/worker/builtin/profiles.go:264`) | **нет** | по умолчанию tmux; при явном `session = "acp"` запустится `claude …`; `claude --help` ACP не содержит **[П]**; итог — таймаут handshake **[В]** |
| **codex** | нет | — | `session = "acp"` отклоняется (`cmd/gc/template_resolve.go:212-213`) |
| **pi** | нет | — | то же; у `pi` 1.5.0 есть `--mode rpc`, ACP нет **[П]** |

- Документация при этом даёт пример `provider = "claude"` + `session = "acp"` (`docs/guides/configuring-an-agent.md:281-282`). Дизайн-док называет `claude/sdk-acp` «future» (`engdocs/design/worker-conformance.md:126`). **[П]**
- **Тесты**: conformance гоняется только против собственного `testdata/fakeacp` (`conformance_test.go:28-38`). В `test/` (acceptance, integration) нет ни одного файла с `session = "acp"`. С реальным харнессом ACP-путь не проверяется. **[П]**

### 2.4. Опыт: диалект gc против реальных адаптеров

Скрипт `lab/04-gascity-acp/gc_dialect_probe.py` шлёт ровно те сообщения, что строит `protocol.go`. Вывод — в `lab/04-gascity-acp/*.out`. **[П]**

| Наблюдение | claude-agent-acp 0.73.0 | codex-acp 1.13.1 |
|---|---|---|
| `initialize` | ok; `serverInfo` отсутствует | ok; `serverInfo` отсутствует |
| `loadSession` / `sessionCapabilities` | `true` / `close, delete, fork, list, resume, …` | то же |
| не-спековое `initialized` | молча проигнорировано | молча проигнорировано |
| `session/new` | 1.4 с | 0.1 с |
| ход «Reply with exactly: OK» | 3.1 с, `end_turn`, `usage` есть | 1.7 с, **`end_turn`, `usage: null`** |
| что gc отбросил бы | `usage_update` ×4, `available_commands_update` ×2 | `session_info_update` ×3, `_auth/status_update` |
| выход по EOF stdin | rc 0 | rc 0 |

- **Квота есть в потоке, но не в стандарте.** claude-адаптер кладёт в `usage_update` поле `_meta."_claude/rateLimit"` (`status`, `resetsAt`, `utilization: 0.42`). gc этот вариант события не читает.
- **codex-acp скрыл ошибку.** Провайдер ответил `model_not_found` (`unknown provider for model gpt-6-astra`); адаптер отдал это текстом в `agent_message_chunk` и завершил ход `end_turn`. Единственный структурный след — не-стандартный `_meta.codex.threadStatus.type = "systemError"`. Ведёт ли себя так же 429 — **[Н]**.
- **Флаги CLI игнорируются.** С `--dangerously-skip-permissions --effort max --model haiku` (`mode_probe.py`) `session/new` вернул те же `mode=auto, model=opus[1m], effort=high`, что и без флагов. gc же собирает опции именно в argv, независимо от транспорта (`internal/config/launch_command.go:38-48`).

## 3. Вердикты по гипотезам

- **H2 — подтверждена.** Около 80% дефектов — Gas City. Причём две трети из них не «баги», а следствие архитектуры: stateless-модель «любой процесс дёргает pane» наложена на протокол, требующий одного долгоживущего владельца соединения. Протокол отвечает примерно за 12%, и это реальные дыры, а не мелочи: модель хода v1, отсутствие сигналов квоты, единственный стандартный транспорт — stdio.
- **H1 — частично.** За: ACP снимает скрейпинг диалогов и 12 пер-харнессных костылей прерывания, даёт структурные permission-запросы, границы хода и MCP in-band. Против: «429 и outOfQuota решаются через ACP» в стандарте v1 не обеспечено — только расширения `_meta` конкретного адаптера, а codex-acp скрыл ошибку провайдера за `end_turn`. tmux бесплатно давал три вещи, которые придётся строить заново: переживание рестарта контроллера, attach человека, ввод посреди хода.
- **H3 — частично, в моей зоне.** claude и codex работают через официальные адаптеры, диалект совместим (опыт). pi 1.5.0 ACP не говорит. Глубину — другим отчётам.
- **H4 — не проверялась здесь.** gc этим не пользуется: процесс на сессию.
- **H10 — косвенно против «просто подключиться».** В v1 нет стандартного сетевого транспорта и семантики нескольких клиентов на одной сессии; нужен собственный демон-посредник.

## 4. Следствия для дизайна новой системы

**Исчезает само при дизайне вокруг ACP** (22 позиции класса A):

- №5, №6, №14 — один демон владеет всеми соединениями, CLI и UI ходят к нему; очередь nudge доставляет тот же процесс.
- №3 — `session/resume` и `session/load` становятся штатным путём восстановления.
- №10, №15 — модель, режим, effort задаются через `session/set_config_option` и `session/set_mode`; capabilities читаются при handshake.
- №11 — события хранятся структурно (план, tool calls, usage), текстовый `Peek` не нужен.
- №8, №9, №1, №2 — подготовку workdir делает демон; адаптеры описаны как первоклассные команды запуска.
- Целиком не нужны: `dialog.go` (2 225 строк), программный статус через OSC, детект простоя по экрану, composite-провайдер `auto` (761 строка), 206 особых случаев.

**Остаётся и требует обхода:**

1. **Долговечность соединения (B).** stdio означает: упал демон — оборвались все агенты. Варианты: (а) принять обрыв и восстанавливать через `session/resume` — просто, но ход в полёте теряется; (б) тонкий процесс-брокер на сессию, который держит stdio агента и отдаёт поток по unix-сокету, — демон перезапускается без потери хода, ценой ещё одного процесса; (в) ждать стандартный Streamable HTTP/WebSocket-транспорт (пока RFD). Рекомендую (а) как базу и (б) только для долгих ходов.
2. **Ввод посреди хода (B).** В v1 не определён. Варианты: очередь на стороне демона с доставкой на границе хода (универсально); расширения адаптера — `_session/steering` и `promptQueueing` у claude (не переносимо); ACP v2 (alpha).
3. **Квота, 429, ошибки хода (B + C).** Нужен слой нормализации на каждый адаптер: `_claude/rateLimit` для claude, `threadStatus` для codex; плюс правило «`end_turn` без `usage` и без tool calls — подозрительный ход». Без этого слоя оркестратор будет считать упавшие ходы успешными.
4. **Attach человека (B).** Собственный клиент к демону или запуск второго ACP-клиента с `session/load`; терминального «подсмотреть» больше нет.
5. **Дрейф (B + C).** Схема v1 выпускалась 30.10, 31.10, 02.11 и 09.11 (`schema/v1/CHANGELOG.md`); адаптеры пинят свои версии харнесса. Нужны пин версий и contract-тесты против реальных адаптеров — то, чего у gc нет (№27).
6. **pi (D).** Нужен либо сторонний ACP-адаптер, либо собственный мост над `pi --mode rpc`.

## 5. Открытые вопросы и непроверенное

- **Не запускал gc с ACP-агентом сам**: правила запрещают трогать живой город. Симптомы в gc взяты из кода и чужих issue; собственной репродукции нет.
- **Запуск `provider = "claude"` + `session = "acp"`** даёт таймаут handshake — вывод из кода и `claude --help`, не опыт.
- **429 и исчерпание квоты через адаптеры** не воспроизводил. Поведение codex-acp показано на `model_not_found`; для 429 оно может отличаться.
- **Причина `model_not_found`** не выяснена: вероятно, модель из `~/.codex/config.toml` неизвестна встроенной в адаптер версии codex — предположение.
- **Опыты шли на claude-agent-acp 0.73.0**, а не на свежем 0.102.0 из клона; набор возможностей мог измениться.
- **Хуки gc под claude-agent-acp** (подхват `.claude/settings`) не проверял.
- **Dashboard-стрим для ACP-сессий** end-to-end не проверял.
- **№17 (кадр больше 1 MiB)** — риск по коду; в опытах максимальная строка была 23 KB.
- **Проценты в вердикте** — подсчёт позиций каталога с ручным делением смешанных; другой состав каталога сдвинет доли на несколько пунктов, но не порядок.
