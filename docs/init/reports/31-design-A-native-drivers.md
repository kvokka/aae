# 31 — Вариант A: тонкий демон-оркестратор с нативными драйверами на харнесс

Дата: 2026-11-10. Проектный документ, кода продукта нет. Вход: отчёты 01–08, 11–19, `WAVE1-SUMMARY.md` с дополнением по br. Отчётов 21 и 22 (инварианты, фактчек) ещё нет: вендорские фичи взяты из 15, 17, 19 без перепроверки.

Метки: **[ФАКТ NN]** — факт из отчёта NN; **[РЕШЕНИЕ]** — выбор этого документа; **[ДОПУЩЕНИЕ]** — не проверено, требует спайка. `<cli>` — рабочее имя бинарника; «демон» — его долгоживущий режим.

## 0. Решения за 60 секунд

- Один процесс-демон на город, один писатель состояния. Язык — TypeScript на Bun: только там у всех четырёх протоколов есть официальные типизированные клиенты (§9).
- claude — напрямую через Agent SDK (тот же stream-json, без ACP-адаптера); codex — собственный detached `codex app-server` на unix-сокете; pi — `--mode rpc`, в v1. ACP — только «вверх», как хаб для редакторов.
- v0 без брокера: claude и pi — stdio-дети с resume; codex app-server сам долгоживущий сервер и переживает рестарт демона.
- br — одна `.beads` на город, только рабочие биды, rig — метка. Всё остальное (claim, run, сессии, ордера, очереди, события, KV бидов) — своя SQLite.
- Формула исполняется как durable run в SQLite; бидами остаются только настоящие задачи.
- Объём: 28–50 тыс. строк без тестов (v0: 20–32 тыс.), v0 — 11–17 человеко-недель. Главный риск — не объём, а три вендорских протокола, дрейфующих каждую неделю, при bus factor = 1.

## 1. Принципы и не-цели

1. **Один демон, один писатель.** Состояние оркестратора меняет только демон. CLI, ACP-шим и агенты — клиенты его сокета. Корень дефектов ACP в Gas City — «любой процесс может дёрнуть сессию» [ФАКТ 04].
2. **Одна реализация каждого механизма.** Один адаптер трекера, один reconciler, один контракт формул, один драйвер на харнесс. Вторую не начинать, пока не удалена первая: двойные реализации дали Gas City 15,6 % веса [ФАКТ 01].
3. **Три харнесса, а не «любой CLI».** Нет tmux, PTY, скрейпинга экрана и ответов на диалоги. Чего нативный протокол не даёт, то не эмулируется: человек уходит в родной TUI через `takeover`.
4. **Трекер хранит только работу.** Ни одной служебной записи в br. Сегодня 99 % строк Dolt — не задачи [ФАКТ 06].
5. **Событие — повод перечитать состояние, а не истина.** Reconcile идемпотентен, редкий resync остаётся [ФАКТ 05].
6. **Суждений в коде нет.** Демон не читает транскрипт, чтобы решить «получилось или нет». Исход шага сообщает агент финишер-командой либо код возврата exec-шага. Политики сбоев — таблица в конфиге.
7. **Ноль ролей в коде.** desk, mayor, planner — конфигурация пака.
8. **Харнессу делегируется:** ретраи API (claude — 10 попыток, pi — 3 [ФАКТ 14, 16]), компакция, субагенты, sandbox и режимы прав, обнаружение skills, память, логин.
9. **Внешним делегируется:** MCP-серверы (у нас только декларация и супервизия процесса), bv как панель задач, редакторы как UI, git.
10. **Нет API-проекции до второго клиента.** Один внутренний JSON-RPC по unix-сокету; CLI и шим живут в том же бинарнике, поэтому совместимость версий не нужна. API + клиент + dashboard в Gas City — 215 тыс. строк [ФАКТ 01].
11. **Домен вне CLI-пакета**, модули с границами, бюджет строк как ratchet (v0 ≤ 35 тыс.). `cmd/gc` — 338 тыс. строк в одном `package main` [ФАКТ 01].
12. **Нет status-файлов.** Живые процессы и сокеты определяются опросом; в SQLite лежат намерения и идентификаторы для resume.
13. **Эффективный конфиг сводит демон**, личный конфиг оператора по умолчанию отсечён [ФАКТ 18].
14. **Не-цели:** несколько хостов, k8s, многопользовательский доступ, hosted-функции, webhooks, extmsg; molecule, wisp, convoy, control-биды, formula v1, convergence; свой трекер, свой MCP-агрегатор, web-dashboard (до v2), ACP v2 в проде, ротация аккаунтов (до v2).

## 2. Компонентная схема и процессная модель

```
systemd --user | pitchfork
└─ <cli> daemon                    один на город; сокет <city>/.run/daemon.sock (0700)
   │  ядро: event core → session manager → run engine → orders
   │  драйверы (в процессе): claude | codex | pi | exec
   │  хранилища: state.db (SQLite WAL) · адаптер br (CLI) · журнал событий
   ├─ claude (stream-json)   ×N    ребёнок, свой pgid, процесс на сессию
   │    └─ stdio-MCP сессии        дети харнесса
   ├─ pi --mode rpc          ×N    ребёнок, свой pgid (v1)
   ├─ exec-шаги, exec-ордера       краткоживущие дети, pgid, таймаут
   ├─ service kb (HTTP-MCP)        ребёнок под супервизией
   └─ br <verb> --json             процесс на операцию
codex app-server --listen unix://<city>/.run/codex-<profile>.sock
                                   detached (setsid); демон — его WebSocket-клиент
<cli> acp                          stdio-шим, ребёнок редактора; клиент daemon.sock
<cli> sessions|tail|send|run|…     CLI; клиент daemon.sock
codex --remote unix://… resume T   TUI человека, второй клиент app-server
```

**Что переживает рестарт демона:** `state.db`, журнал событий, БД br, транскрипты харнессов, процесс codex app-server вместе с идущими ходами. **Что не переживает:** процессы claude и pi, exec-шаги, сервисы (перезапускаются демоном).

**Старт демона.** (1) Скан таблицы процессов по env-маркеру `CITY_SESSION=<id>` и убийство сирот по pgid. Иначе claude доработает ход без наблюдателя [ФАКТ 14], а resume рядом создаст вторую ветку транскрипта [ФАКТ 19]. (2) Подключение к сокетам app-server; `thread/resume` идущего треда подписывает на его события [ФАКТ 15, 19]. (3) Сессии claude/pi в состоянии `running` помечаются `interrupted`, поднимаются через resume и получают промпт-продолжение из шаблона пака; attempt шага растёт. (4) Перевзвод таймеров из `state.db`, полный resync.

**Развилка хостинга процессов.**

| | (1) stdio-дети + resume | (2) broker / detached-хост | (3) codex app-server как сервер |
|---|---|---|---|
| Суть | харнесс — ребёнок демона | отдельный процесс держит харнесс и отдаёт события по сокету с курсором | родной многотредовый сервер codex |
| Рестарт демона | идущие ходы claude/pi теряются; resume 0,4–0,5 с [ФАКТ 14] | ходы продолжаются | ходы продолжаются |
| Цена | 0 | новый компонент со своими отказами, +1,5–3 тыс. строк, перекос версий хоста и демона | `[experimental]`, общий blast radius, один `CODEX_HOME`/env на процесс [ФАКТ 15] |

**[РЕШЕНИЕ] v0 = (1) для claude и pi + (3) для codex.** Основания: сессии владельца живут 27–82 с [ФАКТ 02], поэтому плановый рестарт с дренажом (`<cli> daemon restart --drain 120s`) почти ничего не рвёт; resume дёшев; брокер — отдельный класс отказов, и строить его до измерений рано. App-server запускает и пинит демон. Общий демон codex не используется: он сам обновляется и перезапускается, а у владельца сейчас сломан [ФАКТ 15]. Один экземпляр на codex-профиль (учётка, `CODEX_HOME`, провайдер).

**Критерий перехода к брокеру (v2)** — любое из трёх по журналу событий: (а) рестарты демона прерывают более 5 % ходов агентов за неделю; (б) дважды за неделю потерян ход длиннее 15 минут; (в) демон начинают разрабатывать в его же городе, то есть рестартов много в день. Брокер тогда не вторая реализация: тот же модуль драйвера запускается отдельным процессом `<cli> driver-host` и говорит с ядром по тому же контракту §3 через сокет с курсором событий. Контракт поэтому с первого дня сообщенческий (операции + события с `seq`), без общих объектов в памяти.

## 3. Интерфейс драйвера харнесса

Семантика списана с ACP v2-draft [ФАКТ 13]: `prompt` принимается в любом состоянии и подтверждается `messageId`; конец хода — событие состояния, а не ответ RPC; состояния `running | idle | requires_action`; `stopReason` включает `error`.

**Операции:** `start(profile, cwd, env, model, effort, systemPrompt, mcp[], hooks[], skills[])`, `resume(harnessSessionId, …)`, `close`, `prompt(input, idempotencyKey)`, `steer(input)`, `cancel`, `setModel`, `respond(permissionId, decision)`.

**События** (у каждого `seq`, `sessionId`, `ts`): `turn.started`, `turn.ended{stopReason, usage}`, `state{running|idle|requires_action, background[]}`, `message`, `tool.observed{name, status}`, `permission.requested{id, tool, input}`, `usage{tokens, cost, rateLimit?}`, `retrying{attempt, delayMs, kind}`, `failure{kind, retryable, resetsAt?, retryAfterMs?, raw}`, `exited{code, signal}`.

`failure.kind` = `rate_limit | quota | overloaded | auth | context_overflow | crash | refusal | unknown`. Реакция — таблица политики в session manager: `rate_limit` — экспоненциальный backoff; `quota` — парковка до `resetsAt` и уведомление; `auth` — `requires_action`; `crash` — resume до трёх раз, затем fresh, затем провал шага.

**Capability-флаги:** `steer`, `nativeQueue`, `multiSessionProcess`, `multiClientAttach`, `typedFailures`, `rateLimitSnapshot`, `permissions`, `perSessionEnv`, `perSessionHooks`, `perSessionMcp`, `fork`, `backgroundTasks`.

| Операция / событие | claude (Agent SDK → stream-json) | codex (app-server) | pi (`--mode rpc`) |
|---|---|---|---|
| start | `query()` с Options; процесс на сессию, 160–250 МБ [ФАКТ 14] | `thread/start{cwd, model, config}`; +5–10 МБ на тред [ФАКТ 15] | spawn процесса с флагами; 96 МБ, старт 262 мс [ФАКТ 16] |
| resume | `resume=<id>`, 0,4 с; модель задать заново | `thread/resume`; прерванный ход `interrupted`, результат tool-call потерян | `--session <id>`; ход не продолжается, bash-сироты — kill pgid |
| prompt / steer | streaming input; семантика steer как у `_session/steering` адаптера [ДОПУЩЕНИЕ] | `turn/start` / `turn/steer{expectedTurnId}` | `prompt` / `steer` |
| queue | очередь демона | очередь демона (`thread/queue/*` experimental — не берём) | `follow_up` либо очередь демона |
| cancel | `interrupt()` | `turn/interrupt` | `abort`, 7 мс |
| конец хода, state | `session_state_changed`, `result`; ловушка `subtype:"success"` + `is_error:true` | `turn/completed{status}`, `thread/status/changed` | `agent_settled` + `stopReason` последнего сообщения |
| permission | control-запрос (в SDK — callback) [ДОПУЩЕНИЕ]; в bypass-режиме не приходит | серверный `requestApproval`; при `approvalPolicy=never` не приходит | нет; политика только хуком `tool_call` |
| failure | `api_retry`, `rate_limit_event{status, resetsAt}`, `api_error_status` — типизировано | `codexErrorInfo`, `account/rateLimits/updated{resetsAt}`; 429 codex не ретраит | текст `errorMessage`, exit 0; свой классификатор регулярками |
| конфиг на сессию | всё через Options: `settingSources`, `settings.hooks`, `mcpServers`, `env` | `config` треда; env через `shell_environment_policy.set`; `CODEX_HOME` — на процесс | флаги + сгенерированный agent-dir профиля |
| вне стандарта ACP | все типизированные сбои, хуки, settings | config-оверрайды, multi-client, лимиты | steer, события ретраев |
| что теряется | attach второго клиента | изоляция сбоев между тредами | типизация ошибок, permissions |

**[РЕШЕНИЕ] claude — напрямую, без ACP-адаптера.** Под адаптером и под SDK работает один и тот же процесс `claude --input-format stream-json` [ФАКТ 14], поэтому выбирается только слой над ним. Прямой путь даёт полные сигналы (ретраи, `resetsAt`, authoritative idle) без `_meta`-расширений, экономит 100–115 МБ и снимает зависимость от слоя с 43 релизами за 90 дней и открытыми багами автономных сессий (#864, #1285, #1445, #1269) [ФАКТ 14]. Адаптер дал бы готовые replay и очередь, но в варианте A они и так живут в демоне: его журнал событий — источник replay для CLI и ACP-хаба. Выбор обратим: транскрипты общие, сессии переносятся в обе стороны [ФАКТ 14]; ACP-драйвер «вниз» остаётся возможным четвёртым драйвером (v2), поскольку контракт уже ACP-v2-образный. Выбор зависит от языка: при ядре на Go адаптер стал бы естественным готовым Node-сайдкаром (§9).

## 4. Модель состояния

**br — только работа.** [РЕШЕНИЕ] Одна БД на город: `BEADS_DIR=<city>/.beads` задаётся во всех окружениях. Иначе br поднимается по дереву до `$HOME` и пишет в чужой трекер [ФАКТ 11]. Rig — метка `rig:<name>`, а не отдельная БД: межбазовых parent и зависимостей в br нет [ФАКТ 11], так что **межриговый эпик** — обычный эпик с детьми разных меток, а worktree сессии выбирается по метке бида. «Канонического пути на риг» поэтому нет: worktree работают через `BEADS_DIR`, в ригах `.beads` не создаётся. Цена — теряются префиксы id по ригам. Альтернатива «БД на риг» отложена до появления рига, чей трекер делят с другими людьми.

| Сущность br | Использование |
|---|---|
| типы | `task`, `bug`, `feature`, `epic`; служебных типов нет |
| статусы | `open`, `in_progress`, `closed`, `deferred` |
| рёбра | `parent-child`, `blocks`, `related` |
| метки (лимит 64 [ФАКТ 11]) | `rig:<name>`, `run:<id>` (набор прогона: parent у бида один), `fix`, `lane:<x>` |
| поля | `design` (план), `notes`, `comments` (журнал для людей), `close_reason`, `assignee` (зеркало claim для bv) |

**`state.db` (SQLite WAL), концептуально:**

| Таблица | Содержимое |
|---|---|
| `session` | id, agent, rig, harness, `harness_session_id`, state, `generation`, cwd, model, `last_event_at`, `failure_kind`, `quota_resets_at`, `parked_by` |
| `assignment` | `bead_id` (PK), `session_id`, `run_step`, `generation`, attempt — это и есть claim |
| `run` | id, formula, `target_bead`, rig, vars, state, reason, `parent_run`; уникальность живого (formula, target) |
| `run_step` | `run_id`, `step_id`, iteration, `item_bead`, state, outcome, attempt, `session_id`, `output_json` |
| `gate` | шаг, type (`human`, `timer`, `external`), deadline, `decided_by`, reason |
| `order_state`, `order_run` | `last_run_at`, cursor, `next_due`; кольцо последних 100 запусков на ордер |
| `input_queue` | `session_id`, seq, source (`human`, `run`, `order`, `mail`), mode (`steer`, `queue`), `idempotency_key`, состояние доставки |
| `mail` | from, to, body, `dedup_key`, `read_at` |
| `bead_kv` | `bead_id`, key, value — metadata, которой нет в br [ФАКТ 11], а пакам она обязательна [ФАКТ 02] |
| `timer` | key, `due_at`, kind — перевзводится после рестарта |
| `event` | seq, ts, type, key, payload; ротация |

**Кто куда пишет.** В `state.db` — только демон. В br — демон через адаптер примерно на 10 операций (create, show, update, close, ready, list, dep, comment, events-tail); он ставит `--actor <session-id>`, потому что claim br различает агентов только по имени actor [ФАКТ 11].

**[РЕШЕНИЕ] Агентам даётся `<cli> bead show|ready|create|update|close|comment|dep|meta`** — тонкий прокси в демон, а не «сырой» br. Три причины: (а) fencing — демон сверяет токен сессии с `assignment.generation`, зомби-сессия после рестарта не закроет переназначенный бид; (б) событие рождается в процессе демона, без ожидания файловой системы; (в) `meta` даёт KV, которого нет в br.

Сырые записи `br` человеком или агентом **терпимы, но не доверены.** Демон узнаёт о них через inotify `MOVED_TO` на `issues.jsonl` (ровно раз на мутацию) и короткое read-only чтение `events WHERE id > cursor` (0,05 мс) [ФАКТ 11]. Это зависимость от внутренней схемы br, поэтому страховка — resync раз в 60 с диффом `br list --json` (60 мс на 5 тыс. бидов [ФАКТ 11]).

**Claim** живёт в `assignment`, не в br. Диспетчеризация push-ом: демон сам выбирает ready-бид и отдаёт сессии, гонки «N агентов на `ready --claim`» нет [ФАКТ 06]. В br зеркалируются `status` и `assignee`.

**Гигиена** [ФАКТ 11]: br запинен на 0.7.6 (у владельца 0.6.0), обновление после канареечного прогона; закрытые старше 30 дней выгружаются в архивный JSONL и удаляются (цель ≤ 5 тыс. бидов: цена любой команды линейна по размеру БД); `issues.jsonl` — бэкап (в git он попадёт, только если владелец снимет глобальный ignore `.beads/*`). Запасной выход — свой SQLite-стор с экспортом beads-JSONL для bv.

## 5. Событийное ядро

Каркас «informer + keyed workqueue + resync» [ФАКТ 05].

| Источник события | Ключи reconcile |
|---|---|
| поток драйвера: `turn.ended`, `state`, `failure`, `permission.requested` | `session:<id>`, `run:<id>` |
| выход процесса, EOF, разрыв сокета app-server | `session:<id>` |
| записи через `<cli> bead` (в процессе) | `bead:<id>`, `run:<id>`, `pool:<rig>/<agent>` |
| inotify на `issues.jsonl` | `bead:<id>` |
| команды CLI и ACP-шима | по смыслу |
| таймеры (cron, cooldown, deadline гейта, stall, `resetsAt`) | `order:<name>`, `run:<id>`, `session:<id>` |
| fs-watch конфига и паков | `config` |

**Очередь:** ключ стоит в ней не более одного раза; событие во время обработки ставит флаг dirty, и ключ обрабатывается ещё раз; по одному ключу — строго последовательно; ошибка — backoff 0,5 с → 5 мин. `reconcile(key)` читает состояние из SQLite и памяти, а не из события. Всплеск событий не даёт N полных проходов (урок #8170 [ФАКТ 05]).

**Журнал.** В `event` пишутся укрупнённые события: сообщение целиком, начало и конец tool-вызова, смена состояния. Дельты токенов идут только живым подписчикам. Журнал питает `tail`, replay для ACP `session/load`, event-ордера и уведомления.

**Остаётся периодическим:** resync 60 с (дифф br, сверка таблицы процессов с `session`, проба сокетов и сервисов); cron и cooldown — таймеры, а не опрос; stall-таймер на каждую `running`-сессию; ротация журнала раз в сутки. В простое демон не пишет в br ничего.

| Сценарий | Gas City сегодня | Вариант A |
|---|---|---|
| (а) бид → агент работает | 19,0 с [ФАКТ 05] | событие < 10 мс, `ready` 13–58 мс [ФАКТ 11], старт claude 1–3 с [ДОПУЩЕНИЕ], тред codex ≈ 0,2 с [ДОПУЩЕНИЕ]: **1,5–4 с** |
| (б) шаг → шаг | 4,8 с на control-бид, хоп 22–39 с [ФАКТ 02, 05] | та же сессия < 0,1 с; другая роль — старт 1–3 с; exec → exec — миллисекунды |
| (в) краш → рестарт | 20–40 с [ФАКТ 05] | exit/EOF мгновенно, backoff 1 с, resume 0,4–0,5 с: **≈ 2 с** |
| (д) pool 0→N | ⌈N/5⌉ тиков [ФАКТ 05] | N стартов параллельно; предел — `max_active_sessions` и бюджет памяти города: **2–5 с** при N ≤ 5 [ДОПУЩЕНИЕ] |

**Тёплые процессы.** 468 пробуждений = 468 стартов харнесса, из них 143 — sh-скрипты [ФАКТ 02]; последние становятся exec-шагами демона. [РЕШЕНИЕ]

- claude: старт на шаг, без пула. Тёплый процесс стоит 160–250 МБ простоя ради 1–3 с, а fresh-роли процесс между бидами не делят.
- v1 — lookahead-prewarm: граф run известен заранее, поэтому при старте шага K демон прогревает процесс агента шага K+1 (в SDK есть pre-warm [ФАКТ 18]).
- codex: тёплый пул — сам app-server; он живёт, пока в городе есть codex-агенты, idle-stop через 30 минут.
- pi: пул не нужен.
- named-сессии в режиме resume (desk, mayor): процесс живёт, пока подключён клиент или не истёк `idle_ttl` (10 мин), затем закрывается и поднимается по требованию за 0,4 с.

## 6. Модель работы

**[РЕШЕНИЕ] Гибрид с осью «durable run».** Работа — биды: эпик, дети, `blocks`. Процесс — `run` и `run_step` в SQLite. Шаг формулы бидом не становится. Причины выбора против чистого epic-графа отчёта 07:

- `blocks` не различает pass и fail [ФАКТ 07];
- петлям нужны счётчики, то есть metadata KV, которого в br нет;
- в br нет транзакции на несколько команд, значит возможна полузалитая формула после краша;
- запись в br последовательна и стоит 80–300 мс [ФАКТ 11];
- сегодня 69 % durable-бидов города — шаги и control-биды [ФАКТ 06].

Цена: шаги не видны в bv. Компенсация: `<cli> run ls|show`, комментарий на целевом биде при старте и завершении run. От epic-графа взят fan-out по настоящим детям эпика.

**Что материализуется:** строка `run` с привязкой к целевому биду или эпику и строки `run_step`, одной транзакцией SQLite. Биды создают только скрипты и агенты пака, когда появляется настоящая работа (задачи плана, fix-биды QA).

**Правила движка:**

1. Шаг готов, когда все `needs` в `passed` или `skipped`; ложное `when` даёт `skipped`.
2. Шаг `agent`: сессия профиля (`fresh`, `resume` или `shared:<group>`) получает промпт из шаблона. Исход — команда-финишер `<cli> step done|fail|blocked --json`. Ход кончился без финишера — одно напоминание, затем `fail: no_report`.
3. Шаг `exec` исполняет демон: cwd, env, таймаут, своя process group. Exit 0 — pass, 75 — транзиентный повтор, иное — fail; JSON на stdout становится `output`.
4. Провал шага проваливает scope: неначатые шаги — `skipped`, идущие — `cancel`, шаги `always = true` (cleanup) исполняются; run получает `failed` с причиной.
5. `loop`: тело повторяется до `max` раз; после прохода тела выполняется exec-проверка `until`; exit 0 — петля пройдена, иначе новая итерация (новые строки `run_step`); на пределе — fail с заданной причиной.
6. Дочерний run: `for_each` порождает по run item-формулы на каждый ready-бид набора (`br ready --epic`), волнами до тишины, с `max_parallel` и `exclusive` (уникальность `assignment.bead_id`); `call` — тот же механизм для одного набора с ожиданием.
7. `gate` — шаг ожидания: `human` (`<cli> gate approve|return --reason`), `timer`, `external` (exec-проба с интервалом либо событие). Тип, таймаут и причина отказа — поля гейта (сегодня gc их не читает [ФАКТ 02]).

**Sling** = `<cli> run <formula> --on <bead|epic> [--var k=v]`; `<cli> assign <bead> <agent>` — формула из одного шага. Конвоя нет: набор — дети эпика или метка `run:<id>`.

**Orders:** триггеры `cron`, `cooldown`, `event` (подписка на типы журнала с фильтром), `manual`; действие `exec` или `formula`; env, таймаут, оверрайд из `city.toml`. Запуски пишутся в `order_state` и кольцо `order_run`, в трекер — никогда (сегодня ≈ 5000 бидов в сутки [ФАКТ 06]).

**Stall** — не ордер, а таймер по `last_event_at` сессии; политика `[stall] limit, attempts, then = "defer"` — конфиг. Liveness идёт по протоколу, а не по экрану (must-12 [ФАКТ 02]).

**Формулы владельца (иллюстрация, псевдо-TOML):**

```toml
# servitors.plan-review: было loop(check) + 2 children + gate
formula = "servitors.plan-review"
target  = "bead"
[vars]
rounds   = { default = "3", enum = ["1","2","3","4","5"] }
approval = { default = "auto", enum = ["auto","human"] }

[[steps]]
id = "round"
loop = { max = "{{rounds}}", until = "exec:assets/plan-reviewer/check.py",
         on_exhausted = "fail:review_rounds_exhausted" }
  [[steps.steps]]
  id = "plan"
  agent = "servitors.planner"
  session = "resume"                 # planner правит свой план между раундами
  prompt_file = "assets/planner/plan.md"
  [[steps.steps]]
  id = "review"
  needs = ["plan"]
  agent = "servitors.plan-reviewer"
  session = "fresh"
  prompt_file = "assets/plan-reviewer/review.md"

[[steps]]
id = "approve"
needs = ["round"]
when = "approval == human"
gate = { type = "human", timeout = "72h", on_timeout = "fail" }
```

`check.py` читает вердикты из `output` шагов текущей итерации (`<cli> run steps --json`) вместо `bd list --metadata-field gc.attempt=…`. Кросс-ревью — ещё один шаг `review` на codex-агенте.

```toml
# servitors.implement: было drain(separate, exclusive) по синтетическому конвою
formula = "servitors.implement"
target  = "epic|bead"
[[steps]]
id = "build"
for_each = { over = "ready-children", formula = "servitors.implement-task",
             max_parallel = 3, exclusive = true }

# servitors.implement-task
[[steps]]
id = "work"
agent = "servitors.implementer"
session = "fresh"
workdir = "worktree:{{item}}"        # worktree делает демон до старта сессии (must-8)
prompt_file = "assets/implementer/work.md"
```

```toml
# servitors.qa: было loop + run + 5 lanes + gather на script-агенте
formula = "servitors.qa"
target  = "bead"
[[steps]]
id = "round"
loop = { max = 5, until = "exec:assets/tester/check.py", on_exhausted = "fail:qa_rounds_exhausted" }
  [[steps.steps]]
  id = "run"
  exec = "assets/tester/qa.py run"   # autofix, lint, tests; красное → fix-биды, дети F
  timeout = "15m"
  [[steps.steps]]
  id = "review-code"                 # ещё 4 дорожки так же, параллельно
  needs = ["run"]
  when = "qa_code == true"
  agent = "servitors.qa-reviewer-code"
  session = "fresh"
  [[steps.steps]]
  id = "fix"
  needs = ["run", "review-code", "review-test", "review-docs", "review-security", "review-dependency"]
  call = { formula = "servitors.implement", on = "label:run:{{run_id}}", timeout = "2h" }
```

Из пака исчезают: шим input-конвоя и `servitors-convoy-sweep`; `servitors-stall-sweep` (встроенный таймер); script-агент tester как сессия (`session.py`, `lifecycle = "one_shot"`); `pre_start = git init`; провайдеры-носители с хуками «TOML в TOML»; ожидание чужого run внутри `gather`. Остаются скрипты-финишеры и проверки, переведённые с `gc bd` на `<cli> bead` и `<cli> step`.

## 7. MCP-реестр, хуки, конфиг, skills (v0)

По рекомендациям отчёта 18.

**MCP.** Декларация `[mcp.<name>]`: `url` либо `command`, scope `city < rig < agent`, `share = "session" | "city"`, `harnesses`, `enabled`, `identity_headers`. Победитель по имени забирает запись целиком. Примитив `[[service]]` — процесс под супервизией демона с health-пробой, ленивым стартом и backoff; ссылка `service://kb/mcp` разворачивается в локальный порт. Прокси через демон нет: сегодня прокси держит lock контроллера на время запроса [ФАКТ 02]. В v0 `share = "city"` допустим только для нативно-HTTP серверов — это схема `kb` владельца (296 МБ один раз вместо × N [ФАКТ 18]); stdio-серверы остаются на сессию. Мост stdio→HTTP для тяжёлых — v1; агрегатор и OAuth-брокер не планируются. Правка MCP не рестартит сессии: конфиг применяется к новым.

**Хуки.** Канонический контракт скрипта — диалект Claude Code (JSON на stdin, exit 0/2, `hookSpecificOutput`); claude и codex совпадают по wire [ФАКТ 18]. Декларация `[[hook]] on = "tool.pre", match = "shell", run = "…"` на уровне города, профиля харнесса или агента. Отдельный словарь оркестраторных событий (`session.started`, `turn.ended`, `session.failed{kind}`, `session.stalled`, `run.finished`) питает event-ордера и уведомления. Инъекция промпта (prime, mail, nudge) переезжает в демон — он единственный клиент, все промпты идут через него. Handoff на PreCompact в v0 не делаем: fresh-сессии короткие.

**Конфиг.** Слои `harness profile → agent → rig override` демон сводит в один эффективный конфиг сессии. `[env]` есть на каждом слое (сегодня единого места нет [ФАКТ 02]). `inherit_user_config = false` по умолчанию. `<cli> config explain <agent> --rig R` показывает источник каждого поля. Полей агента — около 15 вместо 73 [ФАКТ 08]: harness, model, effort, prompt, skills, mcp, hooks, env, pool.max, session, idle_ttl, workdir, permissions.

**Skills.** Своей системы нет, только доставка каталогов. Канон — `.agents/skills/` пака.

| Канал доставки | claude | codex | pi (v1) |
|---|---|---|---|
| MCP | `options.mcpServers` + `strictMcpConfig`, без файлов | `thread/start.config.mcp_servers`, без файлов | `mcp.json` в agent-dir профиля |
| Хуки | `options.settings.hooks` | `config.hooks` + `bypass_hook_trust` (снимает «Hooks need review») | один shim-extension, зовущий те же скрипты |
| Отсечение личного конфига | `settingSources: []` | `project_root_markers = []`, плагины выключены | свой `PI_CODING_AGENT_DIR` |

## 8. Control pane

- **Главная сессия (desk)** — обычная named-сессия профиля из пака, `mode = "always"`, процесс ленивый. Конфиг навешивает демон, а не клиент человека: `mcpServers` клиента игнорируются [ФАКТ 19].
- **CLI:** `sessions` (агент, риг, бид, state, возраст), `tail <s> [-f]`, `send <s>`, `respond <s>`, `run ls|show`, `gate`, `inbox`, `daemon status|restart --drain`.
- **ACP-хаб-шим** `<cli> acp [--agent desk]`: демон как ACP-агент v1 для Zed, Toad, agent-shell. Методы: `initialize`, `session/list` по всему городу, `session/load` (replay из журнала и подписка), `session/resume`, `session/prompt` (в `input_queue` с `source = human`; ответ — по концу хода, как ждёт v1), `session/cancel`, `session/request_permission`. Клиентские `fs` и `terminal` не объявляются. Удалённый доступ — `ssh host <cli> acp`.
- **Takeover.** claude и pi: `<cli> takeover <s>` паркует сессию (процесс закрыт, `parked_by = human`) и печатает команду resume для родного TUI; `<cli> release` возвращает. codex парковать не нужно: `codex --remote unix://… resume <thread>` — живое совместное управление [ФАКТ 15].
- **Уведомления** — out-of-band из журнала: `requires_action`, провал или завершение run, `quota`, `auth`, stall. Приёмники: ящик `human` (`<cli> inbox`) и exec-sink (ntfy, Telegram, desktop).
- **Почта** «роль → mayor/human» с dedup: таблица `mail` и инъекция получателю на границе хода.

**В v0 входит:** весь CLI, takeover/release, inbox и exec-sink, шим в режиме «один управляющий клиент на сессию; наблюдатели — через `tail`». **v1:** несколько ACP-клиентов на сессию (broadcast, гонка permission «первый ответ выигрывает»). Web — v2.

**[РЕШЕНИЕ] Весь демон на TypeScript (Bun), один процесс.** Главный риск варианта A — дрейф трёх вендорских протоколов. Его снижают официальные типизированные клиенты, которые обновляются вместе с харнессом; все четыре есть только в TS. На Go каждый протокол пришлось бы сопровождать руками. Плата: 80–150 МБ против 20–40 (несущественно на фоне 160–250 МБ на сессию claude и снятых 0,8–1,4 ГБ Dolt [ФАКТ 02]); однопоточный event loop (для I/O-оркестрации достаточно); зрелость Bun как долгоживущего супервизора — [ДОПУЩЕНИЕ], проверяется спайком S0 (сутки, 10 детей, kill-штормы). Отход — Node 26 с `node:sqlite`. Python отклонён из-за распространения.

**Вариант «ядро на Go + sidecar на Node».** Ядро (события, state, run engine, ордера, адаптер br, CLI, драйвер codex по WebSocket) — Go. Sidecar `driver-host` на Node держит Agent SDK, pi и ACP-хаб на TS SDK; между ними контракт §3 по unix-сокету. Плюсы: ядро на 30 МБ, падение SDK не роняет ядро, sidecar сразу является брокером из §2. Минусы: два языка и тулчейна при bus factor = 1; внутренний протокол как четвёртая поверхность дрейфа; три поверхности из пяти всё равно в Node. Брать, если S0 покажет нестабильность Bun/Node как супервизора либо критерий брокера сработает раньше v1.

**Критерии готовности.**

- **v0** (claude + codex + exec; `servitors` end-to-end): прогон `plan-review → implement → qa` на задаче рига проходит без ручных действий, кроме гейта; `kill -9` claude посреди хода — шаг продолжается; `kill -9` демона — run продолжаются, ход codex не прерван; фейковые провайдеры (прототипы в `lab/claude`, `lab/codex`) дают типизированный `failure` для 429, quota, 529, 401 и overflow; хоп p50 ≤ 5 с; простой — 0 записей в br и < 1 % CPU; 7 суток на dev-городе без «busy forever»; ≤ 35 тыс. строк.
- **v1:** драйвер pi и хуки через shim; ACP-мультиклиент проверен с Zed и Toad; event-ордера, гейты timer/external; парковка по `resetsAt`; мост stdio→HTTP; `config explain`; архивация бидов; Gas City выключен в городе владельца 30 суток.
- **v2 (по потребности):** `driver-host`-брокер; ACP-драйвер «вниз»; ротация профилей и аккаунтов; web-вид; свой SQLite-трекер.

## 11. Риски и открытые вопросы (топ-10)

| № | Риск | Mitigation |
|---|---|---|
| 1 | **Три протокола × дрейф версий**: control-протокол claude — внутренний для SDK; codex — стабильный релиз раз в 2–8 дней; pi — раз в неделю [ФАКТ 14–16] | пин версий харнессов в конфиге города; обновление — отдельная операция с контрактным набором (5 сценариев сбоев и resume на фейковых провайдерах); типы из официальных SDK и `generate-ts`; драйвер ≤ 2,5 тыс. строк |

| 3 | **Политика подписок**: «ordinary, individual usage», разделение пулов на паузе; app-server-auth запрещён для commercial/hosted [ФАКТ 14, 15] | немодифицированные бинарники под логином владельца; система личная; профиль харнесса несёт способ auth, переход на API-ключ — правка конфига; учёт usage по ролям |

## 12. A против B (ACP-only) и C (не переписывать)

Оценки B и C — по материалам первой волны, не по их детальным проектам.

| Критерий | A — нативные драйверы | B — ACP-only | C — остаться на Gas City |
|---|---|---|---|
| Время до первого результата | 7–11 недель до v0 | немного быстрее A: один клиент вместо трёх драйверов, resume и очередь готовы в адаптерах; pi всё равно требует своего решения | ноль: работает сегодня |
| Поддержка | 3 нативных протокола на владельце, все официальные | 1 протокол + 3 чужих адаптера + их `_meta`; миграция v1→v2 впереди [ФАКТ 13] | upstream тянет 930 тыс. строк; на владельце клей (3,6–26 тыс.) и ритуалы обновления |
| Фичи оркестрации | полные: типизированные сбои с `resetsAt`, steer, конфиг на сессию, idle-сигнал | codex: 429 и 503 = `end_turn` без AIR-расширения; pi: нет steer и ошибок; зато любой из 45 ACP-агентов [ФАКТ 13, 15, 16] | всё «на бумаге»; квота по экрану, «busy forever» [ФАКТ 02] |
| Память сверх харнессов | демон ≈ 0,1 ГБ; codex 0,09 ГБ + 5–10 МБ на тред | ещё ≈ 100 МБ на адаптер claude и на адаптер codex; pi-acp вдвое дороже rpc [ФАКТ 14–16] | Dolt 0,8–1,4 ГБ + supervisor 0,24–0,37 ГБ [ФАКТ 02] |
| Восстановление | краш харнесса ≈ 2 с; рестарт демона рвёт ходы claude/pi (v0), codex переживает | то же плюс слой адаптера: его смерть оставляет ход без наблюдателя; у codex-acp свой авто-рестарт | лучшее при рестарте оркестратора (tmux живёт); худшее по обнаружению краша (20–40 с) |
| Attach человека | свой ACP-хаб; у codex — родной `--remote`; claude/pi — takeover | тот же свой хаб; родной attach codex теряется (адаптер держит app-server на stdio) | `tmux attach` — универсально, но без обзора города |
| Зависимость от чужих адаптеров | нет (только харнессы и br) | критическая: два адаптера Zed/JetBrains и community-MVP для pi | нет; есть зависимость от upstream gc, bd и Dolt |
| Свой код | 28–50 тыс. | на 3–6 тыс. меньше [ДОПУЩЕНИЕ] | 0 нового |
| Главный риск | дрейф трёх вендорских протоколов | сбои невидимы или специфичны для адаптера; pi | хоп 22–39 с и Dolt конфигом не лечатся; форк не удержать [ФАКТ 01, 02] |

**Где A честно хуже.** Против B: больше драйверного кода; три места, которые ломаются на вендорском релизе; нет бесплатного длинного хвоста агентов; если ACP v2 стабилизирует steering и типизированные ошибки, преимущество A по фичам сожмётся, а драйверы останутся на балансе. Против C: месяцы работы до паритета; заново оплаченные уроки гонок; потеря «tmux переживает всё» и attach к любому CLI.

**Где A лучше.** Только A сегодня даёт то, ради чего владелец уходит от tmux: квота с `resetsAt`, 429 и idle как типизированные события у claude и codex (у pi класс ошибки при любом варианте выводится из текста). Память и латентность лучше обоих вариантов. Чужих адаптеров в критическом пути нет. Контракт драйвера ACP-v2-образный, поэтому переход к B позже — замена драйвера, а не переписывание.
