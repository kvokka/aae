# 45 — Адвокат дьявола: «город целиком на штатном Claude Code» — разбор по фактам

Дата: 2026-11-11. Вход: тезисы владельца после отчёта 44 и документация Claude Code, скачанная 11.11 в
`lab/cc-native/web/` (`WEB`). Пути вида `WEB/x.md:N` — строка в сохранённой странице. Опыты — из отчётов 36 и 44
(E1–E5). Новых запусков не было.

Метки: **[П]** — проверено (дока со строкой или опыт); **[В]** — вывод; **[НП]** — не проверено.

## Итог за 60 секунд

**Где владелец прав.** Город только на claude можно собрать штатными средствами:
- bd/br — CLI для агентов;
- роли — субагенты с хуками и MCP на роль;
- формулы — saved workflows;
- детерминированные проверки — хуки;
- общение — cross-session messaging.

Это самый дешёвый путь из рассмотренных.

**Где владелец ошибается.**
1. Из JS workflow нельзя дёрнуть bash. Детерминированный bash есть, но в хуках, а не в скрипте.
2. «Cron внутри процесса Claude» не переживает `kill -9` этого процесса и сам workflow не продолжает.
3. GPT-модели в Claude Code через Bedrock штатно не подключаются.
4. Две команды agent teams на двух репо не получают общий канал: команда одна на сессию. Канал между сессиями — это
   cross-session messaging, и оно действительно заменяет agent mail.

**Что остаётся неустранимым.** Нужен кто-то вне процесса Claude, кто:
- переживает его смерть;
- решает «что дальше» по трекеру;
- перезапускает упавший прогон.

Это либо LLM-роутер на `/loop`, который тратит квоту на опрос (тот же антипаттерн, что `bd.dog` — 55 % токенов
города), либо скрипт на 300–800 строк под systemd. Второе дешевле и надёжнее. **[В]**

## Разбор тезисов

| # | Тезис владельца | Вердикт | Факты |
|---|---|---|---|
| 1 | «bd — просто зависимость: планнер режет на биды, workflow берёт ready без блокеров» | **верно** | Агенты зовут `bd`/`br` как любой CLI. `bd ready` и атомарный `--claim` есть (отчёт 11). Оговорка: сам скрипт workflow `bd ready` вызвать не может (см. п. 2) — список ready приносит агент (лучше через `schema`), а захват делает агент шага. Если прогонов несколько, claim обязателен, иначе два прогона возьмут один бид **[П]/[В]** |
| 2 | «Раз есть JS — есть и bash» | **неверно, но обходится** | «No direct filesystem or shell access from the workflow itself… Agents read, write, and run commands» (`WEB/workflows.md:353`); «No module loading: a script that contains `import()` fails» (`:354`). Bash запускает только LLM-агент, а в опыте E3 агент вернул ожидаемый текст, не запустив команду (отчёт 44). **Обход — хуки.** `SubagentStop`/`Stop`/`PostToolUse` выполняют команду детерминированно, exit 2 не даёт агенту закончить и возвращает ему фидбек; хуки на роль работают (E1, E2). Exec-шаг = роль-«раннер», чей Stop-хук гонит скрипт и пишет итог прямо в bd. Истина — в bd, а не в ответе агента **[П]/[В]** |
| 3 | «Мониторить, что шаг не срыгнул, — не высшая материя» | **верно** | Штатно: перезапуск зависшего агента до 5 раз (`WEB/workflows.md:415-429`), `schema` на ответ. «Пустое done» ловит `SubagentStop`-хук роли: проверяет коммит, статус бида, артефакт и при провале отдаёт exit 2. Это shipped-work gate из отчёта 34, сделанный хуком. Нужны дисциплина и пин версии **[П]/[В]** |
| 4 | «Сверху оркестратор, хоть Sonnet, — он просто роутер» | **верно** | Результаты агентов остаются в переменных скрипта и не попадают в контекст сессии (`WEB/workflows.md:331`), поэтому контекст роутера мал. Модель сессии и модели шагов независимы (`agent(…, {model})`, поле `model` роли) **[П]** |
| 5 | «Оркестратору — компакт на 200k, воркеру — 400k» | **верно, если модели разные** | Окно задаётся на модель: `modelSettings.<model>.autoCompactWindow` (`WEB/settings-reference.md:673`, `/autocompact`). Значит, Sonnet-роутер на 200k и Opus-воркеры на 400k настраиваются. Поле `autoCompactWindow` в описании роли умеет только **понижать** окно (`WEB/sub-agents.md:305`): на одной модели воркер не получит окно больше, чем у роутера. `CLAUDE_CODE_AUTO_COMPACT_WINDOW` перекрывает всё, включая поле роли (`:1199`). Вживую не проверялось **[П по доке]/[НП]** |
| 6 | «Claude как сервис, внутри cron перезапускает умершие сессии — переживёт и `kill -9`» | **частично** | Плюсы: супервизор сам перезапускает неожиданно упавший процесс сессии (`WEB/agent-view.md:860`), `/loop` восстанавливается при resume (`WEB/scheduled-tasks.md:29`). Минусы: (а) cron внутри процесса умирает вместе с процессом — перезапускает супервизор, а не cron; (б) workflow сам не продолжается — «continues only when Claude relaunches it» (`WEB/workflows.md:387`, `WEB/agent-view.md:864`); (в) saved workflow из рабочего каталога в фоновой сессии **не возобновить**, только запустить заново, со всеми готовыми шагами (`WEB/workflows.md:390`); (г) recurring-задачи сами удаляются через 7 дней (`WEB/scheduled-tasks.md:207`); (д) если умер сам супервизор, сессии останавливаются через минуту, а установки как сервиса нет («Service install is disabled», отчёт 33); (е) в опыте 36 после `kill -9` занятой сессии супервизор поднял её через ~10 с, но ход и сообщение потерялись. Рабочая цепочка из E3: внешний скрипт → `claude -p --resume <sid> "relaunch"` — готовые шаги из кэша. Это и есть внешний перезапускатель **[П]** |
| 7 | «Сброс лимита — тот же вотчер в фоне» | **верно, но вотчер — вне Claude** | Пауза по лимиту работает только в интерактивной терминальной сессии. В `-p`, SDK, фоновой сессии и у тиммейта агент падает (`WEB/workflows.md:406`); более двух ожиданий за прогон тоже нельзя (`:411`). После сброса упавшие на лимите агенты перезапускаются без повтора готовых (v2.1.318+). Вотчеру нужен `resetsAt`: он есть в `rate_limit_event` stream-json — видит его скрипт, а не модель-роутер. Если вотчер — LLM на `/loop`, он тратит ту же квоту, что и ждёт **[П]/[В]** |
| 8 | «Через Bedrock приделаю в Claude ChatGPT-модели и буду всё миксовать» | **неверно** | «Anthropic… doesn't support routing Claude Code to non-Claude models through any gateway» (`WEB/llm-gateway.md:17`). Mantle на Bedrock «serves Claude models» (`WEB/amazon-bedrock.md:486`). GPT — только через неофициальный прокси вроде LiteLLM с трансляцией формата, без поддержки. Ещё два минуса: (а) модель ≠ харнесс — GPT-кодеры обучены под инструменты codex (`apply_patch` и др.), в чужом харнессе они работают хуже, чем в codex **[В]**; (б) Bedrock — потокенная оплата облаку вместо подписки (`WEB/costs.md:223`) **[П]** |
| 9 | «agent teams: команда на репо A и на репо B, канал из коробки, agent mail не нужен» | **канал — да, через другой механизм** | Команда одна на сессию и не делится между сессиями (`WEB/agent-teams.md:495`), поэтому двух команд с общим каналом нет. Между сессиями есть cross-session messaging (GA): `ListAgents`/`SendMessage`, политика `crossSessionInbound` (`WEB/cross-session-messaging.md:197-202`). Он заменяет agent mail. Минусы agent teams как основы: experimental, только интерактив, в `-p`/SDK тиммейты не порождаются (`WEB/agent-teams.md:11,60`); тиммейтам не передаются хуки и skills из определения, in-process — и MCP (`:282-283`); после resume тиммейты не восстанавливаются (`:492`); статус задач «лагает» и блокирует зависимые (`:493`). Роли с хуками — это субагенты и workflows, не teams **[П]** |

## Что получается, если принять всё лучшее из штатного

```
systemd (Restart=always)
└─ city-tick: скрипт 300–800 строк, по таймеру и по inotify на bd/br
   ├─ br ready → какой workflow; claim; worktree
   ├─ claude -p --resume|--session-id … "run workflow X for bead Y"     (stream-json: видит rate_limit_event.resetsAt)
   │    └─ workflow (JS): роли-субагенты с hooks/mcpServers/model/effort; петли; fan-out; schema
   │         └─ хуки ролей: exec-шаги и shipped-work gate детерминированно; итог пишут в br
   ├─ exit без result → --resume + relaunch (готовые шаги из кэша, E3); 3 провала → бид в defer
   ├─ лимит → парковка до resetsAt, затем relaunch
   └─ gate:human на биде → прогон заканчивается; человек закрывает gate в bv или br
человек: интерактивная сессия-«мэр» (там работает и пауза по лимиту), agent view, cross-session messaging
```

**Чем это отличается от C3 и варианта A** **[В]**:
- Граф шагов, роли, хуки и MCP на роль, перезапуск зависших — штатные, их не пишем.
- Свой код — только внешний цикл (≈ 300–800 строк) и скрипты хуков.
- В отчёте 44 оценка была 0,9–1,9 тыс. строк. Если exec и проверки целиком переносятся в хуки ролей, она опускается
  ближе к нижней границе.
- Цена — только claude, плюс зависимость от research-preview API, которое меняется еженедельно.

**Политика.** Workflows, супервизор и cross-session messaging — штатные функции Claude Code. Флот на них ближе к
«явно разрешённому» использованию подписки, чем свой headless-драйвер. Но `claude -p` во внешнем цикле — это
headless, и серая зона Consumer Terms §3 остаётся. Это вывод, а не юридическая оценка. **[В]**
