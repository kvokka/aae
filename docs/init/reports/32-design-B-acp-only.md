# 32. Вариант B — «ACP-only»: самая сильная честная версия

Дата: 2026-11-10. Вход: отчёты 04, 13–19, сводка первой волны; сверка по клонам `src/agent-client-protocol` (ACP), `src/claude-agent-acp` (CAA), `src/codex-acp-current` (CXA), `src/pi-acp` (PIA). Новых экспериментов не ставил: всё, чего нет в отчётах, — чтение кода и документов клонов.
Метки: **[ФАКТ NN]** — из отчёта NN; **[ФАКТ path:line]** — сам видел в клоне; **[РЕШЕНИЕ]** — проектный выбор; **[ДОПУЩЕНИЕ]** — оценка или непроверенное предположение. Все строки, недели и вероятности — допущения, если не помечено иное.

## 0. Выводы за 60 секунд

- **«Чистый ACP v1 без расширений» как единственный транспорт нежизнеспособен**: codex отдаёт 429/503/overflow как `end_turn`, pi — любую ошибку [ФАКТ 15, 16]. B существует только как «на проводе один протокол, сигналы — через расширения адаптеров».
- **Находка, которой нет в сводке первой волны: расширения двух адаптеров — один контракт.** И CAA, и CXA реализуют `_meta.jetbrains.air` с одинаковой записью `sessionFailure {category, severity, actions}` и одинаковым `_session/steering` [ФАКТ CAA/docs/air-extensions.md:1118-1213; CXA/docs/air-extensions.md:895-981; CXA/docs/steering.md:3-7]. Клиент, объявивший себя AIR, получает единый для claude и codex классификатор сбоев. Это главный аргумент за B.
- **v2-draft в обоих адаптерах уже отдаёт `state_update` и `stopReason: "error"`** [ФАКТ CXA/src/AcpV2Prompt.ts:79-85; CAA/src/v2/prompt.ts:99-108] — дыра «упавший ход выглядит успешным» закрыта в черновике, но в v2 у claude нет steering [ФАКТ CAA/src/v2/initialize.ts:60-63].
- **Развилка уже, чем кажется.** Первая волна сама рекомендует вести claude через ACP-адаптер (отчёт 14 §4). «A против B» на деле — это «codex через codex-acp или app-server» и «pi через адаптер или rpc». У владельца codex — 14 стартов из 458 (3%), pi — 0 [ФАКТ сводка].
- **pi под ACP объективно плох**; честное решение B — исключить pi из v0, позже свой адаптер поверх pi SDK (~3k строк TS).
- **Память: B стоит +0,2…0,4 ГБ** на масштабе владельца (пик 11 сессий); экономии «один сервер» нет у claude, а у codex её съедает адаптер на профиль.
- **Per-harness код в «едином» клиенте — около 25–32%** (против ~40–60% у нативных драйверов), но суммарный объём слоя драйверов почти одинаков.
- **Где B выигрывает по-крупному — хаб «вверх» (H10):** журнал событий = wire-формат ACP, replay = повторная отправка; в A нужны три кодировщика «нативное → ACP» (+2,5…4,5k строк).
- **Чего B не закроет ничем:** время сброса лимита codex, конфиг codex на тред, родной attach `codex --remote`, pi.
- **Вердикт:** для v0 владельца разумен **B′** (ACP — транспорт и модель событий; хуки и транскрипт — побочный канал сигналов), при интерфейсе драйвера, допускающем замену codex на app-server. Чистый B хуже B′ во всём, кроме 1k строк. A выигрывает, когда codex становится основным рабочим харнессом на подписке ChatGPT или pi нужен всерьёз.

## 1. Что значит «ACP-only» точно

**[РЕШЕНИЕ] Определение B.** Оркестратор запускает только процессы ACP-агентов и говорит с ними только JSON-RPC ACP по stdio: методы v1 stable + `_meta` + методы с префиксом `_` (легальная расширяемость: [ФАКТ 13 §2.1]). Не читает файлы харнессов и не говорит на нативных протоколах. Версия на проводе — v1; v2-draft включается флагом на адаптер как канарейка.

**Доля per-harness кода в «едином» клиенте** [ДОПУЩЕНИЕ, оценка по компонентам]: общая часть (JSON-RPC, типы, жизненный цикл сессии, автомат хода, очередь, журнал, политика прав, watchdog) ≈ 5,3k строк Go; профиль claude ≈ 1,0k (сборка `_meta`-опций, повторная установка модели, нормализатор сбоев, idle); профиль codex ≈ 0,8k (CODEX_HOME/CONFIG, материализация хуков в cwd, нормализатор, рестарт 1001); pi ≈ 0,7k для чужого адаптера. Для сравнения, в слое драйверов варианта A (§9) per-harness — 3,8k из 9,1k (~42%) при claude через ACP и 5,0k из 8,5k (~59%) при claude через stream-json. Per-harness код в B — это «края» (конфиг и сбои), а не ядро (фрейминг, ход): унификация реальная, но не полная.

## 3. Процессная модель B

**claude.** Процесс `claude` на сессию при любом драйвере; адаптер добавляет 97–118 МБ PSS [ФАКТ 14 §2.1]. Конфиг различается на сессию через `_meta`, поэтому «сервер на набор хуков» не нужен [ФАКТ 14 §2.3]. Отдельный адаптер требует только другой аккаунт: `SettingsManager` адаптера читает config dir процесса [ФАКТ 14 §2.3].

| Гранулярность адаптера claude | Память сверху (пик 11 сессий ≈ 2,5 ГБ) | Blast radius |
|---|---|---|
| один на город | +0,1 ГБ (~4%) | #1193 или краш рвёт наблюдение за всеми ходами |
| **на rig + один для named-сессий** | +0,3 ГБ (~12%) при 2 ригах | один rig |
| на сессию | +1,2 ГБ (~48%) | одна сессия |

**[РЕШЕНИЕ]** на rig + отдельный для desk/mayor; каждый в своей process group; перезапуск простаивающего адаптера раз в N часов (рост памяти на часах не измерен [ФАКТ 14 §5]). Демон обязан непрерывно вычитывать stdout каждого адаптера (#1269) и держать собственный таймаут на prompt (#1445, #1284) — в ACP нет heartbeat [ФАКТ 13 §2.3g].

**codex.** Один адаптер = один app-server = много тредов (+5–10 МБ на тред), но адаптер стоит ~100 МБ сверху: 0 сессий — 209 МБ RSS, 4 сессии — ~290 МБ [ФАКТ 15 §2.3]. Под ACP конфиг — только на процесс: `CODEX_CONFIG` разбирается при старте, `hooks` уходят в `-c` app-server [ФАКТ CXA/src/index.ts:44-49; CXA/src/CodexHookConfig.ts:13-17]; конфига на сессию нет (#215, #229 открыты [ФАКТ 15 §2.4]). **Следствие: адаптер codex на профиль = (`CODEX_HOME`, набор хуков, env, провайдер).** Хуки на сессию возможны только файлом `.codex/hooks.json` в cwd плюс общий `bypass_hook_trust`; env на роль — только отдельным процессом. Интуиция владельца «для разных сетов хуков нужны разные серверы» под ACP верна именно для codex — и это свойство адаптера, а не codex: app-server различает их на тред [ФАКТ 15 §2.5]. Экономия H4 начинается с двух одновременных тредов одного профиля; при одном треде B дороже процесса `codex exec` (249–278 МБ против 155).

**Что переживает рестарт демона** (stdio ⇒ адаптеры умирают вместе с ним):

| | claude | codex |
|---|---|---|
| идущий ход | дорабатывает без наблюдателя и выходит [ФАКТ 14 §2.4] | обрывается, дети умирают [ФАКТ 15 §2.6] |
| восстановление в рамках ACP | `session/load` 0,5 с, хвост берётся из replay (оговорка: #1297 — до последней компакции) | `session/load`; ход `interrupted`, итог прерванного tool call неизвестен |

**Нужен ли брокер** (тонкий процесс, держащий stdio адаптера и буферизующий события на время рестарта демона)? **[РЕШЕНИЕ] в v0 нет.** Сессии владельца живут десятки секунд, работа персистентна в бидах, claude доделывает ход сам. Брокер (~0,5k строк) — в v1 для desk и долгих ходов codex.

## 4. Сбои под ACP-only

Три уровня клиента: **L0** — v1 без расширений; **L1** — v1 + декларация AIR + разбор `_meta`; **L2** — v2-draft.

| Харнесс / сбой | Что получит клиент | Хватает для политики? |
|---|---|---|
| claude, 429 после 10 ретраев | L0: `-32603`, `data.errorKind:"rate_limit"`, ретраи не видны. L1: warning-записи «Retrying… n of max», финал `category:limit, actions:[retry]` | да: backoff |
| claude, квота подписки | L0: `-32603` + текст «You've hit…» [вывод по коду, вживую не снято — ФАКТ 14 §2.4]. L1: `category:limit, actions:[]`; `resetsAt` и `status:"rejected"` в `_claude/rateLimit` | да: ждать до `resetsAt`; `utilization` позволяет притормозить заранее |
| claude, 529 | `errorKind:"server_error"` / `service,[retry]` | да |
| claude, 401 | `-32000` (стандарт) | да: эскалация |
| claude, overflow | `errorKind:"invalid_request"` (неоднозначно) + упавшая компакция | частично: нужен текст |
| claude, краш дочернего | `-32603` за 9 мс без `data`; дальше `-32002` | да: `session/resume` 0,4 с |
| claude, зависший prompt (#1445) | ничего | только watchdog |
| codex, usage limit | L0: `-32603` + `data.codexErrorInfo:"usageLimitExceeded"`; сброс — только текстом. L1: `limit, []` | класс — да; **«до сброса» — нет** |
| codex, обычный 429 | **L0: `end_turn` + текст**; след — `_meta.codex.threadStatus`. L1: `limit,[retry]` в `PromptResponse._meta`, всё ещё `end_turn`. L2: `stopReason:"error"` | L1/L2 — да; codex 429 не ретраит, backoff на оркестраторе |
| codex, 503 / overflow | L0: `end_turn` + текст. L1: `service,[retry]` / `limit,[new_session]` | L1 — да |
| codex, 401 | `-32000` | да |
| codex, краш app-server | код 1001 `{restartable:true}`, адаптер сам поднимает сервер и треды | да, лучше нативного: восстановление написано за нас |
| pi (а), любой сбой | `end_turn`; смерть pi — тишина | нет |

Источники: [ФАКТ 14 §2.4; 15 §2.6, E6, E7; 16 §2.3; таблицы категорий — CAA/docs/air-extensions.md:1196-1213, CXA/docs/air-extensions.md:961-977].

**Где оркестратор примет упавший ход за успешный:**

| Уровень | claude | codex | pi (а) |
|---|---|---|---|
| L0 | 0 из 5 проверенных | **3 из 5** (429, 503, overflow) + `model_not_found` [ФАКТ 04 §2.4] | 5 из 5 |
| L1 | 0, но сбой теперь приходит как `end_turn` + `_meta` — разбор обязателен [ФАКТ CAA/docs/air-extensions.md:1189] | 0 из известных; #647, #340 открыты | 5 из 5 |
| L2 | 0 | 0 | — |

**[РЕШЕНИЕ] Что добавить в B:**
1. Декларация AIR обоим адаптерам и единый нормализатор `(category, actions)` → `{quota_wait | backoff | new_session | fail | relogin | resume}`; `actions: []` при `limit` = квота, `[retry]` = rate limit. Оговорка: контракт помечен «experimental», и документ прямо говорит, что категория «drives only the icon… does not decide client behavior» [ФАКТ CAA/docs/air-extensions.md:48,1214-1215] — мы используем его не по назначению.
2. Запасные признаки: `errorKind`, `codexErrorInfo`, `threadStatus.type == "systemError"`.
3. Эвристика «`end_turn` без usage и без tool calls — подозрителен» (codex отдал `usage: null` на упавшем ходе [ФАКТ 04 §2.4]).
4. **Независимая от протокола страховка:** «ход закончился, а бид не продвинулся» N раз подряд → экспоненциальный backoff и эскалация. Она ловит неизвестные сбои и не даёт выжечь квоту горячей петлёй.
5. Для codex без `resetsAt`: зонд с растущим интервалом. `/status` адаптера печатает время сброса текстом [ФАКТ CXA/src/CodexCommands.ts:590-610,672-686] — хрупкий запасной вариант. У владельца через прокси лимиты `null` при любом драйвере [ФАКТ 15 §2.6].
6. Чтение транскрипта — уже B′ (§8).

**Оценка надёжности** [ДОПУЩЕНИЕ]: claude L1 ≈ нативному (не хватает только чистого класса overflow); codex L1 — классы есть, времени сброса нет, зависимость от экспериментального контракта; pi — неприемлемо до своего адаптера.

## 5. Оркестратор как ACP-хаб «вверх» (H10)

Реализовать [ФАКТ 19 §4.1 — перечень; объёмы — ДОПУЩЕНИЕ]: шим `<cli> acp` (stdio ↔ unix-сокет демона, ~150 строк); `initialize` со своим набором capabilities; `session/list` по всему городу с курсором; `session/load` с replay из журнала; очередь ввода с источником (`human | order | nudge | formula`) в `_meta`; fan-out `session/update`; рассылка `session/request_permission` всем подключённым, «первый ответ выигрывает», отмена у проигравших; единственный писатель в агента. Итого ≈ 2,5k строк.

**Чем помогает ACP «вниз».** Журнал сессии = append-only лог уведомлений `session/update` как они пришли. Все 14 вариантов `session/update` v1 [ФАКТ 13 §2.2] ретранслируются наверх без перекодирования; `sessionId` менять не нужно (он же id харнесса [ФАКТ 14 §2.6, 15 §2.7]); replay — повторная отправка. В варианте A тот же хаб требует кодировщика «нативные события → ACP» на каждый харнесс: именно это делают адаптеры (30,4k строк `src/*.ts` у CAA и 23,1k у CXA — [ФАКТ `wc -l`]); минимальный собственный вариант (текст, tool call, diff, статус) — [ДОПУЩЕНИЕ] 1–2k строк на харнесс.

**Где прозрачность кончается:**
- **Форма потока задаётся декларацией клиента «вниз».** Объявив AIR, демон получает сбой как `end_turn` + `_meta`, а текст ошибки из ленты убирается [ФАКТ CAA/docs/air-extensions.md:1189,1265]. Zed наверху этого `_meta` не поймёт — хаб должен синтезировать видимую запись (`notice` или чанк). ~100 строк, но это уже перекодирование.
- **Корреляция запрос–ответ** своя на каждое соединение: prompt, permission, elicitation.
- **Наблюдатель в v1 не видит «идёт ход»**, если prompt послал не он; `acp-multiplex` понадобился нестандартный `turn_complete` [ФАКТ 19 §2.7]. Как клиенты рисуют чужой ввод вне replay — не проверено [ФАКТ 19 §5].
- **Конфиг:** `mcpServers` и `systemPrompt` от клиента хаб игнорирует — профиль задаёт демон [ФАКТ 19 §4.2].

Оценка [ДОПУЩЕНИЕ]: ~85–90% трафика событий идёт насквозь; хаб — это маршрутизация и корреляция, а не трансляция.

**hydra-acp** доказывает осуществимость (демон + шим + очередь + гонка permission; один автор, полгода [ФАКТ 19 §2.7]); брать как образец поведения, не как зависимость (47★, experimental). **Proxy chains / conductor**: линейная цепочка «один клиент → прокси → один агент», RFD Draft, реализация только в Rust SDK [ФАКТ ACP/docs/rfds/proxy-chains.mdx:50-52,168]. Как хаб «много агентов × много клиентов» неприменим. Применим принцип: пересылать без пересериализации, чтобы `_meta` переживал хоп [ФАКТ там же :272].

**Язык.** Официального Go SDK нет (TS 2.5.0, Rust 5.1.0, Python 1.0.0 [ФАКТ 13 §2.1]). В Go клиент и агентская сторона пишутся от схемы (кодогенерация + ~1,8k строк). На TypeScript B дешевле на ~1,5–2k строк, а CAA подключается как библиотека (`CAA/src/lib.ts` существует). **Выбор языка ядра влияет на цену B сильнее, чем на цену A.**

## 6. Траектория ACP

[ФАКТ 13 §2.1–2.5; ACP/docs/docs.json — 23 RFD Completed, 3 Active, 13 Active v2, 9 Draft]:
- v2 — Draft с 2026-07-20, сейчас alpha.14 (≈ альфа в 8 дней), даты стабилизации нет. Даёт `state_update`, `stopReason:"error"`, prompt во время хода. Оба адаптера его уже обслуживают.
- Открытые PR: steering #1261 (с 2026-05-19, «adoption blocker»), error classification #2755/#2773 (с 2026-11-03: `kind`, `retryable`, `retryAfterMs`), quotas #2316 (с 2026-10-06), multi-client #533 (с 2026-02-18, вынесен в прокси-слой), durable transport #2208, skills #370 (с января; «needs a substantial rework»). Transport HTTP/WS и MCP-over-ACP — RFD Active.
- Темп: 17 minor-релизов схемы за 5 месяцев, ~20 стабилизаций за 2026; мелкие аддитивные фичи доходят до stable за 2–5 месяцев, спорные висят 6–9+ месяцев.
- Управление: Zed + JetBrains. Клиенты — редакторы. Но JetBrains AIR сам нуждается в оркестраторных сигналах: `sessionFailure`, `asyncTasks`, `sessionIndex` — и пишет, что каждое расширение «shaped so that it can become a first-class ACP API later» [ФАКТ CAA/docs/air-extensions.md:48-49]. Один из двух управляющих тянет протокол в нашу сторону.

Сценарии на 6–12 месяцев [ДОПУЩЕНИЕ — вероятности мои]:

| Сценарий | Вероятность | Что закрывается само | Что остаётся |
|---|---|---|---|
| v2 стабилен за 6–9 мес.; error classification — unstable | 35–45% | idle, «упавший ход», `retryAfterMs`; нормализатор −40% кода | конфиг харнесса на сессию, pi, multi-client, квоты codex |
| v2 остаётся Draft 12+ мес. | 40–50% | ничего; живём на v1 + AIR | всё из §1; AIR-контракт может поменяться без нас |
| ломающее событие (смена политики подписки для Agent SDK, вендор уходит с адаптера) | 10–15% | — | claude: stream-json за дни (тот же процесс); codex: писать app-server-драйвер |

**Окупится ли ставка:** в первом сценарии доля per-harness кода падает с ~25–32% до ~15%, а «вверх» появляется стандартное состояние сессии. **Не закроются за 12 месяцев при любом сценарии:** hooks/skills/env на сессию (стандарта нет и не планируется), нативный pi, multi-client в ядре спеки. То есть `_meta.claudeCode.options` и `CODEX_CONFIG` — навсегда; B никогда не станет «ноль знаний о харнессе».

## 7. Где B выигрывает и где проигрывает

**Выигрывает:**
1. **Одна модель событий** — она же формат журнала и протокол «вверх» (§5): −2,5…4,5k строк против «A + ACP-хаб».
2. **Адаптеры поглощают дрейф нативных протоколов.** app-server — `[experimental]`, ~280 методов, 30 минорных релизов за 151 день [ФАКТ 15 §2.9]; за ним следит команда CXA. В A это наша работа.
3. **Восстановление codex написано за нас**: авто-рестарт app-server, `CrashLoopGuard` [ФАКТ 15 §2.6].
4. **Контрактные тесты против одного протокола**: один fake-агент и записи трафика на адаптер; в A — три фейка.
5. **Готовые клиенты как UI** (Zed, agent-shell, acpx, Toad) через шим. Нужен только хаб «вверх», так что это выигрыш B лишь косвенно.
6. **Любой агент реестра (45) «бесплатно»** — в объёме базового цикла prompt/cancel/resume. Классификация сбоев у каждого своя, так что без профиля это снова «на бумаге».
7. **Будущая совместимость:** v2 сделает клиент тоньше; A от v2 не получает ничего.

**Проигрывает:**
1. **Потолок фич = адаптер.** Нет: времени сброса лимита codex, конфига codex на тред, `thread/queue/*`, мульти-клиента codex (`codex --remote` [ФАКТ 15 E8]), steer у pi.
2. **Лишний процесс и слой багов**: +~100 МБ на адаптер; свои дефекты (#1445, #1284, #1269, #1193 у CAA; #641, #647, #336 у CXA).
3. **Двойной пин.** CXA несёт `@openai/codex ^0.166.0`, CAA — собственный `claude` 2.1.321 при установленном 2.1.322 [ФАКТ 15 §2.1, 14 §2.1]. Новая модель или фича харнесса ждёт релиза адаптера, либо `CODEX_PATH`/`CLAUDE_CODE_EXECUTABLE` запускают непроверенную пару.
4. **Три чужих релизных цикла**: CAA — 43 релиза за 90 дней, CXA — 20 с 20 августа, схема — 4 выпуска за 11 дней [ФАКТ 14 §2.8, 15 §2.9, 04 §4].
5. **Опора на чужой экспериментальный контракт (AIR)**, написанный под рендеринг в другом продукте.
6. **Рынок голосует против**: zeron перевёл Claude, Codex и Cursor на нативные драйверы («adapter-mediated ACP kept manufacturing done-status bugs»); единственный ACP-first проект kandev держит нативный app-server как эксперимент [ФАКТ 13 §2.5, 17].
7. **pi** (§2).

## 8. Гибрид B′

**[РЕШЕНИЕ] B′ = B + побочные каналы только на чтение, не управляющие.**

| Канал | Что даёт | Чего не даёт |
|---|---|---|
| Хуки харнесса → сокет событий оркестратора: claude через `_meta…settings.hooks`, codex — файл в cwd, pi — shim-extension | `StopFailure` claude с классом (`rate_limit\|overloaded\|authentication_failed\|billing_error…` [ФАКТ 18 §2.7]); `Stop`/`SessionEnd` как второй сигнал idle; у pi `message_end` со `stopReason:"error"` | у codex нет `StopFailure`; срабатывание под SDK/ACP не проверено [ДОПУЩЕНИЕ] |
| Хвост транскрипта (claude JSONL, pi JSONL) | claude: `error:"rate_limit"`, `apiErrorStatus` [ФАКТ 14 §2.4]; pi: `stopReason:"error"` + `errorMessage` — снимает маскировку `end_turn` у pi-acp; детектор stall | время сброса — только текстом; rollout codex — формат в движении (миграция на sqlite [ФАКТ 15 §2.7]) |
| `takeover/release` в родной TUI через resume | аварийный выход человека; id сессии общий [ФАКТ 14 §2.6, 15 §2.7] | не совместный доступ: один писатель |
| `codex --remote` | родной TUI на живой тред | под CXA app-server на stdio, сокета нет. Обход: `CODEX_PATH` = обёртка-мост к долгоживущему `app-server --listen unix://…` — [ДОПУЩЕНИЕ, не проверено]; заодно app-server пережил бы рестарт адаптера |
| process group / cgroup | уборка сирот (bash у pi) | — |

`rate_limit_event` побочным каналом не является: он уже в ACP через `_claude/rateLimit`.

**Как меняется картина:** ложный успех у pi падает с 5/5 до 0 известных; у claude появляется второй независимый классификатор; codex выигрывает меньше всех (время сброса живёт только в нотификациях app-server). Цена — ~1,1k строк и знание трёх форматов файлов. Риск — сползание в A: в Gas City читатели сессий разрослись до 959 и 1075 строк [ФАКТ 16 §2.10, 04 §2.6]. **[РЕШЕНИЕ]** каналы только advisory, каждый ≤ 400 строк, решения о ходе принимаются по ACP.

## 10. Вердикт

**Выбрать B′, если одновременно:**
1. человеку нужен пульт из готовых ACP-клиентов уже в v0 (исходная формулировка H10);
2. pi откладывается, либо принимается свой адаптер на 3k строк TS;
3. codex остаётся вспомогательным (до ~10–20% стартов), а его лимиты подписки не нужны как данные — сейчас так и есть: 3% стартов, лимиты через прокси `null` [ФАКТ сводка, 15 §2.6];
4. владелец готов пинить адаптеры и держать контрактные тесты на пять сценариев сбоев (фейковые провайдеры первой волны — готовые прототипы [ФАКТ 14 §2.4, 15 §4]);
5. есть ценность в подключении других агентов реестра позже.

**Выбрать чистый B** — только если принципиально не читать файлы харнессов. Он хуже B′ по надёжности сбоев при экономии ~1k строк; рекомендовать не могу.

**Выбрать A-смеш., если выполняется хотя бы одно:** codex — основной рабочий харнесс на подписке ChatGPT (нужны `resetsAt`, конфиг на тред в одном процессе, `turn/steer`, родной attach); pi нужен в ближайшие месяцы; ACP-пульт не нужен, хватает CLI; ядро пишется на Go, а кодогенерация от схемы неприемлема.

**Честный итог адвоката.** Исходная задумка владельца («ACP как единственный транспорт») в буквальном виде не подтверждается: стандарт v1 не несёт ни сбоев, ни конфига харнесса, ни pi. В версии B′ она жизнеспособна и для реального профиля нагрузки владельца (97% — claude) почти совпадает с рекомендацией первой волны. Отличие сводится к двум решениям: вести ли codex через адаптер (дешевле сейчас, потолок ниже) и делать ли ACP внутренней моделью событий (да, если пульт — ACP). B не лучше A «вообще»; он лучше там, где важны пульт и один формат, и хуже там, где важен codex.

**Точка невозврата — не транспорт:**

| Решение | Обратимость |
|---|---|
| claude: ACP ↔ stream-json | лёгкая: тот же процесс, транскрипты и id; дни [ФАКТ 14 §2.6, §4] |
| codex: codex-acp ↔ app-server | средняя: треды, rollout и `CODEX_HOME` общие; меняется доставка конфига; нужен драйвер 1,8k и, при ACP-журнале, кодировщик ~1,5k |
| pi: адаптер ↔ rpc | лёгкая: сессии лежат в штатном месте [ФАКТ 16 §2.6] |
| хаб «вверх» | независим от «вниз» |
| **журнал в формате ACP v1** | труднообратимо: v2 убирает `tool_call`, `plan`, `current_mode_update` [ФАКТ 13 §2.2]; с первого дня нужны версия записи и слой чтения |
| **AIR-таксономия как канон сбоев** | среднее: держать за своим enum, а не протаскивать `category` в движок |
| **язык ядра** | самое необратимое: B тянет к TS/Rust (официальные SDK), Go делает B дороже |
| процессная модель | лёгкая: меняется конфигом |

**[РЕШЕНИЕ] Страховка:** интерфейс драйвера с семантикой v2 (`running / idle / requires_action`, классифицированная ошибка `{kind, retryable, retryAfter}`), как предлагает отчёт 13 §4; ACP-профили claude и codex — его первые реализации; журнал хранит сырые ACP-уведомления с версией. Тогда A и B — не развилка, а две реализации одного интерфейса, и вопрос «ACP-only?» сводится к тому, появится ли когда-нибудь вторая реализация для codex.

## 11. Не проверено

- AIR-декларация вживую: `sessionFailure` для claude и `asyncTasks` — только по документам адаптеров; для codex — эксперимент E7 отчёта 15. Не проверено, меняется ли поведение адаптера от поля `clientInfo`.
- Квота подписки под ACP вживую не снималась ни для claude, ни для codex [ФАКТ 14 §5, 15 §5].
- `StopFailure`-хук под `claude-agent-acp`; обёртка `CODEX_PATH` → общий app-server; `/status` как зонд лимитов — предположения.
- `@openma/pi-acp` не запускался; оценка своего pi-адаптера — по размеру аналогов (4,4k и 7,4k строк).
- Поведение Zed и Toad как наблюдателей живой сессии хаба [ФАКТ 19 §5].
- Долгие ходы, субагенты и суточная работа адаптеров (#1445, #1284, утечки MCP) — не воспроизводились в первой волне.
- Все объёмы, сроки, дни сопровождения и вероятности сценариев — экспертные оценки без прототипа.
