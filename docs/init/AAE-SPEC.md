сразу берёт работу. Основа — сообщение владельца, его ответы на 12 уточняющих вопросов и исследование

  но не меняет молча.
- **[И NN]** — факт из исследования, отчёт `reports/NN-*.md`.

## 1. Что строим

`aae` — событийный оркестратор агентов-кодеров («программная фабрика»): демон уровня машины, который по запросу
запускает **формулы** на **агентах** в **ригах** (репозиториях) **проектов** и доводит прогоны до явного исхода,
переживая сбои харнессов, лимиты и собственные рестарты.

Продукт пишется с нуля. Опыт Gas City используется как знание (инварианты, классы сбоев, ошибки), код не
наследуется. **[Р]**

Четыре свойства определяют форму продукта **[Р]**:

1. **Очень лёгкое ядро.** В ядре только то, без чего прогон нельзя корректно запустить, наблюдать и завершить.
   Всё остальное — адаптеры (харнессы, трекер, фронтенды) и плагины.
2. **События, а не тики.** Ни одна единица работы не ждёт таймера опроса: задержка от причины до реакции не
   зависит ни от какого интервала.
3. **Нативные протоколы харнессов без tmux.** Экран терминала не является каналом управления ни в каком виде.
4. **Меньше кода — лучше.** Пишется только то, что нужно описанному здесь результату. Никаких заглушек, никаких
   точек расширения и кода «на вырост», никаких полей и флагов под будущие функции. Отложенное названо отложенным
   (§1.1) и в коде не присутствует вовсе.

Поставка: один бинарник `aae` под linux и macOS, x86_64 и arm64. Репозиторий публичный, лицензия MIT. **[Р]**

## 3. Словарь

| Термин | Смысл в aae |
|---|---|
| **оркестратор** | демон `aae` и его настройки уровня машины |
| **проект** | каталог с `aae.toml`: набор ригов, паков, плагинов и одна БД трекера. Аналог city |
| **риг** | репозиторий на диске плюс его переменные (`test_cmd`, `lint_cmd` и т. п.) |
| **харнесс** | вид agent-CLI: `claude`, `codex`, позже `opencode`. Ему соответствует один адаптер |
| **экземпляр харнесса** | запущенный процесс харнесса (app-server или процесс сессии), который обслуживает одну или несколько сессий |
| **агент** | конфигурация роли: харнесс, модель, промпт, плагины, MCP, хуки, skills, env. Ролей в коде ядра нет |
| **ссылка на сессию** | пара «харнесс + id сессии у харнесса». Единственное, что ядро знает о разговоре |
| **формула** | описание работы: имя, описание, входы, один шаг |
| **шаг** | `prompt` (ход агента) или `exec` (команда без LLM) |
| **прогон** (run) | исполнение формулы с конкретными входами; имеет попытки и исход |
| **попытка** (attempt) | один запуск или возобновление сессии в рамках прогона |
| **финишер** | вызов, которым агент сообщает исход прогона |
| **триггер** | правило «событие или расписание → запустить формулу» |
| **correlation** | идентификатор цепочки прогонов, порождённых друг другом |
| **pack** | содержимое: агенты, формулы, триггеры |
| **plugin** | расширение: то, что подключается к агентам (skills, hooks, MCP, скрипты, env), хуки на события оркестратора, сервисы |
| **сервис** | долгоживущий процесс под супервизией оркестратора (например, общий MCP-сервер) |
| **ворота выдачи** | запись «по этому ключу прогоны не запускать до времени или до ручного снятия» (§5.7) |
| **трекер** | хранилище задач за интерфейсом-адаптером; первая реализация — br |
| **бид** | задача в трекере. Только настоящая работа, никаких служебных записей |
| **событие** | запись о случившемся; повод перечитать состояние, а не истина |

## 4. Архитектура

```
                 HTTP API (полная)   CLI (полная)   MCP (малая)
                        └───────────────┼───────────────┘
                                 фронтенд-адаптеры
                                        │  команды / запросы / поток событий
┌───────────────────────────────────────▼──────────────────────────────────────┐
│ ЯДРО: один писатель состояния                                                 │
│  входная очередь → обработка в транзакции SQLite → события (outbox)           │
│  прогоны и попытки · триггеры и таймеры · сборка конфига · реестр экземпляров │
│  исполнение exec-хуков плагинов · владение бидом · восстановление и resync    │
└───────┬───────────────────────┬──────────────────────┬───────────────────────┘
        │ интерфейс драйвера    │ интерфейс трекера    │ события → журнал JSONL
  адаптеры харнессов        адаптер br             плагины (exec-хуки, сервисы)
  claude │ codex │ (opencode)
```

Границы, которые проверяются сборкой, а не договорённостью:

- Ядро не зависит ни от одного адаптера, фронтенда или плагина. В ядре нет имён харнессов, имён ролей и вызовов `br`.
- Фронтенды не содержат доменной логики: каждый только переводит свой протокол в команды и запросы ядра.
- Адаптер харнесса не принимает решений о повторах, парковке и исходе: он переводит протокол харнесса в
  нормализованные события и исполняет операции.
- Решения-политики (повторить, припарковать, отклонить) лежат в плагинах и конфиге. Суждения («сделано ли хорошо») —
  в промптах и проверках плагинов. В ядре — только механизмы.

Адаптеры в первом выпуске — модули того же бинарника за общим интерфейсом. Собственный межпроцессный протокол для
адаптеров не изобретается: внешний путь подключения харнессов в будущем — обобщённый драйвер ACP v2. **[Д]**

## 5. Ядро

### 5.1 Событийная модель

Реализовано: всё входит в ядро сообщением единственному писателю; сообщение — одна транзакция SQLite с событиями
(outbox), эффектами и дедлайнами; эффекты после фиксации через очередь по ключу с дедупликацией и backoff
500 мс → 5 мин; таймеры — дедлайны; хоп без интервала (критерий 6). Resync при старте и раз в 5 минут: трекеры и
здоровье процессов экземпляров (pid + время старта); неоднозначность — `resync.diverged` без эффектов. Код:
`crates/aae-core/src/writer.rs`, `effects.rs`, `run/mod.rs`, `run/registry.rs`. Описание —
`docs/design/event-model.md`.
Сжато: цикл 36, оригинал — git show ef08773:docs/init/AAE-SPEC.md

### 5.2 Состояние

- SQLite в режиме WAL, статически слинкованная. Единственный писатель — демон. CLI, плагины и агенты меняют
  состояние только через API.
- В состоянии лежит только рантайм: прогоны, попытки, ссылки на сессии, экземпляры харнессов (pid, время старта,
  pgid, сокет), владение бидами с поколением, состояние триггеров и таймеров, удержания оператора, ключи
  идемпотентности, outbox, ворота выдачи (§5.7), счётчики неудач по бидам.
- Определения (проекты, риги, агенты, формулы, триггеры, плагины) живут в файлах конфигурации. В состояние
  попадает только снимок эффективного конфига прогона — для воспроизводимости и ответа «с чем это запускалось».
- Файлов-статусов, PID-файлов и lock-файлов нет. Живость процесса проверяется по таблице процессов: pid плюс время
  старта.

### 5.3 Журнал событий

- JSONL, ротация по размеру: 10 МБ на файл, 5 файлов. **[Р]**
- Журнал — канал наблюдения, а не источник истины: при 50 МБ история вытесняется. Источник истины — состояние.
- Журнал один на оркестратор, для всех проектов. **[Д]**
- У события есть монотонный `seq` (один счётчик на оркестратор), версия схемы, время, тип, проект, риг, прогон,
  correlation и полезная нагрузка.
- Потребитель продолжает чтение с `seq`. Если `seq` уже вытеснен, он получает явную ошибку «разрыв» и
  восстанавливается запросом состояния через API.
- В журнал идут события уровня оркестрации (§5.4). Содержимое разговора (сообщения модели, вызовы инструментов)
  ядро не сохраняет и через своё состояние не пропускает: живой просмотр — прямая ретрансляция потока адаптера
  фронтендом, история — в транскрипте харнесса по ссылке на сессию. **[Д]**

### 5.4 События

Наблюдаемые (плагины и клиенты читают, но не влияют):

`daemon.started`, `daemon.stopping`, `config.reloaded`, `instance.starting`, `instance.ready`, `instance.stopped`,
`instance.failed`, `service.*`, `run.queued`, `run.started`, `run.state_changed`, `run.parked`, `run.resumed`,
`run.passed`, `run.failed`, `run.cancelled`, `trigger.fired`, `trigger.skipped`, `gate.closed`, `gate.opened`,
`bead.*`, `tracker.sync_failed`, `plugin.hook_failed`, `resync.diverged`.

Решающие (exec-хук плагина может изменить ход, §11.3). Последняя колонка — что делает ядро, когда ни один плагин
не ответил, в том числе когда `default-policy` выключен:

| Событие | Что может хук | Без решения плагина |
|---|---|---|
| `run.preparing` | изменить рабочий каталог и env, дополнить промпт, отказать в запуске | запуск как есть |
| `run.requires_action` | ответить на запрос разрешения или вопрос | ждать ответа человека до дедлайна, затем отказ («deny») |
| `run.attempt_failed` | выбрать реакцию на типизированный сбой: resume, новая сессия, закрыть ворота выдачи до времени, завершить | прогон завершается как `failed` с классом `infrastructure` |
| `run.turn_ended_without_outcome` | вернуть агенту замечание и продолжить либо завершить | `failed` с причиной `hollow_done` |
| `run.finishing` | наложить вето на `pass` с причиной либо вернуть агенту замечание | исход принимается как заявлен |

Каждый отказ действовать пишет событие с причиной. Молчаливых ожиданий нет: самые длинные простои Gas City были
молчаливыми **[И 21]**.

### 5.5 Инварианты ядра

Реализовано: 20 инвариантов ядра (один писатель, владение с поколением, claim в транзакции демона, условный
возврат, подтверждённая смерть до замены, учёт потомков через subreaper и маркер, намерение до эффекта,
идемпотентность, успех только по финишеру, класс `infrastructure`, дедлайны и сторож, потолки, resume с проверкой,
удержание оператора, resync); номера сохранены, код и документы ссылаются на «invariant N». Пороги — конфиг, реакция —
политика. Проверка — хаос-стенд `aae-testkit/tests/chaos`. Список и где что живёт — `docs/design/invariants.md`.
Сжато: цикл 39, оригинал — git show ef08773:docs/init/AAE-SPEC.md

### 5.6 Восстановление

## 6. Иерархия и конфиг

### 6.1 Уровни

```
оркестратор   ~/.config/aae/config.toml     умолчания харнессов и моделей, общие MCP/hooks/skills/env, плагины
└─ проект     <project>/aae.toml            риги, паки, плагины проекта, оверрайды
   └─ риг     секция в aae.toml             путь к репозиторию, переменные, оверрайды
```

Агент не уровень иерархии, а потребитель: он выбирает харнесс из известных оркестратору и, при желании, модель.
Умолчание модели для каждого харнесса задаётся на уровне оркестратора. **[Р]**

### 6.2 Что настраивается

Нейтральные к харнессу категории: модель и effort, env, MCP-серверы, хуки харнесса, skills, системный промпт,
режим разрешений, плагины, флаг наследования хоста. Плюс блок «родных» настроек конкретного харнесса, который
ядро не интерпретирует и передаёт адаптеру как есть.

### 6.3 Порядок слоёв

От слабого к сильному **[Д]**:

1. настройки хоста для данного харнесса (`~/.claude/settings.json`, `~/.codex/` и т. п.) — если наследование
   включено;
2. общие настройки оркестратора;
3. общие настройки проекта;
4. общие настройки рига;
5. вклад плагинов, подключённых к агенту, в порядке подключения;
6. определение агента из его каталога;
7. оверрайды этого агента, заданные снаружи (оркестратор → проект → риг) — чтобы поправить агента из внешнего пака,
   не форкая пак.

Правила слияния **[Д]**: скаляр — побеждает старший слой; словари (env, MCP по имени) — по ключу, запись
заменяется целиком; списки с именованными элементами (хуки, skills, плагины) — объединение с возможностью
выключить элемент по имени на старшем слое.

Обязательное свойство: команда «объясни конфиг» показывает итог для тройки (проект, риг, агент) и для каждого
значения — слой, из которого оно пришло.

Слой хоста — исключение. Настройки хоста сливает сам харнесс, ядро их не читает и не разбирает. В «объясни
конфиг» он показан одной строкой «наследуется харнессом, содержимое ядру не видно», и выключить отдельный
элемент хоста по имени нельзя — только весь слой.

Конфиг харнесса внутри самого рига (`CLAUDE.md`, `.claude/`, `.mcp.json`, `AGENTS.md`) — свойство репозитория, а
не хоста: он должен действовать и при выключенном наследовании хоста. **[Д]** Достижимо ли это, не проверено
**[НП]**: у claude пустой список источников настроек отсекает и хост, и риг (проектные skills, хуки и `CLAUDE.md`
не загрузились), а вариант «только проект» не испытан (`aae-context/04`, §5). У codex хост отсекается только
отдельным `CODEX_HOME`.

### 6.4 Наследование настроек хоста

Включено по умолчанию, выключается на любом уровне (`inherit_host`). **[Р]** Реализовано: при выключенном
наследовании claude получает свой `CLAUDE_CONFIG_DIR` и токен подписки хоста, codex — свои `CODEX_HOME`/`HOME`,
ссылку на `auth.json` хоста и провайдера хост-конфига с его `env_key`; `doctor` предупреждает о stdio-MCP хоста.
Код — `aae-claude/src/part.rs`, `aae-codex/src/part.rs`, `aae/src/doctor.rs`; цена наследования, замеры и
открытые [НП] (истечение токена claude, подписка ChatGPT в отдельном `CODEX_HOME`) — `docs/design/config.md`
«Host inheritance». Сжато: цикл 40, оригинал — `git show ef08773:docs/init/AAE-SPEC.md`.

### 6.5 Сборка и доставка

- Эффективный конфиг собирает ядро непосредственно перед стартом сессии. Адаптер «материализует» его: переводит в
  флаги запуска, параметры сессии или сгенерированный каталог конфигурации харнесса.
- Сгенерированные файлы лежат в каталоге состояния оркестратора, а не в риге и не в домашних каталогах харнессов.
- Конфиг перечитывается по явной команде, а не слежением за файлами. **[Д]** Невалидный конфиг не применяется:
  остаётся прежний, команда возвращает ошибку. Изменение затрагивает только новые сессии; идущие прогоны работают со своим
  снимком. Правка одного MCP не перезапускает ничего, кроме экземпляров, чей отпечаток изменился.
- Окружение сессии явное: оно собирается из слоёв, а не наследуется от окружения демона целиком.

Внешними зависимостями управляет mise. **[Р]** Отсюда допущение: демон разрешает бинарники харнессов и `br` через
mise и во время работы. **[Д]** Демон под systemd или launchd получает
минимальный `PATH` без shim-каталога mise, поэтому полагаться на `PATH` нельзя: путь и версия бинарника берутся у
mise явно. Запасной путь для машины без mise — явный путь к бинарнику в конфиге. **[Д]** `aae doctor` проверяет
каждый бинарник, его версию и состояние логина.

## 7. Харнессы

### 7.1 Интерфейс драйвера

Семантика повторяет ACP v2: состояние `running | idle | requires_action` и типизированная ошибка хода. **[Р]**

Операции:

- по экземпляру: разделить эффективный конфиг на часть «на процесс» и часть «на сессию» и вычислить отпечаток;
  запустить; проверить здоровье; остановить;
- по сессии: начать, возобновить по ссылке, отправить промпт с ключом идемпотентности, отменить ход, ответить на
  запрос разрешения, закрыть;
- по транскрипту: проверить, что транскрипт сессии существует; прочитать его хвост (нужно для resume и для сверки
  после смерти демона).

Нормализованные события с порядковым номером: `session.started`, `turn.started`, `turn.ended{stop_reason}`,
`state{running|idle|requires_action, background}`, `permission.requested`, `usage{rate_limit?}`, `retrying`,
`failure{kind, scope, retry_at?, retried_by_harness, source, raw}`, `exited`.

Виды сбоя **[И 34]**: `quota_exhausted`, `rate_limited`, `overloaded`, `auth_required`, `billing`,
`context_overflow`, `config_error`, `harness_crash`, `adapter_crash`, `daemon_crash`, `stall`, `runaway_turn`,
`tool_failure`, `transcript_divergence`, `workspace_failure`, `hollow_done`, `unknown{text}`. Из них `daemon_crash`,
`stall`, `runaway_turn`, `workspace_failure` и `hollow_done` порождает ядро, остальные — адаптер. Ожидание
человека и фоновая активность вне хода — состояния, а не сбои.

Ссылка на сессию для ядра непрозрачна: адаптер кладёт в неё всё, что нужно для resume. Одного id мало: у codex
транскрипт лежит в `CODEX_HOME` **[И 34]**, то есть привязан к экземпляру.

Адаптер объявляет способности, от которых зависит поведение ядра и политики: несколько сессий в одном процессе;
даёт ли типизированное время сброса лимита (зависит ещё и от вида логина, см. §7.4); ретраит ли харнесс 429 сам.

В интерфейсе нет: steer посреди хода, смены модели внутри живой сессии, подключения человека. **[Д]**

### 7.2 Обязанности любого адаптера

- Закрыть ловушки «успешного провала». Известная для claude **[И 34]**: `subtype:"success"` при `is_error:true`.
  Выход процесса с кодом 0 без результата наблюдался у pi; для claude и codex это сценарий контрактных тестов.
- Границу «ход закончен» брать из авторитетного сигнала харнесса, а не из факта ответа на запрос.
- Сообщать, ретраит ли харнесс сам: поверх claude повторять нельзя (по умолчанию до 10 своих попыток; в логе
  опыта снято 7; замер 2026-11-10, claude 2.1.322), за codex — нужно **[И 34]**.
  <!-- MEASURE id=claude-self-retries date=2026-11-10 ver=claude-2.1.322 env=linux-arm64-orbstack src=reports/34 note="задержки 0,57→32,8 с на поддельном API; настраивается CLAUDE_CODE_MAX_RETRIES" -->
- Запускать каждую сессию или экземпляр в своей группе процессов.
- Объявлять поддерживаемый диапазон версий харнесса; на непроверенной версии — предупреждение.

### 7.3 Ленивый реестр экземпляров

- Ключ экземпляра — отпечаток (харнесс + «процессная» часть эффективного конфига). **[Р]**
- Экземпляр стартует при первой потребности, переиспользуется всеми сессиями с тем же отпечатком и
  останавливается после простоя без сессий.
- Плагин, меняющий «процессную» часть конфига харнесса, автоматически даёт другой отпечаток и другой экземпляр.
  Плагин, работающий только на стороне оркестратора, экземпляров не плодит. **[Р]**
- У экземпляра, который держит много сессий, есть предел числа сессий: падение общего процесса роняет все его
  сессии сразу **[И 21]**. Сверх предела поднимается второй экземпляр с тем же отпечатком. **[Д]**
- Тот же реестр обслуживает сервисы (§11.4): ленивый старт, счётчик потребителей, остановка по простою, проверка
  здоровья, быстрый перезапуск.

Что считается «процессным», решает адаптер:

| Харнесс | На процесс | На сессию | Следствие |
|---|---|---|---|
| claude | — | всё: настройки, хуки, MCP, промпт, модель, env | процесс на сессию при любом пути; «общего сервера» нет, экономии памяти нет **[И 14]** |
| codex | `CODEX_HOME` (логин, skills, плагины, пользовательский конфиг), окружение процесса (с ним же исполняются хуки), провайдер модели | cwd, модель, effort, инструкции, MCP, env команд; хуки — **[НП]** | один app-server на отпечаток, много тредов: 93 МБ пустой, первый тред +39–62 МБ, каждый следующий ≈ 5–10 МБ (замер 2026-11-10, codex 0.166.0) **[И 15]** <!-- MEASURE id=codex-appserver-rss date=2026-11-10 ver=codex-0.166.0 env=linux-arm64-orbstack src=reports/15 note="RSS, до 4 тредов, ходы reply OK; на длинных историях не проверено: история треда живёт в памяти процесса" --> |
| opencode | **[НП]** | **[НП]** | выясняет спайк |

### 7.4 claude

- Транспорт: `claude -p` с потоковым JSON на вход и выход, подтверждением приёма сообщений и заданным id сессии;
  возобновление — по id.
- Конфиг на сессию доставляется флагами: источники настроек (это и есть переключатель наследования хоста),
  дополнительные настройки с хуками, MCP-конфиг и строгий режим MCP, каталоги плагинов, системный промпт,
  модель, effort, режим разрешений.
- Сигналы: повторы API, событие лимита с временем сброса, итог хода с признаком ошибки, смена состояния сессии,
  heartbeat долгого инструмента раз в 30 с (замер 2026-11-11, claude 2.1.322) **[И 46]**.
  <!-- MEASURE id=claude-tool-heartbeat date=2026-11-11 ver=claude-2.1.322 env=linux-arm64-orbstack src=reports/46a note="tool_progress в stream-json; от интервала зависит порог сторожа stall" -->
- При resume модель передаётся явно. Сброс модели после resume наблюдался через ACP-адаптер **[И 14]**; для
  `claude -p` — **[НП]**.
- Время сброса лимита: событие лимита приходит при логине подпиской. При API-ключе лимит выглядит как обычный
  `rate_limit` без времени сброса **[И 34]**. Форма события при настоящем исчерпании квоты вживую не снята
  **[НП]**.
- «Ход закончен» — это состояние idle без фоновых задач. Субагенты claude по умолчанию фоновые **[И 46]**: по
  одному только концу хода главного треда судить нельзя. Из одного сигнала это не выводится: событие смены
  состояния включается переменной окружения и не учитывает фоновые shell-команды, для них нужен отдельный
  сигнал о фоновых задачах; оба вместе в одном прогоне не снимались **[НП]** (`aae-context/01`).
- До первого сообщения пользователя процесс ничего не пишет: `init` приходит после отправки промпта и
  повторяется на каждый ход. Ждать `init` перед промптом — взаимная блокировка.
- Число итогов хода не равно числу промптов: сессия, разбуженная фоновой задачей, делает ход сама.
- Heartbeat не приходит изнутри субагентов и во время ожидания разрешения **[И 46]** — это учитывает сторож
  (инвариант 15).
- Смерть демона: ход дорабатывает без наблюдателя; исход узнаётся из транскрипта и состояния репозитория
  **[И 34]**.
- Холодный старт: 0,25–0,35 с до init, остальное — время до первого токена модели (замер 2026-11-10,
  claude 2.1.322) **[И 42]**. Тёплый пул ради скорости не нужен.

### 7.5 codex

- Транспорт: собственный `codex app-server` на unix-сокете в каталоге оркестратора; общий демон codex
  пользователя не используется.
- Типы протокола генерируются из схемы, которую выдаёт сам codex; руками описывается только используемое
  подмножество.
- Сигналы: ошибка с признаком повтора и классом, завершение хода со статусом, смена статуса треда, обновление
  лимитов с временем сброса **[И 15]**.
- 429 без заголовка `Retry-After` codex не ретраит — повтор обязана обеспечить политика **[И 34]**. С заголовком
  он повторяет один раз после указанной паузы **[И 46]**.
- Границу хода брать только из завершения хода: статус треда `idle` приходит раньше. Фоновая команда идёт при
  статусе `idle`; пока провайдер молчит до заголовков ответа, нет ни одной нотификации и никакого собственного
  таймаута codex.
- MCP на тред подтверждён только для HTTP-сервера; stdio-MCP на тред в опыте не стартовал **[НП]**.
- Два запроса хода в один тред не ставятся в очередь, а сливаются: второй становится steer **[И 36]**. Ввод в тред
  сериализует демон.
- app-server помечен `[experimental]`, релизы каждые 2–8 дней (наблюдение на 2026-11-10, codex 0.166.0)
  **[И 15]**: версия закрепляется, обновление — только через контрактные тесты.
  <!-- MEASURE id=codex-release-cadence date=2026-11-10 ver=codex-0.166.0 env=linux-arm64-orbstack src=reports/15 note="по истории релизов; пересчитать перед выбором политики обновлений" -->
- Транспорт под вопросом **[НП]**: unix-сокет app-server говорит WebSocket, а не построчный JSON, и WebSocket
  помечен вендором «experimental and unsupported» **[И 15]**. Переживать рестарт демона экземпляру в первом
  выпуске не нужно (§5.6), поэтому stdio — равноправный вариант. Решает опыт 2 (§16).
- Хуки исполняются с окружением процесса app-server, а не треда **[И 15]**. Доставка хуков настройкой треда
  сквозным путём не проверена **[НП]**; если она не работает, набор хуков становится «процессной» частью
  конфига и даёт отдельный экземпляр.
- Песочница codex и её совместимость с финишером (сокет демона) и записью в БД трекера вне рабочего каталога —
  **[НП]**.

### 7.7 Человек и прогон

- `aae` показывает прогоны, отдаёт живой поток прогона и принимает ответы на запросы разрешений.
- В состоянии прогона видна ссылка на сессию. После завершения прогона человек может открыть разговор средствами
  самого харнесса; `aae` в этом не участвует.
- Подключение человека к живой сессии и передача управления — следующий цикл разработки. **[Р]** В первом выпуске
  для этого нет ни операций, ни состояний, ни заглушек.

### 7.8 Контрактные тесты

## 8. Агенты и паки

### 8.1 Агент

Всё, что относится к одному агенту, лежит в одном каталоге: настройки, промпты, связанные файлы. Деление на
подкаталоги — по желанию автора. **[Р]**

```
agents/implementer/
  agent.toml        харнесс, модель, effort, плагины, env, MCP, хуки, skills, режим разрешений
  prompt.md         промпт роли
  …                 skills/, hooks/, scripts/ — если нужны
```

Агент выбирает харнесс и, необязательно, модель; остальное наследует из слоёв (§6.3). В коде ядра нет ни одного
имени роли: любое поведение роли — конфигурация.

### 8.2 Pack

Pack — единица содержимого: агенты, формулы, триггеры. **[Р]**

```
<pack>/
  pack.toml         имя, версия, требуемые плагины, минимальная версия aae
  agents/<agent>/…
  formulas/…
```

- Источники: каталог на диске и внешний источник. **[Р]** Внешний источник — git-репозиторий с закреплённой
  ревизией; разрешённые ревизии фиксируются в lock-файле проекта. **[Д]**
- Корень проекта сам является локальным паком: агенты и формулы можно класть прямо в проект. **[Д]**
- Имена уникальны в пределах пака; при совпадении между паками используется форма `<pack>.<имя>`. **[Д]**
- Pack может требовать плагины, но не содержит их.

## 9. Формулы, прогоны, триггеры

### 9.1 Формула

Формула: имя, описание, объявленные входы и ровно один шаг. **[Р]**

```toml
name = "implement"
description = "Реализовать задачу по биду"

[inputs]
bead = { type = "bead", required = true }

[step]
kind = "prompt"            # или "exec"
agent = "implementer"
prompt = "implement.md"    # шаблон с подстановками входов, полей бида, рига и прогона
timeout = "45m"
```

Виды шага **[Р]**:

- `prompt` — ход агента в сессии харнесса. Исход сообщает финишер.
- `exec` — команда без LLM, которую запускает демон: своя группа процессов, таймаут, рабочий каталог рига. Исход —
  по коду возврата: 0 — `pass`; 75 (`EX_TEMPFAIL`) — временная недоступность **[И 21]**: это сбой попытки
  (`run.attempt_failed`), а не исход формулы; иное — `fail`.
  Хвост вывода ограниченного размера сохраняется в результате.

Шаблон промпта — только подстановка переменных, без логики; отсутствующая переменная — ошибка до запуска. **[Д]**

### 9.2 Приёмка и тест — одно и то же

Отдельного «тестового режима» у продукта нет. Проверка формул и проверка самого `aae` — это одна исполняемая
acceptance spec. **[Р]**

- Acceptance spec — набор исполняемых сценариев в репозитории, который реализует критерии §15.
- Сценарии идут тем же путём, что и рабочие прогоны: настоящий демон и настоящие бинарники харнессов.
- Часть сценариев вызывает настоящую модель. Модель — дешёвая; её задают сами агенты из фикстур spec.
- Полностью spec запускается только по явному запросу пользователя одной командой: прогон стоит денег и требует
  логина. Автоматически (на коммит, по расписанию) сценарии с моделью не запускаются никогда.
- Сценарии без модели (поддельный провайдер, сценарный драйвер, exec-шаги) — те же самые сценарии той же spec;
  CI запускает это подмножество на каждый коммит. Колонка «Запуск» в §15 говорит, к какой части относится
  критерий.
- Результат прогона spec — отчёт с датой, версией `aae` и версиями харнессов (правило замеров, §14).

### 9.3 Прогон

Состояния:

```
queued → preparing → starting → running ⇄ requires_action → finishing → passed | failed{класс} | cancelled
                                   │                            │
                                   │                            └→ running (хук вернул агенту замечание)
                                   ├→ parked{ворота, причина} → starting
                                   └→ interrupted (рестарт демона) → решение по `run.attempt_failed`
```

- Класс провала различает причину: `agent` (финишер сказал `fail`), `check` (вето плагина), `hollow_done`,
  `infrastructure` (попытки исчерпаны или политика завершила прогон).
- `queued` — прогон ещё не стартовал: ждёт лимита параллелизма или открытия ворот (§5.7). `parked` — уже
  стартовавший прогон ждёт открытия ворот, процесса харнесса у него нет.
- Прогону нужен рабочий каталог. Риг берётся из входа, из триггера или из метки бида; нет рига — ошибка до
  запуска. **[Д]**
- Рабочий каталог по умолчанию занят одним живым прогоном: второй прогон в тот же каталог ждёт в `queued`.
  Параллельная работа в одном риге — через плагин `worktree`. **[Д]**
- Попытка — запуск новой сессии или возобновление прежней. У попытки своё поколение.
- Параллелизм ограничивается на уровне оркестратора и на уровне агента. **[Д]**
- Прогон может явно продолжить сессию другого завершённого прогона, чтобы сохранить контекст. **[Р]** Неявного
  переиспользования сессий нет.

### 9.4 Исход

- Агент сообщает исход финишером: `pass` или `fail`, краткое резюме, необязательные данные. **[Р]**
- Финишер — команда CLI `aae` в сессии агента; идентификатор прогона и токен попытки приходят через
  окружение. **[Д]**
- Сбой инфраструктуры — не исход: он порождает `run.attempt_failed`, а не слово агента.
- Данные финишера сохраняются в результате прогона и доступны триггерам.

Поведение финишера **[Д]**:

| Ситуация | Что происходит |
|---|---|
| Финишер вызван, ход ещё идёт | заявленный исход записан в состояние; прогон остаётся `running` |
| Финишер вызван повторно в той же попытке | действует последний вызов |
| Ход закончился и фоновых задач нет, исход заявлен | `finishing`: порождается `run.finishing`, плагины-проверки могут наложить вето |
| Ход закончился, но фоновые задачи (субагенты) ещё идут | прогон остаётся `running` до состояния idle без фона; у ожидания есть дедлайн |
| Ход закончился и фоновых задач нет, исход не заявлен | `run.turn_ended_without_outcome`; без решения плагина — `failed` с классом `hollow_done` |
| Хук на `run.finishing` вернул замечание | замечание уходит агенту следующим промптом в той же сессии и той же попытке; прежний заявленный исход сброшен; токен остаётся действительным |
| Хук на `run.finishing` наложил вето | `failed` с классом `check` и причиной от хука |
| Финишер с токеном устаревшей попытки | отвергнут с явной ошибкой, состояние не меняется |
| Демон недоступен в момент вызова | команда финишера повторяет попытки ограниченное время и завершается ошибкой; после рестарта демона прогон идёт по ветке `interrupted` |

Токен привязан к попытке, а не к одному вызову. Возврат замечания — это и есть check-петля: число возвратов
ограничено потолком ядра (инвариант 16).

Из коробки `pass` — это слово агента. Проверку «работа действительно сделана» (коммит есть, тесты зелёные)
ведёт внешний цикл владельца; в комплект она не входит. **[Р]** Механизм вето для неё есть, плагина — нет.

### 9.5 Триггеры

Реализовано **[Р]**: три способа запуска в ядре — явный вызов (API, CLI, MCP `start_run`), подписка на событие
(`on`/`where`/`inputs`), расписание (`cron` в UTC, `every`, одно догоняющее после простоя); идемпотентность по
(триггер, `seq`) в транзакции события, наложение → `trigger.skipped`, correlation от события и от actor br, глубина
10, вкл/выкл оператором. Код: `crates/aae-core/src/run/triggers.rs`, `crates/aae-core/src/cron.rs`. Документация:
`docs/design/config.md` («Trigger»), `docs/design/contracts.md` (§1.3, §2, §3.5, §5).
Сжато: цикл 35, оригинал — git show ef08773:docs/init/AAE-SPEC.md

## 10. Трекер

### 10.1 Интерфейс

Трекер — адаптер с узким интерфейсом на 10–12 операций: создать, показать, изменить, взять, вернуть, закрыть,
список готовых, список по фильтру, добавить зависимость, комментарий, поток событий, проверка здоровья. Проект
может работать без трекера. **[Д]**

### 10.2 br

Реализовано: `br` — внешний бинарник через mise, не линкуется и не вендорится **[Р]**; предупреждение о лицензии
(MIT с райдером OpenAI/Anthropic) в README, `docs/guide/install.md` и `aae doctor` **[Р]**, применимость райдера —
**[НП]**. Одна БД на проект в `<project>/.beads` вне git ригов, риг — метка `rig:<имя>` **[Р]**; `BEADS_DIR` всегда
явно, свой actor у каждой попытки, файл рабочего пространства `bv` при старте демона, контрактные тесты на
закреплённом br. Код: `crates/aae-br`, `crates/aae-core/src/run/beads.rs`, `run/bead_events.rs`. Документация:
`docs/design/tracker-br.md`, `docs/design/contracts.md` §5.
Сжато: цикл 37, оригинал — git show ef08773:docs/init/AAE-SPEC.md

### 10.3 Бид и прогон

- Прогон может получить бид входом; прогоны без бида разрешены. **[Р]**
- Claim, возврат и закрытие делает демон. **[Р]** Claim берётся при запуске и держится весь прогон, через все его
  попытки. Бид отпускается только в терминальном состоянии прогона: `passed` — закрывается; `failed` и
  `cancelled` — возвращается условно (сравнение владельца и поколения).
- Цепочка нескольких формул над одним бидом не критична. **[Р]** В первом выпуске её нет: `pass` всегда
  закрывает бид. **[Д]** Работа режется на биды, а следующий берётся штатным подбором br — «следующий готовый
  бид», в том числе в пределах эпика. **[Р]**
- Вход прогона может быть не конкретным бидом, а запросом «следующий готовый», необязательно с эпиком. Список
  готовых даёт адаптер трекера; выбор и claim демон делает одной операцией. Если готовых нет, прогон не
  создаётся, а вызывающий получает явный ответ «нечего брать». **[Д]**
- У бида не более одного живого прогона-владельца; второй запрос отклоняется с причиной.
- Счётчик неудач бида: каждый прогон, завершившийся `failed` над этим бидом, увеличивает счётчик в состоянии
  оркестратора. После заданного числа неудач ядро закрывает ворота выдачи по этому биду (§5.7) и пишет событие:
  подбор «следующий готовый» его пропускает, пока человек не снимет ворота. Иначе возврат бида порождал бы
  `bead.ready` и бесконечный повтор. **[Д]**
- Запись о владении в состоянии оркестратора — истина; поле владельца в br — её отражение. Если `br close` или
  возврат не удались, исход прогона не меняется: операция повторяется через очередь по ключу, расхождение видно
  событием.
- Агент пользуется `br` сам для содержательной работы: дочерние задачи, комментарии, зависимости.

## 11. Плагины

### 11.1 Назначение

Плагин — единица расширения. Типовые расширения делаются плагинами, а не кодом ядра. **[Р]** Пример: будущий
плагин почты описывает, как он подключается к агентам, свои skills, хуки и скрипты.

```
aae-plugin-<имя>/
  plugin.toml       имя, версия, параметры, вклад в агентов, хуки оркестратора, сервисы
  skills/ hooks/ bin/ …
```

### 11.2 Сторона агента — декларативная

Плагин добавляет подключившему его агенту: skills, хуки харнесса, MCP-серверы, переменные окружения, скрипты в
`PATH`, фрагменты промпта, родные для харнесса части (например, каталог плагина Claude Code).

- Вклад получают только агенты, которые плагин подключили. **[Р]**
- Хуки харнесса пишутся в диалекте Claude: JSON на stdin, код возврата, JSON на stdout. claude и codex исполняют
  его нативно **[И 18]**.
- Если вклад меняет «процессную» часть конфига харнесса, агент получает отдельный экземпляр в реестре (§7.3).

### 11.3 Сторона оркестратора — exec-хуки

Плагин вешает команды на события ядра. **[Р]**

- Контракт — тот же диалект: событие JSON на stdin; код 0 — «нет возражений»; код 2 — блокировка с причиной в
  stderr; JSON на stdout — решение для решающих событий (§5.4).
- Хук не имеет состояния и исполняется вне цикла ядра; его ответ возвращается сообщением. Падение или таймаут
  хука не роняет демон и порождает `plugin.hook_failed`.
- Для хуков-вето отказ самого хука по умолчанию блокирует («неоднозначность ⇒ ноль эффектов»); для наблюдающих —
  игнорируется. **[Д]**
- Несколько плагинов на одном событии: для вето достаточно одной блокировки; для выбора реакции на сбой действует
  первое решение в порядке подключения. **[Д]**
- В событии уже есть счётчики попыток, времена и состояние ворот, поэтому политикам своё состояние не нужно.
  Хранилища для плагинов в ядре нет.
- У хука есть таймаут. Хук, не успевший до `kill -9` демона, после рестарта запускается заново: решающее
  событие остаётся в outbox, пока по нему нет решения. Хуки обязаны быть идемпотентными.
- Хуки и сервисы стороны оркестратора включаются на уровне оркестратора или проекта.

### 11.4 Сервисы

Плагин или конфиг объявляет долгоживущий процесс: команда, область совместного использования (оркестратор, проект,
сессия), проверка здоровья. Сервисы живут в том же ленивом реестре, что и экземпляры харнессов.

Общий MCP **[Р]**:

- MCP-сервер по умолчанию один на область, а не на сессию. Сессии получают его URL и заголовки идентичности:
  проект, риг, агент, прогон. Опыт: один HTTP-MCP обслужил claude, codex и pi, идентичность дошла заголовками
  (опыт 2026-11-10; claude 2.1.321, codex 0.166.0, pi 1.5.0) **[И 36]**.
  <!-- MEASURE id=shared-http-mcp date=2026-11-10 ver=claude-2.1.321,codex-0.166.0,pi-1.5.0 env=linux-arm64-orbstack src=reports/36 note="6 вызовов, по 2 на харнесс; под нагрузкой не проверялось" -->
- Сервер, который отдаёт сам `aae`, и любой рекомендуемый общий сервер должны понимать обе эпохи протокола MCP:
  stateless 2026-07-28 и `initialize`-эпоху. codex 0.166 говорит только на 2025-06-18 и сервер «только новой
  эпохи» отвергает **[И 36]**.
- Перезапуск сервиса должен быть быстрым: claude переподключается к перезапущенному stateful-серверу за 7–26 с,
  и в одном из четырёх прогонов ход упал (замер 2026-11-10, claude 2.1.321) **[И 36]**.
  <!-- MEASURE id=claude-mcp-reconnect date=2026-11-10 ver=claude-2.1.321 env=linux-arm64-orbstack src=reports/36 note="4 прогона: 6,8 / 15,7 / 20,6 / 25,7 с; stateful HTTP-MCP, рестарт на том же порту; на stateless 2026-07-28 рестарт прозрачен" -->
  Сбой MCP — это сбой инструмента, а не провал прогона.
- stdio-сервер с неявным состоянием на клиента (например, браузерный) делить нельзя: для него область «сессия»
  задаётся явно.
- Делить stdio-сервер между сессиями можно только через мост stdio→HTTP. Мост входит в цель «общий MCP», но не в
  ядро: это отдельный модуль поставки. Если он не помещается в бюджет первого выпуска, он уходит в следующий, а в первом
  старт stdio-сервера «на сессию» сопровождается видимым предупреждением. **[Д]**
- Порт на loopback без аутентификации доступен любому локальному процессу **[И 18]**: общий сервис слушает
  unix-сокет либо loopback с токеном.

### 11.5 Плагины в комплекте

Поставляются внутри бинарника как встроенные исполнители хуков (внешний рантайм не нужен), включены по умолчанию,
отключаемы. В бюджет ядра не входят. **[Д]**

| Плагин | Что делает |
|---|---|
| `default-policy` | Реакции на сбои — «дешёвые страховки» Gas City **[И 21 §4.2]**: resume после краша; после нескольких отказов самого resume — новая сессия; при квоте — закрыть ворота аккаунта до времени сброса; backoff на 429 для харнессов, которые не ретраят сами; при серии крашей — закрыть ворота агента; лестница для `stall`; одно напоминание при конце хода без финишера. Точные пороги, их первоисточники и расхождения между отчётами собраны в `aae-context/06`; там же перечислены значения, которых нет ни в одном отчёте и которые назначает исполнитель. Пороги меняются в конфиге плагина. Работает только на стороне оркестратора и харнесс не меняет **[Р]** |
| `worktree` | На `run.preparing` создаёт git-worktree для прогона и подставляет рабочий каталог; после завершения удаляет, только если коммиты достижимы из refs. Включается на агенте или формуле. Необязательность worktree — **[Р]**, оформление плагином — **[Д]** |

Граница: механизмы — в ядре (возобновить, начать новую сессию с сохранением владения, ворота выдачи, счётчики,
потолок попыток, сторож, дедлайны); выбор реакции и её пороги — в плагине. Без `default-policy` действует колонка
«без решения плагина» из §5.4: сбой попытки завершает прогон как `failed` с классом `infrastructure`.

Плагины в комплекте компилируются в тот же бинарник, но считаются по своей строке бюджета и входят в общий лимит
выпуска (§14).

**Постмортем 0001** (`docs/postmortems/0001-loop-stalled-after-transient-auth-error.md`) — первый инцидент самой разработки: цикл встал на часы после временной ошибки 403 и сам не поднялся. Требования оттуда — ограниченное и перевзводимое ожидание, живость по наблюдению, проба «причина ушла сама», позднее повышение до человека — входят в сторожа ядра (§5, инвариант 15) и в `default-policy`. **[Р]**

### 11.6 Доверие

Плагин исполняет произвольные команды с правами пользователя. Установка и включение — явные действия; внешний
плагин закрепляется ревизией в lock-файле; автообновления нет. **[Д]**

## 13. Поставка

- Один бинарник `aae`: демон, CLI и встроенные плагины. Цели: linux x86_64 и arm64 (статическая

- `aae doctor`: харнессы (путь, версия, логин), br (версия), права на каталоги, здоровье состояния.

<!-- MEASURE id=design-a-v0-loc date=2026-11-10 ver=gascity-f1f75f53c env=не-применимо src=reports/31 note="экспертная оценка дизайна A, не замер; три харнесса и движок графа, которых в aae v0 нет" -->

- Лимит — потолок, а не цель: меньше кода — лучше (§1).
- Считаются строки кода без пустых и без комментариев одним инструментом, зафиксированным в репозитории; тесты и
  сгенерированный код исключаются по путям. **[Д]**
- Файл — не более 400 строк. **[Д]**
- Превышение лимита выпуска блокирует выпуск; превышение жёсткого стопа останавливает добавление функций до
  ревизии с удалением.
- Если бюджет всё же не сходится, первыми уходят **[Д]**: мост stdio→HTTP; загрузка паков из git (остаются
  локальные каталоги); продолжение сессии другого прогона; файл рабочего пространства `bv`. Не вырезается:
  инварианты §5.5, финишер, ворота выдачи, восстановление, «объясни конфиг», контрактные тесты.

Сроков и календарных бюджетов в постановке нет. **[Р]**

**Правила:**

- **Без заглушек и без кода «на вырост». [Р]** Не пишутся: пустые реализации, `todo`-ветки, неиспользуемые
  параметры, поля, флаги и точки расширения под будущие функции, обобщения под единственный случай. Всё, что
  постановка называет отложенным (§1.1), в коде отсутствует полностью.
- Нет механизма без применения. У каждой функции есть запись, какой критерий §15 или какая реальная работа её
  использует; функция без такой записи к моменту выпуска удаляется.
- Тесты — против настоящих бинарников харнессов. Поддельный драйвер допустим только сценарный (задержка, конец
  хода без исхода, ошибка провайдера, код 75, зависание, обрыв канала посреди хода, запрос разрешения, событие
  вне хода) или как запись настоящих транскриптов **[И 21 §4.4]**.
- Детерминированная проверка инвариантов §5.5: управляемые часы, seed, проверка после каждого шага.
- Инъекция сбоев: `kill -9` демона на каждой границе транзакции и между записью в состояние и вызовом трекера;
  восстановление обязано сойтись.
- Проверка идемпотентности: любая операция, применённая дважды, и любое событие, доставленное дважды или не
  доставленное, дают то же конечное состояние.
- Перед каждым новым механизмом — проверка, нет ли его уже у вендора харнесса.
- Версии харнессов и `br` закреплены в mise; обновление — через контрактные тесты (§7.8).
- Ревью до основной ветки.
- **Отчёт о готовности. [Р]** Исполнитель ведёт в репозитории один файл со шкалой готовности каждого компонента
  и обновляет его в конце каждого рабочего сеанса. Оценка — целое от 0 до 10 по опорным точкам:

  | Балл | Что это значит |
  |---|---|
  | 0 | ничего нет |
  | 2 | контракт компонента записан (типы, события, ошибки), кода нет |
  | 4 | код есть, основной путь работает вручную |
  | 6 | тесты без модели зелёные, включая пути сбоев |
  | 8 | относящиеся к компоненту критерии §15 зелёные на хосте владельца |
  | 10 | компонент отработал реальные прогоны владельца без вмешательства (критерий 20) |

  Промежуточные баллы допустимы; рядом с каждой оценкой — одна строка «чего не хватает до следующей точки».
  Оценка — это замер: у неё дата, короткий sha и маркер `MEASURE`. Компоненты: цикл событий и состояние;
  прогоны и финишер; триггеры и расписание; ворота выдачи; восстановление; сборка конфига; реестр экземпляров и
  сервисов; адаптер claude; адаптер codex; адаптер br; исполнение хуков плагинов; `default-policy`; `worktree`;
  общий MCP; HTTP API; CLI; MCP-фронтенд; acceptance spec; поставка и `doctor`.
- **Правило замеров. [Р]** Любой замер (время, память, размер, количество, доля), где бы он ни появился — в
  документации, отчёте acceptance spec, комментарии к порогу в коде или описании PR, — несёт:
  - видимую дату замера;
  - видимую версию измеренного: версию бинарника или короткий sha;
  - невидимый комментарий рядом для того, кто будет править: идентификатор замера, источник, условия, что
    перемерить.

  Формат комментария один на весь проект, чтобы его находил один `grep`:

  ```
  <!-- MEASURE id=<слаг> date=<ГГГГ-ММ-ДД> ver=<версия или sha> env=<ОС и стенд> src=<откуда> note="<условия; что перемерить>" -->
  ```

  В коде тот же маркер пишется в синтаксисе комментария языка. Замер без даты и версии считается дефектом
  документа. CI проверяет, что у каждого маркера заполнены `id`, `date`, `ver` и `env`; замер, у которого маркера
  нет вовсе, CI найти не может — это проверяет ревью.

**Остановиться и пересмотреть, если:**

- превышен жёсткий стоп по строкам;
- обновления харнессов раз за разом ломают контрактные тесты и съедают больше работы, чем сам продукт;
- вендор вводит отдельную оплату headless-режима, которая делает путь без TUI неприемлемым для владельца;
- штатные средства вендоров покрывают подавляющую часть реально используемых формул.

## 15. Критерии приёмки первого выпуска

Критерии реализуются как исполняемая acceptance spec (§9.2): она и есть приёмка. **[Р]** Колонка «Запуск»:

- **CI** — сценарий без модели; входит в spec и дополнительно идёт в CI на каждый коммит;
- **запрос** — сценарий с настоящей моделью; идёт только при явном запуске spec пользователем;
- **вручную** — сценарием не исполняется; отметку ставит владелец.

Числовые пороги предложены автором и правятся владельцем. **[Д]** Ориентиры исследования мягче: хоп p50 ≤ 3 с и
p90 ≤ 10 с, инфраструктура в простое ≤ 150 МБ (`FINAL-REPORT.md` §5.3). Плагин `default-policy` во всех
сценариях включён, если не сказано иное.

Платформа **[Р]**: приёмка идёт только на хосте владельца — Linux arm64. Остальные три цели только собираются;
их работоспособность не проверяется и принимается на веру в переносимость языка.

## 18. Допущения, которые стоит подтвердить

   непрозрачен для ядра.
3. **Ворота выдачи как единственный механизм «не запускать пока» (§5.7)** и счётчик неудач бида (§10.3).
4. **Финишер (§9.4):** только CLI; токен на попытку; возврат замечания хуком вместо check-петли.
5. **Worktree и политика сбоев — плагины в комплекте (§11.5);** отказ хука-вето блокирует прогон (§11.3).
