Редакция: 2026-11-14. Документ описывает, что должен делать продукт и какие решения приняты. По нему исполнитель
планирует и делает работу, а ревьюер проверяет продукт. Истории изменений здесь нет: она в git.

Метки в тексте:

- **[Р]** — решение владельца. Исполнитель его не пересматривает.
- **[Д]** — допущение автора постановки или исполнителя. Действует, пока владелец не поправил; исполнитель может
  предложить замену, но не меняет молча.
- **[И NN]** — факт из исследования, отчёт `NN`. Отчёты исследования и итоговый `FINAL-REPORT.md` лежат на диске
  владельца и в репозиторий не входят **[Р]**; всё нужное из них вынесено в шпаргалки (§19).
- **[НП]** — не проверено. Нужен опыт до того, как на это опирается код. Незакрытые собраны в §17.

Постановка говорит «что» и «зачем» и фиксирует решения. Подробности «как именно» — поля, ключи конфига, форматы
событий, алгоритмы — живут в документации проекта (`docs/design/`, `docs/api/`, `docs/guide/`); в постановке на
них стоит указатель «Подробно: …». Требование, которого в документации нет, изложено здесь полностью; указатель
требование не ослабляет. **[Р]** Если документация расходится с постановкой, права постановка, а расхождение
исправляется в документации. **[Д]**

Примеры конфигов в документе — иллюстрации формы, а не контракт синтаксиса.

Каждый замер несёт видимую дату и версию и невидимый комментарий `<!-- MEASURE … -->` рядом (правило — §14).

## 1. Что строим

`aae` — событийный оркестратор агентов-кодеров («программная фабрика»): демон уровня машины, который по запросу
запускает **формулы** на **агентах** в **ригах** (репозиториях) **проектов** и доводит прогоны до явного исхода,
переживая сбои харнессов, лимиты и собственные рестарты.

Продукт пишется с нуля. Опыт проекта-предшественника используется как знание (инварианты, классы сбоев, ошибки);
код не наследуется, сам предшественник в коде и документации по имени не называется. **[Р]**

Четыре свойства определяют форму продукта **[Р]**:

1. **Очень лёгкое ядро.** В ядре только то, без чего прогон нельзя корректно запустить, наблюдать и завершить.
   Всё остальное — адаптеры (харнессы, трекер, фронтенды) и плагины.
2. **События, а не тики.** Ни одна единица работы не ждёт таймера опроса: задержка от причины до реакции не
   зависит ни от какого интервала. Запрещён опрос как способ ожидания работы; страховочные таймеры (сторож
   сирот, проверка здоровья экземпляра, resync) допустимы.
3. **Нативные протоколы харнессов без tmux.** Экран терминала не является каналом управления ни в каком виде.
4. **Меньше кода — лучше.** Пишется только то, что нужно описанному здесь результату. Никаких заглушек, никаких
   точек расширения и кода «на вырост», никаких полей и флагов под будущие функции. Отложенное названо отложенным
   (§1.1) и в коде не присутствует вовсе.

Поставка: один бинарник `aae` под linux и macOS, x86_64 и arm64. Репозиторий публичный, лицензия MIT. **[Р]**

| Алертинг: уведомление человека о сбое | **[Р]**: только журнал событий и логи |

| Проверка и приёмка на macOS и на x86_64 | **[Р]**: приёмка идёт только на хосте владельца (Linux arm64); остальные цели собираются, их работоспособность принимается на веру в переносимость языка |
| Встроенная проверка «работа действительно сделана» | **[Р]**: это делает внешний цикл владельца (§9.4) |
| Сроки и календарные бюджеты | **[Р]**: работу ведут агенты, сроков в постановке нет |
| Ротация аккаунтов и failover между подписками | зона политического риска **[И 34]**; не ядро |
| Трансляция хуков между диалектами харнессов | у claude и codex формат хуков почти общий **[И 18]**; транслятор — когда появится третий диалект |
| Обобщённый ACP-адаптер, один адаптер на несколько харнессов | **[Р]**: когда появится третий харнесс (§7) |
| Умолчание харнесса для провайдера (`[provider.<p>] harness`) | **[Р]**: пока у каждого провайдера один адаптер (§6.2) |
| Цепочка нескольких формул над одним бидом | **[Р]**: не критична; `pass` закрывает бид (§10.3) |
| Демо «aae разрабатывает себя» | роадмап: сетап агентов этого репозитория как пак aae |
| Миграция данных и паков из проекта-предшественника | отдельная задача |

| **проект** | каталог с `aae.toml`: набор ригов, паков, плагинов и одна БД трекера |
| **риг** | репозиторий на диске плюс его переменные (`test_cmd`, `lint_cmd` и т. п.) |
| **харнесс** | вид agent-CLI: `claude`, `codex`, позже `opencode`. Ему соответствует один адаптер |
| **провайдер** | поставщик модели: `anthropic`, `openai`. Адаптер объявляет провайдеров, с которыми работает его харнесс |
| **экземпляр харнесса** | запущенный процесс харнесса (app-server или процесс сессии), который обслуживает одну или несколько сессий |
| **агент** | общая роль (`coder`, `planner`): промпт роли, skills и умолчания настроек запуска. О конкретной задаче агент не знает. Ролей в коде ядра нет |
| **настройки запуска** | четыре скаляра: харнесс, провайдер, модель, effort (§6.2) |
| **сокращение модели** | имя семейства (`opus`, `luna`), которое адаптер раскрывает в последнюю версию модели этого семейства |
| **вариант агента** | агент пака под другим именем и с другими настройками, объявленный в конфиге пользователя (`claude-coder`, `codex-coder`) |
| **ссылка на сессию** | пара «харнесс + id сессии у харнесса». Единственное, что ядро знает о разговоре |
| **формула** | описание процесса — «как»: имя, описание, входы, один шаг. «Что» — задача — приходит входом от пользователя |
| **шаг** | `prompt` (ход агента) или `exec` (команда без LLM) |
| **прогон** (run) | исполнение формулы с конкретными входами; имеет попытки и исход |
| **дочерний прогон** | прогон, запущенный из сессии агента другого прогона; наследует его correlation |
| **попытка** (attempt) | один запуск или возобновление сессии в рамках прогона |
| **финишер** | вызов, которым агент сообщает исход прогона |
| **триггер** | правило «событие или расписание → запустить формулу» |
| **correlation** | идентификатор цепочки прогонов, порождённых друг другом |
| **pack** | содержимое, пригодное для любого проекта: агенты, формулы, триггеры |
| **plugin** | расширение: то, что подключается к агентам (skills, hooks, MCP, скрипты, env), хуки на события оркестратора, сервисы |
| **сервис** | долгоживущий процесс под супервизией оркестратора (например, общий MCP-сервер) |
| **ворота выдачи** | запись «по этому ключу прогоны не запускать до времени или до ручного снятия» (§5.7) |
| **трекер** | хранилище задач за интерфейсом-адаптером; первая реализация — br |
| **бид** | задача в трекере. Только настоящая работа, никаких служебных записей |
| **событие** | запись о случившемся; повод перечитать состояние, а не истина |

## 4. Архитектура

```
                 HTTP API (полная)   CLI (полная)   MCP (малая)
                        └───────────────┼───────────────┘
                                 фронтенд-адаптеры
                                        │  команды / запросы / поток событий
┌───────────────────────────────────────▼──────────────────────────────────────┐
│ ЯДРО: один писатель состояния                                                 │
│  входная очередь → обработка в транзакции SQLite → события (outbox)           │
│  прогоны и попытки · триггеры и таймеры · сборка конфига · реестр экземпляров │
│  исполнение exec-хуков плагинов · владение бидом · восстановление и resync    │
└───────┬───────────────────────┬──────────────────────┬───────────────────────┘
        │ интерфейс драйвера    │ интерфейс трекера    │ события → журнал JSONL
  адаптеры харнессов        адаптер br             плагины (exec-хуки, сервисы)
  claude │ codex │ (opencode)
```

Границы, которые проверяются сборкой, а не договорённостью:

- Ядро не зависит ни от одного адаптера, фронтенда или плагина. В `aae-core` нет имён харнессов, имён ролей,
  вызовов `br` и знаний о них (`codex`, `max_sessions`, `BEADS_DIR`, `.beads`): они приходят через способности
  драйвера и интерфейс трекера. CI проверяет это поиском по исходникам ядра. **[Р]**
- Харнесс для ядра — абстракция. Корень сборки держит одну таблицу адаптеров; кроме неё, харнесс в корне не
  назван нигде. **[Р]**
- Фронтенды не содержат доменной логики: каждый только переводит свой протокол в команды и запросы ядра.
- Адаптер харнесса не принимает решений о повторах, парковке и исходе: он переводит протокол харнесса в
  нормализованные события и исполняет операции.
- Решения-политики (повторить, припарковать, отклонить) лежат в плагинах и конфиге. Суждения («сделано ли хорошо») —
  в промптах и проверках плагинов. В ядре — только механизмы.

Адаптеры в первом выпуске — модули того же бинарника за общим интерфейсом. Собственный межпроцессный протокол для
адаптеров не изобретается: внешний путь подключения харнессов в будущем — обобщённый драйвер ACP v2. **[Д]**

Подробно: `docs/design/adapters.md`.

## 5. Ядро

### 5.1 Событийная модель

- Всё, что происходит, входит в ядро сообщением единственному писателю: команда фронтенда, событие адаптера
  харнесса, событие трекера, срабатывание таймера, ответ exec-хука.
- Ядро обрабатывает сообщение, меняет состояние в одной транзакции SQLite и в той же транзакции записывает
  порождённые события (outbox). Эффекты (вызовы адаптеров, запуск хуков) выполняются после фиксации.
- Эффекты идут через очередь по ключу (прогон, экземпляр харнесса): сериализация на ключ, дедупликация, backoff
  500 мс → 5 мин **[И 21]**.
- События из outbox получают: журнал JSONL, подписчики API (SSE), сопоставление триггеров, exec-хуки плагинов.
- Таймеры — это дедлайны с точным временем пробуждения, а не опрос.

**Критерий «не тики»:** задержка от события до реакции ядра не содержит ожидания интервала. Проверяется приёмкой
(§15, хоп). Страховочные таймеры — сторож сирот, проверка здоровья экземпляра, resync — этому не противоречат:
они ничего не продвигают в штатной работе. **[Р]**

**Resync — не тик.** Полная сверка состояния с реальностью (таблица процессов, экземпляры харнессов, трекер)
обязательна: при старте демона и раз в несколько минут. Она ловит потерянные события. Расхождение — событие
`resync.diverged` и ноль автоматических эффектов, если ситуация неоднозначна **[И 21]** (инвариант 20).

Подробно: `docs/design/event-model.md`.

### 5.2 Состояние

- SQLite в режиме WAL, статически слинкованная. Единственный писатель — демон. CLI, плагины и агенты меняют
  состояние только через API.
- В состоянии лежит только рантайм: прогоны, попытки, ссылки на сессии, экземпляры харнессов, владение бидами с
  поколением, состояние триггеров и таймеров, удержания оператора, ключи идемпотентности, outbox, ворота выдачи
  (§5.7), счётчики неудач по бидам.
- Определения (проекты, риги, агенты, формулы, триггеры, плагины) живут в файлах конфигурации. В состояние
  попадает только снимок эффективного конфига прогона — для воспроизводимости и ответа «с чем это запускалось».
- Файлов-статусов, PID-файлов и lock-файлов нет. Живость процесса проверяется по таблице процессов: pid плюс время
  старта. Один демон на каталог состояния: второй на тот же каталог не стартует (блокировка самого каталога).

Подробно: `docs/design/event-model.md`, раздел «State».

### 5.3 Журнал событий

- JSONL, ротация по размеру: 10 МБ на файл, 5 файлов. **[Р]**
- Журнал — канал наблюдения, а не источник истины: старая история вытесняется. Источник истины — состояние.
- Журнал один на оркестратор, для всех проектов. **[Д]** У события монотонный `seq` — один счётчик на оркестратор.
- Потребитель продолжает чтение с `seq`. Если `seq` уже вытеснен, он получает явную ошибку «разрыв» и
  восстанавливается запросом состояния через API.
- В журнал идут события уровня оркестрации (§5.4). Содержимое разговора (сообщения модели, вызовы инструментов)
  ядро не сохраняет и через своё состояние не пропускает: живой просмотр — прямая ретрансляция потока адаптера
  фронтендом, история — в транскрипте харнесса по ссылке на сессию. **[Д]**

Подробно: `docs/design/event-model.md`, раздел «Journal»; конверт события — `docs/design/contracts.md`, 1.1.

### 5.4 События

**Наблюдаемые** — плагины и клиенты их читают, но не влияют: `daemon.*`, `config.reloaded`, `instance.*`,
`service.*`, `run.*` (`queued`, `started`, `state_changed`, `parked`, `resumed`, `retrying`, `passed`, `failed`,
`cancelled`), `trigger.*`, `gate.closed`, `gate.opened`, `bead.*`, `tracker.sync_failed`, `plugin.hook_failed`,
`resync.diverged`.

То, что сообщает драйвер, ядро читает и доводит до политики и наблюдателя, а не отбрасывает **[Р]**:

- харнесс сам повторяет запрос — событие `run.retrying`; объявленная пауза не считается тишиной для сторожа;
- экземпляр работает, но харнесс сообщил ухудшение — `instance.degraded`; при восстановлении — `instance.ready`;
- расход токенов суммируется по попыткам, виден в состоянии прогона и в его терминальном событии;
- последний известный лимит аккаунта (доля и время сброса) приходит политике в решающем событии;
- причина конца хода приходит политике в событии `run.turn_ended_without_outcome`.

**Решающие** — exec-хук плагина может изменить ход (§11.3). Последняя колонка — что делает ядро, когда ни один
плагин не ответил, в том числе когда `default-policy` выключен:

| Событие | Что может хук | Без решения плагина |
|---|---|---|
| `run.preparing` | изменить рабочий каталог и env, дополнить промпт, отказать в запуске | запуск как есть |
| `run.requires_action` | ответить на запрос разрешения или вопрос | ждать ответа человека до дедлайна, затем отказ («deny») |
| `run.attempt_failed` | выбрать реакцию на типизированный сбой: resume, новая сессия, закрыть ворота выдачи до времени, завершить | прогон завершается как `failed` с классом `infrastructure` |
| `run.turn_ended_without_outcome` | вернуть агенту замечание и продолжить либо завершить | `failed` с причиной `hollow_done` |
| `run.finishing` | наложить вето на `pass` с причиной либо вернуть агенту замечание | исход принимается как заявлен |

Каждый отказ ядра действовать пишет событие с причиной. Молчаливых ожиданий нет: самые длинные простои
проекта-предшественника были молчаливыми **[И 21]**.

Схема события и её версия, нагрузки всех событий, схема решения хука для каждого решающего события — контракт:
они записаны в `docs/design/contracts.md` (разделы 1 и 3) и не меняются без смены версии схемы **[И 32]**.

### 5.5 Инварианты ядра

Это знание оплачено историей исправлений проекта-предшественника **[И 21]**. Все пункты, кроме 19-го, — механизмы
ядра, и ни один не вырезается ради бюджета. Пороги (сколько раз, как долго) — параметры конфига с умолчаниями;
выбор реакции — политика (§11.5). Номера стабильны: код и документы ссылаются на «invariant N».

| № | Инвариант |
|---|---|
| 1 | Один писатель состояния — демон |
| 2 | Владение с поколением: у прогона и у бида не более одного живого владельца; каждый эффект попытки (финишер, закрытие, возврат) проверяет поколение, устаревший отбрасывается |
| 3 | Claim бида выдаёт демон в той же транзакции, что и решение о запуске. Агент claim не берёт |
| 4 | Возврат бида только условный: сравнение владельца и поколения |
| 5 | Смерть сессии не теряет работу: выход или EOF в одной транзакции переводит прогон в «попытка не удалась». Владение бидом остаётся за прогоном и снимается только в его терминальном состоянии |
| 6 | Подтверждённая смерть до замены: новый процесс на тот же прогон или ту же сессию стартует только после того, как от заменяемого экземпляра не осталось ничего, включая его потомков |
| 7 | После остановки сессии не остаётся ни одного её потомка. Одной группы процессов для этого мало **[И 44]**: демон — subreaper и находит потомков по маркеру экземпляра в окружении |
| 8 | Один писатель на сессию харнесса — демон. Пока прогон жив, никто другой в его сессию не пишет |
| 9 | Намерение до эффекта: запуск, остановка и kill сначала записываются, потом исполняются; восстановление доводит или откатывает |
| 10 | Идемпотентность по ключу (прогон, попытка): создание, выдача, запись исхода и событие повторяемы без дублей |
| 11 | Незавершённый ход после рестарта демона не ждёт молча: он прерывается, за ним следует новая попытка (§5.6) |
| 12 | Успех — только по явному исходу. Конец хода без финишера — не успех |
| 13 | Прерывание инфраструктурой (отмена, рестарт, лимит) — не исход формулы. Если попытки исчерпаны, прогон завершается `failed` с классом `infrastructure`, отличимым от провала по слову агента или по вето |
| 14 | У каждого переходного состояния есть дедлайн и терминальный выход |
| 15 | Сторож выданного прогона: дедлайн до первого события и предел тишины, зависящий от состояния. Ожидание человека — не тишина; у идущего инструмента и у фоновых субагентов предел свой и больше; объявленный харнессом повтор прибавляет свою паузу к пределу. Ядро порождает сбой `stall`, реакцию выбирает политика |
| 16 | Счётчики попыток и рестартов хранятся в состоянии и ограничены. У ядра есть абсолютный потолок попыток и потолок замечаний на попытку, которые политика не может поднять. Ожидание на воротах своего аккаунта после сбоя `auth_required`, `billing` или `quota_exhausted` потолок попыток не расходует; любая другая парковка и парковка на незакрытых воротах — расходует **[Р]** |
| 17 | Resume с проверкой: только если адаптер подтвердил, что транскрипт существует. Механизм «новая сессия с сохранением владения» — в ядре; после скольких отказов resume к нему перейти, решает политика |
| 18 | Удержание оператора сильнее автоматики: пауза и отмена человеком — запись в состоянии, которую читает каждое автоматическое решение |
| 19 | У worktree один владелец; удаляется только когда его коммиты достижимы из refs (реализует плагин `worktree`) |
| 20 | Событие — повод перечитать состояние; resync обязателен; неоднозначность ⇒ ноль эффектов и громкий сигнал |

Проверка — детерминированный хаос-стенд (§14). Подробно: `docs/design/invariants.md` (где живёт каждый инвариант,
значения потолков, известные пределы), опыт по потомкам — `docs/design/experiments.md`.

### 5.6 Восстановление

Старт демона:

1. Открыть состояние, дочитать outbox.
2. Каждый записанный экземпляр харнесса остановить: сверить pid и время старта, убить группу процессов и всех
   потомков с его маркером, дождаться завершения. Переподключение к пережившим рестарт экземплярам в первом
   выпуске не делается. **[Д]**
3. Прогоны с идущей попыткой (`starting`, `running` в ходе, `requires_action`) перевести в `interrupted` и
   породить `run.attempt_failed` с видом `daemon_crash`: дальше решает политика.
4. Перевзвести таймеры и расписания (пропущенное срабатывание — не более одного раза), выполнить resync.

Рестарт и решения хуков **[Р]**:

- Прогон, ждавший решения по решающему событию (`preparing`, `finishing`, `interrupted`, `running` после хода без
  исхода), после рестарта ждёт того же решения. Хуки запускаются заново (осиротевший хук убит по маркеру);
  заявленный исход и результат exec-команды сохраняются; ход и команда не повторяются.
- Решение, которому нужна сессия (замечание агенту, продолжение), завершает попытку сбоем `daemon_crash`: сессии
  больше нет. Текст замечания получает возобновлённая сессия.
- Дедлайны, сторожащие ответ эффекта (решение хука, claim бида), отсчитываются заново от старта демона. Дедлайны
  реального времени и расписания остаются как были.

Плановый рестарт — с дренажом: новые прогоны и новые ходы не начинаются; идущие ходы дорабатывают до границы
хода или до таймаута; дренаж ждёт и решений политики.

Доставка промпта — «не менее одного раза с идемпотентным эффектом»: запись `intent → sent → acked → settled` на
попытку и ключ промпта в транскрипте харнесса **[И 34 §7]**. Протоколы харнессов идемпотентности не дают. После
смерти демона адаптер отвечает по транскрипту, доставлен ли промпт; отвечен ли он, не различается: resume хода в
полёте нет, доставленный промпт всегда сверяется.

macOS в первом выпуске не проверяется (§1.1). Известные отличия: нет subreaper, `/proc` и cgroup;
`PR_SET_PDEATHSIG`, которым codex убивает дочерние команды, есть только в Linux **[И 34]**; слежение за файлами и
хранение учётных данных устроены иначе. Кода под эти отличия заранее не пишется.

Подробно: `docs/design/invariants.md`, раздел «Recovery»; `docs/design/contracts.md`, 3.4 и 6.4.

### 5.7 Ворота выдачи

Единственный механизм ядра для «не запускать пока»: запись «ключ закрыт до времени T или до ручного снятия».
Прогон, чей ключ закрыт, ждёт с видимой причиной: не стартовавший — в `queued`, стартовавший — в `parked`.

- Ключи: аккаунт харнесса, модель, агент, бид, риг, проект, весь оркестратор.
- Ключ модели — `model:<provider>/<раскрытое имя>`. Прогон знает его из своего эффективного конфига до старта, а
  не из собственного первого сбоя. **[Р]**
- Закрывают ворота: политика в ответ на сбой (лимит аккаунта, карантин агента после серии крашей), оператор
  (пауза) и само ядро (бид после серии неудачных прогонов, §10.3).
- Идентификатор аккаунта сообщает адаптер. **[Д]**
- Ворота — запись в состоянии: переживают рестарт, видны в API и CLI, каждое открытие и закрытие — событие.
  Ворота, закрытые оператором, автоматика не снимает (инвариант 18).

Так реализуются «светофор на аккаунт» **[И 34]** и удержание оператора без отдельных подсистем.

Подробно: `docs/design/contracts.md`, раздел 7.

## 6. Иерархия и конфиг

### 6.1 Уровни

```
оркестратор   ~/.config/aae/config.toml     харнессы и умолчания их моделей, общие MCP/hooks/skills/env, плагины
└─ проект     <project>/aae.toml            риги, паки, плагины проекта, варианты агентов, оверрайды
   └─ риг     секция в aae.toml             путь к репозиторию, переменные, отображение агентов, оверрайды
```

Агент не уровень иерархии, а потребитель настроек. Умолчание модели для каждого харнесса задаётся на уровне
оркестратора. **[Р]** Пользователь в своём конфиге (оркестратор, проект, риг) говорит, на чём работает агент, и
даёт задачу; пак об этом не знает. **[Р]**

### 6.2 Что настраивается

Нейтральные к харнессу категории: настройки запуска, env, MCP-серверы, хуки харнесса, skills, системный промпт,
режим разрешений, плагины, флаг наследования хоста. Плюс блок «родных» настроек конкретного харнесса
(`native.<harness>`), который ядро не интерпретирует и передаёт адаптеру как есть.

**Настройки запуска** — четыре обычных послойных скаляра **[Р]**:

| Ключ | Смысл |
|---|---|
| `harness` | agent-CLI: `claude`, `codex` |
| `provider` | поставщик модели: `anthropic`, `openai` |
| `model` | полное имя модели либо сокращение |
| `effort` | уровень усилия модели |

Харнесс и провайдер **[Р]**:

- Адаптер объявляет провайдеров, с которыми работает его харнесс: claude — `anthropic`, codex — `openai`.
- Задан только `provider` — харнессом становится единственный адаптер этого провайдера.
- Задан только `harness` — провайдером становится его родной.
- Не задано ни то, ни другое, либо провайдер не поддержан заданным харнессом — ошибка конфига.
- Таблицы «умолчание харнесса для провайдера» нет, пока у каждого провайдера один адаптер.
- `harness` меняется теми же слоями, что и остальные настройки запуска: оверрайдом, вариантом, паком, формулой.

Модель **[Р]**:

- Полное имя модели передаётся харнессу как есть.
- Сокращение раскрывается в последнюю версию семейства. Таблица сокращений — знание адаптера (§7.2). Сокращения
  первого выпуска: anthropic — `fable`, `opus`, `sonnet`, `haiku`; openai — `astra` → `gpt-6-astra`,
  `luna` → `gpt-6-luna`, `terra` → `gpt-6-1-terra`, `sol` → `gpt-6-1-sol`.
- Если CLI харнесса сам раскрывает сокращение в последнюю версию, оно передаётся как есть.
- Если харнесс не принимает имя из таблицы, это находка для владельца; молча подменять имя нельзя.

### 6.3 Порядок слоёв

От слабого к сильному **[Р]**:

1. настройки хоста для итогового харнесса (`~/.claude/`, `~/.codex/` и т. п.) — если наследование включено;
2. умолчание модели итогового харнесса (`[harness.<h>] model` оркестратора);
3. общие настройки оркестратора;
4. общие настройки проекта;
5. общие настройки рига;
6. вклад плагинов, подключённых к агенту, в порядке подключения;
7. определение агента в паке — умолчания;
8. пак: `[settings]` в `pack.toml` того пака, которому принадлежит формула прогона;
9. формула: ключи настроек запуска в её `prompt`-шаге;
10. вариант агента, объявленный пользователем (§8.1);
11. оверрайды пользователя для этого агента: оркестратор → проект → риг.

Слои 8 и 9 несут только четыре настройки запуска. Явная настройка пользователя (слои 10 и 11) сильнее пака и
формулы: так поправляют агента из внешнего пака, не форкая пак.

Правила слияния **[Д]**: скаляр — побеждает старший слой; словари (env, MCP по имени, `native`) — по ключу,
запись заменяется целиком; списки с именованными элементами (хуки, skills, плагины) — объединение с возможностью
выключить элемент по имени на старшем слое.

Обязательное свойство: команда «объясни конфиг» (`aae config explain`, она же в API) показывает итог для тройки
(проект, риг, агент) и для каждого значения — слой, из которого оно пришло, включая выведенный харнесс и
раскрытое имя модели.

Слой хоста — исключение. Настройки хоста сливает сам харнесс, ядро их не читает и не разбирает. В «объясни
конфиг» он показан одной строкой, и выключить отдельный элемент хоста по имени нельзя — только весь слой.

Конфиг харнесса внутри самого рига (`CLAUDE.md`, `.claude/`, `.mcp.json`, `AGENTS.md`) — свойство репозитория, а
не хоста: он действует и при выключенном наследовании хоста. **[Д]**

Подробно: `docs/design/config.md`, раздел «Effective config and "explain config"»; опыт по доставке —
`docs/design/experiments.md`, раздел «Config and credential delivery».

### 6.4 Наследование настроек хоста

Включено по умолчанию, выключается на любом уровне (`inherit_host`). **[Р]**

Цена включённого наследования, о которой должен знать пользователь **[И 42, 18]**:

- личные MCP-серверы оператора замедляют старт сессии и стартуют в каждой сессии. Общий MCP (§11.4) на них не
  распространяется: `aae` делит только серверы из своего конфига, а `doctor` предупреждает о stdio-MCP в
  настройках хоста;
- личные хуки и плагины оператора исполняются в сессиях агентов;
- codex сам переписывает свой конфиг хоста — адаптер не добавляет к этому своих записей в файлы хоста.

Требования к адаптерам:

- При выключенном наследовании учётные данные всё равно берутся с хоста: адаптер доставляет их в сессию.
- codex при включённом наследовании и наличии skills получает собственный `CODEX_HOME`, который наследует хост
  (ссылки на его логин и конфиг) и добавляет skills. `config_error` на этом пути запрещён. **[Р]**

Подробно: `docs/design/config.md`, раздел «Host inheritance» (замеры цены, способ доставки по харнессам).
Открытые **[НП]** — §17.

### 6.5 Сборка и доставка

- Эффективный конфиг собирает ядро при подготовке прогона, непосредственно перед стартом сессии. Адаптер
  «материализует» его: переводит в флаги запуска, параметры сессии или сгенерированный каталог конфигурации.
- Сгенерированные файлы лежат в каталоге состояния оркестратора, а не в риге и не в домашних каталогах харнессов.
- Конфиг перечитывается по явной команде, а не слежением за файлами. **[Д]** Невалидный конфиг не применяется:
  остаётся прежний, команда возвращает ошибку. Изменение затрагивает только новые сессии; идущие прогоны работают
  со своим снимком. Правка одного MCP не перезапускает ничего, кроме экземпляров, чей отпечаток изменился.
- Окружение сессии явное: оно собирается из слоёв, а не наследуется от окружения демона целиком.

Внешними зависимостями управляет mise. **[Р]** Демон разрешает бинарник харнесса в порядке: явный путь в
конфиге → `mise which` → `PATH`. **[Д]** Демон под systemd или launchd получает минимальный `PATH` без
shim-каталога mise, поэтому на один `PATH` полагаться нельзя. `aae doctor` проверяет каждый бинарник, его версию
и состояние логина.

Подробно: `docs/design/config.md`, раздел «Loading»; `docs/guide/install.md`.

## 7. Харнессы

Харнесс для ядра — абстракция: всё знание о конкретном харнессе (протокол, вид его сбоев, опции, провайдеры,
сокращения моделей, проверки `doctor`) живёт в его адаптере. Новый харнесс — новый крейт и строка в таблице
адаптеров корня сборки. **[Р]** Адаптеров два; обобщённый ACP-адаптер и снятие известных пределов интерфейса
драйвера — когда появится третий харнесс.

Подробно: `docs/design/adapters.md`.

### 7.1 Интерфейс драйвера

Семантика повторяет ACP v2: состояние `running | idle | requires_action` и типизированная ошибка хода. **[Р]**

Операции:

- по экземпляру: разделить эффективный конфиг на часть «на процесс» и часть «на сессию» и вычислить отпечаток;
  запустить; проверить здоровье; остановить;
- по сессии: начать, возобновить по ссылке, отправить промпт с ключом идемпотентности, отменить ход, ответить на
  запрос разрешения, закрыть;
- по транскрипту: проверить, что транскрипт сессии существует и доставлен ли в него промпт с данным ключом;
  отвести живой поток сессии для просмотра.

Адаптер шлёт нормализованные события с порядковым номером: приём промпта, начало и конец хода с причиной,
состояние с признаком фоновой работы, запрос разрешения, расход токенов с лимитом аккаунта, повтор самим
харнессом, сбой, выход процесса. Ядро принимает события экземпляра по порядку номеров: повтор отбрасывает, о
разрыве сообщает событием `resync.diverged`. Всё сообщённое доходит до политики и наблюдателя (§5.4). **[Р]**

Виды сбоя **[И 34]**: `quota_exhausted`, `rate_limited`, `overloaded`, `auth_required`, `billing`,
`context_overflow`, `config_error`, `harness_crash`, `adapter_crash`, `daemon_crash`, `stall`, `runaway_turn`,
`tool_failure`, `transcript_divergence`, `workspace_failure`, `hollow_done`, `unknown{text}`. Из них `daemon_crash`,
`stall`, `runaway_turn`, `workspace_failure` и `hollow_done` порождает ядро, остальные — адаптер (`adapter_crash` —
при панике своей задачи-читателя). Ожидание человека и фоновая активность вне хода — состояния, а не сбои.

Ссылка на сессию для ядра непрозрачна: адаптер кладёт в неё всё, что нужно для resume. Одного id мало: у codex
транскрипт привязан к экземпляру **[И 34]**.

Адаптер объявляет способности, от которых зависит поведение ядра и политики.

В интерфейсе нет: steer посреди хода, смены модели внутри живой сессии, подключения человека. **[Д]**

Подробно: `docs/design/contracts.md`, раздел 4 (4.1–4.5).

### 7.2 Обязанности любого адаптера

- Закрыть ловушки «успешного провала». Известная для claude **[И 34]**: успех с признаком ошибки. Выход процесса
  с кодом 0 без итога хода — сбой `harness_crash`.
- Границу «ход закончен» брать из авторитетного сигнала харнесса, а не из факта ответа на запрос.
- Сообщать, повторил ли харнесс запрос сам: поверх такого повтора политика не повторяет. claude повторяет сам;
  codex повторяет 429 только при заголовке `Retry-After`, без него повтор — за политикой **[И 34, 46]**.
- Запускать каждую сессию или экземпляр в своей группе процессов.
- Объявлять проверенный диапазон версий харнесса; вне его демон и `aae doctor` предупреждают.
- Объявлять провайдеров харнесса и таблицу сокращений моделей (§6.2). **[Р]**
- Доставлять окружение попытки (идентификатор прогона, токен попытки, actor трекера, сокет демона) инструментам
  сессии и её хукам харнесса.

Подробно: `docs/design/adapters.md`, раздел «What the core expects of a driver»; `docs/design/contracts.md`, 4.6.

### 7.3 Ленивый реестр экземпляров

- Ключ экземпляра — отпечаток (харнесс + «процессная» часть эффективного конфига). **[Р]**
- Экземпляр стартует при первой потребности, переиспользуется всеми сессиями с тем же отпечатком и
  останавливается после простоя без сессий.
- Плагин, меняющий «процессную» часть конфига харнесса, автоматически даёт другой отпечаток и другой экземпляр.
  Плагин, работающий только на стороне оркестратора, экземпляров не плодит. **[Р]**
- У экземпляра, который держит много сессий, есть предел числа сессий: падение общего процесса роняет все его
  сессии сразу **[И 21]**. Сверх предела поднимается второй экземпляр с тем же отпечатком. **[Д]**
- Тот же реестр обслуживает сервисы (§11.4): ленивый старт, счётчик потребителей, остановка по простою, проверка
  здоровья, быстрый перезапуск.

Что считается «процессным», решает адаптер. claude — процесс на сессию: «общего сервера» и экономии памяти нет
**[И 14]**. codex — один app-server на отпечаток и много тредов: на процесс приходятся его домашний каталог
(логин, skills), окружение и провайдер; на тред — рабочий каталог, модель, effort, инструкции, MCP, хуки.
opencode — выясняет спайк (§7.6).

Подробно: `docs/design/contracts.md`, раздел 8 и 4.6; память codex — `docs/design/experiments.md`, раздел «codex
app-server».

### 7.4 claude

- Транспорт: `claude -p` с потоковым JSON на вход и выход и заданным id сессии; возобновление — по id.
- Конфиг на сессию доставляется флагами и файлами в каталоге состояния; полный набор, включая модель, передаётся
  и при каждом возобновлении.
- «Ход закончен» — это состояние idle без фоновых задач. Субагенты claude по умолчанию фоновые **[И 46]**: по
  одному только концу хода главного треда судить нельзя.
- До первого промпта процесс ничего не пишет: ждать его приветствия перед промптом — взаимная блокировка.
- Число итогов хода не равно числу промптов: сессия, разбуженная фоновой задачей, делает ход сама.
- Heartbeat долгого инструмента не приходит изнутри субагентов и во время ожидания разрешения **[И 46]** — это
  учитывает сторож (инвариант 15).
- Время сброса лимита приходит только при логине подпиской; при API-ключе лимит выглядит как обычный
  `rate_limited` без времени сброса **[И 34]**.
- Тёплый пул ради скорости не нужен: холодный старт мал по сравнению с временем модели **[И 42]**.

Подробно: `docs/design/contracts.md`, 4.6 (claude); опыты — `docs/design/experiments.md`, разделы «claude protocol»
и «claude processes and background work».

### 7.5 codex

- Транспорт: собственный `codex app-server` на stdio, один на отпечаток, много тредов; общий демон codex
  пользователя не используется.
- Типы протокола не генерируются из схемы: адаптер читает используемые поля вручную, изменения ловят контрактные
  тесты (§7.8). **[Р]**
- Границу хода брать только из завершения хода: статус треда `idle` приходит раньше.
- Два запроса хода в один тред не ставятся в очередь, а сливаются **[И 36]**: следующий промпт ядро шлёт только
  после конца хода.
- Хуки харнесса исполняются с окружением процесса app-server, а не треда **[И 15]**. Окружение попытки они
  получают через `export` в начале команды хука; то, что токен попытки виден в её argv, принято. **[Р]**
- Песочница: адаптер ставит `sandbox_mode = "danger-full-access"`, если его не задал ни конфиг aae, ни конфиг
  хоста; `sandbox_mode` из конфига хоста сильнее этого умолчания. `doctor` и документация предупреждают. **[Р]**
- app-server помечен вендором `[experimental]`, релизы частые **[И 15]**: версия ведётся линией релизов (§13),
  обновление принимается контрактными тестами.

Подробно: `docs/design/contracts.md`, 4.6 (codex); `docs/design/experiments.md`, раздел «codex app-server»;
`docs/harness-updates.md`.

### 7.7 Человек и прогон

- `aae` показывает прогоны, отдаёт живой поток прогона и принимает ответы на запросы разрешений.
- В состоянии прогона у каждой попытки видна ссылка на сессию. После завершения прогона человек может открыть
  разговор средствами самого харнесса; `aae` в этом не участвует.
- Подключение человека к живой сессии и передача управления — следующий цикл разработки. **[Р]** В первом выпуске
  для этого нет ни операций, ни состояний, ни заглушек.

Подробно: `docs/api/frontends.md`, раздел «Humans and runs».

### 7.8 Контрактные тесты

На каждый адаптер — набор из 15 сценариев **[И 34 §9]** против настоящего бинарника харнесса с поддельным API
провайдера из репозитория (без затрат на LLM): 429 с последующим успехом; бесконечный 429; квота с временем
сброса; квота незнакомой формулировкой; 529/503; 401; `insufficient_quota`; переполнение контекста;
несуществующая модель; `kill -9` посреди команды; EOF на stdin посреди хода; молчание провайдера; запрос
разрешения; фоновая задача после конца хода; второй писатель в ту же сессию.

Набор идёт в CI и при каждом обновлении харнесса: обновление принимается, когда набор на нём проходит. Сверх
набора — один живой прогон на дешёвой модели по явной команде (критерий 2).

Оговорка: у claude на поддельном провайдере (логин API-ключом) время сброса квоты не приходит **[И 34]**. Для
него сценарий «квота с временем сброса» ожидает `rate_limited` без времени, а не `quota_exhausted`.

Подробно: `docs/harness-updates.md`; `docs/design/adapters.md`, раздел «Contract suite».

## 8. Агенты и паки

### 8.1 Агент

Агент — общая роль (`coder`, `planner`): промпт роли, skills и умолчания настроек запуска. О конкретной задаче
агент не знает: её приносит пользователь входом формулы. **[Р]** В коде ядра нет ни одного имени роли: любое
поведение роли — конфигурация.

Всё, что относится к одному агенту, лежит в одном каталоге; деление на подкаталоги — по желанию автора. **[Р]**

```
agents/coder/
  agent.toml        умолчания запуска (harness, provider, model, effort), плагины, env, MCP, хуки, skills,
                    режим разрешений
  prompt.md         промпт роли
  …                 skills/, hooks/, scripts/ — если нужны
```

- Настройки запуска в `agent.toml` — умолчания: их меняют пак, формула и пользователь (§6.3). **[Р]**
- Промпт обязателен. Он приходит от пользователя, из пака или из формулы либо наследуется по слоям; прогон без
  промпта не стартует, пустой файл роли и пустой шаблон — ошибка конфига. **[Р]**

**Вариант агента [Р].** Пользователь объявляет в конфиге оркестратора или проекта тот же агент пака под своим
именем и с другими настройками — любыми ключами настроек агента. Риг отображает имя агента из формулы на вариант:

```toml
[agents.codex-coder]
base     = "dev.coder"      # роль, промпт, skills — из агента пака
provider = "openai"
model    = "luna"

[rigs.backend]
path   = "../backend"
agents = { coder = "codex-coder" }   # в этом риге ссылку формулы на coder исполняет вариант
```

- Формулы пака по-прежнему ссылаются на `coder`; отображение живёт в риге.
- Вариант — отдельный агент для лимита параллелизма, ворот выдачи и событий.
- Второй путь к тому же результату — оверрайд без нового имени: `[rigs.backend.overrides.coder]`.

Подробно: `docs/design/config.md`, раздел «Agent».

### 8.2 Pack

Pack — единица содержимого, пригодного для любого проекта: агенты, формулы, триггеры. В паке нет ни слова о
конкретной задаче пользователя. **[Р]**

```
<pack>/
  pack.toml         имя, версия, требуемые плагины, минимальная версия aae, [settings]
  agents/<agent>/…
  formulas/…
```

- `[settings]` пака несёт только настройки запуска; они действуют на прогоны формул этого пака (§6.3). **[Р]**
- Источники: каталог на диске и внешний источник. **[Р]** Внешний источник — git-репозиторий; ревизия
  закрепляется в lock-файле проекта (`aae.lock`) командой `aae fetch`. **[Д]**
- Корень проекта сам является локальным паком: агенты и формулы можно класть прямо в проект. **[Д]**
- Имена уникальны в пределах пака; при совпадении между паками используется форма `<pack>.<имя>`. **[Д]**
- Pack может требовать плагины, но не содержит их.

Подробно: `docs/design/config.md`, разделы «Pack», «Names», «Packs and plugins from git».

## 9. Формулы, прогоны, триггеры

### 9.1 Формула

Формула отвечает на вопрос «как»: это процесс — шаги работы и чем её закончить. «Что» — конкретная задача —
приходит только вводом пользователя (входы прогона) и подставляется в шаблон. **[Р]**

Формула: имя, описание, объявленные входы и ровно один шаг. **[Р]**

```toml
name = "code"
description = "Сделать задачу в риге и проверить её"

[inputs]
task = { type = "string", required = true }    # рассказ пользователя: что он хочет

[step]
kind = "prompt"            # или "exec"
agent = "coder"
prompt = "code.md"         # шаблон процесса; вход task подставляется в него
model = "haiku"            # необязательно: настройки запуска поверх агента и пака (§6.3)
timeout = "45m"
```

Виды шага **[Р]**:

- `prompt` — ход агента в сессии харнесса. Исход сообщает финишер. Шаг может нести настройки запуска
  (`harness`, `provider`, `model`, `effort`). **[Р]**
- `exec` — команда без LLM, которую запускает демон: своя группа процессов, таймаут, рабочий каталог прогона.
  Исход — по коду возврата: 0 — `pass`; 75 (`EX_TEMPFAIL`) — временная недоступность **[И 21]**, то есть сбой
  попытки (`run.attempt_failed`), а не исход формулы; иное — `fail`. Хвост вывода ограниченного размера
  сохраняется в результате.

Требования:

- Контекст exec-шаг получает через окружение: `AAE_RUN`, `AAE_BEAD` (если есть), `AAE_INPUT_<NAME>` (строки как
  есть, остальное — JSON). Подстановки в саму команду нет. **[Р]**
- Типы входов (`string`, `integer`, `boolean`, `bead`) проверяются при старте прогона. **[Р]**
- Шаблон промпта — только подстановка переменных, без логики; отсутствующая переменная — ошибка до запуска.
  **[Д]** Пустой шаблон и промпт, пустой после подстановки, — ошибка (§8.1). **[Р]**
- `worktree = true` в формуле даёт каждому её прогону свой git-worktree; создаёт и убирает его aae (§11.5).
  **[Р]**

Подробно: `docs/design/config.md`, раздел «Formula»; язык подстановки — `docs/design/contracts.md`, 2.3.

### 9.2 Приёмка и тест — одно и то же

Отдельного «тестового режима» у продукта нет. Проверка формул и проверка самого `aae` — это одна исполняемая
acceptance spec. **[Р]**

- Acceptance spec — набор исполняемых сценариев в репозитории, который реализует критерии §15.
- Сценарии идут тем же путём, что и рабочие прогоны: настоящий демон и настоящие бинарники харнессов.
- Часть сценариев вызывает настоящую модель — самую дешёвую; её задают агенты из фикстур spec.
- Полностью spec запускается только по явной команде пользователя: прогон стоит денег и требует логина.
  Автоматически (на коммит, по расписанию) сценарии с моделью не запускаются никогда.
- Сценарии без модели (поддельный провайдер, сценарный драйвер, exec-шаги) — те же сценарии той же spec; CI
  запускает это подмножество на каждый коммит. Колонка «Запуск» в §15 говорит, к какой части относится критерий.
- Результат прогона spec — один отчёт с датой, версией `aae` и версиями харнессов (правило замеров, §14).

Подробно: `docs/guide/development.md`, раздел «Acceptance scenarios».

### 9.3 Прогон

Состояния:

```
queued → preparing → starting → running ⇄ requires_action → finishing → passed | failed{класс} | cancelled
                                   │                            │
                                   │                            └→ running (хук вернул агенту замечание)
                                   ├→ parked{ворота, причина} → starting
                                   └→ interrupted (рестарт демона) → решение по `run.attempt_failed`
```

- Класс провала различает причину: `agent` (финишер сказал `fail`), `check` (вето плагина), `hollow_done`,
  `infrastructure` (попытки исчерпаны или политика завершила прогон).
- `queued` — прогон ещё не стартовал: ждёт лимита параллелизма или открытия ворот (§5.7). `parked` — уже
  стартовавший прогон ждёт открытия ворот, процесса харнесса у него нет.
- Прогону нужен рабочий каталог. Риг берётся из входа, из триггера или из метки бида; нет рига — ошибка до
  запуска. **[Д]**
- Рабочий каталог по умолчанию занят одним живым прогоном: второй прогон в тот же каталог ждёт в `queued`.
  Параллельная работа в одном риге — через worktree (§11.5). **[Д]**
- Попытка — запуск новой сессии или возобновление прежней. У попытки своё поколение.
- Параллелизм ограничивается на уровне оркестратора и на уровне агента. **[Д]**
- Прогон может явно продолжить сессию другого завершённого прогона, чтобы сохранить контекст. **[Р]** Неявного
  переиспользования сессий нет.
- Рестарт демона прерывает только идущую попытку (`starting`, `running` в ходе, `requires_action`). Прогон,
  ждущий решения хука (`preparing`, `finishing`, ход без исхода, `interrupted`), ждёт его и после рестарта (§5.6).

**Дочерний прогон [Р].** Агент делит работу сам: запускает из своей сессии другие прогоны и ждёт их исхода.

- `aae run start …`, вызванный в сессии агента (в окружении есть идентификатор прогона и токен попытки), создаёт
  дочерний прогон: он наследует correlation родителя, его глубина на единицу больше, на него действует общий
  предел глубины цепочки (§9.5). Петля «планировщик запускает планировщика» упирается в этот предел.
- `aae run wait <id>…` ждёт терминального состояния всех названных прогонов по событиям, а не опросом, и
  печатает по каждому состояние, класс и причину провала, резюме и данные финишера. Код выхода 0 — все `passed`.
  У команды есть флаг таймаута.
- Отмена родителя отменяет его живые дочерние прогоны. **[Д]**

Подробно: `docs/design/contracts.md`, раздел 6 (состояния, переходы, дедлайны).

### 9.4 Исход

- Агент сообщает исход финишером: `pass` или `fail`, краткое резюме, необязательные данные. **[Р]**
- Финишер — команда CLI `aae` в сессии агента; идентификатор прогона и токен попытки приходят через
  окружение. **[Д]** Токен привязан к попытке, а не к одному вызову; финишер с токеном устаревшей попытки
  отвергается с явной ошибкой, состояние не меняется.
- Сбой инфраструктуры — не исход: он порождает `run.attempt_failed`, а не слово агента.
- Данные финишера сохраняются в результате прогона и доступны триггерам и ожидающему родителю.

Поведение финишера **[Д]**:

| Ситуация | Что происходит |
|---|---|
| Финишер вызван, ход ещё идёт | заявленный исход записан в состояние; прогон остаётся `running`. Повторный вызов в той же попытке заменяет прежний |
| Ход закончился и фоновых задач нет, исход заявлен | `finishing`: порождается `run.finishing`, плагины-проверки могут наложить вето |
| Ход закончился, но фоновые задачи (субагенты) ещё идут | прогон остаётся `running` до состояния idle без фона; у ожидания есть дедлайн |
| Ход закончился и фоновых задач нет, исход не заявлен | `run.turn_ended_without_outcome`; без решения плагина — `failed` с классом `hollow_done` |
| Хук на `run.finishing` вернул замечание | замечание уходит агенту следующим промптом в той же сессии и той же попытке; прежний заявленный исход сброшен; токен остаётся действительным |
| Хук на `run.finishing` наложил вето | `failed` с классом `check` и причиной от хука |
| Демон недоступен в момент вызова | команда финишера повторяет попытки ограниченное время и завершается ошибкой; после рестарта демона прогон идёт по ветке `interrupted` |
| Демон перезапущен, пока прогон в `finishing` ждёт решения хука | хуки `run.finishing` запускаются заново, заявленный исход сохраняется; принятие и вето применяются как обычно; замечание завершает попытку сбоем `daemon_crash`, его текст получит возобновлённая сессия **[Р]** |

Возврат замечания — это и есть check-петля: число возвратов ограничено потолком ядра (инвариант 16).

Из коробки `pass` — это слово агента. Проверку «работа действительно сделана» (коммит есть, тесты зелёные)
ведёт внешний цикл владельца; в комплект она не входит. **[Р]** Механизм вето для неё есть, плагина — нет.

Подробно: `docs/design/contracts.md`, 6.3.

### 9.5 Триггеры

Три способа запустить прогон, все в ядре **[Р]**:

1. **Явный вызов** через API, CLI или MCP.
2. **Подписка на событие:** тип события, фильтр, формула, отображение полей события во входы.
3. **Расписание:** cron или «не чаще чем раз в интервал».

```toml
[[trigger]]
name = "implement-next"
on = "bead.ready"                       # событие трекера
where = { label = "auto" }              # только биды с этой меткой
run = "implement"
inputs = { bead = { next_ready = true, epic = "{{event.bead.epic}}" } }

[[trigger]]
name = "nightly-audit"
cron = "0 3 * * *"
run = "audit"
```

Требования:

- Триггеры объявляются в паке и в проекте. Риг триггеру назначает проект, а не пак: пак не знает имён ригов.
- Срабатывание идемпотентно: ключ (триггер, `seq` события). Сопоставление идёт в транзакции события, а не по
  журналу JSONL, поэтому `kill -9` демона не теряет и не удваивает срабатывания.
- Прогон, запущенный триггером, наследует correlation от породившего события. Событие трекера несёт correlation
  того прогона, чья попытка сделала запись: `aae` узнаёт её по actor (§10.2). Запись, сделанная человеком,
  начинает новую цепочку. **[Д]**
- Защита от петель — по глубине «прогон породил прогон» (триггером или из сессии агента, §9.3), а не по числу
  прогонов в цепочке: длинный эпик законен. Предел глубины — 10. Готовый бид — следующая работа трекера, а не
  порождённый прогон: `bead.ready` глубину не добавляет. Повтор над одним и тем же бидом ограничивает счётчик
  неудач бида (§10.3). **[Д]**
- Наложение: пока жив прогон, запущенный этим триггером с тем же ключом входов, новое срабатывание
  пропускается с событием `trigger.skipped`. **[Д]**
- Расписание: cron либо «раз в интервал». После простоя демона пропущенное срабатывает не более одного раза
  **[И 21]**. `cron` считается в часовом поясе системы; ключ `timezone` в конфиге оркестратора его
  переопределяет. **[Р]**
- События трекера: `bead.created`, `bead.updated`, `bead.closed`, `bead.ready`. `bead.ready` порождается, когда
  бид впервые попадает в список готовых: открыт, никем не занят, все его блокеры закрыты. **[Д]**
- Оператор включает и выключает триггер и может сработать его вручную.

Язык фильтра `where` и отображения `inputs`, таймауты хуков и срок жизни записей outbox — контракт: записаны в
`docs/design/contracts.md` (разделы 2 и 3) и не меняются без слома **[И 32]**.

Подробно: `docs/design/config.md`, раздел «Trigger».

## 10. Трекер

### 10.1 Интерфейс

Трекер — адаптер с узким интерфейсом; проект может работать без трекера. **[Д]** Операция добавляется в
интерфейс, только когда она нужна вызывающему **[Р]**: claim, условный возврат, закрытие, список готовых, поток
изменений.

Подробно: `docs/design/contracts.md`, раздел 5.

### 10.2 br

- `br` — внешний бинарник. Он ставится отдельно через mise и объявлен зависимостью в конфигурации mise. **[Р]**
  `aae` его не поставляет, не линкует и не вендорит.
- Лицензия br — не чистая MIT, а «MIT с райдером OpenAI/Anthropic» **[И 11 §2.7]**; при линковке или вендоринге
  райдер перешёл бы на дистрибутив `aae`. Об этом — явное предупреждение везде, где пользователь встречает br
  **[Р]**: в README, в документации по установке и в выводе `aae doctor`.
- Одна БД на проект в `<project>/.beads`, вне git ригов; риг — метка `rig:<имя>`. **[Р]** Так работают эпик над
  несколькими ригами и общий список готовых.
- Путь к БД задаётся явно в каждой сессии и каждом вызове: автопоиск br поднимается по дереву до `$HOME`, и
  агент без явного пути молча пишет в чужой трекер **[И 11]**.
- У каждой попытки свой уникальный actor: br различает владельцев claim только по имени **[И 11]**; по actor же
  определяется correlation записей агента (§9.5).
- Событий у br нет. Изменения, сделанные через `aae`, порождают события сразу; внешние (человек вызвал `br`
  руками) ловятся слежением за файлом БД.
- В трекер не пишется ничего служебного: ни прогоны, ни шаги, ни сессии.
- На уровне оркестратора генерируется файл рабочего пространства `bv`, перечисляющий БД всех проектов. **[Д]**
- Для разработки и тестов версия br закреплена точно (через mise). Адаптер объявляет проверенный диапазон
  версий, `aae doctor` предупреждает о версии вне его. У адаптера трекера свой набор контрактных тестов: claim
  под конкуренцией, условный возврат, закрытие, список готовых в эпике.

Подробно: `docs/design/tracker-br.md`; источник событий — `docs/design/experiments.md`, раздел «br as an event
source».

### 10.3 Бид и прогон

- Прогон может получить бид входом; прогоны без бида разрешены. **[Р]**
- Claim, возврат и закрытие делает демон. **[Р]** Claim берётся при запуске и держится весь прогон, через все его
  попытки. Бид отпускается только в терминальном состоянии прогона: `passed` — закрывается; `failed` и
  `cancelled` — возвращается условно (сравнение владельца и поколения).
- Цепочки нескольких формул над одним бидом нет: `pass` всегда закрывает бид. Работа режется на биды, а
  следующий берётся подбором «следующий готовый бид», в том числе в пределах эпика. **[Р]**
- Вход прогона может быть не конкретным бидом, а запросом «следующий готовый», необязательно с эпиком. Выбор и
  claim демон делает одной операцией. Если готовых нет, прогон не создаётся, а вызывающий получает явный ответ
  «нечего брать». **[Д]**
- У бида не более одного живого прогона-владельца; второй запрос отклоняется с причиной. Явно указанный бид с
  меткой `rig:` другого рига отвергается. **[Р]**
- Счётчик неудач бида: каждый прогон, завершившийся `failed` над этим бидом, увеличивает счётчик в состоянии.
  После заданного числа неудач ядро закрывает ворота выдачи по этому биду (§5.7) и пишет событие: подбор его
  пропускает, пока человек не снимет ворота. Иначе возврат бида порождал бы бесконечный повтор. **[Д]**
- Запись о владении в состоянии оркестратора — истина; поле владельца в br — её отражение. Если закрытие или
  возврат в br не удались, исход прогона не меняется: операция повторяется, расхождение видно событием.
- Агент пользуется `br` сам для содержательной работы: дочерние задачи, комментарии, зависимости.

Подробно: `docs/design/tracker-br.md`, раздел «Beads and runs».

## 11. Плагины

### 11.1 Назначение

Плагин — единица расширения. Типовые расширения делаются плагинами, а не кодом ядра. **[Р]** Плагин — каталог с
`plugin.toml` (имя, версия, параметры, вклад в агентов, хуки оркестратора, сервисы) и своими `skills/`, `hooks/`,
`bin/`.

Подробно: `docs/guide/plugin.md`; `docs/design/config.md`, раздел «Plugin».

### 11.2 Сторона агента — декларативная

Плагин добавляет подключившему его агенту: skills, хуки харнесса, MCP-серверы, переменные окружения, скрипты в
`PATH`, фрагменты промпта, родные для харнесса части.

- Вклад получают только агенты, которые плагин подключили. **[Р]**
- Хуки харнесса пишутся в диалекте Claude: JSON на stdin, код возврата, JSON на stdout. claude и codex исполняют
  его нативно **[И 18]**.
- Если вклад меняет «процессную» часть конфига харнесса, агент получает отдельный экземпляр в реестре (§7.3).

### 11.3 Сторона оркестратора — exec-хуки

Плагин вешает команды на события ядра. **[Р]**

- Контракт — тот же диалект: событие JSON на stdin; код 0 — «нет возражений»; код 2 — блокировка с причиной в
  stderr; JSON на stdout — решение для решающих событий (§5.4).
- Хук не имеет состояния и исполняется вне цикла ядра; его ответ возвращается сообщением. Падение или таймаут
  хука не роняет демон и порождает `plugin.hook_failed`.
- Для хуков-вето отказ самого хука по умолчанию блокирует («неоднозначность ⇒ ноль эффектов»); для наблюдающих —
  игнорируется. **[Д]**
- Несколько плагинов на одном событии: для вето достаточно одной блокировки; для выбора реакции на сбой действует
  первое решение в порядке подключения. **[Д]**
- В событии уже есть счётчики попыток, времена, состояние ворот и последний известный лимит аккаунта, поэтому
  политикам своё состояние не нужно. Хранилища для плагинов в ядре нет.
- У хука есть таймаут. Решающее событие остаётся в очереди, пока по нему нет решения; после рестарта демона хук
  запускается заново (§5.6). Хуки обязаны быть идемпотентными.
- Хуки и сервисы стороны оркестратора включаются на уровне оркестратора или проекта.

Подробно: `docs/design/contracts.md`, раздел 3; `docs/guide/plugin.md`, раздел «The orchestrator side».

### 11.4 Сервисы

Сервис — долгоживущий процесс под супервизией: команда, область совместного использования (оркестратор, проект),
проверка здоровья; MCP у него — по желанию. **[Р]** Объявляется в конфиге или в плагине. Сервисы живут в том же
ленивом реестре, что и экземпляры харнессов.

Общий MCP **[Р]**:

- MCP-сервер по умолчанию один на область, а не на сессию. Сессии получают его URL и заголовки идентичности:
  проект, риг, агент, прогон **[И 36]**.
- Сервер, который отдаёт сам `aae`, и любой рекомендуемый общий сервер понимают обе эпохи протокола MCP:
  stateless и `initialize`-эпоху **[И 36]**.
- Перезапуск сервиса должен быть быстрым **[И 36]**. Сбой MCP — это сбой инструмента, а не провал прогона.
- stdio-сервер с неявным состоянием на клиента (например, браузерный) делить нельзя: для него область «сессия»
  задаётся явно.
- Делить stdio-сервер между сессиями можно только через мост stdio→HTTP. Мост входит в первый выпуск **[Р]**;
  это отдельный модуль поставки, не ядро.
- Порт на loopback без аутентификации доступен любому локальному процессу **[И 18]**: общий сервис слушает
  unix-сокет либо loopback с токеном.

Подробно: `docs/design/config.md`, раздел «MCP servers and services»; `docs/design/contracts.md`, раздел 8.

### 11.5 Плагины в комплекте

Поставляются внутри бинарника как встроенные исполнители хуков (внешний рантайм не нужен). В бюджет ядра не
входят: считаются по своей строке бюджета и входят в общий лимит выпуска (§14). **[Д]**

| Плагин | Что делает |
|---|---|
| `default-policy` | Реакции на сбои — «дешёвые страховки» **[И 21 §4.2]**: resume после краша; после нескольких отказов самого resume — новая сессия; при квоте — закрыть ворота аккаунта до времени сброса; backoff на 429 для харнессов, которые не повторяют сами; при серии крашей — закрыть ворота агента; лестница для `stall`; одно напоминание при конце хода без финишера. Включён по умолчанию, отключаем; пороги меняются в его конфиге. Работает только на стороне оркестратора и харнесс не меняет **[Р]** |
| `worktree` | На `run.preparing` создаёт git-worktree для прогона и подставляет рабочий каталог; после завершения удаляет, только если коммиты достижимы из refs. Включается только ключом формулы `worktree = true`; центральных списков агентов и формул и включения на уровне агента нет **[Р]** |

Правила `default-policy` **[Р]**:

- `auth_required` и `billing`: повторы с ростом паузы до раза в час, без повышения до человека; ожидание идёт на
  воротах аккаунта и потолок попыток не расходует (инвариант 16).
- `quota_exhausted` без времени сброса в самом сбое: ворота аккаунта закрываются до времени сброса последнего
  известного лимита аккаунта, если он исчерпан. `rate_limited` при исчерпанном лимите аккаунта — тоже ворота
  аккаунта до сброса, а не короткий backoff.

Граница: механизмы — в ядре (возобновить, начать новую сессию с сохранением владения, ворота выдачи, счётчики,
потолок попыток, сторож, дедлайны); выбор реакции и её пороги — в плагине. Без `default-policy` действует колонка
«без решения плагина» из §5.4.

Подробно: `docs/design/config.md`, раздел «Bundled plugins»; `docs/design/contracts.md`, раздел 10; первоисточники
порогов — `docs/init/aae-context/06-failure-policy-defaults.md`.

### 11.6 Доверие

Плагин исполняет произвольные команды с правами пользователя. Установка и включение — явные действия; плагин из
git работает только на ревизии из lock-файла; автообновления нет. **[Д]**

числа назначил автор постановки по оценке сопоставимого объёма в исследовании: 20–32 тыс. строк на TypeScript с
готовыми клиентами протоколов (оценка 2026-11-10, отчёт 31), тогда как на Rust клиенты claude и codex пишутся
руками.

- Лимит — потолок, а не цель: меньше кода — лучше (§1).
- Считаются строки кода без пустых и без комментариев одним инструментом, зафиксированным в репозитории; тесты и
  сгенерированный код исключаются по путям. **[Д]**
- Файл — не более 400 строк. **[Д]**
- Превышение лимита выпуска блокирует выпуск; превышение жёсткого стопа останавливает добавление функций до
  ревизии с удалением.
- Если бюджет всё же не сходится, первыми уходят **[Д]**: загрузка паков из git (остаются
  локальные каталоги); продолжение сессии другого прогона; файл рабочего пространства `bv`. Не вырезается:
  инварианты §5.5, финишер, ворота выдачи, восстановление, «объясни конфиг», контрактные тесты. Мост stdio→HTTP из этого списка снят: он делается (§2.1 п. 4).

Сроков и календарных бюджетов в постановке нет. **[Р]**

**Правила:**

- **Без заглушек и без кода «на вырост». [Р]** Не пишутся: пустые реализации, `todo`-ветки, неиспользуемые
  параметры, поля, флаги и точки расширения под будущие функции, обобщения под единственный случай. Всё, что
  постановка называет отложенным (§1.1), в коде отсутствует полностью.
- Нет механизма без применения. У каждой функции есть запись, какой критерий §15 или какая реальная работа её
  использует; функция без такой записи к моменту выпуска удаляется.
- Тесты — против настоящих бинарников харнессов. Поддельный драйвер допустим только сценарный (задержка, конец
  хода без исхода, ошибка провайдера, код 75, зависание, обрыв канала посреди хода, запрос разрешения, событие
  вне хода) или как запись настоящих транскриптов **[И 21 §4.4]**.
- Детерминированная проверка инвариантов §5.5: управляемые часы, seed, проверка после каждого шага.
- Инъекция сбоев: `kill -9` демона на каждой границе транзакции и между записью в состояние и вызовом трекера;
  восстановление обязано сойтись.
- Проверка идемпотентности: любая операция, применённая дважды, и любое событие, доставленное дважды или не
  доставленное, дают то же конечное состояние.
- Перед каждым новым механизмом — проверка, нет ли его уже у вендора харнесса.
- Версии харнессов и `br` задаёт `mise.toml`: `br` — точной версией, claude и codex — линией релизов (`2.1`, `0`),
  `mise.lock` нет — решение владельца (журнал, цикл 30, п. 4). Адаптер объявляет проверенный диапазон версий;
  обновление — через контрактные тесты (§7.8).
- Ревью до основной ветки.
- **Отчёт о готовности. [Р]** Исполнитель ведёт в репозитории один файл со шкалой готовности каждого компонента
  и обновляет его в конце каждого рабочего сеанса. Оценка — целое от 0 до 10 по опорным точкам:

  | Балл | Что это значит |
  |---|---|
  | 0 | ничего нет |
  | 2 | контракт компонента записан (типы, события, ошибки), кода нет |
  | 4 | код есть, основной путь работает вручную |
  | 6 | тесты без модели зелёные, включая пути сбоев |
  | 8 | относящиеся к компоненту критерии §15 зелёные на хосте владельца |
  | 10 | компонент отработал реальные прогоны владельца без вмешательства (критерий 20) |

  Промежуточные баллы допустимы; рядом с каждой оценкой — одна строка «чего не хватает до следующей точки».
  Оценка — это замер: у неё дата, короткий sha и маркер `MEASURE`. Компоненты: цикл событий и состояние;
  прогоны и финишер; триггеры и расписание; ворота выдачи; восстановление; сборка конфига; реестр экземпляров и
  сервисов; адаптер claude; адаптер codex; адаптер br; исполнение хуков плагинов; `default-policy`; `worktree`;
  общий MCP; HTTP API; CLI; MCP-фронтенд; acceptance spec; поставка и `doctor`.
- **Правило замеров. [Р]** Любой замер (время, память, размер, количество, доля), где бы он ни появился — в
  документации, отчёте acceptance spec, комментарии к порогу в коде или описании PR, — несёт:
  - видимую дату замера;
  - видимую версию измеренного: версию бинарника или короткий sha;
  - невидимый комментарий рядом для того, кто будет править: идентификатор замера, источник, условия, что
    перемерить.

  Формат комментария один на весь проект, чтобы его находил один `grep`:

  ```
  <!-- MEASURE id=<слаг> date=<ГГГГ-ММ-ДД> ver=<версия или sha> env=<ОС и стенд> src=<откуда> note="<условия; что перемерить>" -->
  ```

  В коде тот же маркер пишется в синтаксисе комментария языка. Замер без даты и версии считается дефектом
  документа. CI проверяет, что у каждого маркера заполнены `id`, `date`, `ver` и `env`; замер, у которого маркера
  нет вовсе, CI найти не может — это проверяет ревью.

**Остановиться и пересмотреть, если:**

- превышен жёсткий стоп по строкам;
- обновления харнессов раз за разом ломают контрактные тесты и съедают больше работы, чем сам продукт;
- вендор вводит отдельную оплату headless-режима, которая делает путь без TUI неприемлемым для владельца;
- штатные средства вендоров покрывают подавляющую часть реально используемых формул.

## 15. Критерии приёмки первого выпуска

Критерии реализуются как исполняемая acceptance spec (§9.2): она и есть приёмка. **[Р]** Колонка «Запуск»:

- **CI** — сценарий без модели; входит в spec и дополнительно идёт в CI на каждый коммит;
- **запрос** — сценарий с настоящей моделью; идёт только при явном запуске spec пользователем;
- **вручную** — сценарием не исполняется; отметку ставит владелец.

Числовые пороги предложены автором и правятся владельцем. **[Д]** Ориентиры исследования мягче: хоп p50 ≤ 3 с и
p90 ≤ 10 с, инфраструктура в простое ≤ 150 МБ (`FINAL-REPORT.md` §5.3). Плагин `default-policy` во всех
сценариях включён, если не сказано иное.

Платформа **[Р]**: приёмка идёт только на хосте владельца — Linux arm64. Остальные три цели только собираются;
их работоспособность не проверяется и принимается на веру в переносимость языка.

### Демо (критерий 20)

Решение владельца 2026-11-14 **[Р]**. Каталог `demos/` — минимальные живые примеры того, как работает aae: пак (агенты,
формулы, конфиг) и то, что агенты сделали. Без мусора сборки (`node_modules` и т. п.). У каталога свой `mise.toml` с
задачами демо: они требуют логина харнессов и тратят реальные токены, поэтому идут только на машине разработчика
(в CI — только `aae config check` пака). У каждого демо — короткий README.

- **Демо 1 — змейка на claude.** Две пустые папки — риги `frontend` и `backend`. Задача: игра «змейка» в браузере,
  бэкенд хранит лучшие счета в plain text. Оба агента — claude haiku.
- **Демо 2 — то же, смешанные харнессы**: фронтенд — claude haiku, бэкенд — codex на самой дешёвой модели. От демо 1
  отличается только `harness`/`model` в `agent.toml` бэкенда — в этом и показ пака.
- **Демо 3 — aae разрабатывает себя** (роадмап, не первый выпуск): сетап агентов этого репозитория как пак aae.

Устройство демо 1 и 2 (KISS):
- Цепочка: формула бэкенда → триггер на `run.passed` → формула фронтенда; финишер бэкенда отдаёт описание API
  (порт, `GET`/`POST` лучшего счёта) в `outcome.data`, триггер передаёт его во входы фронтенда.
- Ограничение стека в задаче: без зависимостей и сборки — фронтенд один `index.html` на чистом JS, бэкенд на
  стандартной библиотеке.
- В конце цепочки — exec-формула дымового теста: поднять бэкенд, `POST` счёта, проверить plain-text файл и `GET`,
  проверить, что фронтенд содержит игру. Код 0 — демо прошло.
- Результат прогона (папки ригов и конфиг) сохраняется в `demos/<демо>/` как снимок; отчёт — с маркером `MEASURE`.
