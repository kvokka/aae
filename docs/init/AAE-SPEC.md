планирует и делает работу, а ревьюер проверяет продукт. Истории изменений здесь нет: она в git.

Метки в тексте:

- **[Р]** — решение владельца. Исполнитель его не пересматривает.
- **[Д]** — допущение автора постановки или исполнителя. Действует, пока владелец не поправил; исполнитель может

- **[И NN]** — факт из исследования, отчёт `NN`. Отчёты исследования и итоговый `FINAL-REPORT.md` лежат на диске
  владельца и в репозиторий не входят **[Р]**; всё нужное из них вынесено в шпаргалки (§19).
- **[НП]** — не проверено. Нужен опыт до того, как на это опирается код. Незакрытые собраны в §17.

Примеры конфигов в документе — иллюстрации формы, а не контракт синтаксиса.

Каждый замер несёт видимую дату и версию и невидимый комментарий `<!-- MEASURE … -->` рядом (правило — §14). Найти все

## 1. Что строим

`aae` — событийный оркестратор агентов-кодеров («программная фабрика»): демон уровня машины, который по запросу
запускает **формулы** на **агентах** в **ригах** (репозиториях) **проектов** и доводит прогоны до явного исхода,
переживая сбои харнессов, лимиты и собственные рестарты.

Продукт пишется с нуля. Опыт проекта-предшественника используется как знание (инварианты, классы сбоев, ошибки); код не
наследуется, сам предшественник в коде и документации по имени не называется. **[Р]**

Четыре свойства определяют форму продукта **[Р]**:

1. **Очень лёгкое ядро.** В ядре только то, без чего прогон нельзя корректно запустить, наблюдать и завершить. Всё
   остальное — адаптеры (харнессы, трекер, фронтенды) и плагины.
2. **События, а не тики.** Ни одна единица работы не ждёт таймера опроса: задержка от причины до реакции не зависит ни
   от какого интервала. Запрещён опрос как способ ожидания работы; страховочные таймеры (сторож сирот, проверка здоровья
   экземпляра, resync) допустимы.
3. **Нативные протоколы харнессов без tmux.** Экран терминала не является каналом управления ни в каком виде.
4. **Меньше кода — лучше.** Пишется только то, что нужно описанному здесь результату. Никаких заглушек, никаких точек
   расширения и кода «на вырост», никаких полей и флагов под будущие функции. Отложенное названо отложенным (§1.1) и в
   коде не присутствует вовсе.

Поставка: один бинарник `aae` под linux и macOS, x86_64 и arm64. Репозиторий публичный, лицензия MIT. **[Р]**

| Алертинг: уведомление человека о сбое | **[Р]**: только журнал событий и логи |

| Встроенная проверка «работа действительно сделана» | **[Р]**: это делает внешний цикл владельца (§9.4) |
| Сроки и календарные бюджеты | **[Р]**: работу ведут агенты, сроков в постановке нет |
| Ротация аккаунтов и failover между подписками | зона политического риска **[И 34]**; не ядро |
| Трансляция хуков между диалектами харнессов | у claude и codex формат хуков почти общий **[И 18]**; транслятор — когда появится третий диалект |
| Обобщённый ACP-адаптер, один адаптер на несколько харнессов | **[Р]**: когда появится третий харнесс (§7) |
| Умолчание харнесса для провайдера (`[provider.<p>] harness`) | **[Р]**: пока у каждого провайдера один адаптер (§6.2) |
| Цепочка нескольких формул над одним бидом | **[Р]**: не критична; `pass` закрывает бид (§10.3) |
| Демо «aae разрабатывает себя» | роадмап: сетап агентов этого репозитория как пак aae |
| Миграция данных и паков из проекта-предшественника | отдельная задача |

| **проект** | каталог с `aae.toml`: набор ригов, паков, плагинов и одна БД трекера |
| **риг** | репозиторий на диске плюс его переменные (`test_cmd`, `lint_cmd` и т. п.) |
| **харнесс** | вид agent-CLI: `claude`, `codex`, позже `opencode`. Ему соответствует один адаптер |
| **провайдер** | поставщик модели: `anthropic`, `openai`. Адаптер объявляет провайдеров, с которыми работает его харнесс |
| **экземпляр харнесса** | запущенный процесс харнесса (app-server или процесс сессии), который обслуживает одну или несколько сессий |
| **агент** | общая роль (`coder`, `planner`): промпт роли, skills и умолчания настроек запуска. О конкретной задаче агент не знает. Ролей в коде ядра нет |
| **настройки запуска** | четыре скаляра: харнесс, провайдер, модель, effort (§6.2) |
| **сокращение модели** | имя семейства (`opus`, `luna`), которое адаптер раскрывает в последнюю версию модели этого семейства |
| **вариант агента** | агент пака под другим именем и с другими настройками, объявленный в конфиге пользователя (`claude-coder`, `codex-coder`) |
| **ссылка на сессию** | пара «харнесс + id сессии у харнесса». Единственное, что ядро знает о разговоре |
| **формула** | описание процесса — «как»: имя, описание, входы, один шаг. «Что» — задача — приходит входом от пользователя |
| **шаг** | `prompt` (ход агента) или `exec` (команда без LLM) |
| **прогон** (run) | исполнение формулы с конкретными входами; имеет попытки и исход |
| **дочерний прогон** | прогон, запущенный из сессии агента другого прогона; наследует его correlation |
| **попытка** (attempt) | один запуск или возобновление сессии в рамках прогона |
| **финишер** | вызов, которым агент сообщает исход прогона |
| **триггер** | правило «событие или расписание → запустить формулу» |
| **correlation** | идентификатор цепочки прогонов, порождённых друг другом |
| **pack** | содержимое, пригодное для любого проекта: агенты, формулы, триггеры |
| **plugin** | расширение: то, что подключается к агентам (skills, hooks, MCP, скрипты, env), хуки на события оркестратора, сервисы |
| **сервис** | долгоживущий процесс под супервизией оркестратора (например, общий MCP-сервер) |
| **ворота выдачи** | запись «по этому ключу прогоны не запускать до времени или до ручного снятия» (§5.7) |
| **трекер** | хранилище задач за интерфейсом-адаптером; первая реализация — br |
| **бид** | задача в трекере. Только настоящая работа, никаких служебных записей |
| **событие** | запись о случившемся; повод перечитать состояние, а не истина |

## 4. Архитектура

```
                 HTTP API (полная)   CLI (полная)   MCP (малая)
                        └───────────────┼───────────────┘
                                 фронтенд-адаптеры
                                        │  команды / запросы / поток событий
┌───────────────────────────────────────▼──────────────────────────────────────┐
│ ЯДРО: один писатель состояния                                                 │
│  входная очередь → обработка в транзакции SQLite → события (outbox)           │
│  прогоны и попытки · триггеры и таймеры · сборка конфига · реестр экземпляров │
│  исполнение exec-хуков плагинов · владение бидом · восстановление и resync    │
└───────┬───────────────────────┬──────────────────────┬───────────────────────┘
        │ интерфейс драйвера    │ интерфейс трекера    │ события → журнал JSONL
  адаптеры харнессов        адаптер br             плагины (exec-хуки, сервисы)
  claude │ codex │ (opencode)
```

Границы, которые проверяются сборкой, а не договорённостью:

- Ядро не зависит ни от одного адаптера, фронтенда или плагина. В `aae-core` нет имён харнессов, имён ролей, вызовов
  `br` и знаний о них (`codex`, `max_sessions`, `BEADS_DIR`, `.beads`): они приходят через способности драйвера и
  интерфейс трекера. CI проверяет это поиском по исходникам ядра. **[Р]**
- Харнесс для ядра — абстракция. Корень сборки держит одну таблицу адаптеров; кроме неё, харнесс в корне не назван
  нигде. **[Р]**
- Фронтенды не содержат доменной логики: каждый только переводит свой протокол в команды и запросы ядра.
- Адаптер харнесса не принимает решений о повторах, парковке и исходе: он переводит протокол харнесса в нормализованные
  события и исполняет операции.
- Решения-политики (повторить, припарковать, отклонить) лежат в плагинах и конфиге. Суждения («сделано ли хорошо») — в
  промптах и проверках плагинов. В ядре — только механизмы.

Адаптеры в первом выпуске — модули того же бинарника за общим интерфейсом. Собственный межпроцессный протокол для
адаптеров не изобретается: внешний путь подключения харнессов в будущем — обобщённый драйвер ACP v2. **[Д]**

Подробно: `docs/design/adapters.md`.

## 5. Ядро

### 5.1 Событийная модель

Всё, что происходит, входит в ядро сообщением единственному писателю и обрабатывается в одной транзакции SQLite вместе с
порождёнными событиями (outbox); эффекты выполняются после фиксации, через очередь по ключу с дедупликацией и backoff
**[И 21]**. Таймеры — дедлайны с точным временем пробуждения, а не опрос: задержка от события до реакции ядра не
содержит ожидания интервала (§15, хоп). Страховочные таймеры — сторож сирот, проверка здоровья экземпляра, resync —
этому не противоречат: в штатной работе они ничего не продвигают. **[Р]**

Resync — полная сверка состояния с процессами, экземплярами харнессов и трекером — обязателен при старте демона и раз в
несколько минут. Неоднозначное расхождение — событие `resync.diverged` и ноль автоматических эффектов **[И 21]**
(инвариант 20).

Подробно: `docs/design/event-model.md`.

### 5.2 Состояние

Состояние — SQLite в режиме WAL, статически слинкованная. Единственный писатель — демон; CLI, плагины и агенты меняют
состояние только через API. В состоянии лежит только рантайм; определения (проекты, риги, агенты, формулы, триггеры,
плагины) живут в файлах конфигурации, а прогон хранит снимок своего эффективного конфига — ответ на вопрос «с чем это
запускалось». Файлов-статусов, PID-файлов и lock-файлов нет: живость процесса — pid плюс время старта; второй демон на
тот же каталог состояния не стартует.

Подробно: `docs/design/event-model.md`, раздел «State».

### 5.3 Журнал событий

- JSONL, ротация по размеру: 10 МБ на файл, 5 файлов. **[Р]** Журнал один на оркестратор, для всех проектов **[Д]**; у
  события монотонный `seq` — один счётчик на оркестратор.
- Журнал — канал наблюдения, а не источник истины: источник истины — состояние. Потребитель продолжает чтение с `seq`;
  вытесненный `seq` — явная ошибка «разрыв».
- Содержимое разговора (сообщения модели, вызовы инструментов) ядро не сохраняет: живой просмотр — прямая ретрансляция
  потока адаптера, история — в транскрипте харнесса по ссылке на сессию. **[Д]**

Подробно: `docs/design/event-model.md`, раздел «Journal»; конверт события — `docs/design/contracts.md`, 1.1.

### 5.4 События

- **Наблюдаемые** события плагины и клиенты читают, но не влияют на ход. **Решающие** ждут решения exec-хука плагина
  (§11.3). Решающих пять; в скобках — что делает ядро, когда ни один плагин не ответил, в том числе когда
  `default-policy` выключен: `run.preparing` (запуск как есть), `run.requires_action` (ждать ответа человека до
  дедлайна, затем отказ), `run.attempt_failed` (`failed` с классом `infrastructure`), `run.turn_ended_without_outcome`
  (`failed` с причиной `hollow_done`), `run.finishing` (исход принимается как заявлен).
- Всё, что сообщает драйвер, ядро читает и доводит до политики и наблюдателя, а не отбрасывает **[Р]**: собственный
  повтор харнесса (`run.retrying`; объявленная пауза — не тишина для сторожа), ухудшение экземпляра
  (`instance.degraded`), расход токенов, последний известный лимит аккаунта, причину конца хода.
- Каждый отказ ядра действовать пишет событие с причиной: молчаливых ожиданий нет **[И 21]**.
- Схема события и её версия, нагрузки всех событий, схема решения хука — контракт: они не меняются без смены версии
  схемы **[И 32]**.

Подробно: `docs/design/contracts.md`, разделы 1 (типы и нагрузки событий — 1.3) и 3 (решения хуков).

### 5.5 Инварианты ядра

Двадцать инвариантов — знание, оплаченное историей исправлений проекта-предшественника **[И 21]**: один писатель,
владение с поколением, подтверждённая смерть до замены, намерение до эффекта, идемпотентность, успех только по явному
исходу, дедлайн у каждого переходного состояния, сторож, потолок попыток, удержание оператора, обязательный resync.
Номера стабильны: код и документы ссылаются на «invariant N». Все, кроме 19-го (у worktree один владелец — плагин), —
механизмы ядра, и ни один не вырезается ради бюджета. Пороги — параметры конфига; выбор реакции — политика (§11.5).

Потолок попыток (инвариант 16) **[Р]**: ожидание на воротах своего аккаунта после сбоя `auth_required`, `billing` или
`quota_exhausted` потолок не расходует; любая другая парковка и парковка на незакрытых воротах — расходует.

Проверка — детерминированный хаос-стенд (§14). Подробно: `docs/design/invariants.md` (формулировки, где живёт каждый
инвариант, значения потолков, известные пределы).

### 5.6 Восстановление

- Старт демона: дочитать outbox; остановить каждый записанный экземпляр харнесса со всеми потомками (переподключения к
  пережившим рестарт экземплярам нет **[Д]**); идущие попытки завершить сбоем `daemon_crash` — дальше решает политика;
  перевзвести таймеры и расписания (пропущенное — не более одного раза); выполнить resync.
- Прогон, ждавший решения по решающему событию, после рестарта ждёт того же решения: хуки запускаются заново, заявленный
  исход и результат exec-команды сохраняются, ход и команда не повторяются. Решение, которому нужна сессия (замечание,
  продолжение), завершает попытку сбоем `daemon_crash`; текст замечания получает возобновлённая сессия. **[Р]**
- Плановый рестарт — с дренажом: новые прогоны и ходы не начинаются, идущие дорабатывают до границы хода или до
  таймаута.
- Доставка промпта — «не менее одного раза с идемпотентным эффектом» **[И 34 §7]**: доставлен ли промпт, адаптер после
  смерти демона отвечает по транскрипту; resume хода в полёте нет.

Подробно: `docs/design/invariants.md`, разделы «Recovery» и «Limits» (отличия macOS); `docs/design/contracts.md`, 3.4 и
6.4.

### 5.7 Ворота выдачи

Единственный механизм ядра для «не запускать пока»: запись в состоянии «ключ закрыт до времени T или до ручного снятия».
Прогон, чей ключ закрыт, ждёт с видимой причиной: не стартовавший — в `queued`, стартовавший — в `parked`. Так
реализуются «светофор на аккаунт» **[И 34]** и удержание оператора без отдельных подсистем.

- Ключи: аккаунт харнесса (идентификатор сообщает адаптер **[Д]**), модель, агент, бид, риг, проект, весь оркестратор.
- Ключ модели — `model:<provider>/<раскрытое имя>`. Прогон знает его из своего эффективного конфига до старта, а не из
  собственного первого сбоя. **[Р]**
- Закрывают ворота политика (в ответ на сбой), оператор (пауза) и само ядро (бид после серии неудачных прогонов, §10.3).
  Ворота переживают рестарт, видны в API и CLI; закрытые оператором автоматика не снимает (инвариант 18).

Подробно: `docs/design/contracts.md`, раздел 7.

## 6. Иерархия и конфиг

### 6.1 Уровни

```
оркестратор   ~/.config/aae/config.toml     харнессы и умолчания их моделей, общие MCP/hooks/skills/env, плагины
└─ проект     <project>/aae.toml            риги, паки, плагины проекта, варианты агентов, оверрайды
   └─ риг     секция в aae.toml             путь к репозиторию, переменные, отображение агентов, оверрайды
```

Агент не уровень иерархии, а потребитель настроек. Умолчание модели для каждого харнесса задаётся на уровне
оркестратора. **[Р]** Пользователь в своём конфиге (оркестратор, проект, риг) говорит, на чём работает агент, и даёт
задачу; пак об этом не знает. **[Р]**

### 6.2 Что настраивается

Нейтральные к харнессу категории: настройки запуска, env, MCP-серверы, хуки харнесса, skills, системный промпт, режим
разрешений, плагины, флаг наследования хоста. Плюс блок «родных» настроек конкретного харнесса (`native.<harness>`),
который ядро не интерпретирует и передаёт адаптеру как есть.

**Настройки запуска** — четыре обычных послойных скаляра **[Р]**:

| Ключ | Смысл |
|---|---|
| `harness` | agent-CLI: `claude`, `codex` |
| `provider` | поставщик модели: `anthropic`, `openai` |
| `model` | полное имя модели либо сокращение |
| `effort` | уровень усилия модели |

Харнесс и провайдер **[Р]**:

- Адаптер объявляет провайдеров, с которыми работает его харнесс: claude — `anthropic`, codex — `openai`.
- Задан только `provider` — харнессом становится единственный адаптер этого провайдера.
- Задан только `harness` — провайдером становится его родной.
- Не задано ни то, ни другое, либо провайдер не поддержан заданным харнессом — ошибка конфига.
- Таблицы «умолчание харнесса для провайдера» нет, пока у каждого провайдера один адаптер.
- `harness` меняется теми же слоями, что и остальные настройки запуска: оверрайдом, вариантом, паком, формулой.

Модель **[Р]**:

- Полное имя модели передаётся харнессу как есть.
- Сокращение раскрывается в последнюю версию семейства. Таблица сокращений — знание адаптера (§7.2). Сокращения первого
  выпуска: anthropic — `fable`, `opus`, `sonnet`, `haiku`; openai — `astra` → `gpt-6-astra`, `luna` → `gpt-6-luna`,
  `terra` → `gpt-6-1-terra`, `sol` → `gpt-6-1-sol`.
- Если CLI харнесса сам раскрывает сокращение в последнюю версию, оно передаётся как есть.
- Если харнесс не принимает имя из таблицы, это находка для владельца; молча подменять имя нельзя.

### 6.3 Порядок слоёв

От слабого к сильному **[Р]**:

1. настройки хоста для итогового харнесса (`~/.claude/`, `~/.codex/` и т. п.) — если наследование включено;
2. умолчание модели итогового харнесса (`[harness.<h>] model` оркестратора);
3. общие настройки оркестратора;
4. общие настройки проекта;
5. общие настройки рига;
6. вклад плагинов, подключённых к агенту, в порядке подключения;
7. определение агента в паке — умолчания;
8. пак: `[settings]` в `pack.toml` того пака, которому принадлежит формула прогона;
9. формула: ключи настроек запуска в её `prompt`-шаге;
10. вариант агента, объявленный пользователем (§8.1);
11. оверрайды пользователя для этого агента: оркестратор → проект → риг.

Слои 8 и 9 несут только четыре настройки запуска. Явная настройка пользователя (слои 10 и 11) сильнее пака и формулы:
так поправляют агента из внешнего пака, не форкая пак.

Правила слияния **[Д]**: скаляр — побеждает старший слой; словари (env, MCP по имени, `native`) — по ключу, запись
заменяется целиком; списки с именованными элементами (хуки, skills, плагины) — объединение с возможностью выключить
элемент по имени на старшем слое.

Обязательное свойство: команда «объясни конфиг» (`aae config explain`, она же в API) показывает итог для тройки (проект,
риг, агент) и для каждого значения — слой, из которого оно пришло, включая выведенный харнесс и раскрытое имя модели.

Слой хоста — исключение. Настройки хоста сливает сам харнесс, ядро их не читает и не разбирает. В «объясни конфиг» он
показан одной строкой, и выключить отдельный элемент хоста по имени нельзя — только весь слой.

Конфиг харнесса внутри самого рига (`CLAUDE.md`, `.claude/`, `.mcp.json`, `AGENTS.md`) — свойство репозитория, а не
хоста: он действует и при выключенном наследовании хоста. **[Д]**

Подробно: `docs/design/config.md`, раздел «Effective config and "explain config"»; опыт по доставке —
`docs/design/experiments.md`, раздел «Config and credential delivery».

### 6.4 Наследование настроек хоста

Включено по умолчанию, выключается на любом уровне (`inherit_host`). **[Р]**

- Цена, о которой должен знать пользователь **[И 42, 18]**: личные MCP-серверы оператора стартуют в каждой сессии и
  замедляют её старт (общий MCP §11.4 на них не распространяется; `doctor` предупреждает о stdio-MCP хоста); личные хуки
  и плагины оператора исполняются в сессиях агентов.
- Адаптер не пишет в файлы хоста.
- При выключенном наследовании учётные данные всё равно берутся с хоста: адаптер доставляет их в сессию.
- codex при включённом наследовании и наличии skills получает собственный `CODEX_HOME`, который наследует хост (его
  логин и конфиг) и добавляет skills. `config_error` на этом пути запрещён. **[Р]**

Подробно: `docs/design/config.md`, раздел «Host inheritance» (замеры цены, доставка по харнессам). Открытые **[НП]** —
§17.

### 6.5 Сборка и доставка

- Эффективный конфиг собирает ядро при подготовке прогона. Адаптер переводит его в флаги запуска, параметры сессии или
  сгенерированные файлы; они лежат в каталоге состояния, а не в риге и не в домашнем каталоге харнесса.
- Окружение сессии собирается из слоёв, а не наследуется от окружения демона.
- Конфиг перечитывается по явной команде, а не слежением за файлами. **[Д]** Невалидный конфиг не применяется. Идущие
  прогоны работают со своим снимком; перезапускаются только экземпляры, чей отпечаток изменился.
- Внешними зависимостями управляет mise. **[Р]** Бинарник харнесса разрешается в порядке: явный путь в конфиге → `mise
  which` → `PATH` **[Д]**; `aae doctor` проверяет каждый бинарник, его версию и состояние логина.

Подробно: `docs/design/config.md`, раздел «Loading»; `docs/guide/install.md`.

## 7. Харнессы

Харнесс для ядра — абстракция: всё знание о конкретном харнессе (протокол, вид его сбоев, опции, провайдеры, сокращения
моделей, проверки `doctor`) живёт в его адаптере. Новый харнесс — новый крейт и строка в таблице адаптеров корня сборки.
**[Р]** Адаптеров два; обобщённый ACP-адаптер и снятие известных пределов интерфейса драйвера — когда появится третий
харнесс.

Подробно: `docs/design/adapters.md`.

### 7.1 Интерфейс драйвера

Семантика повторяет ACP v2: состояние `running | idle | requires_action` и типизированная ошибка хода. **[Р]**

- Операции. Экземпляр: разделить конфиг на часть «на процесс» и «на сессию» и вычислить отпечаток; запустить; проверить
  здоровье; остановить. Сессия: начать, возобновить по непрозрачной ссылке, отправить промпт с ключом идемпотентности,
  отменить ход, ответить на запрос, закрыть. Транскрипт: существует ли он и доставлен ли промпт с данным ключом; живой
  отвод потока для просмотра.
- Адаптер шлёт нормализованные события с порядковым номером. Ядро принимает их по порядку: повтор отбрасывает, о разрыве
  сообщает событием `resync.diverged`. Всё сообщённое доходит до политики и наблюдателя (§5.4). **[Р]**
- Виды сбоя **[И 34]**: `quota_exhausted`, `rate_limited`, `overloaded`, `auth_required`, `billing`, `context_overflow`,
  `config_error`, `harness_crash`, `adapter_crash`, `daemon_crash`, `stall`, `runaway_turn`, `tool_failure`,
  `transcript_divergence`, `workspace_failure`, `hollow_done`, `unknown{text}`. `daemon_crash`, `stall`, `runaway_turn`,
  `workspace_failure` и `hollow_done` порождает ядро, остальные — адаптер (`adapter_crash` — при панике своей
  задачи-читателя). Ожидание человека и фоновая работа вне хода — состояния, а не сбои.
- В интерфейсе нет: steer посреди хода, смены модели внутри живой сессии, подключения человека. **[Д]**

Подробно: `docs/design/contracts.md`, раздел 4 (4.1–4.5).

### 7.2 Обязанности любого адаптера

- Закрыть ловушки «успешного провала». Известная для claude **[И 34]**: успех с признаком ошибки. Выход процесса с кодом
  0 без итога хода — сбой `harness_crash`.
- Границу «ход закончен» брать из авторитетного сигнала харнесса, а не из факта ответа на запрос.
- Сообщать, повторил ли харнесс запрос сам: поверх такого повтора политика не повторяет. claude повторяет сам; codex
  повторяет 429 только при заголовке `Retry-After`, без него повтор — за политикой **[И 34, 46]**.
- Запускать каждую сессию или экземпляр в своей группе процессов.
- Объявлять проверенный диапазон версий харнесса; вне его демон и `aae doctor` предупреждают.
- Объявлять провайдеров харнесса и таблицу сокращений моделей (§6.2). **[Р]**
- Доставлять окружение попытки (идентификатор прогона, токен попытки, actor трекера, сокет демона) инструментам сессии и
  её хукам харнесса.

Подробно: `docs/design/adapters.md`, раздел «What the core expects of a driver»; `docs/design/contracts.md`, 4.6.

### 7.3 Ленивый реестр экземпляров

- Ключ экземпляра — отпечаток (харнесс + «процессная» часть эффективного конфига). **[Р]** Экземпляр стартует при первой
  потребности, служит всем сессиям с тем же отпечатком и останавливается после простоя.
- Плагин, меняющий «процессную» часть конфига, даёт другой отпечаток и другой экземпляр. Плагин, работающий только на
  стороне оркестратора, экземпляров не плодит. **[Р]**
- У экземпляра есть предел числа сессий: падение общего процесса роняет все его сессии сразу **[И 21]**. Сверх предела
  поднимается второй экземпляр с тем же отпечатком. **[Д]**
- Тот же реестр обслуживает сервисы (§11.4).
- Что считается «процессным», решает адаптер: claude — процесс на сессию **[И 14]**; codex — один app-server на
  отпечаток и много тредов; opencode — выясняет спайк (§7.6).

Подробно: `docs/design/contracts.md`, раздел 8 и 4.6; память codex — `docs/design/experiments.md`, раздел «codex
app-server».

### 7.4 claude

- Транспорт: `claude -p` с потоковым JSON на вход и выход и заданным id сессии; возобновление — по id. Конфиг
  доставляется на сессию; полный набор, включая модель, передаётся и при каждом возобновлении.
- «Ход закончен» — это состояние idle без фоновых задач: субагенты claude по умолчанию фоновые **[И 46]**.
- Время сброса лимита приходит только при логине подпиской; при API-ключе лимит выглядит как `rate_limited` без времени
  сброса **[И 34]**.

Подробно: `docs/design/contracts.md`, 4.6 (claude); опыты — `docs/design/experiments.md`, разделы «claude protocol» и
«claude processes and background work».

### 7.5 codex

- Транспорт: собственный `codex app-server` на stdio, один на отпечаток, много тредов; общий демон codex пользователя не
  используется.
- Типы протокола не генерируются из схемы: адаптер читает используемые поля вручную, изменения ловят контрактные тесты
  (§7.8). **[Р]**
- Хуки харнесса исполняются с окружением процесса app-server, а не треда **[И 15]**. Окружение попытки они получают
  через `export` в начале команды хука; то, что токен попытки виден в её argv, принято. **[Р]**
- Песочница: адаптер ставит `sandbox_mode = "danger-full-access"`, если его не задал ни конфиг aae, ни конфиг хоста;
  `sandbox_mode` из конфига хоста сильнее этого умолчания. `doctor` и документация предупреждают. **[Р]**
- app-server помечен вендором `[experimental]`, релизы частые **[И 15]**: версия ведётся линией релизов (§13),
  обновление принимается контрактными тестами.

Подробно: `docs/design/contracts.md`, 4.6 (codex); `docs/design/experiments.md`, раздел «codex app-server»;
`docs/harness-updates.md`.

### 7.6 opencode — следующий выпуск

В исследовании не изучался. На машине стоит 2.1.1 (проверено 2026-11-12 по `opencode --help`): есть `opencode serve`
(HTTP API v2, флаг `--stdio`),

### 7.7 Человек и прогон

`aae` показывает прогоны, отдаёт живой поток прогона и принимает ответы на запросы разрешений. У каждой попытки видна
ссылка на сессию: после прогона человек открывает разговор средствами самого харнесса, без участия `aae`. Подключение
человека к живой сессии и передача управления — следующий цикл разработки **[Р]**: в первом выпуске для этого нет ни
операций, ни состояний, ни заглушек.

Подробно: `docs/api/frontends.md`, раздел «Humans and runs».

### 7.8 Контрактные тесты

На каждый адаптер — набор из 15 сценариев **[И 34 §9]** против настоящего бинарника харнесса с поддельным API провайдера
из репозитория (без затрат на LLM): 429 с последующим успехом; бесконечный 429; квота с временем сброса; квота
незнакомой формулировкой; 529/503; 401; `insufficient_quota`; переполнение контекста; несуществующая модель; `kill -9`
посреди команды; EOF на stdin посреди хода; молчание провайдера; запрос разрешения; фоновая задача после конца хода;
второй писатель в ту же сессию.

Набор идёт в CI и при каждом обновлении харнесса: обновление принимается, когда набор на нём проходит. У claude на
поддельном провайдере (логин API-ключом) время сброса квоты не приходит **[И 34]**: сценарий «квота с временем сброса»
ожидает для него `rate_limited` без времени.

Подробно: `docs/harness-updates.md`; `docs/design/adapters.md`, раздел «Contract suite».

## 8. Агенты и паки

### 8.1 Агент

Агент — общая роль (`coder`, `planner`): промпт роли, skills и умолчания настроек запуска. О конкретной задаче агент не
знает: её приносит пользователь входом формулы. **[Р]** В коде ядра нет ни одного имени роли: любое поведение роли —
конфигурация.

Всё, что относится к одному агенту, лежит в одном каталоге; деление на подкаталоги — по желанию автора. **[Р]**

Файлы агента: `agent.toml` (умолчания запуска, плагины, env, MCP, хуки, skills, режим разрешений) и `prompt.md` (промпт
роли).

- Настройки запуска в `agent.toml` — умолчания: их меняют пак, формула и пользователь (§6.3). **[Р]**
- Промпт обязателен. Он приходит от пользователя, из пака или из формулы либо наследуется по слоям; прогон без промпта
  не стартует, пустой файл роли и пустой шаблон — ошибка конфига. **[Р]**

**Вариант агента [Р].** Пользователь объявляет в конфиге оркестратора или проекта тот же агент пака под своим именем и с
другими настройками — любыми ключами настроек агента. Риг отображает имя агента из формулы на вариант:

```toml
[agents.codex-coder]
base     = "dev.coder"      # роль, промпт, skills — из агента пака
provider = "openai"
model    = "luna"

[rigs.backend]
path   = "../backend"
agents = { coder = "codex-coder" }   # в этом риге ссылку формулы на coder исполняет вариант
```

- Формулы пака по-прежнему ссылаются на `coder`; отображение живёт в риге.
- Вариант — отдельный агент для лимита параллелизма, ворот выдачи и событий.
- Второй путь к тому же результату — оверрайд без нового имени: `[rigs.backend.overrides.coder]`.

Подробно: `docs/design/config.md`, раздел «Agent».

### 8.2 Pack

Pack — единица содержимого, пригодного для любого проекта: агенты, формулы, триггеры. В паке нет ни слова о конкретной
задаче пользователя. **[Р]**

Файлы пака: `pack.toml` (имя, версия, требуемые плагины, минимальная версия aae, `[settings]`), `agents/`, `formulas/`.

- `[settings]` пака несёт только настройки запуска; они действуют на прогоны формул этого пака (§6.3). **[Р]**
- Источники: каталог на диске и внешний источник. **[Р]** Внешний источник — git-репозиторий; ревизия закрепляется в
  lock-файле проекта (`aae.lock`) командой `aae fetch`. **[Д]**
- Корень проекта сам является локальным паком: агенты и формулы можно класть прямо в проект. **[Д]**
- Имена уникальны в пределах пака; при совпадении между паками используется форма `<pack>.<имя>`. **[Д]**
- Pack может требовать плагины, но не содержит их.

Подробно: `docs/design/config.md`, разделы «Pack», «Names», «Packs and plugins from git».

## 9. Формулы, прогоны, триггеры

### 9.1 Формула

Формула отвечает на вопрос «как»: это процесс — шаги работы и чем её закончить. «Что» — конкретная задача — приходит
только вводом пользователя (входы прогона) и подставляется в шаблон. **[Р]**

Формула: имя, описание, объявленные входы и ровно один шаг. **[Р]**

Виды шага **[Р]**:

- `prompt` — ход агента в сессии харнесса. Исход сообщает финишер. Шаг может нести настройки запуска (`harness`,
  `provider`, `model`, `effort`). **[Р]**
- `exec` — команда без LLM, которую запускает демон: своя группа процессов, таймаут, рабочий каталог прогона. Исход — по
  коду возврата: 0 — `pass`; 75 (`EX_TEMPFAIL`) — временная недоступность **[И 21]**, то есть сбой попытки
  (`run.attempt_failed`), а не исход формулы; иное — `fail`. Хвост вывода ограниченного размера сохраняется в
  результате.

Требования:

- Контекст exec-шаг получает через окружение: `AAE_RUN`, `AAE_BEAD` (если есть), `AAE_INPUT_<NAME>` (строки как есть,
  остальное — JSON). Подстановки в саму команду нет. **[Р]**
- Типы входов (`string`, `integer`, `boolean`, `bead`) проверяются при старте прогона. **[Р]**
- Шаблон промпта — только подстановка переменных, без логики; отсутствующая переменная — ошибка до запуска. **[Д]**
  Пустой шаблон и промпт, пустой после подстановки, — ошибка (§8.1). **[Р]**
- `worktree = true` в формуле даёт каждому её прогону свой git-worktree; создаёт и убирает его aae (§11.5). **[Р]**

Подробно: `docs/design/config.md`, раздел «Formula»; язык подстановки — `docs/design/contracts.md`, 2.3.

### 9.2 Приёмка и тест — одно и то же

Отдельного «тестового режима» у продукта нет. Проверка формул и проверка самого `aae` — это одна исполняемая acceptance
spec: набор сценариев в репозитории, который реализует критерии §15. **[Р]**

- Сценарии идут тем же путём, что и рабочие прогоны: настоящий демон и настоящие бинарники харнессов.
- Сценарии с настоящей моделью идут на самой дешёвой модели и только по явной команде пользователя: прогон стоит денег и
  требует логина. Автоматически (на коммит, по расписанию) они не запускаются никогда.
- Сценарии без модели (поддельный провайдер, сценарный драйвер, exec-шаги) — те же сценарии той же spec; CI запускает
  это подмножество на каждый коммит.
- Результат — один отчёт с датой, версией `aae` и версиями харнессов (правило замеров, §14).

Подробно: `docs/guide/development.md`, раздел «Acceptance scenarios».

### 9.3 Прогон

Состояния:

```
queued → preparing → starting → running ⇄ requires_action → finishing → passed | failed{класс} | cancelled
                                   │                            │
                                   │                            └→ running (хук вернул агенту замечание)
                                   ├→ parked{ворота, причина} → starting
                                   └→ interrupted (рестарт демона) → решение по `run.attempt_failed`
```

- Класс провала различает причину: `agent` (финишер сказал `fail`), `check` (вето плагина), `hollow_done`,
  `infrastructure` (попытки исчерпаны или политика завершила прогон).
- `queued` — прогон ещё не стартовал: ждёт лимита параллелизма или открытия ворот (§5.7). `parked` — уже стартовавший
  прогон ждёт открытия ворот, процесса харнесса у него нет.
- Прогону нужен рабочий каталог. Риг берётся из входа, из триггера или из метки бида; нет рига — ошибка до запуска.
  **[Д]**
- Рабочий каталог по умолчанию занят одним живым прогоном: второй прогон в тот же каталог ждёт в `queued`. Параллельная
  работа в одном риге — через worktree (§11.5). **[Д]**
- Попытка — запуск новой сессии или возобновление прежней. У попытки своё поколение.
- Параллелизм ограничивается на уровне оркестратора и на уровне агента. **[Д]**
- Прогон может явно продолжить сессию другого завершённого прогона, чтобы сохранить контекст. **[Р]** Неявного
  переиспользования сессий нет.
- Рестарт демона прерывает только идущую попытку (`starting`, `running` в ходе, `requires_action`). Прогон, ждущий
  решения хука (`preparing`, `finishing`, ход без исхода, `interrupted`), ждёт его и после рестарта (§5.6).

**Дочерний прогон [Р].** Агент делит работу сам: запускает из своей сессии другие прогоны и ждёт их исхода.

- `aae run start …`, вызванный в сессии агента (в окружении есть идентификатор прогона и токен попытки), создаёт
  дочерний прогон: он наследует correlation родителя, его глубина на единицу больше, на него действует общий предел
  глубины цепочки (§9.5). Петля «планировщик запускает планировщика» упирается в этот предел.
- `aae run wait <id>…` ждёт терминального состояния всех названных прогонов по событиям, а не опросом, и печатает по
  каждому состояние, класс и причину провала, резюме и данные финишера. Код выхода 0 — все `passed`. У команды есть флаг
  таймаута.
- Отмена родителя отменяет его живые дочерние прогоны. **[Д]**

Подробно: `docs/design/contracts.md`, раздел 6 (состояния, переходы, дедлайны).

### 9.4 Исход

- Агент сообщает исход финишером: `pass` или `fail`, краткое резюме, необязательные данные. **[Р]** Данные сохраняются в
  результате прогона и доступны триггерам и ожидающему родителю.
- Финишер — команда CLI `aae` в сессии агента; идентификатор прогона и токен попытки приходят через окружение. **[Д]**
  Токен привязан к попытке: в ней действует последний вызов; финишер с токеном устаревшей попытки отвергается с явной
  ошибкой, состояние не меняется.
- Сбой инфраструктуры — не исход: он порождает `run.attempt_failed`, а не слово агента.
- Финишер посреди хода только записывает заявленный исход. Прогон завершается, когда ход закончился и фоновых задач
  (субагентов) нет; у ожидания фона есть дедлайн. **[Д]**
- Исход заявлен — `run.finishing`: хук может наложить вето (`failed` с классом `check`) или вернуть замечание. Замечание
  уходит агенту следующим промптом в той же сессии и той же попытке, прежний исход сброшен. Это и есть check-петля;
  число возвратов ограничено потолком ядра (инвариант 16). **[Д]**
- Исход не заявлен — `run.turn_ended_without_outcome`; без решения плагина — `failed` с классом `hollow_done`.
- Демон недоступен в момент вызова — команда повторяет попытки ограниченное время и завершается ошибкой. Демон
  перезапущен, пока прогон ждёт решения по `run.finishing`, — заявленный исход сохраняется (§5.6). **[Р]**

Из коробки `pass` — это слово агента. Проверку «работа действительно сделана» (коммит есть, тесты зелёные) ведёт внешний
цикл владельца; в комплект она не входит. **[Р]** Механизм вето для неё есть, плагина — нет.

Подробно: `docs/design/contracts.md`, 6.3 (таблица ситуаций финишера).

### 9.5 Триггеры

Три способа запустить прогон, все в ядре **[Р]**: явный вызов через API, CLI или MCP; подписка на событие (тип события,
фильтр `where`, формула, отображение полей события во входы); расписание (cron или «не чаще чем раз в интервал»).

- Триггеры объявляются в паке и в проекте. Риг триггеру назначает проект, а не пак: пак не знает имён ригов.
- Срабатывание идемпотентно: ключ (триггер, `seq` события). Сопоставление идёт в транзакции события, а не по журналу
  JSONL, поэтому `kill -9` демона не теряет и не удваивает срабатывания.
- Прогон, запущенный триггером, наследует correlation от породившего события. Событие трекера несёт correlation того
  прогона, чья попытка сделала запись (по actor, §10.2); запись человека начинает новую цепочку. **[Д]**
- Защита от петель — по глубине «прогон породил прогон» (триггером или из сессии агента, §9.3), а не по числу прогонов в
  цепочке: длинный эпик законен. Предел глубины — 10. Готовый бид — следующая работа трекера, а не порождённый прогон:
  `bead.ready` глубину не добавляет. Повтор над одним и тем же бидом ограничивает счётчик неудач бида (§10.3). **[Д]**
- Наложение: пока жив прогон, запущенный этим триггером с тем же ключом входов, новое срабатывание пропускается с
  событием `trigger.skipped`. **[Д]**
- После простоя демона пропущенное расписание срабатывает не более одного раза **[И 21]**. `cron` считается в часовом
  поясе системы; ключ `timezone` в конфиге оркестратора его переопределяет. **[Р]**
- События трекера: `bead.created`, `bead.updated`, `bead.closed`, `bead.ready`. `bead.ready` порождается, когда бид
  впервые попадает в список готовых: открыт, никем не занят, все его блокеры закрыты. **[Д]**
- Оператор включает и выключает триггер и может сработать его вручную.

Язык `where` и `inputs`, таймауты хуков и срок жизни записей outbox — контракт: записаны в `docs/design/contracts.md`
(разделы 2 и 3) и не меняются без слома **[И 32]**.

Подробно: `docs/design/config.md`, раздел «Trigger» (форма объявления, переходы часов).

## 10. Трекер

### 10.1 Интерфейс

Трекер — адаптер с узким интерфейсом; проект может работать без трекера. **[Д]** Операция добавляется в интерфейс,
только когда она нужна вызывающему **[Р]**: claim, условный возврат, закрытие, список готовых, поток изменений.

Подробно: `docs/design/contracts.md`, раздел 5.

### 10.2 br

- `br` — внешний бинарник: ставится отдельно через mise и объявлен зависимостью там же. **[Р]** `aae` его не поставляет,
  не линкует и не вендорит.
- Лицензия br — «MIT с райдером OpenAI/Anthropic» **[И 11 §2.7]**. Явное предупреждение об этом стоит везде, где
  пользователь встречает br **[Р]**: в README, в документации по установке и в выводе `aae doctor`.
- Одна БД на проект в `<project>/.beads`, вне git ригов; риг — метка `rig:<имя>`. **[Р]**
- Путь к БД задаётся явно в каждой сессии и каждом вызове: без него br молча пишет в чужой трекер **[И 11]**.
- У каждой попытки свой actor: по нему br различает владельцев claim, а `aae` — correlation записей агента.
- Событий у br нет: изменения через `aae` порождают события сразу, внешние ловятся слежением за файлом БД.
- В трекер не пишется ничего служебного: ни прогоны, ни шаги, ни сессии.
- Версия br для разработки закреплена точно; адаптер объявляет проверенный диапазон версий. У адаптера свой набор
  контрактных тестов: claim под конкуренцией, условный возврат, закрытие, список готовых в эпике.

Подробно: `docs/design/tracker-br.md`; источник событий — `docs/design/experiments.md`, раздел «br as an event source».

### 10.3 Бид и прогон

- Прогон может получить бид входом; прогоны без бида разрешены. **[Р]**
- Claim, возврат и закрытие делает демон. **[Р]** Claim держится весь прогон, через все его попытки. В терминальном
  состоянии: `passed` — бид закрывается; `failed` и `cancelled` — возвращается условно.
- Цепочки нескольких формул над одним бидом нет: `pass` всегда закрывает бид. Работа режется на биды, а следующий
  берётся подбором «следующий готовый бид», в том числе в пределах эпика. **[Р]**
- Вход «следующий готовый» (необязательно с эпиком): выбор и claim демон делает одной операцией. Готовых нет — прогон не
  создаётся, вызывающий получает явный ответ «нечего брать». **[Д]**
- У бида не более одного живого прогона-владельца. Явно указанный бид с меткой `rig:` другого рига отвергается. **[Р]**
- Счётчик неудач бида: после заданного числа прогонов, завершившихся `failed` над бидом, ядро закрывает ворота выдачи по
  этому биду (§5.7); подбор его пропускает, пока человек не снимет ворота. **[Д]**
- Владение в состоянии оркестратора — истина; поле владельца в br — её отражение. Неудача закрытия или возврата в br
  исход прогона не меняет: операция повторяется, расхождение видно событием.

Подробно: `docs/design/tracker-br.md`, раздел «Beads and runs».

## 11. Плагины

### 11.1 Назначение

Плагин — единица расширения. Типовые расширения делаются плагинами, а не кодом ядра. **[Р]** Плагин — каталог с
`plugin.toml` (имя, версия, параметры, вклад в агентов, хуки оркестратора, сервисы) и своими `skills/`, `hooks/`,
`bin/`.

Подробно: `docs/guide/plugin.md`; `docs/design/config.md`, раздел «Plugin».

### 11.2 Сторона агента — декларативная

Плагин добавляет подключившему его агенту: skills, хуки харнесса, MCP-серверы, переменные окружения, скрипты в `PATH`,
фрагменты промпта, родные для харнесса части. Вклад получают только агенты, которые плагин подключили. **[Р]** Хуки
харнесса пишутся в диалекте Claude; claude и codex исполняют его нативно **[И 18]**. Вклад в «процессную» часть конфига
харнесса даёт агенту отдельный экземпляр (§7.3).

Подробно: `docs/guide/plugin.md`, раздел «The agent side».

### 11.3 Сторона оркестратора — exec-хуки

Плагин вешает команды на события ядра. **[Р]**

- Контракт — диалект хуков Claude: событие JSON на stdin; код 0 — «нет возражений»; код 2 — блокировка с причиной в
  stderr; JSON на stdout — решение для решающих событий (§5.4).
- Хук не имеет состояния и исполняется вне цикла ядра. Падение или таймаут хука не роняет демон и порождает
  `plugin.hook_failed`. Отказ хука-вето блокирует, отказ наблюдающего игнорируется. **[Д]**
- Несколько плагинов на одном событии: для вето достаточно одной блокировки; для выбора реакции на сбой действует первое
  решение в порядке подключения. **[Д]**
- Всё, что нужно политике (счётчики попыток, времена, состояние ворот, последний известный лимит аккаунта), уже есть в
  событии. Хранилища для плагинов в ядре нет.
- Решающее событие ждёт решения и после рестарта демона: хук запускается заново (§5.6), поэтому хуки идемпотентны.
- Хуки и сервисы стороны оркестратора включаются на уровне оркестратора или проекта.

Подробно: `docs/design/contracts.md`, раздел 3; `docs/guide/plugin.md`, раздел «The orchestrator side».

### 11.4 Сервисы

Сервис — долгоживущий процесс под супервизией: команда, область совместного использования (оркестратор, проект),
проверка здоровья; MCP у него — по желанию. **[Р]** Объявляется в конфиге или в плагине и живёт в том же ленивом
реестре, что и экземпляры харнессов.

Общий MCP **[Р]**:

- MCP-сервер один на область, а не на сессию. Сессии получают его URL и заголовки идентичности: проект, риг, агент,
  прогон **[И 36]**.
- Сервер, который отдаёт сам `aae`, и любой рекомендуемый общий сервер понимают обе эпохи протокола MCP.
- stdio-сервер делится между сессиями только через мост stdio→HTTP; мост входит в первый выпуск **[Р]** и не является
  частью ядра. Сервер с неявным состоянием на клиента делить нельзя: ему область «сессия» задаётся явно.
- Перезапуск сервиса быстрый; сбой MCP — это сбой инструмента, а не провал прогона **[И 36]**.
- Общий сервис слушает unix-сокет либо loopback с токеном **[И 18]**.

Подробно: `docs/design/config.md`, раздел «MCP servers and services»; `docs/design/contracts.md`, раздел 8.

### 11.5 Плагины в комплекте

Поставляются внутри бинарника как встроенные исполнители хуков (внешний рантайм не нужен). В бюджет ядра не входят:
считаются по своей строке бюджета и входят в общий лимит выпуска (§14). **[Д]**

| Плагин | Что делает |
|---|---|
| `default-policy` | Реакции на сбои — «дешёвые страховки» **[И 21 §4.2]**: resume после краша; после нескольких отказов самого resume — новая сессия; при квоте — закрыть ворота аккаунта до времени сброса; backoff на 429 для харнессов, которые не повторяют сами; при серии крашей — закрыть ворота агента; лестница для `stall`; одно напоминание при конце хода без финишера. Включён по умолчанию, отключаем; пороги меняются в его конфиге. Работает только на стороне оркестратора и харнесс не меняет **[Р]** |
| `worktree` | На `run.preparing` создаёт git-worktree для прогона и подставляет рабочий каталог; после завершения удаляет, только если коммиты достижимы из refs. Включается только ключом формулы `worktree = true`; центральных списков агентов и формул и включения на уровне агента нет **[Р]** |

Правила `default-policy` **[Р]**:

- `auth_required` и `billing`: повторы с ростом паузы до раза в час, без повышения до человека; ожидание идёт на воротах
  аккаунта и потолок попыток не расходует (инвариант 16).
- `quota_exhausted` без времени сброса в самом сбое: ворота аккаунта закрываются до времени сброса последнего известного
  лимита аккаунта, если он исчерпан. `rate_limited` при исчерпанном лимите аккаунта — тоже ворота аккаунта до сброса, а
  не короткий backoff.

Граница: механизмы — в ядре (возобновить, начать новую сессию с сохранением владения, ворота выдачи, счётчики, потолок
попыток, сторож, дедлайны); выбор реакции и её пороги — в плагине. Без `default-policy` действует колонка «без решения
плагина» из §5.4.

Подробно: `docs/design/config.md`, раздел «Bundled plugins»; `docs/design/contracts.md`, раздел 10; первоисточники
порогов — `docs/init/aae-context/06-failure-policy-defaults.md`.

### 11.6 Доверие

Плагин исполняет произвольные команды с правами пользователя. Установка и включение — явные действия; плагин из git
работает только на ревизии из lock-файла; автообновления нет. **[Д]**

## 12. Фронтенды

Три адаптера над одним типизированным интерфейсом ядра. **[Р]**

| Фронтенд | Поверхность | Требования |
|---|---|---|
| **HTTP API** | полная | unix-сокет по умолчанию; TCP — только по явному включению, loopback и токен. JSON; поток событий и живой просмотр прогона — SSE с продолжением по `seq`. Спецификация OpenAPI генерируется из кода и проверяется на расхождение. Мутирующие операции принимают ключ идемпотентности |
| **CLI** | полная | тонкий клиент HTTP API в том же бинарнике. У каждой операции API есть команда CLI — проверяется тестом. Везде есть машинный вывод JSON. Без демона работают запуск демона, `doctor`, `fetch`, проверка и объяснение конфига, версия |
| **MCP** | малая | только частое: список формул, запуск формулы, состояние прогона, список прогонов, отмена — пять инструментов **[Д]**. HTTP-транспорт в демоне, обе эпохи протокола |

Полная поверхность API и CLI: проекты и риги; агенты, формулы, паки, плагины (список, проверка, объяснение конфига);
прогоны (запуск, список, состояние, живой просмотр, ожидание исхода, отмена, ответ на запрос, финишер); триггеры
(список, включение, ручное срабатывание); экземпляры и сервисы (список, остановка); ворота выдачи (список, закрыть,
снять — пауза оркестратора, проекта, агента, бида); события; перечитывание конфига; демон (состояние, дренаж, рестарт);
`doctor`.

Ожидание исхода — `aae run wait <id>…` (§9.3): по событиям, не опросом. **[Р]**

MCP-сервер `aae` не подключается ко всем агентам подряд: описания инструментов стоят токенов в каждой сессии. Агент
получает его, только если это задано в его конфиге. **[Д]** Набор инструментов MCP не расширяется: агент, которому нужно
больше (планировщик), пользуется CLI. **[Р]**

Подробно: `docs/api/frontends.md`, `docs/api/mcp.md`, `docs/api/openapi.json`.

## 13. Поставка

- Один бинарник `aae` на Rust: демон, CLI и встроенные плагины. Цели: linux x86_64 и arm64 (статическая линковка), macOS
  x86_64 и arm64. **[Р]** Приёмка — только на хосте владельца (Linux arm64). **[Р]**
- Внешние зависимости времени исполнения: только бинарники харнессов и, если нужен трекер, `br`. Ими управляет mise.
  **[Р]** Сам `aae` бинарники не скачивает и не устанавливает.
- В репозитории `mise.toml` задаёт инструменты сборки и `br` точными версиями, claude и codex — линией релизов (`2.1`,
  `0`); `mise.lock` нет. **[Р]** Задачи разработки запускаются через mise. **[Д]**
- Обновление харнесса у пользователя — его забота; в репозитории — забота разработчика aae (§7.8). **[Р]**
- Внешние паки и плагины — каталоги из git, закреплённые ревизией в lock-файле проекта (§8.2, §11.6); mise их не
  касается. Скачивает их отдельная команда CLI; ядро читает только готовые каталоги на диске. **[Д]**
- Лицензия MIT; зависимости — только с совместимыми лицензиями; код br и bv в дерево не попадает. Репозиторий публичный:
  никаких секретов и абсолютных путей машины владельца. **[Р]**
- Каталоги — по XDG. Демон запускается в foreground; файлы сервиса для systemd и launchd генерируются командой; неявного
  автозапуска из CLI нет. **[Д]**
- `aae doctor`: харнессы (путь, версия, логин), br (версия), права на каталоги, здоровье состояния. Работает без демона;
  те же проверки из работающего демона отдаёт API.
- Документация для пользователя: установка, первый проект, первая формула, написание плагина.

Подробно: `docs/guide/install.md`, `docs/guide/development.md`.

- Лимит — потолок, а не цель: меньше кода — лучше (§1).
- Считаются строки кода без пустых и без комментариев одним инструментом, зафиксированным в репозитории; тесты и
  сгенерированный код исключаются по путям. **[Д]**
- Файл — не более 400 строк. **[Д]**
- Превышение лимита выпуска блокирует выпуск; превышение жёсткого стопа останавливает добавление функций до ревизии с
  удалением.
- Если бюджет не сходится, первыми уходят **[Д]**: загрузка паков из git (остаются локальные каталоги); продолжение
  сессии другого прогона; файл рабочего пространства `bv`. Не вырезается: инварианты §5.5, финишер, ворота выдачи,
  восстановление, «объясни конфиг», контрактные тесты, мост stdio→HTTP.
- Код опытов (`experiments/`) — вне этих бюджетов, но в сумме не больше 5 000 строк. **[Р]**

Сроков и календарных бюджетов в постановке нет. **[Р]**

**Правила кода:**

- **Без заглушек и без кода «на вырост». [Р]** Не пишутся: пустые реализации, `todo`-ветки, неиспользуемые параметры,
  поля, флаги и точки расширения под будущие функции, обобщения под единственный случай. Всё, что постановка называет
  отложенным (§1.1), в коде отсутствует полностью.
- Нет механизма без применения. У каждой функции есть запись, какой критерий §15 или какая реальная работа её
  использует; функция без такой записи к моменту выпуска удаляется.
- Перед каждым новым механизмом — проверка, нет ли его уже у вендора харнесса.
- Ревью до основной ветки. Временные логи рабочего процесса в репозиторий не коммитятся; история git не переписывается.
  **[Р]**
- У каждого отдельного каталога вроде `experiments/*`, `demos/*`, `examples/*` — короткий README: что там и зачем.
  **[Р]**

**Правила тестов:**

- Тесты — против настоящих бинарников харнессов. Поддельный драйвер допустим только сценарный (задержка, конец хода без
  исхода, ошибка провайдера, код 75, зависание, обрыв канала посреди хода, запрос разрешения, событие вне хода) или как
  запись настоящих транскриптов **[И 21 §4.4]**.
- Детерминированная проверка инвариантов §5.5: управляемые часы, seed, проверка после каждого шага.
- Инъекция сбоев: `kill -9` демона на каждой границе транзакции и между записью в состояние и вызовом трекера;
  восстановление обязано сойтись.
- Проверка идемпотентности: любая операция, применённая дважды, и любое событие, доставленное дважды или не
  доставленное, дают то же конечное состояние.
- **Никаких залоченных сидов. [Р]** Тест проходит на любом сиде, а не на заранее известном наборе. Случайные стенды
  берут новый базовый сид при каждом прогоне и печатают его; повтор упавшего — по напечатанному сиду. Диапазон сидов,
  подобранный под зелёный прогон, запрещён.
- **Быстрые тесты — приоритет над новыми функциями. [Р]** Медленный или нестабильный набор чинится раньше, чем строится
  новое: скорость, флейки, случайные сиды, ожидание событий вместо ожидания времени.
- Раскладка **[Р]**: unit- и интеграционные тесты гоняются локально, acceptance без модели — в CI на каждый коммит.
- **Живые модели. [Р]** В CI доступа к LLM нет — это архитектурное решение. Контрактные тесты на живом харнессе, опыты,
  сценарии «запрос» и демо идут только на машине разработчика по явной команде, на самой дешёвой модели каждого харнесса
  и точечно: до запуска понятно, что проверяется; после — записан итог. Намеренно сжигать квоту ради проверки запрещено.
- Обновление харнесса или `br` принимается контрактными тестами (§7.8, §10.2).

**Отчёт о готовности. [Р]** Исполнитель ведёт в репозитории один файл (`docs/READINESS.md`) со шкалой готовности каждого
компонента и обновляет его в конце каждого рабочего сеанса. Оценка — целое от 0 до 10 по опорным точкам:

| Балл | Что это значит |
|---|---|
| 0 | ничего нет |
| 2 | контракт компонента записан (типы, события, ошибки), кода нет |
| 4 | код есть, основной путь работает вручную |
| 6 | тесты без модели зелёные, включая пути сбоев |
| 8 | относящиеся к компоненту критерии §15 зелёные на хосте владельца |
| 10 | компонент отработал демо без вмешательства (критерий 20) |

- Оценка ставится по букве шкалы. Критерий компонента, который не проходит или не запускался, — потолок его балла: такой
  компонент не получает 8 и выше; 10 — только при зелёном критерии 20. **[Р]**
- Промежуточные баллы допустимы; рядом с каждой оценкой — одна строка «чего не хватает до следующей точки» и список
  критериев компонента.
- Оценка — это замер: у неё дата, короткий sha и маркер `MEASURE`; sha не старше последнего изменения кода.
- Компоненты: цикл событий и состояние; прогоны и финишер; триггеры и расписание; ворота выдачи; восстановление; сборка
  конфига; реестр экземпляров и сервисов; адаптер claude; адаптер codex; адаптер br; исполнение хуков плагинов;
  `default-policy`; `worktree`; общий MCP; HTTP API; CLI; MCP-фронтенд; acceptance spec; поставка и `doctor`.

**Правило замеров. [Р]** Любой замер (время, память, размер, количество, доля), где бы он ни появился — в документации,
отчёте acceptance spec, комментарии к порогу в коде или описании PR, — несёт:

- видимую дату замера;
- видимую версию измеренного: версию бинарника или короткий sha;
- невидимый комментарий рядом для того, кто будет править: идентификатор замера, источник, условия, что перемерить.

Формат комментария один на весь проект, чтобы его находил один `grep`:

```
<!-- MEASURE id=<слаг> date=<ГГГГ-ММ-ДД> ver=<версия или sha> env=<ОС и стенд> src=<откуда> note="<условия; что перемерить>" -->
```

В коде тот же маркер пишется в синтаксисе комментария языка. Замер без даты и версии считается дефектом документа. CI
проверяет, что у каждого маркера заполнены `id`, `date`, `ver` и `env`; замер, у которого маркера нет вовсе, CI найти не
может — это проверяет ревью.

**Остановиться и пересмотреть, если:**

- превышен жёсткий стоп по строкам;
- обновления харнессов раз за разом ломают контрактные тесты и съедают больше работы, чем сам продукт;
- вендор вводит отдельную оплату headless-режима, которая делает путь без TUI неприемлемым для владельца;
- штатные средства вендоров покрывают подавляющую часть реально используемых формул.

## 15. Критерии приёмки первого выпуска

Критерии реализуются как исполняемая acceptance spec (§9.2): она и есть приёмка. **[Р]** Колонка «Запуск»:

- **CI** — сценарий без модели; входит в spec и дополнительно идёт в CI на каждый коммит;
- **запрос** — сценарий с настоящей моделью либо долгая сборка; идёт только при явном полном запуске spec.

Все строки таблицы, включая проверки, которые живут в cargo-тестах и CI-скриптах, попадают в один отчёт приёмки. **[Р]**
Числовые пороги предложены автором и правятся владельцем. **[Д]** Ориентиры исследования мягче: хоп p50 ≤ 3 с и p90 ≤ 10
с, инфраструктура в простое ≤ 150 МБ (`FINAL-REPORT.md` §5.3). Плагин `default-policy` во всех сценариях включён, если
не сказано иное.

Платформа **[Р]**: приёмка идёт только на хосте владельца — Linux arm64. Остальные три цели только собираются; их
работоспособность не проверяется и принимается на веру в переносимость языка.

### Демо (критерий 20)

Демо «планировщик — исполнители» **[Р]** повторяет базовую возможность субагентов: пользователь рассказывает, что он
хочет; агент-планировщик делит работу и раздаёт её исполнителям в ригах. Каталог `demos/` — минимальные живые примеры:
пак, конфиги пользователя и то, что агенты сделали, без мусора сборки. У каталога свой `mise.toml` с задачами демо: они
требуют логина харнессов и тратят реальные токены, поэтому идут только на машине разработчика; CI проверяет только, что
конфиги демо загружаются. У каждого демо — короткий README.

```
demos/dev-pack/                 пак dev: агенты planner и coder, формулы plan и code — без единого слова о задаче
demos/snake-claude/root/        корневой репозиторий: config.toml (оркестратор), aae.toml (проект, риги, настройки),
                                REQUEST.md (рассказ пользователя), smoke.sh (проверка итога)
demos/snake-claude/backend/     риг: пустой репозиторий до прогона
demos/snake-claude/frontend/    риг: пустой репозиторий до прогона
```

- Запуск — одна команда пользователя: `aae run start snake-claude root dev.plan --input request="$(cat REQUEST.md)"`.
- Задача в `REQUEST.md`: игра «змейка» в браузере, бэкенд хранит лучшие счета в plain text; без зависимостей и сборки.
  Задача живёт только в запросе пользователя, не в паке.
- `dev.plan` (агент `planner`) работает в риге `root`, чтобы не занимать риги исполнителей: читает запрос, смотрит,
  какие риги есть в проекте, делит работу, для каждой части запускает `dev.code` в нужном риге с текстом задачи и ждёт
  исходы (`aae run wait`). При провале части решает сам: переформулировать и запустить ещё раз либо завершиться `fail`.
  Завершает прогон сводкой.
- `dev.code` (агент `coder`) получает вход `task`, делает работу в своём риге, проверяет её и завершает прогон резюме и
  данными, нужными соседям (например, адрес API).
- Проверка итога — `smoke.sh` корневого репозитория: exec-формула локального пака проекта и триггер на `run.passed`
  формулы `dev.plan`. Это проверка пользователя, а не часть пака. Код 0 — демо прошло.
- **Демо 1** (`demos/snake-claude/`): все агенты на claude, модель `haiku`.
- **Демо 2, смешанные харнессы** (`demos/snake-mixed/` с теми же `root`, `backend`, `frontend`): тот же пак; отличается
  только `root/aae.toml` — вариант `codex-coder` на провайдере openai (модель `luna`) и отображение для рига `backend`.
  README показывает и второй путь — оверрайд.
- Результат прогона (содержимое ригов и `RESULT.md` с маркером `MEASURE`) сохраняется в каталоге демо как снимок.

  Исполнителю отчёты не нужны: всё нужное из них вынесено в шпаргалки и документацию проекта.
