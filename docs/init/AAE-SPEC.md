## 1. Что строим

`aae` — событийный оркестратор агентов-кодеров («программная фабрика»): демон уровня машины, который по запросу
запускает **формулы** на **агентах** в **ригах** (репозиториях) **проектов** и доводит прогоны до явного исхода,
переживая сбои харнессов, лимиты и собственные рестарты.

Продукт пишется с нуля. Опыт проекта-предшественника используется как знание (инварианты, классы сбоев, ошибки); код не
наследуется, сам предшественник в коде и документации по имени не называется. **[Р]**

Четыре свойства определяют форму продукта **[Р]**:

1. **Очень лёгкое ядро.** В ядре только то, без чего прогон нельзя корректно запустить, наблюдать и завершить. Всё
   остальное — адаптеры (харнессы, трекер, фронтенды) и плагины.
2. **События, а не тики.** Ни одна единица работы не ждёт таймера опроса: задержка от причины до реакции не зависит ни
   от какого интервала. Запрещён опрос как способ ожидания работы; страховочные таймеры (сторож сирот, проверка здоровья
   экземпляра, resync) допустимы.
3. **Нативные протоколы харнессов без tmux.** Экран терминала не является каналом управления ни в каком виде.
4. **Меньше кода — лучше.** Пишется только то, что нужно описанному здесь результату. Никаких заглушек, никаких точек
   расширения и кода «на вырост», никаких полей и флагов под будущие функции. Отложенное названо отложенным (§1.1) и в
   коде не присутствует вовсе.

Поставка: один бинарник `aae` под linux и macOS, x86_64 и arm64. Репозиторий публичный, лицензия MIT. **[Р]**

### 1.1 Чего в первом выпуске нет

| Не входит | Почему и что вместо |
|---|---|
| Молекулы, wisps, конвои, control-биды | **[Р]**. Цепочки собираются шагами формулы (§9.1), подписками на события (§9.5) и дочерними прогонами (§9.3) |

| Постоянно живущие агенты | **[Р]**: сессия на прогон |
| Почта и nudge между агентами | **[Р]**: отдельный модуль-плагин позже |
| Хранение сессий и транскриптов | **[Р]**: это задача харнесса; ядро хранит ссылку «харнесс + id» |
| opencode | **[Р]**: следующий выпуск, после спайка (§7.6) |
| pi и прочие харнессы | вне списка владельца |
| ACP как транспорт «вниз» | **[Р]**: нативные протоколы; интерфейс драйвера повторяет семантику ACP v2, чтобы ACP-драйвер стал ещё одной реализацией |
| Подключение человека к живой сессии и передача управления | **[Р]**: следующий цикл разработки. В первом выпуске нет ни её, ни заглушек под неё. Человек видит ссылку на сессию в состоянии прогона и после его завершения открывает разговор средствами самого харнесса (§7.7) |
| ACP-хаб «вверх» для редакторов | **[Д]**: владелец этого не обсуждал |
| Human gate как шаг формулы | его роль выполняют запрос разрешения (§7.7) и удержание оператора (§5.7) |
| Web-интерфейс, dashboard | панель задач — `bv`; наблюдение — CLI и поток событий |
| Алертинг: уведомление человека о сбое | **[Р]**: только журнал событий и логи |
| Windows, несколько машин, несколько пользователей | локальный однопользовательский демон **[Д]** |
| Проверка и приёмка на macOS и на x86_64 | **[Р]**: приёмка идёт только на хосте владельца (Linux arm64); остальные цели собираются, их работоспособность принимается на веру в переносимость языка |
| Готовая проверка «работа действительно сделана» в комплекте | **[Р]**: проверка — шаг формулы, скрипт или агент (§9.1); её пишет автор пака или проекта |
| Сроки и календарные бюджеты | **[Р]**: работу ведут агенты, сроков в постановке нет |
| Ротация аккаунтов и failover между подписками | зона политического риска **[И 34]**; не ядро |
| Трансляция хуков между диалектами харнессов | у claude и codex формат хуков почти общий **[И 18]**; транслятор — когда появится третий диалект |
| Обобщённый ACP-адаптер, один адаптер на несколько харнессов | **[Р]**: когда появится третий харнесс (§7) |
| Настройка поставщика модели отдельно от харнесса | **[Р]**: пользователь называет харнесс; поставщик внутри харнесса — его родные настройки (§6.2) |
| Цепочка нескольких формул над одним бидом | **[Р]**: не критична; `pass` закрывает бид (§10.3) |
| Демо «aae разрабатывает себя» | роадмап: сетап агентов этого репозитория как пак aae |
| Миграция данных и паков из проекта-предшественника | отдельная задача |

## 3. Словарь

| Термин | Смысл в aae |
|---|---|
| **оркестратор** | демон `aae` и его настройки уровня машины |
| **проект** | каталог с `aae.toml`: корень, набор ригов, паков, плагинов и одна БД трекера |
| **корень** | каталог с `aae.toml`, корневой репозиторий проекта: здесь лежат конфиг, файлы агентов от проекта и трекер. Имя по умолчанию — `root` |
| **риг** | репозиторий проекта на диске плюс его префикс бидов и переменные (`test_cmd`, `lint_cmd` и т. п.) |
| **харнесс** | вид agent-CLI: `claude`, `codex`, позже `opencode`. Ему соответствует один адаптер |
| **экземпляр харнесса** | запущенный процесс харнесса (app-server или процесс сессии), который обслуживает одну или несколько сессий |
| **агент** | общая роль (`coder`, `planner`): промпт роли, шаблон промпта, skills, область и умолчания настроек запуска. О конкретной задаче агент не знает. Ролей в коде ядра нет |
| **область агента** | `rig` — агент работает в каталоге одного рига; `root` — в корне, над всеми ригами проекта |
| **настройки запуска** | три скаляра: харнесс, модель, effort (§6.2) |
| **сокращение модели** | имя семейства (`opus`, `luna`), которое адаптер раскрывает в последнюю версию модели этого семейства |
| **вариант агента** | агент пака под другим именем и с другими настройками, объявленный в конфиге пользователя (`claude-coder`, `codex-coder`) |
| **ссылка на сессию** | пара «харнесс + id сессии у харнесса». Единственное, что ядро знает о разговоре |
| **формула** | воркфлоу — «как»: имя, описание, входы и шаги по порядку. «Что» — задача — приходит только от пользователя |
| **шаг** | `ai` (ход агента), `exec` (команда без LLM), `drain` (выдача бидов исполнителям) или `formula` (другая формула) |
| **задача** | текст, который пользователь даёт формуле при запуске: что сделать. Либо называет существующий бид, либо становится новым корневым бидом |
| **прогон** (run) | исполнение формулы с конкретными входами; имеет попытки и исход |
| **дочерний прогон** | прогон, запущенный шагом `drain` или `formula` другого прогона либо из сессии его агента; наследует его correlation |
| **попытка** (attempt) | один запуск или возобновление сессии в рамках прогона |
| **финишер** | вызов, которым агент сообщает исход прогона |
| **триггер** | правило «событие или расписание → запустить формулу» |
| **correlation** | идентификатор цепочки прогонов, порождённых друг другом |
| **pack** | содержимое, пригодное для любого проекта: агенты, формулы, триггеры |
| **plugin** | расширение: то, что подключается к агентам (skills, hooks, MCP, скрипты, env), хуки на события оркестратора, сервисы |
| **сервис** | долгоживущий процесс под супервизией оркестратора (например, общий MCP-сервер) |
| **ворота выдачи** | запись «по этому ключу прогоны не запускать до времени или до ручного снятия» (§5.7) |
| **трекер** | хранилище задач за интерфейсом-адаптером; первая реализация — br |
| **бид** | задача в трекере. Только настоящая работа, никаких служебных записей |
| **корневой бид** | бид с задачей пользователя; под ним — все биды, заведённые по этой задаче |
| **событие** | запись о случившемся; повод перечитать состояние, а не истина |

## 4. Архитектура

```
                 HTTP API (полная)   CLI (полная)   MCP (малая)
                        └───────────────┼───────────────┘
                                 фронтенд-адаптеры
                                        │  команды / запросы / поток событий
┌───────────────────────────────────────▼──────────────────────────────────────┐
│ ЯДРО: один писатель состояния                                                 │
│  входная очередь → обработка в транзакции SQLite → события (outbox)           │
│  прогоны и попытки · триггеры и таймеры · сборка конфига · реестр экземпляров │
│  исполнение exec-хуков плагинов · владение бидом · восстановление и resync    │
└───────┬───────────────────────┬──────────────────────┬───────────────────────┘
        │ интерфейс драйвера    │ интерфейс трекера    │ события → журнал JSONL
  адаптеры харнессов        адаптер br             плагины (exec-хуки, сервисы)
  claude │ codex │ (opencode)
```

Границы, которые проверяются сборкой, а не договорённостью:

- Ядро не зависит ни от одного адаптера, фронтенда или плагина. В `aae-core` нет имён харнессов, имён ролей, вызовов
  `br` и знаний о них (`codex`, `max_sessions`, `BEADS_DIR`, `.beads`): они приходят через способности драйвера и
  интерфейс трекера. CI проверяет это поиском по исходникам ядра. **[Р]**
- Харнесс для ядра — абстракция. Корень сборки держит одну таблицу адаптеров; кроме неё, харнесс в корне не назван
  нигде. **[Р]**
- Фронтенды и адаптеры харнессов только переводят протоколы. Подробно: `docs/api/frontends.md` (вступление),
  `docs/design/adapters.md` раздел «What the core expects of a driver».
- Решения-политики (повторить, припарковать, отклонить) лежат в плагинах и конфиге. Суждения («сделано ли хорошо») — в
  промптах и проверках плагинов. В ядре — только механизмы.

Адаптеры в первом выпуске — модули того же бинарника за общим интерфейсом. Собственный межпроцессный протокол для
адаптеров не изобретается: внешний путь подключения харнессов в будущем — обобщённый драйвер ACP v2. **[Д]**

Подробно: `docs/design/adapters.md`.

## 5. Ядро

### 5.1 Событийная модель

Всё, что происходит, входит в ядро сообщением единственному писателю и обрабатывается в одной транзакции SQLite вместе с
порождёнными событиями (outbox); эффекты выполняются после фиксации **[И 21]**. Таймеры — дедлайны, а не опрос: задержка
от события до реакции ядра не содержит ожидания интервала (§15, хоп); страховочные таймеры — сторож сирот, проверка
здоровья экземпляра, resync — в штатной работе ничего не продвигают. **[Р]** Подробно: `docs/design/event-model.md`
(resync — раздел «Resync»).

### 5.2 Состояние

Подробно: `docs/design/event-model.md`, раздел «State».

### 5.3 Журнал событий

JSONL, ротация по размеру: 10 МБ на файл, 5 файлов. **[Р]** Журнал и монотонный счётчик `seq` — одни на оркестратор, для
всех проектов. **[Д]** Содержимое разговора ядро не сохраняет: живой просмотр — прямая ретрансляция
потока адаптера, история — в транскрипте харнесса. **[Д]** Подробно: `docs/design/event-model.md`, раздел «Journal»;
конверт события — `docs/design/contracts.md`, 1.1.

### 5.4 События

Всё, что сообщает драйвер (собственный повтор харнесса, ухудшение экземпляра, расход токенов, лимит аккаунта, причина
конца хода), ядро доводит до политики и наблюдателя, а не отбрасывает. **[Р]** Подробно: `docs/design/contracts.md`,
разделы 1 (версия схемы — 1.1; наблюдаемые и решающие события, поведение без решения плагина, отказы с причиной — 1.3)
и 3.

### 5.5 Инварианты ядра

Потолок попыток (инвариант 16) **[Р]**: ожидание на воротах своего аккаунта после сбоя `auth_required`, `billing` или
`quota_exhausted` потолок не расходует; любая другая парковка и парковка на незакрытых воротах — расходует.

Подробно: `docs/design/invariants.md` (формулировки, где живёт каждый инвариант, значения потолков, известные пределы).

### 5.6 Восстановление

На старте демон дочитывает outbox, останавливает каждый записанный экземпляр харнесса со всеми потомками
(переподключения нет **[Д]**), идущие попытки завершает сбоем `daemon_crash` — дальше решает политика, — перевзводит
таймеры и расписания и выполняет resync. Прогон, ждавший решения по решающему событию, после рестарта ждёт того же
решения: хуки запускаются заново, заявленный исход и результат exec-команды сохраняются, ход и команда не повторяются.
**[Р]** Прогон формулы из нескольких шагов продолжает с того шага, на котором был; законченные шаги не повторяются.
**[Р]** Подробно (плановый рестарт с дренажом, доставка промпта): `docs/design/invariants.md`, разделы «Recovery» и
«Limits» (отличия macOS); `docs/design/contracts.md`, 3.4 и 6.4.

### 5.7 Ворота выдачи

Подробно (механизм, кто закрывает и снимает): `docs/design/contracts.md`, раздел 7.

- Ключи: аккаунт харнесса (идентификатор сообщает адаптер **[Д]**), модель, агент, бид, риг, проект, весь оркестратор.
- Ключ модели — `model:<harness>/<раскрытое имя>`. У прогона одна модель — та, что в его эффективном конфиге; ключ
  известен до старта, из сбоев он не берётся. **[Р]**

## 6. Иерархия и конфиг

### 6.1 Уровни

```
оркестратор   ~/.config/aae/config.toml     умолчания харнессов, общие MCP/hooks/skills/env, плагины, настройки агентов
└─ проект     <project>/aae.toml            имя корня, риги, паки, плагины проекта, настройки и варианты агентов
   └─ риг     секция в aae.toml             путь к репозиторию, префикс бидов, переменные, настройки агентов
```

Агент не уровень иерархии, а потребитель настроек. Умолчание модели для каждого харнесса задаётся на уровне
оркестратора. **[Р]** Пользователь в своём конфиге (оркестратор, проект, риг) говорит, на чём работает агент, и даёт
задачу; пак об этом не знает. **[Р]**

Харнесс, у которого в сборке есть адаптер, доступен сразу: секция `[harness.<имя>]` в конфиге оркестратора не
обязательна и нужна, только чтобы задать умолчания этого харнесса (модель, путь к бинарнику, его собственные ключи).
Конфиг с пустой секцией ради «включения» харнесса — ошибка дизайна. **[Р]**

Корень **[Р]**:

- Каталог, в котором лежит `aae.toml`, и есть корень проекта: там же ищутся остальные файлы конфига. Его путь нигде
  не пишется; секции вида `[rigs.root] path = "."` нет.
- У корня есть имя, по умолчанию `root`; пользователь может назвать его иначе. Внутри `aae` он остаётся корнем при
  любом имени: корнем проекта пользователь делает тот репозиторий, в который кладёт `aae.toml`.
- Корень — не риг: задач исполнителям в нём не раздают, в списке ригов проекта он показан отдельно.

Подробно: `docs/design/config.md`, разделы «Orchestrator» и «Project».

### 6.2 Что настраивается

Нейтральные к харнессу категории: настройки запуска, env, MCP-серверы, хуки харнесса, skills, системный промпт,
плагины, флаг наследования хоста. Плюс блок «родных» настроек конкретного харнесса (`native.<harness>`), который ядро
не интерпретирует и передаёт адаптеру как есть.

В нейтральных категориях нет ключа, значение которого понимает только один харнесс. **[Р]** Режим разрешений — как
раз такой: у claude это `--permission-mode`, у codex — политика подтверждений, и значения у них разные. Поэтому общего
`permission_mode` нет; режим задаётся в блоке своего харнесса, например `[settings.native.codex]` с
`approval_policy = "never"`. **[Р]**

**Настройки запуска** — три обычных послойных скаляра **[Р]**: `harness` (agent-CLI: `claude`, `codex`), `model`
(полное имя модели либо сокращение), `effort` (уровень усилия модели).

Харнесс **[Р]**:

- Пользователь называет харнесс, а не провайдера: отдельной настройки `provider` нет. Через какого поставщика харнесс
  ходит к модели — его родные настройки (хост либо `native.<harness>`), ядро их не читает.
- Харнесс не задан ни одним слоем — ошибка конфига.
- `harness` меняется теми же слоями, что и остальные настройки запуска: секцией `[agents.<имя>]` (правкой агента или
  вариантом), паком, формулой.

Модель **[Р]**:

- Полное имя модели передаётся харнессу как есть.
- Сокращение (`opus`, `luna` и т. п.) раскрывается в последнюю версию семейства. Таблицу сокращений держит адаптер
  (§7.2) и сверяет её со списком моделей харнесса; в постановке идентификаторов версий нет. Семейства на сегодня:
  anthropic — `fable`, `opus`, `sonnet`, `haiku`; openai — `astra`, `luna`, `terra`, `sol`.
- Если CLI харнесса сам раскрывает сокращение в последнюю версию, оно передаётся как есть.
- Если харнесс не принимает имя из таблицы, это находка для владельца; молча подменять имя нельзя.

Подробно: `docs/design/config.md`, разделы «Settings (any layer)» и «Harness and model».

### 6.3 Порядок слоёв

От слабого к сильному **[Р]**: настройки хоста для итогового харнесса (если наследование включено) → умолчание модели
итогового харнесса → общие настройки оркестратора → проекта → рига → вклад плагинов, подключённых к агенту → определение
агента в паке → `[settings]` пака, которому принадлежит формула прогона → `ai`-шаг формулы → вариант агента (§8.1) →
настройки пользователя для этого агента, `[agents.<имя>]`: оркестратор → проект → риг. Пак и формула несут только
настройки запуска; явная настройка пользователя сильнее их: так поправляют агента из внешнего пака, не форкая пак.

Секция пользователя об агенте одна — `[agents.<имя>]` **[Р]**: по её имени видно, чьи настройки она переписывает.
Имя агента пака — правка этого агента; новое имя с ключом `base` — вариант (§8.1). Секций `[overrides.*]` нет. В риге
`agents.<имя>` — те же настройки для этого рига либо имя варианта, который работает в риге вместо агента. **[Д]**

- Правила слияния **[Д]**: скаляр — побеждает старший слой; словари — по ключу, запись заменяется целиком; списки с
  именованными элементами — объединение с возможностью выключить элемент по имени на старшем слое.
- Обязательное свойство: «объясни конфиг» (`aae config explain`, она же в API) показывает для тройки (проект, риг,
  агент) каждое значение и слой, из которого оно пришло, включая выведенный харнесс и раскрытое имя модели.
- Слой хоста сливает сам харнесс: ядро его не читает, в «объясни конфиг» он — одна строка и выключается только целиком.
  Конфиг харнесса внутри рига (`CLAUDE.md`, `.claude/`, `.mcp.json`, `AGENTS.md`) — свойство репозитория: он действует и
  при выключенном наследовании. **[Д]**

Подробно: `docs/design/config.md`, раздел «Effective config and "explain config"»; опыт по доставке —
`docs/design/experiments.md`, раздел «Config and credential delivery».

### 6.4 Наследование настроек хоста

Включено по умолчанию, выключается на любом уровне (`inherit_host`). **[Р]** Цена, о которой должен знать пользователь
**[И 42, 18]**: личные MCP-серверы, хуки и плагины оператора работают в каждой сессии агента (общий MCP §11.4 на них не
распространяется; `doctor` предупреждает о stdio-MCP хоста). Адаптер не пишет в файлы хоста; при выключенном
наследовании учётные данные всё равно берутся с хоста. codex при включённом наследовании и наличии skills получает
собственный `CODEX_HOME`, который наследует хост и добавляет skills; `config_error` на этом пути запрещён. **[Р]**
Подробно: `docs/design/config.md`, раздел «Host inheritance»; открытые **[НП]** — §17.

### 6.5 Сборка и доставка

Конфиг перечитывается по явной команде, а не слежением за файлами **[Д]**. Внешними зависимостями управляет mise
**[Р]**: бинарник харнесса разрешается в порядке «явный путь в конфиге → `mise which` → `PATH`» **[Д]**. Подробно (кто и
когда собирает эффективный конфиг, куда его материализует адаптер, окружение сессии, невалидный конфиг, `aae doctor`):
`docs/design/config.md`, разделы «Loading» и «Effective config and "explain config"»; `docs/guide/install.md`.

## 7. Харнессы

Харнесс для ядра — абстракция: всё знание о конкретном харнессе (протокол, вид его сбоев, опции, сокращения
моделей, проверки `doctor`) живёт в его адаптере. Новый харнесс — новый крейт и строка в таблице адаптеров корня сборки.
**[Р]** Адаптеров два; обобщённый ACP-адаптер и снятие известных пределов интерфейса драйвера — когда появится третий
харнесс.

Подробно: `docs/design/adapters.md`.

### 7.1 Интерфейс драйвера

Семантика повторяет ACP v2: состояние `running | idle | requires_action` и типизированная ошибка хода. **[Р]** Операции
— над экземпляром, сессией и транскриптом; промпт несёт ключ идемпотентности. Адаптер шлёт нормализованные события с
порядковым номером, и всё сообщённое доходит до политики и наблюдателя (§5.4). **[Р]** Виды сбоя — закрытый перечень
плюс `unknown{text}` **[И 34]**. В интерфейсе нет
steer посреди хода, смены модели внутри живой сессии и подключения человека. **[Д]** Подробно:
`docs/design/contracts.md`, раздел 4 (4.1–4.5; виды сбоя — 4.4).

### 7.2 Обязанности любого адаптера

Закрыть ловушки «успешного провала» **[И 34]**; границу «ход закончен» брать из авторитетного сигнала харнесса;
сообщать, повторил ли харнесс запрос сам, — поверх такого повтора политика не повторяет **[И 34, 46]**; запускать каждую
сессию или экземпляр в своей группе процессов; доставлять окружение попытки инструментам сессии и её хукам; объявлять
проверенный диапазон версий харнесса и таблицу сокращений моделей (§6.2). **[Р]** Подробно:
`docs/design/adapters.md`, разделы «Adding a harness» и «What the core expects of a driver»; `docs/design/contracts.md`,
4.5 и 4.6.

### 7.3 Ленивый реестр экземпляров

Ключ экземпляра — отпечаток (харнесс + «процессная» часть эффективного конфига): экземпляр стартует при первой
потребности, служит всем сессиям с тем же отпечатком и останавливается после простоя. **[Р]** Плагин, меняющий
«процессную» часть, даёт другой экземпляр; плагин, работающий только на стороне оркестратора, экземпляров не плодит.
**[Р]** У экземпляра есть предел числа сессий **[И 21]**; сверх него поднимается второй с тем же отпечатком. **[Д]**
Подробно (что «процессное» у claude и codex): `docs/design/contracts.md`, раздел 8 и 4.6; память codex — `docs/design/experiments.md`, раздел «codex
app-server».

### 7.4 claude

«Ход закончен» — состояние idle без фоновых задач: субагенты claude по умолчанию фоновые **[И 46]**.

Подробно (транспорт, возобновление, время сброса лимита): `docs/design/contracts.md`, 4.6 (claude); опыты — `docs/design/experiments.md`, разделы «claude protocol» и

## 8. Агенты и паки

### 8.1 Агент

Агент — общая роль (`coder`, `planner`): промпт роли, skills и умолчания настроек запуска. О конкретной задаче агент не
знает: её приносит пользователь входом формулы. **[Р]** В коде ядра нет ни одного имени роли: любое поведение роли —
конфигурация.

- Всё, что относится к одному агенту, лежит в одном каталоге; деление на подкаталоги — по желанию автора. **[Р]**
- Настройки запуска в `agent.toml` — умолчания: их меняют пак, формула и пользователь (§6.3). **[Р]**
- **Агент самодостаточен [Р].** Шаблон его промпта лежит в том же каталоге, файлом `prompt.template.md`: шаг `ai`
  называет агента и получает его шаблон, своего файла промпта у шага нет **[Д]**.
- **Проект переписывает агента файлами [Р].** Каталог `.aae/agents/<агент>/` в корне проекта накладывается на каталог
  агента в паке: `prompt.template.md` оттуда заменяет шаблон пака — так пользователь переписывает чужого `coder`, не
  форкая пак. Текст, который агенту даёт сам проект (условия проверки для `qa` и т. п.), лежит там же отдельным файлом,
  например `.aae/agents/qa/checks.md`, а не строкой в `aae.toml`: видно, к какому агенту он относится, и конфиг не
  смешан с промптами. Шаблон подставляет такой файл по имени; файла нет ни в проекте, ни в паке — ошибка конфига,
  которая называет, куда его положить. **[Д]** Переменные рига остаются для коротких значений вроде `test_cmd`.
- **Область [Р]** — настройка агента `scope`:
  - `rig` — агент привязан к ригу и запускается в его каталоге. Это исполнитель: один репозиторий — один риг.
  - `root` — агент не привязан к конкретному репозиторию: запускается в корне, работает над всеми ригами проекта и с
    общим пространством бидов. Планирование поверх нескольких репозиториев — только `root`; `rig`-планировщик имеет
    смысл, лишь когда он планирует внутри одного репозитория.
  - Умолчание — `rig`. **[Д]** Шаг агента области `rig` в прогоне без рига — ошибка до запуска (§9.3).
- Промпт обязателен: прогон без промпта не стартует, пустой файл роли и пустой шаблон — ошибка конфига. **[Р]**
- **Вариант агента [Р].** Пользователь объявляет в конфиге оркестратора или проекта тот же агент пака под своим именем и
  с другими настройками, а риг отображает имя агента из формулы на вариант; формулы пака по-прежнему ссылаются на
  исходное имя. Вариант — отдельный агент для лимита параллелизма, ворот выдачи и событий. Второй путь к тому же
  результату — правка агента под его же именем. И то и другое — секция `[agents.<имя>]` (§6.3).

Подробно: `docs/design/config.md`, разделы «Agent» и «Agent variants».

### 8.2 Pack

Pack — единица содержимого, пригодного для любого проекта: агенты, формулы, триггеры. В паке нет ни слова о конкретной
задаче пользователя. **[Р]** `[settings]` в `pack.toml` несёт только настройки запуска; они действуют на прогоны формул
этого пака (§6.3). **[Р]** Корень проекта сам является локальным паком; имена уникальны в пределах пака, при совпадении
между паками — форма `<pack>.<имя>`. **[Д]** Pack может требовать плагины, но не содержит их.

Формулы живут в области видимости проекта **[Р]**: демон системный, проектов в нём много, и проект видит только
формулы подключённых к нему паков. Одинаковые формулы двух проектов не объединяются: у каждого проекта свои, и формула
одного проекта никак не влияет на другой. Структура формул плоская, без иерархии: каталог формул проекта — список
имён (§9.1, §12).

Источник пака **[Р]**:

- Каталог на диске либо git-репозиторий.
- У git-источника закрепление — sha коммита или тег. Закрепления нет — берётся последняя ревизия.
- Скачать пак, которого нет на диске, — задача `aae`, а не пользователя.
- Теги считаются неизменяемыми: версия по тегу или sha, которая уже лежит в кеше, годится без обращения к сети.
- Кеш скачанных паков сам не чистится: его чистит пользователь командой CLI.

Допущения **[Д]**: «последняя ревизия» — вершина ветки по умолчанию; она выясняется при загрузке конфига (старт демона,
перечитывание), а при недоступной сети проект работает на ревизии из кеша с предупреждением. Кеш — один на пользователя,
в каталоге кеша XDG. Lock-файла и отдельной команды закрепления нет: закрепление записано в конфиге. Идущие прогоны
работают со своим снимком (§6.5).

Подробно: `docs/design/config.md`, разделы «Pack», «Names», «Packs and plugins from git».

## 9. Формулы, прогоны, триггеры

### 9.1 Формула

Формула отвечает на вопрос «как»: это воркфлоу — какие шаги пройти и в каком порядке: вызовы агентов и проверки между
ними, скриптом или другим агентом. Что именно делать, формула не знает: задача приходит только от пользователя (входы
прогона, корневой бид §10.3) и подставляется в шаблоны. **[Р]** У формулы имя, описание, объявленные входы и шаги,
которые идут по порядку; формула из одного шага — частный случай. **[Р]**

Задача **[Р]**: пользователь даёт формуле просто задачу — текст, что сделать. Формула не рассчитывает, что бид за
пользователя кто-то заранее завёл: вход типа `task` принимает текст, а подхватить существующий бид (если задача
называет его id) или завести новый — забота `aae` (§10.3). Отдельного типа входа `bead` нет.

Виды шага **[Р]**:

- `ai` — ход агента в сессии харнесса; исход шага сообщает финишер. Шаг называет агента и получает шаблон его промпта
  (§8.1); может нести настройки запуска (§6.2).
- `exec` — команда без LLM, которую запускает демон. Исход — по коду возврата: 0 — `pass`; 75 (`EX_TEMPFAIL`) — сбой
  попытки, а не исход **[И 21]**; иное — `fail`. Контекст команда получает через окружение (`AAE_RUN`, `AAE_BEAD`,
  `AAE_INPUT_<NAME>`); подстановки в саму команду нет.
- `drain` — отдаёт в работу все биды, заведённые под корневым бидом прогона (§10.3). Каждый готовый бид получает
  дочерний прогон (§9.3); агент, риг и харнесс этого прогона известны из самого бида. Биды, ставшие готовыми по ходу,
  выдаются тоже. Шаг кончается, когда под корневым бидом не осталось ни готовых, ни занятых бидов. (Дренаж демона
  при плановом рестарте, §5.6, — другое.) Настройки шага:
  - `pool` — сколько бидов одновременно в работе у этого шага; по умолчанию 1. При `pool = 3` стартуют три готовых
    бида, если они есть, остальные ждут.
  - `on_item_failure` — что делать, когда прогон бида провалился: `continue` (умолчание) — шаг выдаёт остальные биды,
    провал одного их не останавливает и шаг не проваливает, а что осталось несделанным, видит следующий шаг;
    `soft_stop` — новые биды не выдаются, начатые доделываются; `hard_stop` — начатые обрываются сразу. После
    остановки шаг завершается `fail`. **[Д]**
- `formula` — шагом является другая формула того же проекта: она идёт дочерним прогоном (§9.3), её исход — исход
  шага. Входы родителя наследуются, но только те, что объявлены входами дочерней формулы; любой из них можно задать
  на шаге явно, и явное значение сильнее унаследованного.

Повтор шага и скрипт-проверка **[Р]** — пара необязательных настроек любого шага:

- `max_attempts` — сколько раз шаг исполняется самое большее; по умолчанию 1. Пока предел не исчерпан, не прошедший
  шаг повторяется; исчерпан — шаг провален.
- `step_check_script_path` — скрипт, который оценивает шаг; по умолчанию не задан. Задан — прошёл ли шаг, решает его
  код возврата: 0 — прошёл; 75 — неизлечимая ошибка, шаг провален без повторов; иное — не прошёл.
- Допущения **[Д]**: скрипт запускается после того, как шаг отработал сам; собственный провал шага (финишер `fail`,
  ненулевой код команды) — тоже неудачная попытка. Путь — относительно файла формулы, окружение — как у `exec`-шага.
  Повтор `ai`-шага продолжает его сессию и получает вывод скрипта замечанием. `max_attempts` — счётчик исполнений
  шага, а не попыток сессии из инварианта потолка (§5.5): сбой инфраструктуры его не расходует.

Вызов и каталог **[Р]**: по умолчанию формулу запускает пользователь, и она видна в каталоге формул проекта. Формула
с `internal = true` вызывается только как часть другой формулы (шагом `formula` или `drain`): прямой запуск отвергается,
из каталога она скрыта. `aae formula list --all` её показывает; API отдаёт у каждой формулы свойство `internal` —
отдельного эндпоинта нет.

Порядок шагов и возврат **[Р]**:

- Следующий шаг стартует по событию окончания предыдущего, без ожидания интервала (§1).
- Между вызовами агентов формула проверяет, сделана ли работа: шаг-проверка — это `exec` (скрипт) или `ai` (другой
  агент).
- Шаг-проверка может при провале вернуть формулу на названный более ранний шаг вместе со своими замечаниями: так
  проверка отдаёт работу обратно планировщику. Число возвратов ограничено настройкой формулы; предел исчерпан — прогон
  `failed`, замечания остаются в его итоге.

Допущения **[Д]**: итог каждого шага (исход, резюме, данные, хвост вывода команды) доступен шаблонам и окружению
следующих шагов; провал шага, у которого возврат не задан, завершает прогон `failed`; проверки, идущие подряд,
отрабатывают все, и их замечания уходят на возврат вместе; процесс исполнителя бида — формула, названная в шаге `drain`;
повтор шага (`max_attempts`) идёт внутри раунда и раунды возврата не расходует.

Типы входов проверяются при старте прогона. **[Р]** Шаблон промпта — только подстановка переменных, без логики;
отсутствующая переменная — ошибка до запуска. **[Д]** Пустой шаблон и промпт, пустой после подстановки, — ошибка (§8.1).
**[Р]** `worktree = true` даёт каждому прогону формулы свой git-worktree (§11.5). **[Р]** Подробно:
`docs/design/config.md`, раздел «Formula»; язык подстановки — `docs/design/contracts.md`, 2.3.

### 9.2 Приёмка и тест — одно и то же

Отдельного «тестового режима» у продукта нет: проверка формул и проверка самого `aae` — одна исполняемая acceptance
spec, набор сценариев в репозитории, который реализует критерии §15 и идёт тем же путём, что и рабочие прогоны. **[Р]**
Сценарии с настоящей моделью идут на самой дешёвой модели и только по явной команде пользователя, автоматически —
никогда. Подробно (подмножество без модели в CI, отчёт прогона): `docs/guide/development.md`, раздел «Acceptance
scenarios».

### 9.3 Прогон

Состояния, переходы и классы провала: `docs/design/contracts.md`, 6.1 и 6.2.

- Риг берётся из входа, из триггера или из префикса бида (§10.3). Прогон без рига идёт в корне; шаг агента области
  `rig` в таком прогоне — ошибка до запуска. Шаг агента области `root` идёт в корне, какой бы риг ни был у прогона
  (§8.1). **[Д]**
- Рабочий каталог по умолчанию занят одним живым прогоном; параллельная работа в одном риге — через worktree (§11.5).
  **[Д]** Параллелизм ограничивается на уровне оркестратора и на уровне агента. **[Д]**
- Прогон проходит шаги формулы по порядку (§9.1); состояния от `preparing` до `finishing` относятся к текущему шагу.
  **[Д]**
- Сессия — новая на прогон, у формулы из нескольких шагов — своя у каждого `ai`-шага; возврат на шаг продолжает его
  сессию. **[Д]** Прогон может явно продолжить сессию другого завершённого прогона; неявного переиспользования сессий
  нет. **[Р]**
- **Дочерний прогон [Р].** Его создаёт шаг `drain` — по одному на бид, шаг `formula` — один на шаг, либо агент из
  своей сессии командой `aae run start …`. Дочерний прогон наследует correlation родителя, его глубина на единицу
  больше, на него действует общий предел глубины цепочки (§9.5).
- `aae run wait <id>…` ждёт терминального состояния всех названных прогонов по событиям, а не опросом, и отдаёт по
  каждому состояние, класс и причину провала, резюме и данные финишера; код выхода 0 — все `passed`; у команды есть
  таймаут. **[Р]**
- Отмена родителя отменяет его живые дочерние прогоны. **[Д]**

Подробно: `docs/design/contracts.md`, раздел 6 (состояния, переходы, дедлайны); `docs/api/frontends.md`, раздел «CLI».

### 9.4 Исход

- Агент сообщает исход своего шага финишером: `pass` или `fail`, краткое резюме, необязательные данные. **[Р]** Данные
  доступны следующим шагам, триггерам и ожидающему родителю. Исход прогона — исход его последнего шага. **[Д]**
- Финишер — команда CLI `aae` в сессии агента с токеном попытки из окружения; финишер устаревшей попытки отвергается.
  **[Д]** Вызванный посреди хода, он только записывает заявленный исход: шаг завершается, когда ход закончился.
- **Фон после исхода [Р].** Исход заявлен и ход закончен — фоновые процессы, которые агент оставил (поднятый для
  проверки сервер и т. п.), шаг не держат: демон их останавливает и идёт дальше, сирот после прогона нет. Пока исход
  не заявлен, фоновая работа агента (субагенты, долгая команда) ждётся как раньше, в пределах своего бюджета.
- Исход заявлен — `run.finishing`: хук может наложить вето (`failed` с классом `check`) или вернуть замечание, которое
  уходит агенту следующим промптом в той же сессии и попытке. Это возврат внутри шага; число таких возвратов ограничено
  потолком ядра (инвариант 16). **[Д]** Возврат между шагами — §9.1.
- Исход не заявлен — `run.turn_ended_without_outcome` (§5.4). Сбой инфраструктуры — не исход. Рестарт демона заявленный
  исход не теряет (§5.6). **[Р]**
- Из коробки `pass` — это слово агента. Проверка «работа действительно сделана» — шаг формулы (§9.1) либо вето плагина:
  её пишет автор пака или проекта, готовой проверки в комплекте нет. **[Р]**

Подробно: `docs/design/contracts.md`, 6.3 (таблица ситуаций финишера).

### 9.5 Триггеры

Три способа запустить прогон, все в ядре **[Р]**: явный вызов через API, CLI или MCP; подписка на событие (тип события,
фильтр `where`, формула, отображение полей события во входы); расписание (cron или «не чаще чем раз в интервал»).
Триггеры объявляются в паке и в проекте; риг триггеру назначает проект: пак не знает имён ригов.

- Прогон, запущенный триггером, наследует correlation породившего события; запись человека в трекере начинает новую
  цепочку. **[Д]**
- Защита от петель — по глубине «прогон породил прогон» (триггером или из сессии агента, §9.3), предел — 10;
  `bead.ready` глубину не добавляет: длинный эпик законен. **[Д]**
- Пока жив прогон, запущенный этим триггером с тем же ключом входов, новое срабатывание пропускается с событием
  `trigger.skipped`. **[Д]**
- После простоя демона пропущенное расписание срабатывает не более одного раза **[И 21]**. `cron` считается в часовом
  поясе системы; ключ `timezone` оркестратора его переопределяет. **[Р]**
- `bead.ready` порождается, когда бид впервые попадает в список готовых: открыт, никем не занят, все блокеры закрыты.
  **[Д]**

Подробно (ручное срабатывание и выключение, идемпотентность срабатывания): `docs/design/config.md`, разделы «Trigger» и
«How runs start and what a firing guarantees»; язык `where` и `inputs`, таймауты хуков и срок жизни outbox как контракт —
`docs/design/contracts.md`, разделы 2 и 3.

## 10. Трекер

### 10.1 Интерфейс

Трекер — адаптер с узким интерфейсом; проект может работать без трекера. **[Д]** Операция добавляется в интерфейс,
только когда она нужна вызывающему **[Р]**: claim, условный возврат, закрытие, список готовых, поток изменений, а для
корневого бида и шага `drain` (§10.3) — создание бида и биды под корневым. **[Д]** Подробно:
`docs/design/contracts.md`, раздел 5.

### 10.2 br

`br` — внешний бинарник: ставится отдельно через mise и объявлен зависимостью там же; `aae` его не поставляет, не
линкует и не вендорит. **[Р]** Лицензия br — «MIT с райдером OpenAI/Anthropic» **[И 11 §2.7]**: явное предупреждение
стоит везде, где пользователь встречает br, — в README, в документации по установке и в выводе `aae doctor`. **[Р]**
Одна БД на проект в `<project>/.beads`, вне git ригов. **[Р]** Риг бида — префикс его id **[Р]**:

- Бид рига несёт префикс рига. По умолчанию это акроним из слов имени рига (`backend` → `b`, `my-project` → `mp`);
  ключ `prefix` в настройках рига его переписывает (`backend` с `prefix = "api"` → `api-…`).
- Биды корня префикса рига не несут. Пустого префикса у br нет, поэтому id корневого бида начинается с собственного
  префикса БД трекера. **[Д]**
- Одна БД — общее пространство бидов: агент области `root` видит биды всех ригов. Бид, который заводит агент области
  `rig`, получает префикс его рига без усилий агента; агент области `root` заводит бид для рига с префиксом этого
  рига. **[Д]**
- Метки `rig:<имя>` нет: два источника одного факта расходятся. Префиксы ригов проекта различны и не совпадают с
  префиксом корня — иначе ошибка конфига либо предупреждение `doctor`. **[Д]**

Подробно (явный путь к БД,
actor попытки, что не пишется в трекер, версия br и его контрактные тесты): `docs/design/tracker-br.md`; источник событий —
`docs/design/experiments.md`, раздел «br as an event source».

### 10.3 Бид и прогон

- Прогон может работать над бидом; прогоны без бида разрешены. Claim, возврат и закрытие делает демон: claim держится
  весь прогон, `passed` закрывает бид, `failed` и `cancelled` возвращают его условно. **[Р]**
- **Задача — корневой бид [Р].** Пользователь даёт формуле задачу («сделай то-то»), а не бид: заранее его никто не
  заводит. Вход типа `task` — строка. Она называет id существующего бида проекта — прогон подхватывает этот бид;
  иначе это текст задачи, и `aae` сам заводит по нему бид. В графе бидов он корень: под ним лежит всё, что заведено по
  этой задаче. Первый шаг формулы читает задачу из бида. Подбор «следующий готовый бид» остаётся отдельной формой
  того же входа. **[Д]**
- **Бид исполнителя несёт всё нужное [Р]:** текст задачи, риг — префиксом id (§10.2) — и метки `agent:<агент>`,
  `harness:<харнесс>`. Какие биды завести, сколько их и кому поручить, решает планировщик своим суждением; пак и
  формула этого не знают. `agent:` называет агента или вариант, видимый проекту. Харнесс определяет конфиг
  пользователя (§6.3), метка `harness:` его показывает; бид, чья метка расходится с эффективным конфигом, не выдаётся,
  причина видна. Так же не выдаётся бид без префикса рига, порученный агенту области `rig`. **[Д]**
- Цепочки нескольких формул над одним бидом нет: работа режется на биды, следующий берётся подбором «следующий готовый
  бид», в том числе в пределах эпика. **[Р]** Выбор и claim демон делает одной операцией; готовых нет — прогон не
  создаётся, вызывающий получает явный ответ. **[Д]**
- У бида не более одного живого прогона-владельца. Явно указанный бид другого рига отвергается. **[Р]**
- После заданного числа прогонов, завершившихся `failed` над бидом, ядро закрывает ворота выдачи по этому биду (§5.7),
  пока человек их не снимет. **[Д]**
- Владение в состоянии оркестратора — истина: неудача закрытия или возврата в br исход прогона не меняет.

Подробно: `docs/design/tracker-br.md`, раздел «Beads and runs».

## 11. Плагины

### 11.1 Назначение

Плагин — единица расширения: типовые расширения делаются плагинами, а не кодом ядра. **[Р]** Устройство каталога
плагина: `docs/guide/plugin.md`; `docs/design/config.md`, раздел «Plugin».

### 11.2 Сторона агента — декларативная

Плагин добавляет агенту skills, хуки харнесса (в диалекте Claude **[И 18]**), MCP-серверы, переменные окружения, скрипты
в `PATH`, фрагменты промпта, родные для харнесса части. Вклад получают только агенты, которые плагин подключили. **[Р]**
Подробно: `docs/guide/plugin.md`, раздел «The agent side»; вклад в «процессную» часть и экземпляры —
`docs/design/contracts.md`, раздел 8.

### 11.3 Сторона оркестратора — exec-хуки

Плагин вешает команды на события ядра. **[Р]** Контракт — диалект хуков Claude: событие JSON на stdin; код 0 — «нет
возражений»; код 2 — блокировка с причиной в stderr; JSON на stdout — решение для решающих событий (§5.4). Хук не имеет
состояния, исполняется вне цикла ядра и идемпотентен: всё нужное политике есть в событии, хранилища для плагинов в ядре
нет, а после рестарта демона хук запускается заново (§5.6).

- Падение или таймаут хука не роняет демон и порождает `plugin.hook_failed`. Отказ хука-вето блокирует, отказ
  наблюдающего игнорируется. **[Д]**
- Несколько плагинов на одном событии: для вето достаточно одной блокировки; для выбора реакции на сбой действует первое
  решение в порядке подключения. **[Д]**
- Хуки и сервисы стороны оркестратора включаются на уровне оркестратора или проекта.

Подробно: `docs/design/contracts.md`, раздел 3; `docs/guide/plugin.md`, раздел «The orchestrator side».

### 11.4 Сервисы

Сервис — долгоживущий процесс под супервизией: команда, область совместного использования (оркестратор, проект),
проверка здоровья; MCP у него — по желанию. **[Р]**

Общий MCP **[Р]**: сервер один на область, а не на сессию; сессии получают его URL и заголовки идентичности (проект,
риг, агент, прогон) **[И 36]**. stdio-сервер делится между сессиями только через мост stdio→HTTP; мост входит в первый
выпуск **[Р]** и не является частью ядра. Серверу с неявным состоянием на клиента область «сессия» задаётся явно. Сервер
самого `aae` и любой рекомендуемый общий сервер понимают обе эпохи протокола MCP. Сбой MCP — сбой инструмента, а не
провал прогона **[И 36]**. Общий сервис слушает unix-сокет либо loopback с токеном **[И 18]**.

Подробно: `docs/design/config.md`, раздел «MCP servers and services»; `docs/design/contracts.md`, раздел 8.

### 11.5 Плагины в комплекте

Поставляются внутри бинарника как встроенные исполнители хуков (внешний рантайм не нужен). В бюджет ядра не входят:
считаются по своей строке бюджета и входят в общий лимит выпуска (§14). **[Д]**

- `default-policy` — реакции на сбои, «дешёвые страховки» **[И 21 §4.2]**: resume, новая сессия, ворота аккаунта и
  агента, backoff, лестница для `stall`, напоминание о финишере. Включён по умолчанию, отключаем; пороги меняются в его
  конфиге. Работает только на стороне оркестратора и харнесс не меняет. **[Р]**
- `auth_required` и `billing`: повторы с ростом паузы до раза в час, без повышения до человека; ожидание идёт на воротах
  аккаунта и потолок попыток не расходует (инвариант 16). **[Р]**
- `quota_exhausted` без времени сброса в самом сбое и `rate_limited` при исчерпанном лимите аккаунта: ворота аккаунта
  закрываются до времени сброса последнего известного лимита аккаунта, а не короткий backoff. **[Р]**
- `worktree` — на `run.preparing` создаёт git-worktree для прогона и подставляет рабочий каталог; после завершения
  удаляет, только если коммиты достижимы из refs. Включается только ключом формулы `worktree = true`; центральных
  списков агентов и формул и включения на уровне агента нет. **[Р]**

Подробно: `docs/design/config.md`, разделы «Bundled plugins» и «Where the bundled plugins end and the core begins»
(граница механизмов ядра и выбора реакции); `docs/design/contracts.md`, раздел 10; первоисточники
порогов — `docs/init/aae-context/06-failure-policy-defaults.md`.

### 11.6 Доверие

Плагин исполняет произвольные команды с правами пользователя. Установка и включение — явные действия; плагин из git
обязан быть закреплён sha или тегом (§8.2): незакреплённый — ошибка конфига; автообновления нет. **[Д]**

## 12. Фронтенды

Три адаптера над одним типизированным интерфейсом ядра. **[Р]**

- **HTTP API** — полная поверхность. Транспорт, SSE, OpenAPI, идемпотентность: `docs/api/frontends.md`, раздел
  «HTTP API».
- **CLI** — полная поверхность (устройство: `docs/api/frontends.md`, раздел «CLI»). Без демона работают запуск
  демона, `doctor`, очистка кеша паков (§8.2), проверка и объяснение конфига, версия.
- **MCP** — малая поверхность: список формул, запуск формулы, состояние прогона, список прогонов, отмена — пять
  инструментов **[Д]**; HTTP-транспорт в демоне, обе эпохи протокола. К агентам подряд сервер не подключается (описания
  инструментов стоят токенов в каждой сессии): только если это задано в конфиге агента. **[Д]** Набор инструментов не
  расширяется: агент, которому нужно больше (планировщик), пользуется CLI. **[Р]**

Полная поверхность: проекты и риги; агенты, формулы, паки, плагины и конфиг (список, проверка, объяснение,
перечитывание); прогоны (запуск, список, состояние, живой просмотр, ожидание исхода, отмена, ответ на запрос, финишер);
триггеры; экземпляры и сервисы; ворота выдачи (пауза оркестратора, проекта, агента, бида); события; демон (состояние,
дренаж, рестарт); `doctor`. Ожидание исхода — `aae run wait <id>…` (§9.3): по событиям, не опросом. **[Р]**

Объяснение конфига берёт агента (`aae config explain --agent <a>`) либо формулу на риге (`--formula <f> --rig <r>`:
агент её `ai`-шага со слоями пака, шага и рига; у формулы из нескольких шагов шаг называется) и называет агента в
ответе полем `agent`. Каталог формул проекта (`aae formula list`) показывает формулы, которые пользователь может
запустить; `--all` добавляет формулы с `internal = true`, а API отдаёт у каждой свойство `internal` (§9.1). **[Р]**
Список агентов
(`GET /v1/agents`) даёт для каждого итоговый харнесс в проекте вне рига и формулы, `null` — если слои агента его не
задают.

Подробно: `docs/api/frontends.md`, `docs/api/mcp.md`, `docs/api/openapi.json`.

## 13. Поставка

- Один бинарник `aae` на Rust: демон, CLI и встроенные плагины. Цели: linux x86_64 и arm64 (статическая линковка), macOS
  x86_64 и arm64. **[Р]** Приёмка — только на хосте владельца (Linux arm64). **[Р]**
- Внешние зависимости времени исполнения — только бинарники харнессов и, если нужен трекер, `br`; ими управляет mise
  **[Р]**, сам `aae` их не скачивает и не устанавливает.
- В репозитории `mise.toml` задаёт инструменты сборки и `br` точными версиями, claude и codex — линией релизов (`2.1`,
  `0`); `mise.lock` нет. **[Р]** Задачи разработки запускаются через mise **[Д]**, но mise — удобство, а не требование:
  те же инструменты ставятся любым способом, и документация для разработчика говорит это прямо. **[Р]**
- Обновление харнесса у пользователя — его забота; в репозитории — забота разработчика aae (§7.8). **[Р]**
- Внешние паки и плагины — каталоги из git (§8.2, §11.6); mise их не касается; скачивает их `aae` вне ядра: ядро
  читает только готовые каталоги на диске. **[Д]**
- Лицензия MIT; зависимости — только с совместимыми лицензиями; код br и bv в дерево не попадает. Репозиторий публичный:
  никаких секретов и абсолютных путей машины владельца. **[Р]**
- Каталоги — по XDG. Демон запускается в foreground; файлы сервиса для systemd и launchd генерируются командой; неявного
  автозапуска из CLI нет. **[Д]**
- Документация для пользователя: установка, первый проект, первая формула, написание плагина.

Подробно: `docs/guide/install.md`, `docs/guide/development.md`.

**Правила кода:**

- **Без заглушек и без кода «на вырост». [Р]** Не пишутся: пустые реализации, `todo`-ветки, неиспользуемые параметры,
  поля, флаги и точки расширения под будущие функции, обобщения под единственный случай. Всё, что постановка называет
  отложенным (§1.1), в коде отсутствует полностью.
- Нет механизма без применения. У каждой функции есть запись, какой критерий §15 или какая реальная работа её
  использует; функция без такой записи к моменту выпуска удаляется.
- Перед каждым новым механизмом — проверка, нет ли его уже у вендора харнесса.
- Ревью до основной ветки. Временные логи рабочего процесса в репозиторий не коммитятся; история git не переписывается.
  **[Р]**
- У каждого отдельного каталога вроде `experiments/*`, `demos/*`, `examples/*` — короткий README: что там и зачем.
  **[Р]**

**Правила тестов:**

- Тесты — против настоящих бинарников харнессов. Поддельный драйвер допустим только сценарный (задержка, конец хода без
  исхода, ошибка провайдера, код 75, зависание, обрыв канала посреди хода, запрос разрешения, событие вне хода) или как
  запись настоящих транскриптов **[И 21 §4.4]**.
- Детерминированная проверка инвариантов §5.5: управляемые часы, seed, проверка после каждого шага.
- Инъекция сбоев: `kill -9` демона на каждой границе транзакции и между записью в состояние и вызовом трекера;
  восстановление обязано сойтись.
- Проверка идемпотентности: любая операция, применённая дважды, и любое событие, доставленное дважды или не
  доставленное, дают то же конечное состояние.
- **Никаких залоченных сидов. [Р]** Тест проходит на любом сиде, а не на заранее известном наборе. Случайные стенды
  берут новый базовый сид при каждом прогоне и печатают его; повтор упавшего — по напечатанному сиду. Диапазон сидов,
  подобранный под зелёный прогон, запрещён.
- **Быстрые тесты — приоритет над новыми функциями. [Р]** Медленный или нестабильный набор чинится раньше, чем строится
  новое: скорость, флейки, случайные сиды, ожидание событий вместо ожидания времени.
- Раскладка **[Р]**: unit- и интеграционные тесты гоняются локально, acceptance без модели — в CI на каждый коммит.
- **Живые модели. [Р]** В CI доступа к LLM нет — это архитектурное решение. Контрактные тесты на живом харнессе, опыты,
  сценарии «запрос» и демо идут только на машине разработчика по явной команде, на самой дешёвой модели каждого харнесса
  и точечно: до запуска понятно, что проверяется; после — записан итог. Исключение — демо, которому модели назначил
  владелец (§15). Намеренно сжигать квоту ради проверки запрещено.
- Обновление харнесса или `br` принимается контрактными тестами (§7.8, §10.2).

**Отчёт о готовности. [Р]** Исполнитель ведёт в репозитории один файл (`docs/READINESS.md`) со шкалой готовности каждого
компонента и обновляет его в конце каждого рабочего сеанса. Оценка — целое от 0 до 10 по опорным точкам:

| Балл | Что это значит |
|---|---|
| 0 | ничего нет |
| 2 | контракт компонента записан (типы, события, ошибки), кода нет |
| 4 | код есть, основной путь работает вручную |
| 6 | тесты без модели зелёные, включая пути сбоев |
| 8 | относящиеся к компоненту критерии §15 зелёные на хосте владельца |
| 10 | компонент отработал демо без вмешательства (критерий 20) |

- Оценка ставится по букве шкалы. Критерий компонента, который не проходит или не запускался, — потолок его балла: такой
  компонент не получает 8 и выше; 10 — только при зелёном критерии 20. **[Р]**
- Промежуточные баллы допустимы; рядом с каждой оценкой — одна строка «чего не хватает до следующей точки» и список
  критериев компонента.
- Оценка — это замер: у неё дата, короткий sha и маркер `MEASURE`; sha не старше последнего изменения кода.
- Компоненты: цикл событий и состояние; прогоны и финишер; триггеры и расписание; ворота выдачи; восстановление; сборка
  конфига; реестр экземпляров и сервисов; адаптер claude; адаптер codex; адаптер br; исполнение хуков плагинов;
  `default-policy`; `worktree`; общий MCP; HTTP API; CLI; MCP-фронтенд; acceptance spec; поставка и `doctor`.

**Правило замеров. [Р]** Любой замер (время, память, размер, количество, доля), где бы он ни появился — в документации,
отчёте acceptance spec, комментарии к порогу в коде или описании PR, — несёт:

- видимую дату замера;
- видимую версию измеренного: версию бинарника или короткий sha;
- невидимый комментарий рядом для того, кто будет править: идентификатор замера, источник, условия, что перемерить.

Формат комментария один на весь проект, чтобы его находил один `grep`:

```
<!-- MEASURE id=<слаг> date=<ГГГГ-ММ-ДД> ver=<версия или sha> env=<ОС и стенд> src=<откуда> note="<условия; что перемерить>" -->
```

В коде тот же маркер пишется в синтаксисе комментария языка. Замер без даты и версии считается дефектом документа. CI
проверяет, что у каждого маркера заполнены `id`, `date`, `ver` и `env`; замер, у которого маркера нет вовсе, CI найти не
может — это проверяет ревью.

**Остановиться и пересмотреть, если:**

- превышен жёсткий стоп по строкам;
- обновления харнессов раз за разом ломают контрактные тесты и съедают больше работы, чем сам продукт;
- вендор вводит отдельную оплату headless-режима, которая делает путь без TUI неприемлемым для владельца;
- штатные средства вендоров покрывают подавляющую часть реально используемых формул.

## 15. Критерии приёмки первого выпуска

Критерии реализуются как исполняемая acceptance spec (§9.2): она и есть приёмка. **[Р]** Колонка «Запуск»:

- **CI** — сценарий без модели; входит в spec и дополнительно идёт в CI на каждый коммит;
- **запрос** — сценарий с настоящей моделью либо долгая сборка; идёт только при явном полном запуске spec.

Все строки таблицы, включая проверки, которые живут в cargo-тестах и CI-скриптах, попадают в один отчёт приёмки. **[Р]**
Числовые пороги предложены автором и правятся владельцем. **[Д]** Ориентиры исследования мягче: хоп p50 ≤ 3 с и p90 ≤ 10
с, инфраструктура в простое ≤ 150 МБ (`FINAL-REPORT.md` §5.3). Плагин `default-policy` во всех сценариях включён, если
не сказано иное.

Платформа **[Р]**: приёмка идёт только на хосте владельца — Linux arm64. Остальные три цели только собираются; их
работоспособность не проверяется и принимается на веру в переносимость языка.

### Демо (критерий 20)

Демо — минимальные живые примеры, каждое в своём каталоге `demos/<номер>-<имя>/`. **[Р]** Запрос пользователя в демо —
одна фраза, как в жизни: «Create me snake game in browser and a simple backend which store the high-scores, KISS». Как
это делать и в каком порядке, решают агенты.

Общее для всех демо **[Р]**:

- Демо — четыре каталога: `pack/` (пак: агенты и формула, без единого слова о задаче), `root/` (корневой репозиторий:
  конфиг `aae`, проект и его трекер) и два репозитория проекта, `frontend/` и `backend/`, пустые до запуска.
- Конфиг демо — образец, по нему пользователь пишет свой, поэтому в нём нет ничего лишнего и непонятного **[Р]**: нет
  пустой секции харнесса, нет секции рига для корня, настройки агентов — в `[agents.<имя>]`, родная настройка харнесса
  — в блоке этого харнесса. Каждый агент пака самодостаточен: `agent.toml`, `scope` и `prompt.template.md` в одном
  каталоге. `planner` и `qa` — области `root`, `coder` — `rig`. Риг `backend` назван в бидах `api` (ключ `prefix`),
  `frontend` получает акроним: по графу бидов видно, чей бид.
- Пользователь запускает демо у себя, и запуск не конфликтует с файлами репозитория: всё, что запуск создаёт
  (содержимое `frontend/` и `backend/`, биды, состояние демона), — в `.gitignore`.
- Результат прогона автора сохранён рядом, с суффиксом `-example` (`frontend-example/`, `backend-example/`, граф бидов,
  итог прогона): пользователю есть с чем сравнить свой. Исполнение недетерминировано, поэтому у сохранённого
  результата обязательно сказано, когда и на чём он получен: дата, версии, модели (маркер `MEASURE`).
- Зависимости демо — в его собственном `mise.toml`, без lock-файла; mise — удобство, а не требование (§13).
- `root/config.toml` — конфиг оркестратора внутри демо: с ним демо идёт на собственном демоне и не трогает настройки
  пользователя в `~/.config/aae`. Зачем он лежит рядом с `aae.toml`, сказано в самом файле, в README демо и в
  документации по конфигу.
- Демо требуют логина харнессов и тратят реальные токены: идут только на машине разработчика; CI проверяет только, что
  конфиги демо загружаются. У каждого демо — короткий README.

**Демо 1, `demos/1-planner-executor/`** — «планировщик — исполнители» **[Р]**: то, что штатный харнесс делает
субагентами, повторено на двух репозиториях. Ничего сверх этого: ни QA, ни общей проверки результата.

1. Запрос пользователя — задача формулы: `aae` заводит по ней корневой бид (§10.3), его читает первый шаг.
2. Шаг `ai`, агент `planner` (область `root`): смотрит, что есть в проекте (репозитории пусты), и сам решает, какие
   биды завести под корневым — что сделать во `frontend`, что в `backend`, одной задачей или несколькими, в каком
   порядке. В каждом биде — задача, риг (префиксом), агент и харнесс.
3. Шаг `drain`: отдаёт заведённые биды в работу; их делает агент `coder`.
4. Шаг `exec`: скрипт проверяет, что все биды под корневым закрыты, и отдаёт пользователю итог как есть, с ошибками
   или без: что сделано, что нет.

Демо 1 показывает и выбор харнесса: агент `coder` один, а на чём он работает, задаёт конфиг `root/` — исполнитель
`frontend` на claude, исполнитель `backend` на codex; README показывает оба пути — правку агента и варианты
`claude-coder` и `codex-coder` (§8.1), и то и другое в `[agents.<имя>]`. Модели — самые дешёвые (§14). Следующие демо
выбор харнесса не показывают.

**Демо 2, `demos/2-multirepo-qa/`** — та же задача и та же раскладка; после исполнения идёт проверка с возвратом
**[Р]**:

- Проверка скриптом: форматирование (`rumdl`). Что может, скрипт правит сам; что не смог — уходит замечаниями на
  доработку.
- Проверка агентом `qa`: убеждается, что змейка на деле запускается и что-то делает — например, по снимку экрана через
  `agent-browser`. Условия проверки заданы на уровне `root/`, а не в паке: пак о змейке не знает. Они лежат файлом
  агента, `root/.aae/agents/qa/checks.md`, а не переменной в `aae.toml` (§8.1).
- Замечания проверок возвращают формулу планировщику: он заводит новые биды, `drain` отдаёт их в работу, проверки идут
  снова. Раундов «проверка — возврат» не больше трёх.
- Все агенты — на моделях openai: `sol`, `terra`, `luna`. `astra` не используется.
- Демо проходит стабильно: фоновый процесс, оставленный агентом после заявленного исхода, прогон не держит (§9.4).

## 18. Допущения, которые стоит подтвердить

Открытых вопросов, блокирующих работу, нет. Ниже — допущения **[Д]**, которые сильнее всего меняют результат;
исполнитель работает по ним, пока владелец не поправил.

1. **Числа бюджета (§14):** выпуск 30 тыс., стоп 35 тыс. и лимиты частей, кроме ядра.
2. **Правила слияния слоёв (§6.3);** слои хоста и умолчания модели берутся для итогового харнесса; слой хоста
   непрозрачен для ядра.
3. **Ворота выдачи как единственный механизм «не запускать пока» (§5.7)** и счётчик неудач бида (§10.3).
4. **Финишер (§9.4):** только CLI; токен на попытку; возврат замечания хуком внутри шага.
5. **Worktree и политика сбоев — плагины в комплекте (§11.5);** отказ хука-вето блокирует прогон (§11.3).
6. **Рабочий каталог по умолчанию занят одним прогоном (§9.3).**
7. **Отмена родителя отменяет его живые дочерние прогоны (§9.3).**
8. **mise во время работы демона (§6.5):** демон разрешает бинарники через mise; паки и плагины mise не касаются.
9. **Конфиг перечитывается командой (§6.5);** автозапуска демона из CLI нет (§13).
10. **Вход «следующий готовый бид» разрешает демон (§10.3);** корень проекта — неявный локальный пак (§8.2).
11. **После рестарта демон останавливает все экземпляры харнессов и возобновляет прогоны (§5.6),** а не
    переподключается.
12. **Шкала готовности (§14):** опорные точки и список компонентов.
13. **Пороги приёмки (§15).**
14. **Шаги формулы (§9.1, §9.3):** итог шага доступен следующим; провал шага без возврата завершает прогон; замечания
    проверок одного раунда уходят на возврат вместе; у каждого `ai`-шага своя сессия; повтор шага и его скрипт-проверка
    (когда запускается скрипт, чем продолжается `ai`-шаг); после остановки `drain` по `on_item_failure` шаг — `fail`.
15. **Биды задачи (§10.2, §10.3):** вход `task` — id существующего бида либо текст, по которому корневой бид заводит
    `aae`; метка `harness:` показывает харнесс, а не задаёт его; корневой бид несёт префикс БД трекера, потому что
    пустого префикса у br нет; кто и как даёт биду префикс рига.
16. **Паки из git (§8.2):** «последняя ревизия» — вершина ветки по умолчанию, выясняется при загрузке конфига; кеш — в
    каталоге XDG; lock-файла нет; плагин обязан быть закреплён (§11.6).
17. **Агент (§8.1):** умолчание области — `rig`; своего файла промпта у шага `ai` нет; как шаблон подставляет файл из
    каталога агента; в риге `agents.<имя>` — настройки либо имя варианта (§6.3).

Правила пользования:

- Решения берутся из постановки, факты о харнессах и br — из шпаргалок и `docs/design/experiments.md`. Если шпаргалка
  расходится с постановкой в факте, прав источник, на который шпаргалка ссылается; расхождение исправляется в
  постановке.
- Шпаргалки — снимок на 2026-11-10…12 для claude 2.1.322, codex 0.166.0, br 0.7.6. При другой версии харнесса факт
  сначала перепроверяется контрактным тестом.
- В шпаргалках есть таблицы «расхождения в отчётах». Выбор между значениями делает опыт, а не исполнитель на глаз.
- Отчёты исследования (**[И NN]**) и лаборатория `docs/init/aae-context/lab/` в репозиторий не входят **[Р]**:
  лаборатория содержит абсолютные пути машины владельца и ответы модели и попадает в репозиторий только после чистки.
  Исполнителю отчёты не нужны: всё нужное из них вынесено в шпаргалки и документацию проекта.
