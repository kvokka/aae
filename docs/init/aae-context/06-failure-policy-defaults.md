## 1. Вид сбоя → область → реакция по умолчанию

Реакция — это ответ `default-policy` на `run.attempt_failed`. Колонка «attempt» — растёт ли счётчик попыток
(R34:200-211). Вся колонка «реакция» — **[В]** отчёта 34 §5, вживую как политика не исполнялась.

| kind (§7.1) | Область (ключ ворот) | Реакция по умолчанию | Параметры и умолчания | attempt | Источник |

### Бюджеты сторожа

Правило: `now − last_signal > budget(state)`; дедлайн пересчитывается на каждом сигнале, а не глобальным тиком
(R46:30-31, R46:260-261). `last_signal` обновляет **любая** строка потока (R46a:283). Тишина никогда не
трактуется как idle (R34:288).

| Бюджет | Значение | Основание | Метка, источник |
|---|---|---|---|
| До первого события | **значения нет.** Symphony считает тот же `stall_timeout` (5 мин) от `started_at`. | ориентир снизу: claude до init 0,25–0,30 с, с личным конфигом оператора (наследование хоста) — 2,21 с; до первого токена 1,8–1,9 с и 3,55 с на haiku (замер 2026-11-10, claude 2.1.322) | [В] R21:172 · [К] SYM:823-828 · [П] R42:21-25 |
| Тишина в ходе, модель думает | 120 с (отчёт 46) либо 5 мин (отчёт 34, Symphony `stall_timeout_ms`=300000) | дельты идут примерно раз в секунду; свой watchdog claude — 180–300 с | [В] R46:134, R46a:295 · [В] R34:225, SYM:489-490 |
| Тишина при идущем инструменте, claude, главный тред | 45 с | `tool_progress{heartbeat:true}` раз в 30 с (замер 2026-11-11, claude 2.1.322) | [В] порог R46:135 · [П] пульс R46a:35, R46a:178 |
| Инструмент дольше бюджета | `budget(tool)` на инструмент, умолчания нет | у codex пульса нет; у claude foreground Bash уходит в фон через 120 с (`BASH_DEFAULT_TIMEOUT_MS`), у stdio-MCP idle-таймаут 30 мин **[К док]** | [В] R46:136, R46a:296 |
| Инструмент, codex | пульса нет; unified exec отдаёт yield не позже 30 с — модель сама опрашивает команду | `core/src/unified_exec/mod.rs:70` | [К] R46b:134, R46b:153 |

Собственные watchdog-и харнессов срабатывают позже этих бюджетов — рассчитывать на них нельзя:
- claude: byte-level 180 с на прямом API и 300 с за `ANTHROPIC_BASE_URL`; event-level 300 с, меньше не ставится
  **[К док]**, стандартные значения опытом не сняты (R46a:211-212, R46a:335).
- codex: `stream_idle_timeout_ms` 300 с × (1 + `stream_max_retries` 5) ≈ до 30 мин **[В]**; до заголовков ответа
  таймаута нет совсем — в опыте молчал 40 с без единой нотификации (замер 2026-11-11, codex 0.166.0) **[П]**
  (R46b:28-30, R46b:248, R46b:272-273). Совет отчёта: снизить оба параметра в конфиге провайдера **[В]** (R46:212-213).
- `requires_action` у claude приходит только при SDK-разрешениях (`--permission-prompt-tool=stdio`) и при
  `CLAUDE_CODE_EMIT_SESSION_STATE_EVENTS=1` **[П]** (R46a:39-40). При разрешениях через MCP состояние остаётся
  `running` — сторож примет ожидание человека за тишину (R46:78).
- codex: фоновый терминал идёт при статусе треда `idle` **[П]** (R46:82, R46b:247) — «idle» ≠ «фона нет».

## 3. «Светофор» в терминах ворот выдачи (§5.7)

Источник — R34:234; всё **[В]**, как механизм не исполнялось.

| Понятие отчёта 34 | Что это в aae |
|---|---|
| Ключ `(харнесс, аккаунт)` — для `quota_exhausted`, `auth_required`, `billing` | ворота по ключу «аккаунт харнесса» |
| Ключ `(провайдер, модель)` — для `rate_limited`, `overloaded` | ворота по ключу «провайдер + модель» |
| green | ворот нет |
| yellow: `rate_limit_event.status = allowed_warning` или `utilization` ≥ 0,9 | ворота **не** закрыты; только событие-предупреждение. В §5.7 такого состояния нет — решать исполнителю |
| red{until}: первый же сигнал закрывает выдачу всем сессиям ключа | `gate.closed` с временем T = `retry_at` + `reset_margin`; для auth/billing — без T, до ручного снятия |
| поглощение | однотипные сбои уже идущих ходов того же ключа: attempt не растёт, уведомление не повторяется (R34:234, R34:296) |
| half-open: один пробный ход | после T пропускается ровно один прогон ключа; успех → `gate.opened`, тот же сбой → ворота закрыты снова. В §5.7 пробного хода нет: его надо добавить в механизм или в политику |
| «постепенное открытие» после пробы | в отчёте не расшифровано (R34:296) |

Откуда `retry_at`: claude — `rate_limit_event.resetsAt` (только логин подпиской; форма `status:"rejected"` — **[К]**,
вживую снят только `allowed`, R34:58); codex — `account/rateLimits/updated.primary.resetsAt` **[П на поддельном
провайдере]** (R34:86; `X:e5_run.txt`), в самой ошибке времени нет (R34:103). Нет `retry_at` → backoff с потолком
и пробами (R34:296).

Суждением (конфиг, не код) остаются: переход на платный API, ждать или эскалировать при недельном лимите, бросить
ли работу после N попыток, принять ли частичный результат (R34:245). Ротация подписок ради обхода лимита — зона
риска, не делать (R34:240).

## 4. Сценарии восстановления — шаги для кода

### (а) `kill -9` харнесса посреди инструмента — R34:249-258

1. Адаптер: `failure{kind: harness_crash}` с кодом выхода и сигналом. Обнаружение: exit + EOF; у codex EOF за
   0,00 с (замер 2026-11-10, codex 0.166.0) **[П]** (R34:93, R15:216).
2. Убить всю группу процессов сессии и дождаться завершения. Дочерние команды: codex — умирают сами
   (`PR_SET_PDEATHSIG`, `core/src/spawn.rs:117`), **только Linux** **[П+К]**; claude — **[НП]** (R34:254).
3. Прогон → «попытка не удалась», claim удержан.
4. Счётчики: быстрый краш (< 30 с), crash-loop.
5. Resume: claude `--resume <id>`; codex `thread/resume` → тред `idle`, прерванный ход `interrupted` **[П]** (R34:255).
   Тред codex без единого сообщения теряется **[К]** (R34:256).

### (б) Смерть посредника — R34:262

Для нативного claude класса нет. Для codex посредник — сам app-server: падение рвёт все треды и убивает их команды
**[П]**. Шаги: для каждого треда экземпляра — сценарий (а), экземпляр поднять один раз. Общее правило: resume
только после того, как старый процесс вышел, иначе два писателя.

### (в) Смерть, рестарт, апгрейд демона — R34:264-280

Что происходит с детьми на stdio при EOF:
- claude: простаивающий выходит сразу; посреди хода — **дорабатывает ход без наблюдателя** и выходит (в опыте
  через 17 с; замер 2026-11-10, claude 2.1.321, снято на смерти ACP-адаптера — для процесса `claude` это тот же
  EOF) **[П]** (R34:267, R14:125). Побочные эффекты хода происходят.
- codex app-server на stdio: EOF завершает сервер — до 30 с на слив RPC, жёсткий выход через 45 с **[К]**
  (`app-server-transport/src/transport/stdio.rs:124-133,168-181`; `app-server/src/lib.rs:1235-1240`). Судьба
  идущего хода — **[НП]** (R34:268).

Шаги после старта (R34:271):

1. Прочитать реестр из состояния: id сессии у харнесса, pid, время старта pid, группа, поколение.
2. Сверить с таблицей процессов; реестр — подсказка, процессы — истина. Метка сессии в env ребёнка
   (`/proc/<pid>/environ`); у claude `--session-id=<uuid>` виден в cmdline **[П]**.
3. Осиротевшим дать до T секунд выйти самим, затем убить группу. T в отчёте не задано; ориентир — 17 с и 30/45 с выше.
4. Только после этого resume. У codex страхует writer-lock: `-32600 thread … already has an active writer`
   **[П]** (R15:101-102); у claude блокировки нет — второй писатель молча ветвит транскрипт (R34:271, R14:142).
5. Прочитать хвост транскрипта: ход завершён → проверка результата; не завершён → reconcile-промпт.

Плановый рестарт — дренаж: остановить выдачу, ждать конца ходов до N минут, затем рестарт; N не задано (R34:280).

### (г) Перезагрузка машины — R34:284

Сирот нет. Порядок: состояние (SQLite WAL восстанавливается сам) → общие MCP-сервисы → предстартовая проверка
логина по аккаунтам → resume прогонов, бывших в ходе, через reconcile-промпт. Демон — unit системы.

### (д) Зависший ход — R34:288

1. Сторож: время от последнего события хода, отдельно для «модель молчит» и «идёт инструмент» (§2).
2. Interrupt: codex `turn/interrupt` **[П]** (R15:91). Для claude 16 мс измерено только для `session/cancel`
   **через ACP-адаптер** (замер 2026-11-10, claude 2.1.321; R14:130); нативный interrupt в `-p` — **[НП]**.
3. Нет подтверждения за 10 с → kill группы → сценарий (а).
4. Повторный `stall` того же прогона → новая сессия (R34:207).

### (е) Агент часами ждёт человека — R34:292

1. Состояние `requires_action`: сторож тишины и idle-TTL выключены.
2. Уведомление сразу, затем напоминания с backoff.
3. По `human_timeout` — ответ `deny` либо отмена хода (в §5.4 постановки: «затем отказ»).
4. Не парковать с убийством процесса: запрос живёт в памяти процесса и теряется; переспросит ли харнесс после
   resume — **[НП]**.

### (ж) Квота исчерпана у всех агентов аккаунта — R34:296

1. Первый `quota_exhausted` → закрыть ворота аккаунта до `retry_at`.
2. Остальные идущие ходы упадут с тем же видом — поглотить (attempt не растёт).
3. Новые прогоны аккаунта ждут в `queued`; сессии закрыть.
4. Claim удержан за прогонами — шторма возвратов и `bead.ready` нет.
5. `retry_at` дальше порога (недельное окно) → эскалация человеку с ETA.
6. После T — один пробный ход, затем открытие.

## 5. Журнал `intent → sent → acked → settled`

Ключ: `(прогон, попытка)` плюс поколение; маркер ключа вставляется в текст промпта (R34:302). Идемпотентности
протоколы не дают (R34:300 — про ACP **[К]**; для нативных путей вывод **[В]**).

| Харнесс | Чем подтверждается `acked` | Метка, источник |
|---|---|---|
| claude | эхо пользовательского сообщения на stdout при `--replay-user-messages` (только с `--input-format=stream-json` и `--output-format=stream-json`) | **[К]** `lab/cc-native/logs/claude-help.txt:191-194`. Отчёт пишет «[Э, exp4]» (R34:303), но exp4 подтверждает лишь присутствие флага в cmdline процесса под ACP-адаптером (R14:30). Форма эхо-события нативно **не снята** |
| codex | `turn.id` в ответе на `turn/start` | **[П]** R34:303; сверено: `X:e5_usage.jsonl:10` (`result.turn.id`, `status:"inProgress"`) |

Действие после рестарта по последней записи (R34:304):

| Состояние | Действие |
|---|---|
| `intent` без `sent` | отправить |
| `sent` без `acked` | искать маркер ключа в транскрипте; нет — отправить снова |
| `acked` без `settled` | читать хвост транскрипта: ход завершён → проверка исхода; не завершён → reconcile-промпт |
| `settled` | ничего |

Оговорки:
- codex: повторный `turn/start` в тред, где ход уже идёт, **не ставится в очередь, а сливается** — оба ответа несут
  один turn id **[П]** (R36:19, R36:143-144). Повтор при `sent` без `acked` безопасен только после проверки
  транскрипта и статуса треда.
- Финишер от устаревшего поколения отбрасывается (R34:305).
- Промпт формулируется как «добейся состояния X» и требует сначала сверить текущее состояние (R34:307).
- Итог — доставка «не менее одного раза» с идемпотентным эффектом, не exactly-once (R34:309).

## 6. Расхождения между источниками

| Тема | Значение 1 | Значение 2 |
|---|---|---|
| Crash-loop | «5 подряд → карантин сессии», 5 мин (R34:224, R03:125) | «5 рестартов за 1 ч» (R21:183); `AAE-SPEC` §11.5 — «5 крашей агента за час → ворота агента». Это два разных механизма Gas City; область тоже разная: сессия против агента |
| Resume → новая сессия | «3 **неудачных resume**» — отказ самого resume (R34:224, R21:174, R21:187) | «resume **до 3 раз** после краша» (FR:746, `AAE-SPEC` §11.5) — счёт крашей, а не отказов resume |
| Владение при новой сессии | `requeued`: «claim снят, gen+1» (R34:195) | «fresh сохраняет владение шагом» (R21:174); `AAE-SPEC` инварианты 5, 17 — владение остаётся за прогоном. Действует постановка |
| Предел тишины | 5 мин, один на всё (R34:225, Symphony) | 120 с модель / 45 с инструмент claude (R46:134-135) |
| Область `rate_limited` | «аккаунт + модель» (R34:30) | ключ светофора `(провайдер, модель)` (R34:234) |
| Источник эпизода rate limit | `work_ladder_ratelimit.go:1-18` (R21:186) | `:1-35`, с паузой 10 мин (R03:124) |
| Backoff | 10 с → 5 мин — повтор за харнесс (R34:218) | 500 мс → 5 мин — очередь эффектов ядра (R21:188). Разные механизмы, не путать |
| Resume claude | 0,4–0,5 с — через ACP-адаптер, 2.1.321 (R34:18, R14:124) | 0,30 с до init — нативно, 2.1.322 (R42:25) |

## 7. Что отчёты прямо называют непроверенным

- Пороги 5 мин stall, 30 с быстрый краш, 3 resume взяты у Symphony и Gas City, не калиброваны (R34:387). Пороги
  120 с / 45 с — рекомендация, не опыт (R46:130).
- Исчерпание настоящей подписочной квоты у claude и codex: только код и поддельный провайдер (R34:378, R46:273);
  истечение OAuth посреди сессии (R34:379).
- Судьба дочерних команд claude после `kill -9`; codex вне Linux (R34:380). codex при EOF посреди хода: что с
  командой и транскриптом (R34:381).
- Переспрашивает ли харнесс разрешение после resume (R34:382).
- Цена resume в токенах, промах prompt-кэша (R34:383); resume длинного транскрипта (R42:116).
- Падение MCP-сервера посреди сессии — сигналы только по схеме (R34:384). Перенос треда codex между `CODEX_HOME`
  (R34:385).
- Долгие ходы и субагенты (R34:386); `tool_progress` внутри субагентов — по документации (R46a:333); стандартные
  watchdog-и claude 180–300 с — только документация (R46a:335).
- codex `waitingOnUserInput` и хук `PermissionRequest` вживую (R46:86, R46:269).
- `billing` у обоих харнессов — по коду (R34:62, R34:90); `config_error` у claude — по коду (R34:64).
- Контрактные сценарии 3, 4, 7, 9, 11, 13, 14 опираются на непроверенное (R34:345).

## Чего здесь нет

Выяснять опытом; ни один отчёт целиком читать для этого не нужно.

- **Значений без первоисточника:** дедлайн до первого события, `human_timeout`, `reset_margin`, `max_attempts`
  backoff, абсолютный потолок попыток ядра, время дренажа, T ожидания сирот, N напоминаний при `hollow_done`,
  бюджет фона. Назначает исполнитель; каждое — параметр конфига.
- **Нативный interrupt claude** в `-p` stream-json и время его подтверждения — опыт 1 из §16 постановки.
- **Форма эхо `--replay-user-messages`** и то, несёт ли оно идентификатор, пригодный для сопоставления с ключом.
- **Сброс модели после нативного `--resume`** — наблюдался только через ACP.
- **Пробный ход и «жёлтый»** — в воротах §5.7 их нет; форма решения хука для них не определена.
- **Сигналы и поля каждого вида сбоя** (как адаптер получает `kind`) — в файлах про харнессы; здесь только реакции.
  Если тех таблиц не хватит: `reports/34-failure-recovery-spec.md` §2.1 и §2.2 (строки 54-103), только колонки
  «stream-json нативно» и «app-server».
- **Контрактные сценарии** — список в `AAE-SPEC.md` §7.8; ожидания по каждому — `reports/34…md:327-343`, 17 строк.
- **macOS:** все пороги и шаги сняты на Linux; `PR_SET_PDEATHSIG` и `/proc` там нет.
