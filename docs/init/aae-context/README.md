## Чему здесь можно верить

- Шпаргалки писали три агента по отчётам и сверяли с логами и скриптами лаборатории. Автор постановки выборочно
  перепроверил по первоисточникам: доставку токена claude в изолированный каталог конфигурации; отсечение хоста
  и рига пустым списком источников настроек; флаги `br update`/`br close` по справке 0.7.6; осиротевшего потомка
  claude после `kill -9`; повтор 429 у codex при `Retry-After`; `init` claude только после первого промпта.
  Остальное перепроверено не было.
- В конце файлов 01–04 и 06 есть таблицы расхождений: где отчёты противоречат друг другу или своим логам,
  показаны оба значения. Выбирает опыт, а не исполнитель на глаз.
- Если шпаргалка расходится с постановкой в факте о харнессе или br — прав первоисточник, на который ссылается
  шпаргалка; постановку надо поправить. Если расходится в решении — права постановка.

## Самое опасное (легко ошибиться)

1. claude ничего не пишет до первого промпта; ждать `init` перед промптом — взаимная блокировка (01 §3).
2. `result.subtype` у claude остаётся `"success"` при `is_error:true`; число `result` не равно числу промптов (01 §3).
3. Группа процессов не убивает всех потомков claude (01 §6).
4. «Idle без фона» у claude не выводится из одного сигнала (01 §4); у codex статус `idle` приходит раньше
   завершения хода (02 §6).
5. При API-ключе и на поддельном API у claude нет времени сброса лимита (01 §5).
6. Второй `turn/start` посреди хода codex сливается с идущим ходом (02 §7).
7. Unix-сокет codex говорит WebSocket; каталог сокета — 0700 (02 §1).
8. У br код ошибки занятого claim различается между версиями; проверен только флаг `--actor`; условного закрытия
   в 0.7.6 нет (03 §3, §5).
9. Пустой список источников настроек claude отсекает и хост, и риг (04 §5).
10. В поддельных провайдерах codex нет режима успешного ответа (05 §1).
