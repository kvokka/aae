Правила разбора [В\*]:
- Решение принимать по **rc и флагу `retryable`**, а не по строке `code`: между 0.7.6 и main строка для занятого claim меняется с `VALIDATION_FAILED` на `CLAIM_CONFLICT` (§12).
- Убитый или не уложившийся в таймаут процесс br — исход **неизвестен**: запись могла примениться. Перед повтором перечитать состояние (`show`/`list`). Скрипт стенда отдельно считал «бид есть, хотя писатель убит» (`L:crash.py:55`).

- `--help` и ошибки разбора аргументов конвертом не оформляются (`S:docs/ARCHITECTURE.md:529-531`) [К].

## 4. Обнаружение `.beads`, worktree, клоны

- Без `BEADS_DIR` br ищет `.beads` (и `_beads`) вверх от cwd **без потолка**: мимо границы git-репозитория, до `$HOME` (R11:95-96; `S:src/config/mod.rs:303-369`) [П].
- Инцидент исследования: в каталоге без `.beads` команда `br create` (0.7.6) молча записала тестовый бид в `/home/ubuntu/.beads` владельца (R11:9-11, R11:265-267) [П]. Поэтому путь задаётся всегда: и вызовам демона, и окружению сессии агента.
- Linked worktree: получает из git только отслеживаемую часть `.beads` (без БД); br в нём разрешается в `.beads` основного checkout'а — одинаково в 0.6.0 и 0.7.6. 8 claim из двух worktree на один бид → 1 победитель (R11:101-103; каталог `L:wt/`) [П]. Побочно: `issues.jsonl` меняется только в основном checkout'е.
- Для aae БД лежит в `<project>/.beads` вне ригов: сессия в риге или его worktree находит её **только** через `BEADS_DIR` (R11:247-248) [В].
- Отдельные клоны со своими БД — не поддерживать. Опыт: оба клона успешно взяли один бид; после `git pull` — конфликт в `issues.jsonl`; `br ready` → `CONFIG_ERROR: Merge conflict markers detected`; `sync --flush-only` → `SYNC_CONFLICT`; `sync --merge [--force]` → `beads.base.jsonl is missing… choose --force-db or --force-jsonl`. Клон стоит до вмешательства человека (R11:106-110; `L:clones/`) [П]. Автор br: `--claim` «is not a distributed lock across independent clones» (R11:109-110).
- `routes.jsonl` (маршрутизация по префиксу в чужую БД) для разбиения проекта не использовать: `ready`/`list` чужие БД не агрегируют (R11:153, R11:256) [П]/[В].

## 5. Актор и claim

- br различает владельцев claim **только по строке актора**. Без `--actor` на стенде assignee = `unknown`, и второй claim с тем же именем проходит с rc=0 (R11:92-94; `L:t1/.beads/issues.jsonl`, бид «default actor claim») [П].
- Ключ `claim_exclusive=true` в 0.7.6 не сработал ни в одном из трёх написаний (R11:93-94; R11:276) [П]; причина — [НП].
- Следствие [В\*]: повтор claim тем же актором идемпотентен — им можно закрывать окно «намерение записано, ответа br нет».
- Следствие [В\*]: если актор уникален на попытку (постановка §10.2), а claim держится весь прогон (§10.3), `assignee` в br остаётся актором первой попытки. `--claim` другим актором даст rc=4; сменить владельца можно только `--assignee <новый>`. Истина о владении — в состоянии aae; что писать в `assignee` — решение исполнителя.
- Гонка claim: 16 процессов × 12 бидов → у каждого бида ровно 1 победитель, 180 отказов rc=4, 0 расхождений assignee с победителем (замер 2026-11-10, br 0.7.6; то же на 0.6.0) — `L:conc-run1.log:4-7,36-39`; R11:80 [П].

- Следить за размером `.br_recovery/` (100 МБ при 50 тыс. бидов, R11:126) и `.br_history/` (резервные копии JSONL, R11:157).
- `sync.auto_flush=true` оставить: `issues.jsonl` — единственный бэкап, из него br пересобирает БД (R11:48, R11:253) [П]/[В]. У aae `.beads` лежит вне git ригов, значит резервирование JSONL — отдельная забота [В\*].

`doctor`:
- `br doctor` без флагов только читает (`--dry-run` без `--repair` — no-op, H:). `--repair` пересобирает БД из JSONL; `--repair-indexes` — только REINDEX (H:) [К]. Автоматически `--repair` не запускать [В\*].
- Уровни здоровья (`S:docs/reliability/HEALTH_CONTRACT.md:6-13`, main) [К]: `healthy` — всё разрешено; `degraded` — всё, с предупреждением; `recoverable` — **только чтение до восстановления**; `unsafe` — нужен человек. На стенде наблюдался только `healthy` (`L:conc-run1.log:14-16`).

«Refuse instead of lose» (R11:187-189) [П]/[В]: при сомнении в целостности br **отказывает командам** до ручного `br doctor …`; для автономного контура это риск простоя, а не потери данных. Как это выглядит для вызывающего:
- ненулевой rc (2, 6 или 7) на командах, которые только что работали, **включая чтение**: регрессия 0.7.5→0.7.6 #569 «blocks every command, reads included», 0.7.0→0.7.1 #521 «wedge on a stale WAL index» (R11:188);

- повтор не помогает; состояние не меняется, пока не вмешался человек.

Реакция адаптера [В\*]: такие отказы — не сбой прогона. Исход прогона не меняется, операция остаётся в очереди, событие `tracker.sync_failed`, выдача по проекту останавливается воротами (постановка §10.3, §5.7). Поведение «отказать вместо потери» в автономном контуре вживую не наблюдалось — [НП] (постановка §17).
