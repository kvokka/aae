## Часть 1. Соответствие

### 1. claude: транскрипт ищется не там при наследовании хоста с `CLAUDE_CONFIG_DIR`

**класс**: баг · **важность**: средняя · **где**: `crates/aae-claude/src/lib.rs:359-362` против
`crates/aae-claude/src/part.rs:273-280` · **требование**: §7.1 «проверить, что транскрипт существует» (resume,
сверка после смерти демона), п. 11 первого аудита.

**факт**: после первого аудита наследующей сессии стали передавать `CLAUDE_CONFIG_DIR` демона (`daemon_vars`,
part.rs:279) — claude пишет транскрипт в `$CLAUDE_CONFIG_DIR/projects/…`. Но `SessionRef.config_dir` у наследующей
сессии — `null` (lib.rs:105-107), и `transcript()` при `null` смотрит в `$HOME/.claude` (lib.rs:361), а не в
`part::host_dir()`. Итог: `Transcript::Missing` → ядро даёт `transcript_divergence` (`run/exec.rs:210-212`) →
политика `new_session`. На хосте с `CLAUDE_CONFIG_DIR` любой resume claude (kill -9, рестарт демона, сбой
попытки) теряет сессию. Тестов на этот путь нет (`grep CLAUDE_CONFIG_DIR crates/aae-claude` — только состав
окружения, tests.rs:212-218).
**как проверено**: чтение трёх мест; `host_dir()` существует и используется для `account` и токена, но не для
транскрипта.
**что сделать** (S): в `transcript()` брать `part::host_dir()`; лучше — класть фактический каталог в `SessionRef`
при старте, чтобы ссылка не зависела от окружения будущего демона. Тест: наследующая сессия с
`CLAUDE_CONFIG_DIR` → `Present`.

### 2. codex: «фоновая команда после конца хода» — код есть, тестов нет, сценарий 14 утверждает обратное

**класс**: недоделка (контрактный сценарий проверяет не то, что заявлено) · **важность**: средняя · **где**:
`crates/aae-codex/src/stream.rs:139,181-187,254-258`; `crates/aae-codex/tests/contract.rs:173-197`;
`docs/harness-updates.md` (таблица codex, строка 14) · **требование**: §7.5 «фоновая команда идёт при статусе
`idle`», §7.8 сценарий «фоновая задача после конца хода»; шпаргалка `aae-context/02` §198: «`item/completed`
команды приходит позже, вне хода (36 с после конца хода) … idle без фона = нет `commandExecution` с
`item/started` без `item/completed`».

**факт**: адаптер это правило реализует (множество `commands`, `State{Idle, background:true}` на
`turn/completed`, поздний `State{Idle,false}` на `item/completed`). Но ни один тест не приводит codex в это
состояние: `grep -rn background crates/aae-codex crates/aae/tests/codex.rs` — везде только `background: false`.
Сценарий s14 запускает `(sleep 1 && touch bg) … &` — команда shell возвращается сразу, `item/completed` приходит
в ходе — и закрепляет противоположный тезис: «codex has no background tasks a session waits for». Адаптер при этом
объявляет «idle без фона», пока порождённый процесс ещё жив. Удаление веток 181-187 и 254-258 не уронит ни одного
теста (выведено из grep, мутацию не делал — репозиторий менять нельзя).
**что сделать** (S–M): сценарий 14 для codex — на команду, которая переживает ход штатно (как в опыте R46b:
`exec_command` с долгим процессом и ранним выходом хода); ожидать `idle{background:true}` → `idle{false}` после
`item/completed`. Unit-тест потока на ту же последовательность. Формулировку в `harness-updates.md` исправить.

### 3. Ключ ворот «провайдер + модель» известен прогону только после собственного сбоя; провайдера в ключе нет

**класс**: отход от запроса · **важность**: средняя · **где**: `crates/aae-core/src/run/machine.rs:253-259`
(единственное место записи `model:`), `run/gates.rs:59` («known once an attempt reported them»),
`crates/aae-core/src/driver.rs:247` (у драйвера есть `account()` до старта, а модели/провайдера — нет) ·
**требование**: §5.7 «прогон, чей ключ закрыт, ждёт в `queued`»; ключи — «аккаунт харнесса, пара „провайдер +
модель“»; §7.1 «`failure{… scope …}`», `rate_limited`/`overloaded` → scope `provider_model`.

**факт**: аккаунт после первого аудита берётся из `driver.account(&split.process)` до запуска
(machine.rs:181-184). Ключ `model:<m>` — только из `failure.provider_model` уже упавшей попытки. Политика на
429/529 закрывает `model:<m>` на 10 минут (`aae-plugins/src/policy.rs:122-126`), но новый прогон на той же модели
своего ключа ещё не знает, стартует, получает свой 429 и лишь затем паркуется. «Светофор» на модель не
останавливает очередь, а пропускает каждый прогон по одному разу. Сам ключ — имя модели без провайдера, причём
у claude это строка из конфига (`haiku` и `claude-haiku-5-5` — разные ворота).
**как проверено**: `grep -rn 'model:' crates/aae-core/src crates/aae-plugins/src` — одна запись, одно чтение.
**что сделать** (S–M): вернуть ключи из драйвера до старта (см. часть 2, п. «ключи ворот»): `keys(&Split)` →
`{account, provider_model}`; ключ — `<провайдер>/<модель>`.

### 5. `doctor`: ложное «ok» логина по ключу из окружения, который адаптер сессии не передаёт

### 2.2 Что в `Driver` и типах скроено под эти два харнесса

Обобщается хорошо (менять не надо):

- **`split` → `ProcessPart`/`SessionPart`/отпечаток** — лучшее место интерфейса: покрывает и «процесс на сессию»
  (claude: всё в процессной части), и «сервер с тредами» (codex), и HTTP-сервер вроде `opencode serve`.
  `sessions_per_instance` и `instance_idle` — достаточные способности.
- **`SessionRef` — непрозрачный JSON**; `Answer`; `live()`; `Failure{kind, retry_at, retried_by_harness, account,
  provider_model, raw}` — это ровно «429 и прочее у каждого своё, отслеживает адаптер».
- **`[harness.X]` и `native`** — см. выше.
- Третья реализация трейта уже есть (`ScriptedDriver` в testkit, 333 строки, без pid) — трейт не привязан к
  настоящему процессу намертво.

Скроено под двоих (обобщится с трением):

1. **`harness() -> &'static str` = имя в конфиге = вид адаптера** (`driver.rs:244`, `run/mod.rs:65`). Один
   адаптер — одно имя. Позиция владельца «простой набор команд — по ACP дефолтным адаптером» означает N имён
   конфига на один вид адаптера (`[harness.gemini] adapter = "acp"`, `[harness.opencode] adapter = "acp"`).
   Сейчас невозможно.
2. **`account(&ProcessPart)`** (`driver.rs:247`) — допущение «аккаунт определяется процессом». Верно для
   claude/codex (ключ в env или каталог логина). У многопровайдерных харнессов (opencode, pi) провайдер и его
   учётка выбираются моделью сессии — нужен `&Split`, а не `&ProcessPart`. Плюс находка 3 (модели до старта нет)
   и п. 13 таблицы (аккаунт в пространстве имён харнесса: общий ключ Anthropic у claude и opencode — двое ворот).
3. **`PromptKey` «как собственный id сообщения харнесса» и `transcript(key)`** (`driver.rs:93-95, 294-299`) — оба
   харнесса умеют принять наш id и отдать историю. В ACP у `session/prompt` клиентского id нет, истории по
   запросу нет: `transcript` сможет честно вернуть только «сессия есть/нет», и защита от двойной доставки после
   смерти демона (инвариант 17) для такого адаптера не работает. Это надо назвать способностью
   («проверяет доставку промпта: да/нет»), а не молчаливым `Present{Absent}`.
4. **Обязательные синтетические события**: ядро уходит из `starting` только по `PromptAcked` (`events.rs:123`) и
   завершает ход только по паре `TurnEnded` + `State{Idle, background:false}` (`events.rs:139-154`). У харнесса
   без подтверждения приёма и без событий состояния адаптер обязан их выдумать; контракт 4.3 этого прямо не
   требует — новый адаптер узнает по `stall` через 120 с.
5. **`capabilities(&ProcessPart)` с `versions` внутри** — версия не зависит от процесса; отсюда хак
   `harness.rs:84`.
6. **`InstanceHandle{pid, start_time, pgid}`** — «экземпляр = локальный дочерний процесс демона». Для любого
   CLI-харнесса верно; на этом держатся инварианты 6/7. Нормальное ограничение спеки §4, отметить в контракте.
7. **`SessionPlan{run, attempt, token, actor}`** — адаптер обязан доставить окружение попытки и инструментам, и
   хукам. У codex хукам не доставлено (находка 4): требование «куда именно доставить» в контракте не записано.
8. **`EffectiveConfig.hooks` — диалект Claude**. У codex совпал формат `hooks.json`; у opencode (JS-плагины), pi
   (TS-расширения), ACP-агентов командных хуков нет. По контракту адаптер вернёт `config_error`, и любой
   комплектный плагин с хуком харнесса делает агента на таком харнессе незапускаемым — причём узнаётся это на
   старте прогона (находка 8). Нужна объявленная способность «какие категории §6.2 адаптер выражает» и проверка
   на `config check`.
9. **Неявный контракт подстановки портов** (п. 14 таблицы): адаптер обязан держать URL сервисов в своих частях
   дословной подстрокой. Не записано в 4.2.
10. Мёртвые поля (находка 7) — каждый новый адаптер будет честно вычислять то, что никто не читает.

### 2.4 Цена третьего харнесса сегодня

- Новый крейт: 900–1 100 строк + тесты 800–1 000 (из них ~600 — копии).
- Подделка провайдера: 0 строк, если харнесс ходит в Anthropic/OpenAI (п. 18), иначе ~250.
- Правки вне крейта — пп. 1, 2, 3, 5, 6, 8 (шесть мест с ветвлением; в двух ветка по умолчанию молча примет новый
  харнесс за codex), 9, 15, 16, 17, 19, 20, 22. Около десяти файлов.
- Плюс трение трейта из 2.2: пп. 2, 3, 4, 8 для opencode/pi; п. 1 для ACP.

Обобщённый ACP-адаптер честно: `initialize`, `session/new{cwd, mcpServers}`, `session/load`, `session/prompt`
(ответ = конец хода со `stopReason` — авторитетная граница есть), `session/cancel`,
`session/request_permission`, `session/update` → активность. Чего ACP не даёт: типизации сбоев (ошибки —
свободный текст → почти всё `unknown`), времени сброса лимита, признака «ретраил сам», сигнала фоновой работы,
ключа идемпотентности и чтения транскрипта, доставки env/хуков/skills на сессию (значит процесс на сессию, как
у claude), способа отсечь конфиг хоста. То есть ровно как говорит владелец: команды — общие, особенности —
свои. Практичная форма — ACP-адаптер с «профилем харнесса» (таблица формулировок, рецепт окружения и логина,
бинарник, диапазон версий); профиль — данные, отдельный адаптер нужен только когда профиля мало. Размер: M–L
(600–800 строк + скриптованный ACP-агент для контрактных тестов).

### 2.5 Целевая форма (минимальная)

Адаптер экспортирует **одну функцию-конструктор**, всё остальное — методы `Driver`:

```rust
// aae-core::driver
pub struct Setup<'a> { pub name: &'a str, pub binary: PathBuf, pub options: &'a toml::Table,
                       pub state: &'a Path, pub socket: Option<&'a Path> }
pub struct Adapter { pub kind: &'static str, pub binary: &'static str,
                     pub new: fn(&Setup) -> Result<Arc<dyn Driver>, String> }

trait Driver {
    fn harness(&self) -> &str;                       // имя из конфига, не константа
    fn tested(&self) -> [(u32, u32, u32); 2];        // вместо capabilities(null).versions
    fn doctor(&self, agents: &[(String, EffectiveConfig)]) -> Vec<Check>;  // логин, MCP хоста, песочница
    fn keys(&self, split: &Split) -> Keys;           // account + provider/model до старта (вместо account())
    …остальное как есть
}
```

Корень сборки: `const ADAPTERS: &[Adapter] = &[aae_claude::ADAPTER, aae_codex::ADAPTER];` и поиск по
`harness.adapter` (по умолчанию — имя таблицы). Ноль `match` по имени.

Куда что уезжает:

- **Разбор `[harness.X]`** — в `new`: `CodexOptions` переезжает в `aae-codex`; ошибка конструктора — ошибка
  загрузки конфига (`options_error` исчезает); имя без адаптера — тоже ошибка загрузки (находка 8).
- **Проверки `doctor`** — в `Driver::doctor`: `login`, `host_mcp`, `sandbox`, `claude_json`, `home` уходят в
  адаптеры, где уже есть `host_dir()`/`host_home()`/`unconfined`/`host_key` (два последних перестают быть `pub`
  ради корня). `doctor.rs` печатает то, что вернули. Заодно чинится находка 5.
- **Пути учётных данных** — остаются только в адаптерах (сейчас три копии).
- **Общий код адаптеров** — модуль поддержки рядом с `stderr_tail` и `HOST_NETWORK_ENV` (сейчас они уже лежат в
  `aae_core::driver`): запуск процесса с маркером, лесенка остановки, `alive`, отправитель событий, сворачивание
  активности, `Failure` с обрезкой, текст выхода, хуки в JSON диалекта, каркас окружения, id аккаунта. Отдельный
  крейт не нужен, пока бюджет ядра позволяет; иначе `aae-harness` между ядром и адаптерами.
- **Контрактный стенд** — `Live<D: Driver>` в `aae-testkit` + перечень 15 сценариев как обязательный список
  имён тестов (проверка скриптом: у каждого крейта-адаптера есть `s01…s15`).

Шаги:

## Проверено и чисто

- Операции §7.1 — все на месте (`driver.rs:242-302`): split/отпечаток, запуск, здоровье, остановка; сессия:
  старт, resume, промпт с ключом, отмена, ответ, закрытие; транскрипт и живой поток.

- Ловушки §7.2: `subtype:"success"` + `is_error:true` → сбой (`aae-claude/src/stream.rs:176`); выход с кодом 0 в
  открытом ходе → `harness_crash` (оба адаптера; codex с11 на настоящем бинарнике, claude — unit).
- Граница хода: claude — `result` + правило трёх условий (`stream.rs:101-118`, с14 и приёмка 4a); codex — только

## Гипотезы (не проверено)

- claude: при простое с живой фоновой задачей `background_tasks_changed{[]}` без `task_notification` не даёт
  нового `State` (`stream.rs:111-114`) — прогон дождётся `background_silence` и упадёт как `stall`.

  форму, чем у `commandExecution`; сценарий 13 проверяет только команду.
