# Проект изменений: агент, пак, формула, провайдер и демо «планировщик — исполнители» (2026-11-15)

Источник — замечания владельца после просмотра первого демо и его ответы на четыре развилки. Всё ниже — решения
владельца **[Р]**, кроме помеченного [Д].

## Что было понято неверно

Демо `snake` зашило задачу в пак: формулы `snake.backend`/`snake.frontend` содержат готовое ТЗ, агенты `backend` и
`frontend` специализированы под него, пользователь только запускает цепочку. Владелец:

> есть агент coder, который изначально заточен на то, чтобы кодить, и ему даётся задача — написать что-то. В настройке
> рига пользователь может указать, что этот кодер работает на таком-то провайдере и на такой-то модели (полное имя
> модели либо её аббревиатуру, такую как `opus` или `luna`, что берёт последнюю версию данного типа модели)… указывает
> effort, и уже задача пользователя — накинуть, что в кодера пойдёт: рассказ о том, что он хочет, — это и есть его ввод.
> Формула отвечает на вопрос «как» — это только процесс и шаги, что должны быть проделаны, но не то, что именно. Эта
> часть идёт от пользователя и только от него, а формула задаёт воркфлоу.
> Агент ИМЕЕТ настройку модели, провайдера и effort, НО это лишь defaults, которые могут быть переписаны как на уровне
> пака, так и на уровне формулы.
> Для другого харнесса для агента-кодера — это просто смена настроек aae, ЛИБО создание отдельных агентов
> `claude-coder` и `codex-coder` в настройках, что пользуют тот же пак, просто он сконфигурирован иначе.

## 1. Роли сущностей

- **Агент** — общая роль (`coder`, `planner`): промпт роли, skills и **умолчания** четырёх настроек запуска: харнесс,
  провайдер, модель, effort. О конкретной задаче агент не знает.
- **Формула** — «как»: процесс, который агент проходит (шаблон промпта описывает шаги работы и чем её закончить). «Что»
  приходит только входом пользователя (`--input task=…`, `request=…`) и подставляется в шаблон. В паке нет ни слова о
  конкретной задаче.
- **Пак** — агенты и формулы (воркфлоу), пригодные для любого проекта.
- **Пользователь** — в своём конфиге (оркестратор, проект, риг) говорит, на чём работает агент, и даёт задачу.

## 2. Настройки запуска и порядок слоёв

Четыре настройки: `harness`, `provider`, `model`, `effort` — обычные послойные скаляры. От слабого к сильному:

1. настройки хоста харнесса (если наследование включено);
2. умолчание модели харнесса `[harness.<h>] model`;
3. общие настройки оркестратора → проекта → рига;
4. вклад плагинов агента;
5. **определение агента** в паке (умолчания);
6. **пак**: `[settings]` в `pack.toml` пака, которому принадлежит формула прогона (только четыре настройки запуска);
7. **формула**: ключи `provider`, `model`, `effort`, `harness` в `[step]` prompt-шага;
8. **вариант агента**, объявленный пользователем (п. 4 ниже);
9. **оверрайды пользователя для агента**: `[overrides.<agent>]` оркестратора → проекта → `[rigs.<r>.overrides.<agent>]`.

Явная настройка пользователя (8, 9) сильнее пака и формулы. `aae config explain` показывает итог и слой каждого
значения, включая выведенный харнесс и раскрытое имя модели.

## 3. Провайдер, харнесс, сокращения моделей

- `provider` — поставщик модели (`anthropic`, `openai`). `harness` — agent-CLI (`claude`, `codex`).
- **Харнесс выводится из провайдера**: адаптер объявляет провайдеров, с которыми работает (claude — `anthropic`,
  codex — `openai`); если `harness` не задан, берётся единственный адаптер этого провайдера. Задан только `harness` —
  провайдер по умолчанию его родной. Не задано ни то, ни другое, либо провайдер не поддержан харнессом, — ошибка
  конфига. Таблицу `[provider.<p>] harness = …` (умолчание харнесса для провайдера) **не делать**, пока у провайдера
  один адаптер: упомянуть в `docs/design/adapters.md` как путь на будущее.
- `harness` можно менять оверрайдом, вариантом, паком и формулой (сейчас он зафиксирован в `agent.toml`).
- **Сокращения моделей** — знание адаптера (таблица в крейте адаптера, экспорт через описание адаптера): полное имя
  передаётся как есть, сокращение раскрывается в последнюю версию семейства. openai: `astra` → `gpt-6-astra`,
  `luna` → `gpt-6-luna`, `terra` → `gpt-6-1-terra`, `sol` → `gpt-6-1-sol`. anthropic: `fable`, `opus`, `sonnet`,
  `haiku` — если CLI claude сам раскрывает сокращение в последнюю версию, оно передаётся как есть, иначе таблица.
  Соответствие проверяется на настоящем харнессе (список моделей харнесса либо один дешёвый живой прогон на
  сокращение; запись в журнал). Если харнесс не принимает имя из таблицы владельца — находка в журнал, не молчаливая
  подмена.
- Ключ ворот модели — `model:<provider>/<раскрытое имя>`, известен прогону из конфига **до** первого сбоя (сейчас
  узнаётся только из собственного сбоя, провайдера в ключе нет — находки А17 аудита и расхождение с contracts).

## 4. Варианты агента в настройках пользователя

```toml
# aae.toml проекта или config.toml оркестратора
[agents.codex-coder]
base     = "dev.coder"      # роль, промпт, skills — из агента пака
provider = "openai"
model    = "luna"

[rigs.backend]
path   = "../backend"
agents = { coder = "codex-coder" }   # в этом риге ссылку формулы на coder исполняет вариант
```

Вариант — тот же агент пака с другими настройками (любые ключи настроек агента), под своим именем: лимит `max_runs`,
ворота и события считают его отдельным агентом. Формулы пака по-прежнему ссылаются на `coder`; отображение — в риге.
Второй путь к тому же результату — оверрайд без нового имени: `[rigs.backend.overrides.coder] provider = "openai"`.

## 5. Прогон, запущенный из сессии агента

- `aae run start …`, вызванный в сессии агента (в окружении есть `AAE_RUN` и токен попытки), создаёт **дочерний**
  прогон: он наследует correlation родителя, глубина +1, действует общий предел глубины цепочки (10). Сейчас такой
  прогон получает новый correlation и глубину 0 — петля «планировщик запускает планировщика» ничем не ограничена.
- `aae run wait <id>…` — ждёт терминального состояния всех названных прогонов **по событиям** (не опросом), печатает
  по каждому состояние, класс и причину провала, резюме и данные финишера; код выхода 0 — все `passed`. Флаг таймаута.
- Отмена родителя отменяет его живые дочерние прогоны [Д] — если это правка размера S; иначе записать в журнал.
- Набор инструментов MCP не расширяется (малая поверхность): планировщик пользуется CLI.

## 6. Демо «планировщик — исполнители» (критерий 20)

Повторяет базовую возможность субагентов Claude Code — это первый нужный шаг. Четыре папки на демо:

```
demos/dev-pack/                 пак dev: агенты planner и coder, формулы plan и code — без единого слова о змейке
demos/snake-claude/root/        корневой репо: config.toml (оркестратор), aae.toml (проект, риги, настройки),
                                REQUEST.md (рассказ пользователя — что он хочет), smoke.sh (проверка итога)
demos/snake-claude/backend/     риг: пустой репозиторий до прогона
demos/snake-claude/frontend/    риг: пустой репозиторий до прогона
```

- Пользователь: `aae run start snake-claude root dev.plan --input request="$(cat REQUEST.md)"`.
- `dev.plan` (агент `planner`, работает в риге `root` — в своём каталоге, чтобы не занимать риги исполнителей): читает
  запрос, смотрит, какие риги есть в проекте, делит работу, для каждой части запускает `dev.code` в нужном риге с
  текстом задачи, ждёт исходы (`aae run wait`), при провале части решает сам (переформулировать и запустить ещё раз
  либо завершиться `fail`), завершает прогон сводкой.
- `dev.code` (агент `coder`): получает `task`, делает работу в своём риге, проверяет её, завершает резюме и данными,
  нужными соседям (например, адрес API).
- Проверка итога — `smoke.sh` в корневом репо (exec-формула локального пака проекта, триггер на `run.passed` формулы
  `dev.plan`): это проверка пользователя, а не часть пака.
- **Демо 2, смешанные харнессы** (`demos/snake-mixed/{root,backend,frontend}`): тот же пак, другое только в
  `root/aae.toml` — вариант `codex-coder` на провайдере openai и отображение для рига `backend`; README показывает и
  второй путь (оверрайд). Модели — самые дешёвые: `haiku` и `luna`.
- Снимок результата (`RESULT.md` с маркером `MEASURE`, содержимое ригов) — как сейчас; CI проверяет только, что
  конфиги демо загружаются.
