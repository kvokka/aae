# Правила владельца для coder и reviewer (действуют с цикла 39)

Эти правила дополняют `.claude/agents/*.md` и `CLAUDE.md`; при расхождении — приоритет у этого файла.
Файл не харнесс: его можно читать и дополнять внутри цикла только владельцу; агенты его не правят.

## 1. CI долгий — не ждём

- Полный `mise run ci` идёт долго. Не блокируйся на нём ни при кодинге, ни при написании ревью.
- Запусти его в фоне (`run_in_background`, вывод — в файл, например `/tmp/ci-<sha>.log`), продолжай работу, а
  результат читай тогда, когда он уже есть. Берёшь **последний доступный** результат (свой лог, лог кодера,
  `gh run list`/`gh run view` по `main`) и правишь по нему позже, в этом или следующем цикле.
- Быстрые точечные проверки по затронутым крейтам (`cargo check -p …`, `cargo nextest run -p … <фильтр>`, clippy на
  крейт) — можно и нужно, ими и живёшь в процессе.
- **В процессе разработки красные тесты или CI допустимы**: они проявятся позже и будут исправлены. Красное,
  найденное из последнего результата, — первая работа следующего шага, а не повод остановиться.
- **На сдаче красного быть не должно.** Сдача — это закрытие пакета в плане как `done` и финальное состояние
  проекта. Для пакета со статусом `done`: CI на его последнем коммите запущен и зелёный. Если результата ещё нет
  (CI не успел) — пакет остаётся `doing`, в отчёте написан sha коммита и «CI ожидается»; следующий цикл читает
  результат первым делом. Нельзя писать «CI зелёный», если это не относится к указанному sha.
- Ревьюер: не запускает полный CI заново, если есть результат для `HEAD` или близкого коммита; смотрит последний
  доступный и называет sha, к которому он относится. Красный CI, который не успели починить, — пункт «Обязательно до
  продолжения» для следующего цикла, а не автоматический блокер текущего. Блокер — красное на коммите, который
  кодер объявил сданным (`done`).

## 2. Эксперт: пользоваться, в том числе для планирования

- Для сложных частей (ядро, инварианты §5.5, восстановление, протоколы харнессов, спорное архитектурное решение,
  тупиковый баг) **стоит** звать `expert`. Он не только советует: он умеет писать **план работ**. Отдавай ему
  планирование явно.
- В брифе эксперту скажи прямо: «от тебя требуется планирование, не реализация». Приложи: цель, секции спеки (по
  номерам), затронутые файлы/крейты, ограничение «исполнитель работает в окне контекста 300k (мягкий предел), план
  должен делиться на куски по ~100–150k, каждый с проверяемым «Готово, когда»». Попроси: разбить на куски, указать
  порядок и зависимости, пометить, какие куски можно делать параллельно (непересекающиеся файлы — их отдают
  `subcoder`-ам), назвать риски. И записать план в beads (см. раздел 3) или вернуть структуру, которую внесёшь ты.
- Не пытайся спланировать всё и не пытайся сделать всю задачу за один цикл. Эксперт планирует крупную часть, ты
  берёшь столько кусков, сколько помещается в бюджет; остальное остаётся в beads и подхватывается следующим
  циклом. Если эксперт говорит, что 2–3 куска можно делать одновременно, — так и делай (до трёх субагентов).
- Если эксперт указывает, как лучше сделать вещь, — следуй, это твой помощник. Отклониться можно с причиной в отчёте.
- Если агента `expert` в этой сессии нет в списке (так уже бывало), напиши об этом в журнал одной строкой и
  планируй сам; не трать цикл на поиски.

## 3. br (beads) — короткая шпаргалка для агентов

Подробности: `br robot-docs guide`, `br capabilities --format json`, `br <команда> --help`. Полные описания
берём из `docs/init/aae-context/03-br-adapter.md` по разделам, не целиком.

- Рабочий каталог — корень репозитория. Если `.beads/` нет: `br init` (префикс по имени каталога). `.beads/`
  коммитится вместе с кодом (`br sync --flush-only`, затем `git add .beads`).
- Для агентов всегда машинный вывод: `--json`, а для токен-экономии — `--format toon` (где команда его
  поддерживает). Любой JSON можно сжать утилитой `toon`: `br list --json | toon`; обратно — `toon -d`.
  Диагностика идёт в stderr; для чистого вывода `RUST_LOG=error br …`.
- Начало работы: `br ready --json` (единственная точка «что делать дальше»), `br show <id> --json`.
- Завести задачу: `br create "<заголовок>" -t task -p 2 -d "<описание>" -l <метка> --parent <epic-id> --json`
  (типы: `epic`, `task`, `bug`; приоритет 0 — самый высокий). Длинное описание — `--description-file`.
- Зависимости: `br dep add <задача> <от-чего-зависит>` (задача ждёт вторую). `br blocked` — что стоит.
- Взять в работу: `br update <id> --claim --actor "$AGENT_NAME" --json`. Заметка по ходу: `br comments add <id> "<текст>"`.
- Закрыть: `br close <id> --reason "Completed: <что именно и чем доказано>" --json`.
- Планы эксперта — epic на пакет плана и дочерние задачи на куски (`--parent`); в описании куска: цель, файлы,
  «Готово, когда», что можно параллелить. Статус пакета в `.loop/PLAN.md` ссылается на epic по id.
- Голый `bv` в автоматике не запускай (интерактивный); только `bv --robot-*`.
- Тесты самого aae по-прежнему создают свои временные рабочие каталоги br; не используй рабочий `.beads` репозитория
  как фикстуру.

## 4. codex доступен

Владелец подтвердил: codex на хосте залогинен и работает, trust для каталога проекта сделан. Не записывай «codex не залогинен»
как факт, не проверив: запусти `codex login status` и один дешёвый живой прогон (самая дешёвая модель, точечно, запись в
журнал по `CLAUDE.md`). Если проверка из твоей оболочки не проходит — проверь `HOME`/`CODEX_HOME` и обычный путь до
`~/.codex`; только если и это не помогло, опиши точную команду и ответ в журнале. Критерий 2 и codex-часть WP-39
выполняются на настоящем codex.
