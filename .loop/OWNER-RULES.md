# Правила владельца для coder и reviewer (действуют с цикла 39)

Эти правила дополняют `.claude/agents/*.md` и `CLAUDE.md`; при расхождении — приоритет у этого файла.
Файл не харнесс: его можно читать и дополнять внутри цикла только владельцу; агенты его не правят.

## 1. CI долгий — не ждём

- Полный `mise run ci` идёт долго. Не блокируйся на нём ни при кодинге, ни при написании ревью.
- Запусти его в фоне (`run_in_background`, вывод — в файл, например `/tmp/ci-<sha>.log`), продолжай работу, а
  результат читай тогда, когда он уже есть. Берёшь **последний доступный** результат (свой лог, лог кодера,
  `gh run list`/`gh run view` по `main`) и правишь по нему позже, в этом или следующем цикле.
- Быстрые точечные проверки по затронутым крейтам (`cargo check -p …`, `cargo nextest run -p … <фильтр>`, clippy на
  крейт) — можно и нужно, ими и живёшь в процессе.
- **В процессе разработки красные тесты или CI допустимы**: они проявятся позже и будут исправлены. Красное,
  найденное из последнего результата, — первая работа следующего шага, а не повод остановиться.
- **На сдаче красного быть не должно.** Сдача — это закрытие пакета в плане как `done` и финальное состояние
  проекта. Для пакета со статусом `done`: CI на его последнем коммите запущен и зелёный. Если результата ещё нет
  (CI не успел) — пакет остаётся `doing`, в отчёте написан sha коммита и «CI ожидается»; следующий цикл читает
  результат первым делом. Нельзя писать «CI зелёный», если это не относится к указанному sha.
- Ревьюер: не запускает полный CI заново, если есть результат для `HEAD` или близкого коммита; смотрит последний
  доступный и называет sha, к которому он относится. Красный CI, который не успели починить, — пункт «Обязательно до
  продолжения» для следующего цикла, а не автоматический блокер текущего. Блокер — красное на коммите, который
  кодер объявил сданным (`done`).

## 2. Эксперт: пользоваться, в том числе для планирования

- Для сложных частей (ядро, инварианты §5.5, восстановление, протоколы харнессов, спорное архитектурное решение,
  тупиковый баг) **стоит** звать `expert`. Он не только советует: он умеет писать **план работ**. Отдавай ему
  планирование явно.
- В брифе эксперту скажи прямо: «от тебя требуется планирование, не реализация». Приложи: цель, секции спеки (по
  номерам), затронутые файлы/крейты, ограничение «исполнитель работает в окне контекста 300k (мягкий предел), план
  должен делиться на куски по ~100–150k, каждый с проверяемым «Готово, когда»». Попроси: разбить на куски, указать
  порядок и зависимости, пометить, какие куски можно делать параллельно (непересекающиеся файлы — их отдают
  `subcoder`-ам), назвать риски. И записать план в beads (см. раздел 3) или вернуть структуру, которую внесёшь ты.
- Не пытайся спланировать всё и не пытайся сделать всю задачу за один цикл. Эксперт планирует крупную часть, ты
  берёшь столько кусков, сколько помещается в бюджет; остальное остаётся в beads и подхватывается следующим
  циклом. Если эксперт говорит, что 2–3 куска можно делать одновременно, — так и делай (до трёх субагентов).
- Если эксперт указывает, как лучше сделать вещь, — следуй, это твой помощник. Отклониться можно с причиной в отчёте.
- Если агента `expert` в этой сессии нет в списке (так уже бывало), напиши об этом в журнал одной строкой и
  планируй сам; не трать цикл на поиски.

## 3. br (beads) — короткая шпаргалка для агентов

Подробности: `br robot-docs guide`, `br capabilities --format json`, `br <команда> --help`. Полные описания
берём из `docs/init/aae-context/03-br-adapter.md` по разделам, не целиком.

- Рабочий каталог — корень репозитория. Если `.beads/` нет: `br init` (префикс по имени каталога). `.beads/`
  коммитится вместе с кодом (`br sync --flush-only`, затем `git add .beads`).
- Для агентов всегда машинный вывод: `--json`, а для токен-экономии — `--format toon` (где команда его
  поддерживает). Любой JSON можно сжать утилитой `toon`: `br list --json | toon`; обратно — `toon -d`.
  Диагностика идёт в stderr; для чистого вывода `RUST_LOG=error br …`.
- Начало работы: `br ready --json` (единственная точка «что делать дальше»), `br show <id> --json`.
- Завести задачу: `br create "<заголовок>" -t task -p 2 -d "<описание>" -l <метка> --parent <epic-id> --json`
  (типы: `epic`, `task`, `bug`; приоритет 0 — самый высокий). Длинное описание — `--description-file`.
- Зависимости: `br dep add <задача> <от-чего-зависит>` (задача ждёт вторую). `br blocked` — что стоит.
- Взять в работу: `br update <id> --claim --actor "$AGENT_NAME" --json`. Заметка по ходу: `br comments add <id> "<текст>"`.
- Закрыть: `br close <id> --reason "Completed: <что именно и чем доказано>" --json`.
- Планы эксперта — epic на пакет плана и дочерние задачи на куски (`--parent`); в описании куска: цель, файлы,
  «Готово, когда», что можно параллелить. Статус пакета в `.loop/PLAN.md` ссылается на epic по id.
- Голый `bv` в автоматике не запускай (интерактивный); только `bv --robot-*`.
- Тесты самого aae по-прежнему создают свои временные рабочие каталоги br; не используй рабочий `.beads` репозитория
  как фикстуру.

## 6. Третий цикл (с цикла 68, после аудита-2)

- Основа — `.loop/AUDIT2-2026-11-14.md`, `.loop/PLAN.md` «Третий цикл» (WP-57…WP-64, порядок как записан: первым
  WP-59). Бюджет — 50 циклов (68…117).
- **Спека — постановка, а не история.** Она говорит, что должно быть сделано. В неё не пишут «реализовано», номера
  циклов и пакетов, ссылки на коммиты. Ревьюер секции спеки больше не сжимает и не заменяет выжимками: правило
  `CLAUDE.md` «спека со временем сжимается» и соответствующий шаг ревьюера отменены. Подробности решения живут в
  `docs/`, спека на них ссылается.
- **Харнесс, а не провайдер.** Пользователь называет харнесс (`claude`, `codex`), модель и effort; настройки
  `provider` нет. У прогона одна модель.
- **Никаких `rm -rf` и похожих конструкций** (`rm -r`, `rm -fr`, с переменными и подстановками тем более) — ни в
  командах агента, ни в скриптах, которые он пишет: на них агент встаёт намертво (запрос разрешения, которого
  некому дать). Старые демо, их снимки и временные каталоги чистить иначе: отслеживаемое — `git rm -r -q <путь>`,
  неотслеживаемое — `git clean -fdq -- <путь>` или `find <путь> -delete`; временное — в `mktemp -d` и не убирать
  вовсе. `demos/run.sh` уже переведён на `find … -delete`.
- **У каждой операции есть таймаут.** Любая команда, которая может не вернуться (сборка, тесты, CI, демон, демо,
  живой харнесс, `aae run wait`, сеть, ожидание файла или порта), запускается с явным пределом: параметр `timeout`
  инструмента Bash или `timeout <сек> <команда>`; фоновая — тоже с `timeout` внутри, а не «пока не кончится».
  Циклы ожидания — с числом попыток или общим сроком. Субагенту в брифе называется срок, к которому он сдаёт то,
  что успел. Сработал таймаут — это находка: записать, что зависло и на чём, и идти дальше, а не повторять ту же
  команду без предела.
- Диск почти полон (`target/` десятки гигабайт): worktree не создавать, вторую копию `target/` не собирать.

## 7. Два правила против флейков (с цикла 68)

- **`tokio::select!` в `aae-core` — только с `biased;`** и строкой-комментарием, почему ветки стоят в этом порядке.
  Случайный выбор между готовыми ветками уже ломал повтор по сиду (журнал, цикл 44, 20:20; образец —
  `aae-core/src/writer.rs`). Сейчас без `biased;` три места: `run/service_proc.rs` (два) и `process.rs` (одно);
  порядок — сначала остановка и настоящий исход процесса, потом таймер. Проверка — скрипт в `scripts/` рядом с
  `core-boundary.sh`, подключённый в `mise run ci`: `select!` в `crates/aae-core/src` без `biased;` — красное.
- **`start_paused` запрещён в тесте, который запускает настоящий процесс** (сервис, exec-шаг, харнесс, `sh`): пока
  рантайм ждёт процесс, виртуальные часы прыгают к следующему таймеру (журнал, цикл 51, флейки `services.rs`).
  Такой тест идёт на настоящем времени с короткими интервалами. Проверить первыми: `aae-testkit/tests/services.rs`,
  `restart_decisions.rs`, `recovery.rs`. Ревьюер считает нарушение обязательным пунктом; флейк такого теста
  чинится переводом на настоящее время, а не подбором таймаутов.
- Оба пункта — попутная работа первого же цикла, который трогает эти файлы, отдельного пакета не нужно.

- **Что было понято неверно в демо третьего цикла.**

    шаг. Она говорит, как и в какой последовательности; что именно делать — только ввод пользователя.

- **Хранение демо.** Пользователь запускает демо у себя и не конфликтует с файлами репозитория: всё, что создаёт

  4. `bead = { type = "bead", required = true }` некорректно: будто корневой бид за `aae` кто-то создаст. Формула

     исчерпан, шаг повторяется (93).

  7. У агента в его настройке — `scope` со значениями `rig` и `root`. `root`: агент запускается относительно всех
     ригов проекта, не привязан к конкретному репозиторию и работает с глобальным пространством бидов — именно такой
     нужен для планирования поверх нескольких репозиториев. `rig`: агент привязан к репозиторию и запускается в его
     каталоге; rig-планировщик имеет смысл, только когда планирует внутри одного репозитория. Планировщик демо 2 —
     `root`, каким он и является (95). Это же меняет имена бидов: биды корня — без префикса, бид рига — с префиксом:
     акроним из слов имени рига (`backend` → `b`, `my-project` → `mp`) либо ключ `prefix` в настройках рига; в демо
     `backend` назван `api` — для читаемости и чтобы показать, что это работает (96).
  8. Агент не самодостаточен: у `pack/agents/coder/agent.toml` нет промпта. Его логично держать там же как
     `prompt.template.md`; тогда пользователь, который хочет переписать этого кодера у себя, кладёт свой
     `root/.aae/agents/coder/prompt.template.md` (97).
  9. Корневой репозиторий владелец называет `root`, но имя настраиваемо. Внутренняя отсылка «корень» остаётся, а
     пользователь делает корнем тот репозиторий, какой хочет, независимо от имени (99).
  10. У `drain` — параметр `pool`, по умолчанию 1: сколько бидов одновременно в работе у одной сессии `drain`. При 3
      стартуют три готовых бида, если они есть, остальные ждут (100).
  11. У `drain` — параметр `on_item_failure` со значениями `continue`, `soft_stop`, `hard_stop`. `continue` —
      умолчание: `drain` делает остальные биды. `soft_stop` — начатые биды заканчивают работу. `hard_stop` — начатые
      обрываются грубо (101).
  12. `[rigs.root] path = "."` — тавтология: где лежит `aae.toml`, там и корень, там же ищутся остальные файлы
      конфига. Нужно там имя: пользователь может назвать корень иначе, по умолчанию — `root` (99).
      **Поправка владельца того же дня:** путь корню всё-таки нужен, и в коде, и в документации, — как минимум для
      работы на одном репозитории, который сам же и корень (возможны и другие сценарии). И корень может вообще не
      быть репозиторием, а быть просто папкой: работе это мешать не должно. Итог: у корня настраиваются имя и путь,
      оба с умолчаниями (`root`, каталог с `aae.toml`); обязательной строки о корне в конфиге по-прежнему нет.
  13. `[rigs.root.vars]`: непонятно, к чему относится переменная, а длинные значения смешивают конфиг с промптами.
      Условия проверки демо 2 — «частичка» промпта корневого агента `qa`, и лежать она должна там, где её логично
      искать: `root/.aae/agents/qa/checks.md` (98, вместе с п. 8).
  14. «Демо 2 проходит не каждый раз: агенты оставляют фоновые процессы» — это требуется стабилизировать (104).
  15. Виды шага сейчас — `ai`, `exec`, `drain`; нужен и `formula`: шаг — другая формула. Входы родителя
      наследуются, но только те, что объявлены входами дочерней; на шаге их можно задать явно (102).
  16. `aae` — системный демон, поэтому формулы живут в области видимости проекта: проект А видит только подключённые
      к нему формулы, проект Б — только свои. Одинаковые формулы не объединяются, формула одного проекта на другой не
      влияет. Структура формул плоская, без иерархии. По умолчанию формула вызывается пользователем и видна в каталоге;
      с `internal = true` она вызывается только как часть другой формулы и скрыта из каталога (флаг `--all` в CLI её
      показывает; в API — свойство в выдаче, отдельного эндпоинта не надо) (103).
- **Имена.** Названные владельцем ключи и значения — буква: `[agents.<имя>]`, `kind = "ai"`, `scope` (`rig`, `root`),
  `prefix`, `prompt.template.md`, `.aae/agents/<агент>/`, `pool`, `on_item_failure` (`continue`, `soft_stop`,
  `hard_stop`), `max_attempts`, `step_check_script_path`, `internal`, `--all`. Имена, которые владелец не называл и
  которые предложены при записи решений, — допущения [Д]: секция корня с ключами имени и пути, тип входа `task`, блок
  `native.<harness>` для режима разрешений, способ подставить файл агента в шаблон. Исполнитель вправе заменить их
  лучшими с записью в журнал.
- **Чего владелец не просил — не делать.** Переменные рига (`vars`) остаются для коротких значений; команды `aae` для
  заведения бидов нет, пока без неё можно обойтись; отдельного эндпоинта для `internal` нет.
- **Совместимости со старым конфигом нет.** Первый выпуск не вышел: старый ключ (`[overrides.*]`, `permission_mode`,
  `kind = "prompt"`, тип входа `bead`, риг с путём корня, метка `rig:`) — ошибка конфига одной строкой с подсказкой,
  куда это пишется теперь. Кода «на вырост» и переходных слоёв нет.
- **`rm -r`, `rm -rf`, `rm -fr` не использовать нигде:** ни в командах агентов, ни в их скриптах, ни в `run.sh` демо,
  ни в тестах. Агент на такой команде встаёт на запросе разрешения, которого некому дать, и цикл прерывается; хук в
  цикле её отклоняет в любом написании флагов. Отслеживаемое — `git rm -r -q <путь>`; неотслеживаемое —
  `git clean -fdq -- <путь>` или `find <путь> -delete`; временное — в `mktemp -d` и не убирать. Особенно это касается
  WP-84: каталоги демо между живыми прогонами чистятся только так.
- **Демо грузятся на каждом коммите.** Пакет, который меняет поверхность конфига, в том же пакете правит `demos/`,
  `examples/`, гайды и фикстуры приёмки. Живые прогоны демо — только в WP-84.
- **Живые модели** — как в разделе 8: демо 1 — `haiku` и `luna`, демо 2 — `sol`, `terra`, `luna`; `astra` не запускать
  нигде. Прогоны точечно, с записью в журнал. Критерий 34 и опыт WP-83 — на поддельном провайдере, без модели.
- **br.** Пустого префикса у br нет (0.7.6: `issue_prefix "" contains no usable ASCII…`), поэтому «без префикса» у
  корневых бидов значит «без префикса рига»: id начинается с префикса самой БД. Если владелец захочет иное — запись в
  журнале от него.
- **Ревьюер.** `VERDICT: complete` — только когда критерии 27–34 зелёные в `acceptance-ci`, критерий 20 зелёный на
  демо нового вида (оба прогнаны вживую на коде цикла, демо 2 — два запуска подряд, `-example` сохранён с датой) и в
  дереве не осталось старых ключей из пункта о совместимости (кроме текстов подсказок и их тестов).
