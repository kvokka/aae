## Обязательно до продолжения
1. **Живой просмотр течёт задачами: серверная задача не замечает ухода клиента и может жить до остановки демона.**
   - Где: `crates/aae-front/src/api/live.rs:76–140`, функция `relay`. Когда журнал прочитан до конца
     (`caught_up`), `select!` ждёт только трёх вещей: `written.changed()`, сообщения сессии и `sleep(LOOK)`.
     После каждого `sleep` вызывается `look`, и это запрос к SQLite раз в 500 мс.
   - Уход клиента задача замечает только на `tx.send`. А `send` бывает лишь для событий **своего** прогона и
     сообщений его сессии.
   - Простые случаи, когда задача не завершится никогда (до выхода демона):
     - `aae run watch <законченный прогон> --from <seq после его конца>`, затем Ctrl-C;
     - конец законченного прогона вытеснен из журнала (это и есть `shortcut:`).
   - Отсюда же: если клиент ушёл посреди прогона, задача живёт до конца прогона. Прогон, припаркованный воротами,
     может стоять днями. Каждая такая задача — запрос раз в 500 мс, и они копятся. Это бьёт по критерию 7
     (простой демона).
   - Комментарий `shortcut:` («keeps the stream open until the client leaves») неправдив: задача не закрывается и
     после ухода клиента.
   - Как исправить:
     - добавить `tx.closed()` в `select!`;
     - в `look` (или на `caught_up`) закрывать поток, если прогон по `reader.run` уже терминален и непрочитанных
       событий нет. Это снимает и сам `shortcut:`.
   - Как проверить: тест на настоящем демоне.
     - Открыть `/live?from=<written+1>` на прошедшем прогоне, проверить, что поток закрывается сам.
     - Открыть на живом прогоне и бросить клиента. Убедиться, что задача ушла: через счётчик или через то, что
       `look` больше не зовётся. Например, через `Api` с метрикой открытых просмотров в `GET /v1/daemon` — если
       такая метрика нужна; иначе через закрытие потока в первом случае.

## Желательно
1. **Ветки `lagged` и `gap` живого просмотра без тестов**, это записано в READINESS. Нужен как минимум тест `gap`:
   `from` ниже самого старого `seq` даёт 410 до начала потока. И тест `lagged` на сценарном драйвере с маленьким
   буфером.
2. **Просмотр без `from` читает весь журнал с самого старого события** (до 50 МБ JSONL) ради одного прогона.
   Лучше начинать с `seq` события `run.queued` этого прогона, если оно известно состоянию.
3. **Живой просмотр на настоящем codex не проверен.** Тест есть только для claude. `Driver::live` у codex
   (`crates/aae-codex/src/lib.rs:340`) ни одним тестом через API не задет.
4. **`wait_up` перенесён в `run/exec.rs` только ради лимита 400 строк** и ссылается на
   `services::READY_WAIT`. Связность от этого хуже. Можно вынести сервисные функции в отдельный модуль
   `run/services_proc.rs` или подобный.
5. **Токен пишется `fs::write`, потом идёт `chmod`.** Пока каталог состояния приватный (0700), окна нет, но
   надёжнее создать файл сразу с `mode(0o600)` через `OpenOptions`.
6. **CLI не умеет работать по TCP с токеном** — ни флага, ни переменной. Спека этого не требует, но
   «`api.token` для клиентов владельца» из комментария в `daemon.rs` сейчас нужен только внешним клиентам.
   Стоит описать это в `docs/api/` или убрать из комментария.
7. Хвосты: ревью 34 жел. 2 (проверка «обрывы во все три вида» только в `acceptance-ci`), жел. 3
   (`aae-testkit/src/lib.rs` 423 строки без [Д]), жел. 6 (`triggers_off` не виден оператору); ревью 31 жел. 2
   (здоровье сервиса только по порту без [Д]) и жел. 4; ревью 30 жел. 2–4; ревью 28 жел. 3.
