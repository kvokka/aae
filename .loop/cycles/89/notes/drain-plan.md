## 1. §9.1: все биды под корневым

### 1.1 Что проверено на `br 0.7.6`

Стенд: корень `R` (эпик, взят `--claim`), под ним эпик `E` с задачами `G1`, `G2`, задача `C`, задача `T` с подзадачей.

| Команда | Результат |
|---|---|
| `br ready --unassigned --limit 0` | `G1 G2 C T TT`. Эпика `E` в списке **нет**, пока у него открыты дети |
| `br show G1 E --json` | `parent` есть у обоих (`G1 → E`, `E → R`) |
| `br ready --unassigned --limit 0 --parent R --recursive` | `G1 G2 C T TT` — все потомки, вглубь |
| то же после `br close G1 G2` | `E` появился в `ready` как обычный готовый бид |
| `br ready … --parent <нет такого> --recursive` | код 3, `ISSUE_NOT_FOUND` |
| то же для листа без детей | `[]`, код 0 |

### 1.2 Почему «обход вверх по `epic` по готовому списку» не работает

Внук `G1` несёт `epic = E`. Чтобы дойти до корня, нужен родитель `E`. Но `E` в `ready()` нет ровно тогда, когда его
дети готовы (см. таблицу). Цепочка рвётся на первом же промежуточном эпике. Вариант (б) из журнала (цикл 80) в
записанном виде неисполним.

### 1.3 Решение: операция трекера `under`

Решение 52 [Р] не запрещает операцию, оно говорит «добавляется, когда нужна вызывающему» — теперь нужна. §10.1 [Д]
прямо перечисляет «биды под корневым» среди операций. Отказ от неё в цикле 79 сам был отступлением от [Д]; правка его
снимает.

```rust
/// The ids of the ready beads under `root`, at any depth.
fn under<'a>(&'a self, root: &'a str) -> BoxFuture<'a, Result<Vec<String>, TrackerError>>;
```

Отвергнутые варианты:

- Поле `Bead.ancestors`. Меняет публичный контракт событий `bead.*` (contracts 5.2), адаптер br платит лишним
  `br show` на каждое чтение любого проекта, поле заполнено только в `ready` и пусто в `changes`.
- Хранить связи «бид → родитель» в ядре из потока `changes`. Новое состояние, зависит от того, что демон видел
  создание эпика.

### 1.5 Промежуточные эпики

Отдельного правила нет, и вводить его не надо:

- Эпик с открытыми детьми трекер готовым не называет — он не выдаётся.
- Эпик, чьи дети закрыты, трекер называет готовым. Он под корнем, значит выдаётся как любой готовый бид (§9.1:
  «каждый готовый бид получает дочерний прогон»). Есть метки `rig:`/`agent:` — получит прогон и закроется. Нет меток —
  старт отвергнут («has no `rig:` label»), бид попадает в `refused` с причиной и остаётся открытым. Так же сейчас
  ведёт себя любой прямой ребёнок без метки.
- Корень занят родительским прогоном (`beads.owner`), `ready_in` его отсекает.

Условие конца шага не меняется по форме: проход ничего не выдал, нет живого ребёнка, позади нет другого чтения. По
смыслу оно теперь считает всех потомков, потому что и «выдал», и «ребёнок» берутся по всему поддереву.

## 2. §5.6: попытка `drain` получает `daemon_crash`

### 2.1 Что делает политика

`crates/aae-plugins/src/policy.rs:198`: `"daemon_crash" | "tool_failure" => resume(0)`. Дальше
`decide.rs:apply` → `retry` → дедлайн `state` на «сейчас» → `start_attempt` → `machine.rs:107` → `start_drain`: новая
строка попытки (`harness = drain`), своё чтение трекера, дедлайн шага заново. Путь тот же, что у exec-шага; в c24 шаг
`plan` уже так ходит. Без хука на `run.attempt_failed` решение — `no_decision`, прогон `failed{infrastructure}`
(`decide.rs:93`), как у любого шага: это «дальше решает политика».

Заход в шаг = хвост попыток прогона с `step = row.step`: всё, что новее последней попытки другого шага. Между двумя
заходами в `drain` всегда есть попытка другого шага: возврат идёт от шага-проверки, а у него попытка есть.

```sql
SELECT r.bead, r.state, r.created_ms >= (
    SELECT MIN(a.started_ms) FROM attempts a WHERE a.run = ?1
    AND a.n > (SELECT COALESCE(MAX(n), 0) FROM attempts WHERE run = ?1 AND step != ?2))
FROM runs r WHERE r.parent_run = ?1 AND r.bead IS NOT NULL ORDER BY r.n
```

Схема БД не меняется. Новый раунд (возврат) даёт новый заход, упавшие биды в нём выдаются снова — как сейчас.

### 2.3 Инварианты §5.5 и критерий 24

- Инв. 2–5 (один живой владелец бида). Живой ребёнок держит `beads.owner`, `ready_in` его бид не отдаёт при любом
  ключе. Ключ нужен только для бидов, чей прогон уже кончился `failed`/`cancelled` и бид снова готов. Ключ «на заход»
  закрывает их после рестарта; ключ «на попытку» выдал бы их второй раз. Критерий 24 («ни один бид не исполнен
  дважды») держится именно этим.
- Инв. 15 (сторож). Попытка 2 ставит дедлайн `state` в `start_drain`; в `interrupted` сторож не нужен.
- Инв. 16 (потолок попыток). Каждый рестарт посреди `drain` теперь стоит прогону одной попытки из
  `MAX_ATTEMPTS = 20` (`decide.rs:155`), как у exec- и prompt-шагов. По букве; записать в журнал.
- Дети восстанавливаются сами, как любые прогоны: это не меняется.
- Чтения, оставшиеся в очереди от старой попытки, несут корень и безвредны: пока прогон `interrupted`, `drained` его
  пропускает (`DRAINING` требует `running`); после новой попытки это обычные проходы.

### 2.4 Найденная регрессия, которую правка внесла бы сама

Пока родитель `interrupted`, он не `DRAINING`: держит слот `max_runs` (`queue.rs:361`) и рабочий каталог от своих
детей (`queue.rs:272`). Сценарий: ребёнок ждёт в очереди; после рестарта тот, кто его загораживал, кончается раньше,
чем политика ответила родителю. `schedule` отрабатывает впустую. Потом родитель возвращается в `running`, но
`schedule` никто не зовёт: проход ничего не создаёт (все биды уже выданы), ребёнок стоит до таймаута шага (24 ч).
Лечится одной строкой — `self.schedule(tx)` в конце `start_drain`. Вложенный `schedule` в коде штатный
(`queue.rs:346`, комментарий «A nested schedule»).

- **РЕШЕНИЕ.** §5.6: попытка шага `drain` при рестарте получает `daemon_crash`, дальше политика (по умолчанию —

  прогону одной попытки из 20; без хука на `run.attempt_failed` такой прогон кончается `no_decision`, как на любом шаге.

  `rig:` — попадает в `refused` с причиной и остаётся открытым. Особого правила для эпиков нет.

## 7. Риски

1. **Живые демо обязательны** для `complete` после этой правки (шаг 5) — главная цена.
2. **Планировщик-LLM и вложенные эпики.** Если планировщик в демо заведёт под корнем эпик без меток, после закрытия
   его детей он уйдёт в `refused` и останется открытым; скрипт демо «все биды закрыты» это увидит. Раньше дети такого
   эпика не выдавались вовсе, так что хуже не стало, но на живом прогоне на это смотреть.
3. **Chaos.** Случайные решения политики теперь приходят и прогону в `drain` (`Park`, `Fail`, молчание). Логика общая
   с exec-шагом, но сюрпризы возможны именно тут.
4. **Сравнение по миллисекундам** (`created_ms >= started_ms`) осталось как было: ребёнок прошлого раунда и заход
   нового в одну миллисекунду неразличимы. На настоящих часах между ними целый шаг-проверка; в тестах на управляемых
   часах между раундами должен быть `sleep`.
5. **Два чтения br не атомарны** (`ready`, затем `under`). Бид, появившийся между ними, в этот проход не выдаётся;
   запись в трекер будит наблюдателя, следующее чтение его выдаст. Записи самого aae идут через ту же очередь
   `tracker:<project>` и между двумя чтениями не вклиниваются.
6. `MemoryTracker` считает неготовым любого родителя с открытыми детьми, br — только эпик. На план не влияет; тест
   вложенности делать на эпике-контейнере без меток, как в br.
