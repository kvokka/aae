## Обязательно до продолжения
1. **Новая строка `docs/design/event-model.md:27-29` расходится с кодом.**
   - Строка утверждает: «A lock held by another connection is waited out for 5 s … then the statement fails: … a
     message fails back to its sender».
   - Проверил вживую (`/tmp/rv72`, изолированные `HOME`/`XDG_*`). Внешнее соединение держит `BEGIN EXCLUSIVE` 3 с,
     через 0,5 с запускаю `aae run start hello main check`. Ответ пришёл за 8 мс: `aae: state storage: database is
     locked (500 storage)`. Сообщение не ждало 5 с, хотя замок держался меньше срока. Демон жив, после снятия замка
     `run_2 passed`, чтение (`run list`, `project list`) под замком работает (WAL).
   - Причина: `process`/`fire_deadlines`/`started` открывают `conn.transaction()`, то есть DEFERRED. Транзакция
     сначала читает, а потом повышается до записи. При повышении SQLite не вызывает обработчик ожидания (btree
     вызывает его только из `TRANS_NONE`) и сразу отдаёт `SQLITE_BUSY`. 5 с ждёт только транзакция, которая
     начинается с записи. Например, `DELETE FROM deadlines` в `fire_deadlines`: отсюда 1 + 5 с в тесте
     `the_daemon_exits_with_an_error_once_its_core_stops`.
   - Как исправить, на выбор кодера:
     - (а) `transaction_with_behavior(TransactionBehavior::Immediate)` в писателе. Тогда срок одинаково действует на
       все записи, и документ станет правдой. Но сообщение при внешнем замке будет держать цикл писателя до 5 с;
     - (б) переписать строку документа по факту: ждут только записи, которые начинаются с записи, а сообщение при
       чужом замке отказывает сразу.
   - Как проверить: тот же опыт с замком на 3 с. При (а) `run start` проходит примерно через 2,5 с; при (б) отказ
     приходит сразу, и документ говорит то же самое. Желательно тест в `aae-core`: внешний `BEGIN IMMEDIATE`, затем
     `handle` — с проверкой того поведения, которое выбрано.
