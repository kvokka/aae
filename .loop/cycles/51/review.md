## Обязательно до продолжения
1. **Чужой слушатель, занявший порт после проверки, получает `ready` и токен** (`crates/aae-core/src/run/service_proc.rs:86-90`
   и `healthy`, строки 166-170).
   - Проверка `bind` перед стартом ловит только того, кто пришёл до старта. Окно «проверка → `bind` самого
     сервиса» — это всё время запуска сервиса (у node/python — секунды). Поэтому оно почти не меньше прежнего окна
     «выбор → `bind`».
   - В этом окне `Health::Port` (`TcpStream::connect`) и `Health::Http` (`GET` с `Authorization: Bearer`) проходят
     по чужому слушателю. Сервис становится `ready` на чужом порту, `resolve` отдаёт этот порт сессиям вместе с токеном.
     Дальше рестарты идут «на том же порту» (порт уже `ready`) и бесконечно падают `port N is taken`.
   - **Воспроизведено** (журнал 13:20). В `a_service_whose_port_is_taken_before_it_is_ready_moves_and_the_session_follows`
     между `bind` чужого слушателя и записью `go` вставлено ожидание 400 мс, которое уступает рантайму
     (`tokio::time::sleep` + `std::thread::sleep`). Итог: тест красный, `http://127.0.0.1:34179/mcp is the taken port`.
     Без вставки тест обычно зелёный только потому, что окно (`sleep 0.05` в скрипте) меньше `CHECK_EVERY` = 100 мс.
     Под нагрузкой оно открывается само: прогон `sv-27`, чужой слушатель получил соединение, сработал
     `"the token went elsewhere"`.
   - Нужно: здоровье должно засчитываться, только если порт слушает процесс сервиса. На Linux это видно так:
     inode LISTEN-сокета `127.0.0.1:<port>` из `/proc/net/tcp` есть среди `/proc/<pid>/fd` процессов с маркером
     сервиса (обход маркеров уже есть в `orphans`/`process`). Для macOS — свой путь или [НП] с записью в журнал.
     Запрос `http` с токеном — только после этой проверки.
