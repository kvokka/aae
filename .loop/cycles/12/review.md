## Обязательно до продолжения
1. **Два демона на одном состоянии — два писателя.** `crates/aae/src/daemon.rs:53–90`: единственность проверяется
   только по сокету (`bind`, строки 100–113), а состояние (`$XDG_STATE_HOME/aae/state.db`, журнал) ничем не
   заперто. Проверил руками: `aae daemon --socket a.sock` и `aae daemon --socket b.sock` с одним `XDG_STATE_HOME`
   — оба поднялись и отвечают на `status`. Реальный путь — не только `--socket`: при пустом `XDG_RUNTIME_DIR` (ssh,
   cron, systemd без user-сессии) сокет уходит в каталог состояния, при заданном — в runtime-каталог, то есть два
   разных сокета на одно состояние. Два писателя ломают основу ядра (§5.1, единственный писатель; инварианты
   эффектов: двойной `launch`, двойной исход, два ротатора журнала). При одновременном первом старте второй ещё и
   падает на гонке схемы («table outbox already exists»). Исправление маленькое: эксклюзивная блокировка
   (`flock`/`fcntl` на `state/aae/lock` или на сам каталог) до `open()` и до `bind`; занято — понятная ошибка
   «another daemon owns <state dir>». Тест в `crates/aae/tests/api.rs`: второй демон с другим `XDG_RUNTIME_DIR` и тем
   же `XDG_STATE_HOME` не стартует (код ≠ 0, сообщение называет каталог).
2. **План и READINESS расходятся со сделанным.**
   - contracts 3.1 (`docs/design/contracts.md:180–182`) обещает `AAE_SOCKET` в окружении хуков «с API-сокетом
     (WP-22)»; WP-22a закрыт без этого, а WP-22b его не перечисляет — пункт выпал из плана. Либо передать
     `AAE_SOCKET` хукам (и exec-шагу, если контракт этого требует) уже сейчас, либо явно вписать в WP-22b.
   - `docs/READINESS.md`: строки «Runs and finisher» и «Issue gates» до сих пор называют недостающим «`aae finish`
     command (WP-23)» / «the CLI (WP-23)» — WP-23 сделан; «Config assembly» ссылается на WP-23 за «explain», а по
     плану это WP-22b; «account and model once reported» и «state schema v3» устарели (аккаунт — из конфига до
     старта, схема v5). Критерий 22 требует актуального файла готовности.

## Желательно
1. Финишер ретраит без `Idempotency-Key` (`cli/finish.rs:43–66`): если ответ потерян после фиксации, повтор
   получит `invalid` (прогон уже `finishing`) и выйдет с кодом 1, хотя исход принят. Ключ из `(run, token, тело)`
   снимает вопрос. Путь «60 с → 75» не покрыт тестом — сделать `FINISH_RETRY` переопределяемым из окружения для
   теста (или проверить на сокете, который не отвечает) — без этого CLI не дотягивает до 6.
2. CLI отдаёт `--key` только у `run start`; `run cancel`, `run answer`, `gate close/open` ключ идемпотентности не
   передают, хотя API его принимает (§12).
3. Сокет при `--socket` в общем каталоге (`/tmp`) создаётся с правами по umask: `private_dir` не меняет права уже
   существующего каталога. Выставить 0600 на сам сокет после `bind`.
4. До WP-20 рестарт демона оставляет прогоны в `running` без процесса — они навсегда держат каталог и слот
   (`shortcut:` в `daemon.rs:85` это усиливает). Знать при планировании: ручной путь «остановил и поднял демон» пока
   ломает живые прогоны.
5. `GET /v1/gates` берёт системное время в обход `Clock` ядра (`api/gates.rs:69–73`) — в демоне это одно и то же,
   но в будущей acceptance spec на управляемых часах список ворот разойдётся с ядром.
6. Хвосты прежних ревью: желательный 3 ревью 11 (порядок `parked`/`queued` при одном слоте); 5 ревью 10 — WP-33;
   3, 5, 6 ревью 09 — WP-21, WP-27.
