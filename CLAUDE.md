# loop-manager — правила для агентов

`loop-manager` — событийный оркестратор агентов-кодеров на Rust. Что это и как устроено — в `docs/` (по-английски, для
людей и агентов). Правила работы над самим репозиторием — в `docs/agents/`. Этот файл — указатель: читай то, что нужно
задаче, а не всё подряд.

## Что читать и когда

| Задача | Читать |
|---|---|
| Понять проект | `docs/overview.md` (одна страница, словарь), `docs/architecture.md` (части, крейты, путь прогона) |
| Найти документ по теме | `docs/README.md` — карта документации |
| Пишешь или ревьюишь код | `docs/agents/rules-code.md` |
| Запускаешь или пишешь тесты, трогаешь `demos/` | `docs/agents/rules-tests.md` |
| Меняешь поведение, ключ конфига, интерфейс | `docs/agents/decisions.md` (решения владельца, не пересматриваются) и `docs/agents/assumptions.md` (допущения: менять можно, с записью решения в комментариях эпика) |
| Работаешь ролью автономного цикла | `docs/agents/loop.md` и своё определение в `devloop/agents/` |

Большие справочники (`docs/design/contracts.md`, `docs/design/config.md`) читаются по разделам:
`grep -n '^##' <файл>`, затем Read с `offset`/`limit`.

## Главное

- **Истина — код и `docs/`.** Спеки над ними нет. Документ расходится с кодом — это дефект, он чинится в той же
  правке. `docs/` описывает, как продукт работает сейчас: истории («было», номера циклов и пакетов, коммиты) там нет.
- **Рабочий devloop.** Демон, его сокет, БД, установленный бинарник и трекер обслуживают реальные прогоны.
  Администрирование, обновление и проверки на них — только по явному запросу владельца именно на это действие.
  При разрешённом запуске или восстановлении сначала найди регистрацию devloop в системном или пользовательском
  systemd, launchd (через `launchctl`), Pitchfork или другом менеджере служб. Используй его, даже если служба
  остановлена. tmux — только запасной вариант, когда менеджера для devloop нет. Порядок — в `devloop/README.md`.
  Агент отчитывается по своему прогону и эпику. Проверки поведения — в изолированных тестах, включая ревью.
- **Гейт — `mise run ci`.** Один раз, на закоммиченном HEAD, перед сдачей работы (в devloop его запускает шаг `ci_report`).
  По ходу — только точечные тесты затронутого.
- **Acceptance-сценарии, живые модели и демо — только по явной просьбе владельца.** Сам их не запускаешь, условием
  «готово» не считаешь, `demos/` без просьбы не трогаешь. Сценарии без модели и chaos-стенд идут только в CI
  (workflow `acceptance`, запуск вручную). Модель `astra` не запускается никогда.
- **Не делать больше, чем просили.** Без заглушек и кода «на вырост»; меньше кода — лучше.
- **Язык.** Продукт — только английский: код, идентификаторы, комментарии, rustdoc, `docs/` (включая
  `docs/agents/`), `README`, тексты CLI и ошибок, OpenAPI, CI, сообщения коммитов. Отчёты и вопросы
  владельцу в комментариях эпика — по-русски, служебные заголовки — по формату роли.

## Работа с контекстом

- Вывод команд всегда обрезан: `cargo build -q --message-format short 2>&1 | head -60`,
  `cargo clippy --all-targets -q --message-format short -- -D warnings 2>&1 | head -60`,
  `cargo nextest run --no-fail-fast --status-level fail --final-status-level fail 2>&1 | tail -80`.
  Крейт `loop-manager-acceptance` не входит в `default-members`: трогаешь его — добавляй `--workspace`.
- Grep до Read; Read с offset/limit; не читать `Cargo.lock`, `target/`, длинные логи целиком.
- Структурный поиск по Rust — `ast-grep`: `ast-grep -l rust -p '$X.unwrap()' crates/ | head -40`.
- Тяжёлое чтение и прогоны — субагентам; они возвращают выжимку, детали — в файл.
- Команда не находится — `mise exec -- <команда>`.

## Работа с владельцем

В devloop находки, вопросы и принятые решения записываются в комментарии эпика. Форматы комментариев и порядок ответа
описаны в `devloop/README.md`. Вопрос владельцу в комментарии, отчёте или чате должен читаться сам по себе.
Объясни, что поставлено на карту и какие есть варианты.

## Git

- Работа в `main`. Коммиты атомарные, понятные. В devloop пуш делает финальный шаг `close`; force-push, переписывание
  истории, `--no-verify` запрещены.
- `rm -r` и `rm -rf` не использовать ни в командах, ни в своих скриптах: отслеживаемое — `git rm -r -q <путь>`,
  неотслеживаемое — `git clean -fdq -- <путь>` или `find <путь> -delete`, временное — в `mktemp -d` и не убирать.
- Репозиторий публичный, MIT: никаких секретов и абсолютных путей машины владельца.
